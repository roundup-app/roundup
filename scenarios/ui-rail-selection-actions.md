# UI: act on the selected Rail rows

Acceptance for [#5690](https://github.com/roundup-app/roundup/issues/5690). Journey: Intervene and Review, organizing or removing several finished Agents without repeating the same action. This specification delivers acceptance only. Tests below marked planned belong to the implementation.

## Precedence and boundaries

Policy: U5690a replaces U2694g's pointer-selection preservation only when the clicked row is outside the selection: that row becomes the sole selection. Opening a menu still never activates a row. U5690b replaces the single-object menu for a selected set of at least two rows. U5690d replaces U358's single-target dispatch and U3787a's no-question rule only for a Rail selection of at least two rows: that set always asks once, including five done Agents without irreversible losses. A single selected row retains its current menu, removal judgment, confirmation, Undo and keyboard ownership.

Policy: “Remove all” in the selection menu means remove the selected rows, not U4461's `scope: all` for everything inside one Workstream. Each selected row keeps its existing default removal semantics (A16/A34); selecting a Workstream does not authorize a wider cascade. Existing Workstream consequence reporting, unread-list handling, failure/recovery and irreversible-loss consent remain applicable. No unselected row outside those existing authorized cascades is removed.

Policy: Group is the owner's label for the new organizational container. It must hold every selected Rail row, not just Agents eligible for `rail.move` today. Grouping is an explicit user placement, not starting or promoting an Agent. It does not turn a selected Workstream into an Agent or create a Door for the Group. A6/A26's existing restriction on creating or moving a Workstream under another Workstream remains; the Group representation must support the requested organization without treating a Group as another Workstream. Implementation adds its canonical term and public names to `GLOSSARY.md` with every caller in the same Contract change; this specification selects no new RPC spelling or storage format. No legacy-data conversion is restored.

**U5690a a context click selects its target only when it is outside the selection.** Given visible Rail rows A, B, C and D, with A and C selected by ⌘-click or a contiguous range selected by ⇧-click, when the user right-clicks a selected row, then the selected identities remain exactly that set. When the user right-clicks an unselected row D instead, then D alone becomes selected before its usual single-row native menu opens. Both paths open exactly one menu and no Terminal, Bubble, branch, Agent or Drawer; dismissing runs no action. macOS Ctrl-click follows the same targeting rule, including its compatibility click. Planned test: `u5690a_context_click_uses_the_selected_set_or_replaces_it`, mounted App through the existing fake App menu seam, table of both gestures, both selection gestures and selected/unselected branch/leaf targets. Compare selected identities, menu calls and zero activation/mutation calls, not paint.

**U5690b a selection has two menu actions.** Given two or more selected Rail rows, when the user opens the menu on any selected row, then its only selectable items are Group followed by Remove all, and Remove all carries the existing ⌘⌫ shortcut metadata. There are no per-row run, rename, alert, share or creation actions in this menu. The focused row and `rail.selected()` need not identify the selected set: a set assembled entirely by modifier clicks still works. Opening and dismissing this menu change no Rail data. The existing focused-row context-menu keys use the same selection menu when their target is in the set. Planned test: `u5690b_selection_menu_has_group_then_remove_all`, through the mounted App's `showContextMenu` probe, with two and five rows and focus on a different selected member; assert action identities/order, shortcut contract and zero mutation calls. Exact copy and native shortcut-column appearance are rendered policy.

**U5690c Group collects the selection in Rail order and opens its name.** Given five sibling rows in displayed Rail order A, B, C, D, E, with C, A and E selected in that click order, when the user chooses Group, then one new Group holds A, C and E in that Rail order, each once, and B and D retain their relative order and identities outside it. The Group is expanded, selected and its in-place Name field has keyboard focus, ready for typing. Enter after typing commits its name through the existing rename flow; Escape keeps the Group and returns focus to its row using the existing rename-cancellation behavior. No Agent or Terminal starts or stops. Planned mounted-App test: `u5690c_group_collects_in_rail_order_and_focuses_rename`, asserting membership identities/order, one created container, focused textbox, rename dispatch and no lifecycle calls. Exercise Enter and Escape independently.

Given a selection containing a Workstream, an Agent from another Workstream, and a selected ancestor and descendant, when Group completes, then every selected identity is held by the one new Group, each once in its pre-action Rail order; no node becomes its own ancestor, and existing unselected descendants retain their identities and their relative order. Existing Workstreams retain their Door identity and work, and no extra Workstream or Door is created. Reopening the Project retains the Group, its committed name, membership and order without starting a program. Planned real-Daemon test: `u5690c_group_preserves_selected_identities_and_reopens`, through the public Rail contract with persisted data; assert the returned tree before and after reopen, preserved Door identities and zero launches. Grouping selected descendants is authorized placement, not deletion of their former containers. Placement policy: sibling selections put the Group at the first selected sibling's former position; selections from different parents put it at their nearest common ancestor, or the Project root when there is none, before the first affected branch. No selected node can be that destination.

**U5690d menu and chord ask once for the same whole selection.** Given at least two selected rows, when the user chooses Remove all or presses ⌘⌫ with Rail row focus, then one native question names every selected row in Rail order and the losses the existing removal judgment detects for each, including Worktree removal and ending its running programs, with each loss associated with its row. Descendant losses and Goes/Stays follow the existing default Workstream removal judgment; deduplicate any overlapping affected identity. No removal or process stop runs before the answer. Every selected name is available in the question, not replaced by an aggregate count or a “more” omission. The answers are Remove all and Keep; Keep or Escape changes nothing, preserving the selected set. One affirmative answer removes every selected row using its default removal scope, without further questions, and leaves unchosen rows outside authorized cascades unchanged. Selecting five done Agents with no Worktree or running program still asks once. Planned mounted-App test: `u5690d_remove_menu_and_chord_share_one_selection_question`, parameterized over both entries and five reversible rows versus mixed Worktree/live-program consequences, with names that distinguish every row; inspect native-question payload, per-row consequences, zero writes before answer and exact removed identities after each answer. Use `u5690d_overlapping_selection_removes_each_identity_once` for a selected Workstream and its selected descendant, asserting no repeated removal and no forced `scope: all` on the Workstream.

Given that same set with focus on a different selected row, or with `rail.selected()` null after modifier selection, when ⌘⌫ is pressed, then that complete set is used. After successful removal, selection and focus move to the first surviving visible row following the removed set, else the last preceding survivor, else the Rail's existing empty destination. A held chord, another invocation while the question is open, or another invocation while removal is pending never opens another question or repeats a removal. Planned test: `u5690d_selection_chord_uses_collection_and_advances_once`, through `mountRail`, with null/different active selection, middle/last/all-row sets, key repeat and pending duplicate invocation; assert one question, exact mutation identities and the surviving focus destination. Existing pane, editor, Terminal and modal ownership is unchanged (policy; retain U358's scope tests).

**U5690e one selected row keeps its existing behavior.** Given one selected row, when its menu opens or ⌘⌫ runs, then it uses the existing single-row actions and default removal path: a reversible row still removes without a question, and an irreversible row still asks its existing consequence question. Right-clicking an outside row first makes it the single selection under U5690a, then follows that same path. Planned test: `u5690e_one_row_keeps_its_menu_and_removal`, table of reversible Agent, Agent with running program/Worktree, and Workstream, through the existing mounted-App/menu/native-question seams, asserting the selected identity, applicable actions, confirmation count, scope and zero removal of former selected rows. Existing U358 focus/repeat/ownership and U3787a focused Undo/Redo observers remain regression requirements; reuse their assertions rather than duplicate them.

## Gates, observers and implementation scope

Policy: P1 asks whether grouping hides direct Agent access; grouped Agents remain selectable and their Terminals reachable. P6 asks whether a user placement or removal changes unchosen work; compare exact identities, placement, order and existing Workstream removal boundaries. P9 asks whether opening a menu or grouping starts an Agent or types input; observe zero such calls. P11 applies to the Group name field through the existing rename draft owner, including cancellation and failed submit. Grouping introduces no second name editor, selection machine or draft store.

Policy: use the existing mounted App seams (`apps/desktop/src/rail/railFixture.tsx`, `apps/desktop/src/testing/menuProbe.ts`, native-question probes) for interaction behavior, and the real Daemon/public Rail seam for persisted grouping and removal effects. Extend the existing Rail contract observers to prove accepted selection removal affects all and only the requested identities with their existing cascades; planned `u5690d_selection_removal_preserves_unselected_work` in the existing test modules of `crates/rupd/src/removal.rs` covers selected Agents and a Workstream with kept running/unlanded children, preserving other Workstreams' Todos, Pads, branches and directories. Do not substitute fake RPC calls for this effect observer. Match identity, roles, focus, call counts and contracts; layout and exact prose belong to the critic.

Implementation uses the existing Rail selection collection and native context-menu/NativeAlert paths. Contract changes must update all callers together and regenerate generated contracts. Rule 9 research applies before adding grouping or bulk-removal machinery; inspect installed Ark UI, Tauri and existing Rail/deletion facilities first. Reversible selected removal retains focused Undo/Redo with one selection removal per undo step under U3787a; irreversible removal advertises no Undo. Planned `u5690d_reversible_selection_is_one_undo_step` extends the existing Rail deletion observer to restore and redo the exact selected identities, order and relationships, without starting programs. Refusals and failures retain the existing originating failure/recovery path; this work promises one consent decision, not transactional rollback of external process effects.

Rendered policy: at 1512×950 in dark, use the U26 `tree-40` harness with five selected rows, a 60-character name, Worktree and running-program losses, plus visible failure feedback on the dense seed. The implementation runs `just capture U5690a U5690b U5690c U5690d U5690e`, leaving paired main/head PNGs and interaction recordings under `artifacts/ux/<id>/`; no images or videos are committed. Observe the selection menu, Group rename and full question, then Keep and accepted removal. Native menu/question payload and real-Daemon effects establish behavior on Linux; the user's Mac report owns native look and OS key routing. No Mac-only observation blocks this specification.
