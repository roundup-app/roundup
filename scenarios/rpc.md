# RPC client

Module: `crates/rpc`. Ids: C1, C6493a, C6493b, C6493c.

The `rpc::Client` in `crates/rpc` is how the App, `rup` and the tests call a Daemon. This file holds the one scenario about what a dropped connection tells its caller (`.claude/sound/resilience/remote-call-has-a-third-outcome.md`). Tests use a fake server on a temp socket.

**C1 a call that may have run is not reported as one that failed.** Given a Client whose request line has been written, when the connection closes before the reply, then `request` fails with the new code `rpc::code::UNKNOWN_OUTCOME`, whose message says the Daemon may have run the call, and every other pending call on that Client fails the same way and none hangs. A request that could not be written at all fails with `INTERNAL` and says it was not sent. A request made after the connection is known closed fails at once and says it was not sent. Every caller of `request` that matches on `INTERNAL` for a dropped connection changes in the same PR (no v2); the Builder greps `crates/` for them first and lists them in the PR. Narrowing: `s3_after_the_daemon_exits_rpc_fails_with_internal` keeps passing as written, because the App fails those calls itself.

**C6493a a handler is the domain method, typed.** Given a method declared in `crates/contracts/src/declarations.rs` as `"todo.create": CreateParams => Todo, create, …`, when `rpc::dispatch_methods!` expands for its owning module, then the macro decodes the request value into `CreateParams`, calls `create(&self, ctx: &Ctx, p: CreateParams)` and encodes the `Todo` it returns; a handler declared to return `Value` does not compile (proved by a `compile_fail` doctest on the macro, `c6493a_a_handler_returning_value_does_not_compile`); a handler of a method with no params takes `ctx` only. The declarations table names `create`, never `rpc_todo_create`, and no `async fn rpc_*` remains in `crates/` (`rg -c 'async fn rpc_' crates` is empty). No second dispatch macro and no shim lives beside the typed one (`seam-is-not-a-v2-interface`). Modules call one another by typed function, never by method name and JSON.

**C6493b parse and encode happen once, in the macro.** Given a request whose params do not match the declared type, when it is dispatched, then the macro answers `INVALID_PARAMS` with the message `invalid params: <serde error>` that `rpc::params` gives today, and no handler runs (`c6493b_bad_params_answer_invalid_params_without_calling_the_handler`). Given a valid request, then the reply bytes and codes equal those before the change for every method: the existing per-module router tests and the `rupd` router tests pass unchanged, and a method that replies through `rpc::json` (`rail.tree`) keeps its single-pass text reply. A sync handler becomes `async fn` with a sync body and awaits nothing while it holds a store guard (`await_holding_lock` stays denied). Inline user-only guards in `terminal`, `pads` and `messages` stay in their handlers; the declared role is MCP exposure only (`mcp_choice!`), and no new declared field carries a guard (policy).

**C6493c the wire and the generated surfaces do not move.** Given the migrated modules, when the contracts are regenerated and `rup mcp` answers `tools/list`, then `contracts/generated/` regenerates with an empty diff (C4's freshness observer, `tools/contracts/test_fresh.py` `Freshness.test_c4_contracts_fresh_detects_drift`), the `tools/list` reply is byte-identical to the reply on `main` (the C5459c consumer test in `scenarios/rpc-metadata.md` plus a before/after byte comparison recorded in the PR), no method name, param or result shape, or code changes, and C1, C4 and C5459a to c keep passing.

**Size and why one PR.** The change is a Contract-recipe PR (AGENTS.md rule 4): it changes `crates/rpc` (`dispatch_methods!` in `src/module.rs`), `crates/contracts/src/declarations.rs`, and the handlers in `todos`, `pads`, `messages`, `terminal`, `agents` and `rupd` together, because the macro's one form decodes and encodes for every module and a series would keep the `Value` form and the typed form both live. Checks on `main`: `rg -c 'async fn rpc_' crates` counts todos 24, pads 15, terminal 14, messages 6, agents 49 (`dispatch.rs` 45, `asks.rs` 4), rupd 18 (`contract_handlers.rs` 16, `actions.rs` 2), 126 in all; about 40 of those bodies only forward to a domain method (`Ok(self.m(ctx, params(value)?)?)`), and deleting them is most of the diff, about 1,000 lines mostly removed. If the cut passes that, the PR shows why no split avoids two live interfaces. Every new name is added to `GLOSSARY.md` in the same PR.

Reuse: `macro_rules!` is the dispatch form today and the declarations table is the one source of the method table, owning router, TS bindings and MCP exposure. Rejected: `jsonrpsee` 0.26.1 (a second registry beside `contracts::*_methods!`), `tower` 0.5.3 (middleware hides effects from the call site), rmcp `#[tool]` macros (repeat the declarations).

Keeper: the typed macro, which the compiler holds, and clippy `unused_async` and `needless_pass_by_value` on the new handlers.
