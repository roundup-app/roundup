# RPC client

Module: `crates/rpc`. Ids: C1, C6493a, C6493b, C6493c, C7707a to C7707e.

The `rpc::Client` in `crates/rpc` is how the App, `rup` and the tests call a Daemon. This file holds the one scenario about what a dropped connection tells its caller (`.claude/sound/resilience/remote-call-has-a-third-outcome.md`). Tests use a fake server on a temp socket.

**C1 a call that may have run is not reported as one that failed.** Given a Client whose request line has been written, when the connection closes before the reply, then `request` fails with the new code `rpc::code::UNKNOWN_OUTCOME`, whose message says the Daemon may have run the call, and every other pending call on that Client fails the same way and none hangs. A request that could not be written at all fails with `INTERNAL` and says it was not sent. A request made after the connection is known closed fails at once and says it was not sent. Every caller of `request` that matches on `INTERNAL` for a dropped connection changes in the same PR (no v2); the Builder greps `crates/` for them first and lists them in the PR. Narrowing: `s3_after_the_daemon_exits_rpc_fails_with_internal` keeps passing as written, because the App fails those calls itself.

**C6493a a handler is the domain method, typed.** Given a method declared in `crates/contracts/src/declarations.rs` as `"todo.create": CreateParams => Todo, create, …`, when `rpc::dispatch_methods!` expands for its owning module, then the macro decodes the request value into `CreateParams`, calls `create(&self, ctx: &Ctx, p: CreateParams)` and encodes the `Todo` it returns; a handler declared to return `Value` does not compile (proved by a `compile_fail` doctest on the macro, `c6493a_a_handler_returning_value_does_not_compile`); a handler of a method with no params takes `ctx` only. The declarations table names `create`, never `rpc_todo_create`, and no `async fn rpc_*` remains in `crates/` (`rg -c 'async fn rpc_' crates` is empty). No second dispatch macro and no shim lives beside the typed one (`seam-is-not-a-v2-interface`). Modules call one another by typed function, never by method name and JSON.

**C6493b parse and encode happen once, in the macro.** Given a request whose params do not match the declared type, when it is dispatched, then the macro answers `INVALID_PARAMS` with the message `invalid params: <serde error>` that `rpc::params` gives today, and no handler runs (`c6493b_bad_params_answer_invalid_params_without_calling_the_handler`). Given a valid request, then the reply bytes and codes equal those before the change for every method: the existing per-module router tests and the `rupd` router tests pass unchanged, and a method that replies through `rpc::json` (`rail.tree`) keeps its single-pass text reply. A sync handler becomes `async fn` with a sync body and awaits nothing while it holds a store guard (`await_holding_lock` stays denied). Inline user-only guards in `terminal`, `pads` and `messages` stay in their handlers; the declared role is MCP exposure only (`mcp_choice!`), and no new declared field carries a guard (policy).

**C6493c the wire and the generated surfaces do not move.** Given the migrated modules, when the contracts are regenerated and `rup mcp` answers `tools/list`, then `contracts/generated/` regenerates with an empty diff (C4's freshness observer, `tools/contracts/test_fresh.py` `Freshness.test_c4_contracts_fresh_detects_drift`), the `tools/list` reply is byte-identical to the reply on `main` (the C5459c consumer test in `scenarios/rpc-metadata.md` plus a before/after byte comparison recorded in the PR), no method name, param or result shape, or code changes, and C1, C4 and C5459a to c keep passing.

**Size and why one PR.** The change is a Contract-recipe PR (AGENTS.md rule 4): it changes `crates/rpc` (`dispatch_methods!` in `src/module.rs`), `crates/contracts/src/declarations.rs`, and the handlers in `todos`, `pads`, `messages`, `terminal`, `agents` and `rupd` together, because the macro's one form decodes and encodes for every module and a series would keep the `Value` form and the typed form both live. Checks on `main`: `rg -c 'async fn rpc_' crates` counts todos 24, pads 15, terminal 14, messages 6, agents 49 (`dispatch.rs` 45, `asks.rs` 4), rupd 18 (`contract_handlers.rs` 16, `actions.rs` 2), 126 in all; about 40 of those bodies only forward to a domain method (`Ok(self.m(ctx, params(value)?)?)`), and deleting them is most of the diff, about 1,000 lines mostly removed. If the cut passes that, the PR shows why no split avoids two live interfaces. Every new name is added to `GLOSSARY.md` in the same PR.

Reuse: `macro_rules!` is the dispatch form today and the declarations table is the one source of the method table, owning router, TS bindings and MCP exposure. Rejected: `jsonrpsee` 0.26.1 (a second registry beside `contracts::*_methods!`), `tower` 0.5.3 (middleware hides effects from the call site), rmcp `#[tool]` macros (repeat the declarations).

Keeper: the typed macro, which the compiler holds, and clippy `unused_async` and `needless_pass_by_value` on the new handlers.

## Search Messages, Pads and Todos by their words (C7707a to C7707e)

Work order: #7707. Module: `crates/contracts`, `crates/storage`, `crates/rupd`, `crates/pads`, `crates/todos`, `crates/messages`. Consumer: U7707a to U7707e (`scenarios/ui-quick-jump.md`). Contract recipe (rule 4): `search.find` and its types are new; `GLOSSARY.md` gains `Search`. No Message, Route, Held or Takeover behaviour changes, so M1 to M10 are untouched; Messages are only read. Since N16 one `project.db` holds Messages, Pads and Todos, so one index lives beside its rows and `pads.db` no longer exists.

**C7707a `search.find` finds a word in a Message, a Pad and a Todo.** Given a Project holding a Message whose body has `renew the token`, a Pad whose text has `token rotation notes` and a Todo whose body has `rotate the token`, when the user calls `search.find {query: "token"}` (`FindParams {query, limit?}`), then it answers `Found {hits, more}` holding all three `SearchHit {kind, id, title, snippet, ranges, opens?}`: `kind` is `message`, `pad` or `todo`, `id` is the Message id, Pad name or Todo id as a string, `title` is the Todo or Pad title (a Message's is `<sender> to <receiver>`), `snippet` is at most 80 characters of the matching text around the first match, `ranges` are `{start, end}` offsets in UTF-16 code units into `snippet` covering each matched word, and `opens` (Messages only) is the id of the Agent the Message opens (U7707b). A word in a Todo's or Pad's title finds it too. The call records no Touch (as `todo.list` records none). Tests: `c7707a_a_word_in_a_message_a_pad_and_a_todo_finds_each_with_its_ranges`, `c7707a_a_title_word_finds_its_pad_and_todo`.

**C7707b the matching rule is SQLite FTS5's, bounded.** Given the same Project, when a query runs, then each whitespace-separated word matches as a case-blind, accent-blind prefix (FTS5 `unicode61` with `remove_diacritics 2`; each word is quoted and given `*`), every word must match in the same item, and no query text is read as FTS5 syntax: `"`, `*`, `-`, `NEAR` and `:` in a query are searched as characters and never fail. Hits are ranked by `bm25` (a title match before a body match), then newest first. A blank query, or one with no word character, answers no hits and runs no search. `limit` defaults to 20 and is capped at 50; `more` is true when a further hit exists. Tests: `c7707b_words_match_as_case_and_accent_blind_prefixes_in_one_item`, `c7707b_fts_syntax_in_a_query_is_literal`, `c7707b_a_blank_query_answers_nothing_and_the_cap_sets_more`.

**C7707c the index is written with its rows.** Given the three tables, when a row is inserted, edited or deleted by any store path (a Pad write, rename or deletion, a Todo edit or deletion, a Message send, status change or removal with its Agent), then the index changes in the same transaction by SQLite triggers on `todos`, `pads` and `messages` over external-content FTS5 tables, so no Rust write path indexes and the index cannot drift. A rolled-back transaction leaves no hit; a deleted row leaves none. Tests: `c7707c_edit_delete_and_rollback_keep_the_index_with_its_rows`, which ends with FTS5's `integrity-check` for each table passing.

**C7707d existing rows are indexed once, by the migration.** Given a `project.db` at the previous migration holding Messages, Pads and Todos, when the Daemon opens it, then the new migration creates the index tables and triggers and fills them with one FTS5 `rebuild` each in that migration, so every earlier row is found on the first open and no startup scan runs. The migration is additive (MG1): MG1 is amended to also pass `CREATE VIRTUAL TABLE … USING fts5`, `CREATE TRIGGER` and `INSERT INTO <fts table>(<fts table>) VALUES('rebuild')` for a table the same file creates, and still fails every `DROP`, rename and `UPDATE` or `DELETE` of an older table. The previous build opens the result (MG3) and its writes fire the triggers, so the index follows its rows there too. Bundled SQLite's FTS5 (`rusqlite` is pinned `=0.40.2`, vendored, `bundled`; the work order's 0.43.0 is not the pin) is proved by this migration test, not assumed. Tests: `c7707d_rows_written_before_the_migration_are_found_on_first_open`, `mg1_a_virtual_table_triggers_and_a_rebuild_of_its_own_table_pass`, and the existing `mg1_dropping_renaming_or_rewriting_fails_naming_the_statement` unchanged.

**C7707e the method is the user's.** Given an Agent actor, when it calls `search.find`, then it is refused with `FORBIDDEN` and no query runs; the method is declared `none("…")` in `declarations.rs`, so `rup mcp` `tools/list` and the Agent surface do not gain it (C6493c's byte comparison holds) and the user's App call answers. Test: `c7707e_an_agent_call_is_refused_and_the_tool_list_does_not_move`.

Reuse (rule 9), selected: SQLite FTS5 through the installed `rusqlite` (MIT, already the Daemon's store, `bundled`), because it is the one candidate that adds no second store to keep in sync (C7707c) and no dependency or binary size. Rejected: `tantivy` 0.27.0 (MIT, 2026-10-17, <https://github.com/quickwit-oss/tantivy>), a separate on-disk index beside `project.db` that a crash or a Fork copy (`scenarios/data-fork.md`) could leave out of step, with segment memory counted against rule 7's 150 MB budget for ten idle Agents and no gain at a Project's row counts; `fuzzysort` 4.0.2 (installed), which works only on what the App holds (U7707 Reuse). Verify versions and release dates again in the implementing PR.

Keeper: the triggers, which SQLite holds, and FTS5's `integrity-check` in C7707c.
