# Make it yours (step 6 of the Multi-Machine Strategy)

Module: `crates/rupd` (`src/extensions/`, the config reader) and `apps/desktop` (`settings/`, `keys/`). Ids: MC40–MC46 and MC49. Principles: P3 and P16 in `PRINCIPLES.md`; `scenarios/machines.md` holds MC1–MC4. This file is specification only; each planned test ships with its implementation Issue. Implementation Issues name these ids and stand on this file.

Decided by the owner (2026-11-07, after reading the Multi-Machine Strategy plan: "I read the plan and I like it let's fill the issues and let's get that designed and shaped and built"): roundup owns attention and coordination. Customisation through plain files changes how a matter looks and what acts on it, never P16. Theme, keys, actions and Door behaviour as plain files are allowed. A side-by-side diff of two Agents' results is allowed: it is one matter. A PR can be the matter in the centre when the user chooses it. Refused: a mod that pings on every finish (only the alerts the user turns on interrupt), a PR panel beside the terminal, a machine sidebar or Rail level, a dispatch panel. Not doing: Rex or tmux adapters, calls to boxd's API, moving `rupd` off this Mac. The idea comes from Herdr: the window is plain files that apply live, with an AGENTS.md that teaches the user's agent to edit them. The GUI does not.

**Config** (`Config`, the folder `~/.roundup/`, or the folder the Daemon is opened with; tests do): the user's own plain files, shipped with no content but the AGENTS.md of MC44. Its parts are `look.json` (MC40), `keys.json` (MC41), `extensions/` (MC42), `door.md` (MC43) and `AGENTS.md` (MC44). A Project folder never loads one (`docs/extension-interface.md`, "Where Extensions run"). A part is read by the Daemon, which answers one `config.problem` per refused file (a Toast, like `extension.problem`); a refused file leaves the last good state as it was.

## Checks on main

1. `PRINCIPLES.md`, headings `P3 Cards over chatter` and `P16 The centre and the way to the next matter`: the Gates MC45 and MC46 rely on, unchanged.
2. `docs/extension-interface.md`, headings `User actions` and `Where Extensions run`: MC42 keeps them as they are.
3. `scenarios/ui-app-settings.md`, `U3806 settings persist and apply at once` and `U5242d a setting that changes looks previews live`: MC40 reuses their apply-at-once rule.
4. `scenarios/ui-shortcut-settings.md`, `U5239e export the overrides`: the `{ "<action name>": "<press>" }` shape MC41 reads.
5. `scenarios/user-actions.md`, `UA1 an Extension's actions load`, `UA2 a bad manifest loads nothing and says why` and `UA7 hot reload`: MC42 restates none of them.
6. `scenarios/named-actions.md`, `NA1 every command has one name`: the names MC41 binds.
7. `scenarios/machines.md`, `MC3 a machine shows as a chip or status on an Agent, nowhere else`: MC46 holds it for files.

**MC40 the look comes from a plain file, applied live.** Given `look.json` naming Tokens of `docs/design-system.md` (colours, interface scale, Terminal font family and size, the Mode), when the file is saved, then the App shows the new look without a restart, as U3806 applies a setting; a value outside the Token's type, or a key that is no Token, refuses the file whole (`config.problem` naming the key) and the previous look stays; deleting the file returns the defaults. A setting the user chose in App Settings (U3799) and a value in the file name the same Token: the file's value shows and App Settings shows it as set by the file, read-only. Tests (planned): `mc40_saved_look_applies_without_restart` (Daemon event and App state), `mc40_bad_value_or_unknown_key_refuses_the_whole_file`, `mc40_deleting_the_file_restores_defaults`. Observer: the design critic compares the applied look with the file.

**MC41 keys come from a plain file, applied live.** Given `keys.json` as `{ "<action name>": "<press>" }` (U5239e's shape) naming Named actions (NA1) and User actions (MC42), when the file is saved, then each chord runs its action at once with no restart and the Shortcuts group shows it; a name no action holds, a press that does not parse or one that a focused Terminal needs (U5239d) refuses that file whole with a cause, and the previous keys stay. A chord that names an attention rule's action (MC45) is refused. Tests (planned): `mc41_saved_keys_apply_without_restart`, `mc41_unknown_name_or_bad_press_refuses_the_file`, `mc41_terminal_keys_stay_with_the_terminal`.

**MC42 actions come from plain files.** Given Extension folders in `extensions/` (UA1), then a file there declares named actions as UA1–UA8 and `docs/extension-interface.md` say, and this scenario adds one thing: a single-file action (`extensions/<name>.js` exporting `register(on)` with no manifest) loads with the permissions `todos`, `pads` and `store` only; a file asking for more has a manifest (UA2) and nothing else changes. Saving it applies live (UA7). Tests (planned): `mc42_single_file_action_loads_with_the_narrow_permissions` (stand-in child, like UA1), `mc42_a_call_outside_the_narrow_permissions_is_denied` (UA4's refusal). UA1–UA8 stay the proof for everything else.

**MC43 Door behaviour comes from a plain file.** Given `door.md`, when a Door starts a turn, then its text is added to the Door's instructions after roundup's own, so the file shapes how the Door words, orders and summarises what it hands the user; the file never replaces roundup's instructions and never removes a tool. A saved change applies from the next turn of each Door, not mid-turn. Given no file, the Door is as `main` renders it. A refused file (MC45) leaves the last good text. Tests (planned): `mc43_door_instructions_end_with_the_file`, `mc43_saving_applies_from_the_next_turn_only`, `mc43_no_file_changes_nothing`.

**MC44 an AGENTS.md in the config tells the user's agent what it may change.** Given a first start with no `AGENTS.md` in the Config, then the Daemon writes one, and a later start never overwrites the user's edits. It names each part (MC40–MC43) with its file name, its shape and one example; says that a change applies on save and a refused file says why in a `config.problem`; names what is out of reach (MC45, MC46) in the user's terms,. It is the user's own config AGENTS.md, shipped with the product; the repository's `AGENTS.md` is not touched. Tests (planned): `mc44_first_start_writes_the_agents_md`, `mc44_a_later_start_keeps_the_users_edits`, `mc44_the_file_names_each_part_and_the_limits` (asserting the five file names and the two refused kinds appear, never the exact prose). Policy: the text is written for the user's agent by the `writing-for-agents` skill.

**MC45 the attention rules are out of reach.** Given any Config file that names which matter sits in the centre, who may ask the user (Messages, Routes, Held, Takeover), an alert setting (`alertLevel`, a Project's alerts, a State alert) or the shelf following the Rail's selection, when it is read, then the file is refused loud: one `config.problem` names the file, the key and "attention rules are not customisable", and nothing is applied from that file, the rest of the Config going on as it was. An Extension that calls `rail.setAlertLevel`, a State alert setting or `$.bus` on a Message topic is denied as UA4 denies an unpermitted call, with the same Problem. Tests (planned): `mc45_a_file_naming_an_attention_key_is_refused_whole` (one case per part and key), `mc45_the_refusal_is_loud_and_applies_nothing` (the Problem raised, the state unchanged), `mc45_an_extension_cannot_reach_the_alert_or_message_calls`. Observer: P3's replay holds with a Config that tries each.

**MC46 no file adds a second matter beside the centre or a new interruption.** Given a Config file that asks for a panel beside the centre, a machine sidebar or Rail level, a dispatch panel, a PR panel beside the terminal, a bell, an OS notification, a Toast or a badge outside the alerts the user turned on, when it is read, then it is refused as MC45 refuses, naming the request, and the App shows what it showed before. Given an action that finishes, then it raises nothing the alerts the user turned on would not raise. A side-by-side diff of two Agents' results and a PR the user chose are one matter in the centre and are not refused: each is specified by its own scenario when built, never by a file. Tests (planned): `mc46_a_request_for_a_second_surface_or_interrupt_is_refused` (by role, no panel, sidebar or Rail level opens), `mc46_a_finished_action_raises_no_alert_of_its_own` (P3's Observer, with an Extension that tries a ping on finish).

**MC50 a Config folder made after the Daemon started is watched.** Given a Daemon started with no Config folder, when the folder is created and `look.json` or `keys.json` is saved in it, then the file applies as MC40 and MC41 say, with no restart; a refused file answers `config.problem` as before. Given the folder was there at start, nothing changes. Tests (planned): `mc50_a_folder_created_after_start_applies_its_look` (the Daemon started on a missing folder, then the folder and `look.json` written; the look event arrives), `mc50_a_file_in_the_late_folder_is_refused_whole_when_bad` (a bad value in the late `look.json` raises one `config.problem`).

**MC49 a refused door.md leaves the last accepted text.** Given `door.md` accepted once (MC43) and then saved with a key MC45 refuses or a problem that raises a `config.problem`, when a Door starts its next turn, then its instructions end with the last accepted text, not the refused file and not roundup's text alone; the accepted text is kept in the Daemon's memory and a Daemon restart with only a refused file adds nothing, as MC43 with no file. A later accepted save replaces it. Tests (planned): `mc49_a_refused_door_file_keeps_the_last_accepted_text`, `mc49_a_later_accepted_save_replaces_it`, `mc49_a_restart_with_only_a_refused_file_adds_nothing`.

Policy: MC40–MC46, MC49 and MC50 add no RPC method that an implementing PR does not name by the Contract recipe of `.agents/builder.md`; `config.problem` is added to `GLOSSARY.md` there. Observer: `loop/rules.sh vocab` exits 0.
