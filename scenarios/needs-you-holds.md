# An Agent that waits on the user shows `needs-you` until the user answers (U8030a–U8030c)

Modules: `crates/agents` (`claude_code/`, `agent/fold.rs`, `stop_judge.rs`) and `crates/rupd` (the Rail, `digest.rs`, `wake.rs`, `attention.rs`). Ids: U8030a, U8030b, U8030c. Work order: [#8030](https://github.com/roundup-app/roundup/issues/8030); the implementation Issue is filed blocked by it. Terms: Status, Kind, Signal, Observation, Message (`GLOSSARY.md`). Refines A3564a and A3564b (`scenarios/native-questions.md`), TS1 to TS5 (`scenarios/agent-turn-status.md`), A7180a to A7180e (`scenarios/stop-needs-you.md`) and PS9 (`scenarios/terminal-program-status.md`). Principles served: P3, P11 (`PRINCIPLES.md`).

Source: the owner, 2026-11-27 (#8030): an Agent's Claude Code `AskUserQuestion` dialog stayed open in its Terminal while the Rail showed the Agent `working`, so nothing called the owner to it, and the owner lost work. Words: a **wait** is the span in which the vendor shows the user a dialog it blocks on, and **open** means it has begun and the user has not yet answered it. Wait kinds: an `AskUserQuestion` dialog, a permission prompt, a plan approval and an MCP elicitation. Policy: no new Kind, RPC, Message kind, contract or second marker beside the Status, and no timer that re-raises `needs-you`; the one Status is right.

**U8030a an open wait holds `needs-you` against every other event.** Given an Agent whose Status is `needs-you` because a wait is open, then no Observation that is not the wait's end changes its Kind, label or `since`, and none counts a finish. These are not the wait's end, and each leaves the Status as it was: a Signal of another tool call (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) or of a subagent (`SubagentStart`, `SubagentStop`), a `Notification`, `PreCompact` and `PostCompact`, `MessageDisplay`, a spinner or ✳ title, a `Tick` (`STAR_HOLD`, `SPINNER_HOLD`), the Message delivery Observation, a process snapshot of background work (DCL3, held or released), the model's answer to a stop check (A7180b), a program status report (PS9.1) and a Todo or Route change (A33). The wait's end is only: the user's answer, which the vendor reports as the `PostToolUse` or `PostToolUseFailure` of the tool the wait is for; the user's Esc or a roundup Interrupt; a `Stop`, `StopFailure`, `SessionStart` or `SessionEnd`; and the Terminal's exit. A wait kind whose opening no Signal reaches `hook_status` today (an MCP elicitation) gets one in the same change, so it opens `needs-you` as a permission prompt does. Tests: `u8030a_no_other_event_ends_an_open_wait` and `u8030a_the_answer_the_interrupt_and_the_stop_end_it` in `crates/agents/tests/scenarios/u8030.rs`. Observer: `cargo nextest run -p agents`, the production Adapter with an injected clock, no PTY and no real `claude`.

**U8030b every reader sees the open wait.** Given an Agent with an open `AskUserQuestion` dialog, when it receives a Message, or any other event of U8030a, then `rail.tree` still gives it Kind `needs-you` with its label, a read of the attention entries (`crates/rupd/src/attention.rs`, the lists the App's menu-bar list, tab counts and Dock badge count from, PS12.2) includes it, its `agent_digest` entry reads `needs-you`, and no `[wake]` note or Digest to its parent says `working`; the parent's `needs-you` wake fires once, as before. When the user answers, the Agent moves on as U8030a's end says and leaves the lists in the same read. Tests: `u8030b_an_agent_with_an_open_question_that_receives_a_message_stays_needs_you_in_every_reader` in `crates/rupd/tests/`, on the fake vendor `waiting_peer` of `crates/rupd/tests/support/native_questions.rs` (A3564a's seam) and the real Daemon, reading `rail.tree`, the attention entries and the digest after the Message and again after the answer. Observer: `cargo nextest run -p rupd`. The App's own counts are PS12's and U3770a's tests, unchanged.

**U8030c one guard holds every wait against every event, and the audit names each writer.** Given each wait kind of the source line, opened through the fake vendor (no real `claude`), when each event kind of U8030a is fired in turn, then the Status stays `needs-you` until the wait's end. The guard is one table over wait kinds and event kinds, so a new wait kind or event kind is one added row, and it fails when any cell leaves `needs-you` early. It fails on `main` as built for the event that cleared the Status in the owner's incident, and passes on the implementation PR. The implementation PR also lists, in its body, every writer of an Agent's Status in `crates/agents` and `crates/rupd` (`program_status`, `claude_code/status_label`, `agent/fold`, `stop_judge`, `claude_code/background`, and the Observation arms of `claude_code/mod.rs`) with the events that can replace `needs-you` while a wait is open and the fix or the cell of the guard that holds each. Writers read from `main` that the audit starts from: `hook_status` maps `PreToolUse`, `PostToolUse` and `PostToolUseFailure` to `working` with no regard for the open wait, and `observe_processes` settles `working` from background work after a `Stop`. Tests: `u8030c_every_wait_kind_survives_every_event_kind` in `crates/rupd/tests/`, through the Daemon and the fake vendor, with `u8030a_` tests as its unit-level cases. Observer: `cargo nextest run -p rupd -p agents`; the guard is a behaviour test (rule 10), takes no timer and starts no real process beyond the fake vendor.
