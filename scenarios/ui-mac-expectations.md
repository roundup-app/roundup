# macOS expectations

Specification for #3787. Implementation is separate. X1–X4 are acceptance labels within U3787a–U3787d, not Terminal scenario ids. These clauses are obligations, not claims that main implements them.

Journey: Enter (window, names and prompts), Understand (selection and action feedback), Intervene (Rail actions and Terminal ownership), Review (delete and restore work). Existing App, real Daemon and native Tauri seams are the observers; do not add a parallel command dispatcher, persistence holder, selection machine or clock. Implementation names new public contracts in `GLOSSARY.md` and changes every caller under the Contract recipe; this specification invents no RPC name.

### Rail Undo independence (#4667)

These clauses extend U3787a. They specify the Review-stage recovery after removing work; implementation is separate. An unrelated change means a write to a node outside the removed identities and their retained relationships, including a sibling reorder, a new Agent in another Workstream, or an automatic order normalization. A Project-wide snapshot comparison is not a restore conflict.

- Given an idle/exited Agent or reversible Workstream with its authorized cascade, when the user removes it, lets the normal removal events and App refreshes settle, changes nothing by hand and immediately invokes Edit > Undo or Rail-focused ⌘Z, then restore the acknowledged cascade without a failure message. Repeat with an unrelated sibling reorder and a new Agent in another Workstream between removal and Undo: both changes remain and Undo still succeeds. Restore original identities, metadata, Home/Todo assignment, Todo completion/blocker edges, Pad incarnation/content/Revision and retained children; start no Agent or Terminal. With no intervening change, restore the original sibling order. With intervening sibling changes, preserve the surviving siblings' current relative order and insert the restored item before its first surviving original following sibling, or after the current siblings if none survives. Test: planned `u3787a_rail_undo_preserves_unrelated_changes`, one parameterized behavior test covering Agent/Workstream × immediate/reorder/new-Agent, through the real Daemon in `crates/rupd/src/removal/restoration_tests.rs`; extend the existing App-seam `u3787a_rail_%s_deletes_without_question_and_restores_retained_identity` in `apps/desktop/src/rail/menu/u3787a_undo.test.tsx` for normal refresh settlement, both Edit-menu and keyboard Undo entry points and absence of failure feedback. UI assertions cover identities, calls and roles, never copy or layout.
- Given a retained Rail removal, when its original parent has since been removed or an identity to be restored now exists, then refuse the entire restore without replacing that identity, changing any participant or consuming the retained operation. Keep Undo available; after the blocking parent is restored or the conflicting item is explicitly removed by the user through its existing authorized removal action, the same retained operation can restore once; equal replay changes nothing. A missing parent that is itself restored by this cascade is not a conflict. Test: extend `u3787a_conflict_rolls_back_graph_and_mirrors_and_allows_retry` in `crates/rupd/src/removal/restoration_tests.rs` with parent-missing and restored-id-collision cases, asserting all Rail/Todo/Pad/file participants and receipt state before refusal, after refusal and after recovery. No raw replacement or deletion is authorized by Undo.
- Given a genuine refusal, then its message identifies the blocking item using its user-visible name, states the cause and names an available recovery action. A removed parent reads `Can't undo: "<parent>" was removed too. Undo that first.` An occupied Pad name identifies the existing Pad and directs the user to rename that Pad before retrying Undo. An occupied identity must never suggest that renaming changes its identity: identify the blocking item and direct the user to remove that item only when its existing removal action can free the identity; otherwise state that this Undo cannot currently be completed and that the deletion is retained. Expose no SQL, table name or internal id; never say “resolve the conflict and retry” or “retry after resolving the conflict.” Test: planned `u3787a_undo_refusal_names_cause_and_recovery`, parameterized in the formatter's unit-test area, asserting exact copy for missing parent, occupied identity and occupied Pad name; the real-Daemon refusal test above checks the reported cause and blocking identity. Exact copy belongs here, never in a UI test.
