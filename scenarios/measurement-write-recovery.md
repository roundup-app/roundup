# Measurement revision write recovery

Module: the existing measurement collector and Rail storage in `crates/agents`.
Ids: U3119a–U3119b.

Outcome: a request collected across a failed revision write becomes discoverable to revision-based readers after storage recovers, exactly once and under a newer retained revision.

Amendment (#3574, P14): a "request" in these scenarios is an Execution interval or Timed activity after tokens and money are removed (U3016l); the acceptance is otherwise unchanged and its tests read an interval where they read a request.

Scope: repair collection persistence and revision notification using the existing Measurement, Measurements and MeasurementsChanged contracts. No new RPC, vendor interpretation, dashboard behavior, schema requirement or Message/delivery change is requested. U3016d's source/read-failure acceptance remains in force; these scenarios add the distinct revision-write failure case. This specification changes acceptance only; #3119 owns implementation and progress.

**U3119a recovered contributions publish a newer revision.** Given an isolated Project with one supported request already collected, retain its successful `project.measurements` snapshot, revision R and contribution identity/value, and subscribe to `project.measurementsChanged`. No Agent is running and no Timed activity changes during this probe. When the fixture renames `measurement_state` so revision writes fail, appends a second distinct supported request, drives the production collector through a collection attempt, restores the table unchanged and drives collection again without another source append, then a successful public read contains both requests exactly once, preserves the first request's identity/value and original attribution, and has a numeric revision greater than R. Every successful read containing the second request, including a read immediately after table restoration before collection retries, has a revision greater than R; an explicit read error while storage is unavailable is permitted, a successful snapshot pairing changed contributions with R is not. After recovery the subscriber receives a MeasurementsChanged revision greater than R, and a public read at or beyond that notified revision contains the second request. Assert `u3119a_revision_write_recovery_publishes_the_request` at the existing in-process Agents dispatch/Event seam with isolated supported source files and real Project storage. Count request contributions by identity, not unrelated measurements or source-status revisions.

**U3119b recovery survives reopen and unchanged replay.** Given U3119a's baseline and the same failed-write collection attempt, when the fixture restores `measurement_state` and reopens the Project before any successful recovery collection, then collection without another append recovers both requests exactly once under a revision greater than R. Reopen again after successful recovery and collect the unchanged source: both request identities, values and attribution remain equal to the recovered snapshot, and the retained revision does not advance merely from unchanged replay. Assert `u3119b_revision_write_recovery_survives_reopen` through the same in-process production collection/public-read seam and real storage reopen. This must also pass when the failed attempt persisted no contribution: retaining a replay position must never skip an uncommitted request.

Policy: the two named observers are implementation tests to add, not claims of existing tests on main. Reuse existing fixtures and real transaction ownership; do not launch a Daemon, PTY, browser or vendor program for a failure an in-process collector/storage test can prove. Inject the write failure in isolated storage, never the user's Project. Drive collection directly or use paused time tied to `OBSERVATION_PERIOD` in `crates/agents/src/measurement.rs`; do not wait on guessed sleeps. Do not assert a particular transaction layout, exact revision increment or number of intermediate failure notifications. No test scans this specification to claim recovery.

2. `scenarios/workstream-dashboard.md`, **U3016d realtime updates survive reconnect and failure**, and `crates/rupd/tests/workstream_measurement.rs`, `u3016d_reconnect_reconciles_without_double_counting`: source/read-failure recovery keeps retained contributions and coherent revision reconciliation.
3. `crates/rupd/tests/workstream_measurement.rs`, `u3016d_empty_collection_failures_notify_subscribers`: failure notifications remain observable even before any request has been collected.
4. `PRINCIPLES.md`, **P4 Black-box harness** and **P9 roundup spends the user's usage only when asked**: repair storage without moving vendor parsing outside its Adapter, adding an Adapter seam or starting/prompting an Agent. Observer: the new in-process U3119a/U3119b fixtures exercise passive collection with no vendor program; inspect the implementing diff for unchanged Adapter boundaries and launch/prompt callers.
