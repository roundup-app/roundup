# Orders

Module: `crates/agents` (the order on each Agent, set at spawn and at a Door's start, persisted with the Rail), `crates/contracts` (`Order`, `RailNode.order` (named `work` in the wire type if `order` collides with the sibling position field), `SpawnParams.order`, `CreateWorkstreamParams.order`, `ContextSelf.order`, `agent.setOrder`), `crates/rupd` (registration), `crates/rup` (the `agent_set_order` MCP tool), `apps/desktop` (O6 only). Terms: Work order, Clarification order, Workstream, Door, Steer, Decision, Provenance (`GLOSSARY.md`). Principles served: P1, P3, P6. Contract change (rule 4): the fields and method above, with every caller in the same PR. Reported in #389. Workstream becomes Workstream with #369, and these clauses rename with it. Ids: O1–O16 (O1, O2 and O6 are narrowed by Q4 and Q5; O1, O2 and O4 by O7 to O9; O2 and O4 by O11 to O13). O7 to O9 are the Daemon slice and O10 the App slice (rule 3), reported in #732. O11 to O13 make the Door write the order for a typed prompt (#1177).

**O1 every Agent holds one order.** Given any node in `rail.tree`, then each Agent node and each Workstream node (its Door) has an order that is exactly one of `{kind: "work", ask, done?, limits}` (O7) or `{kind: "clarification", question}`. `ask` and `question` are non-empty after trimming. `limits` is a list, possibly empty, of non-empty strings, each a rule that reads on its own (Q4). Test: `o1_`, over a real Daemon after each path of O2 and O3.

**O2 a spawn sets the order.** Given `agent.spawn {cwd, prompt?, parent?, order?}`:
- With `order`, that order is stored.
- With `prompt` and no `order`, the order is `{kind: "work", ask: prompt, limits: []}`.
- With neither, it is `{kind: "clarification", question: "What should this Agent do?"}`.
- Both `prompt` and `order`, or an order that breaks O1's shape, is `INVALID_PARAMS` and changes nothing (A18), except that an Agent's `agent.spawn` takes both (O8).

Once H19's gate opens (the first `SessionStart` and the first star title), the Agent gets one Steer in place of A4's prompt Steer:
- For a Work order, the ask, then `Done when:` and the done condition (left out when absent, O7), then `Limits:` and one line per limit (left out when `limits` is empty), as Q4 says.
- For a Clarification order, the question and an instruction to find the intent, elicit what is missing (from whom `agent.context` says to ask) and record a Work order with `agent_set_order`.

A Door's `agent_spawn` (F3) takes the same `order`; B24's policy (fixed limits, not decisions) is what its Brief tells the Door to put there. Narrowing: A9's no-prompt spawn now also holds a Clarification order; its naming rule is unchanged. Test: `o2_`, with a fake `claude` recording the first Steer.

**O3 a Door's order is its Workstream's.** Given `rail.createWorkstream {name, parent, order?}`, then the Workstream's Door holds `order` when given, else `{kind: "clarification", question: "What is this Workstream for?"}`. `rail.startDoor` (A7) sends the Door O2's Steer for that order. Stopping the Door keeps the order with the Workstream. Test: `o3_`.

**O4 settling an order.** Given `agent.setOrder {id, order}`, then the Agent itself, the Door of its Workstream, or the user may replace its order with any order of O1's shape. The change emits `rail.changed` and records a Touch with the Actor (Provenance).

If a caller other than the Agent changes the order, the new order is sent to the Agent as O2's Steer, except during a Takeover (P1), when it is not sent. In both cases `agent.context` returns it as `this.order`.

Errors:
- Another Agent: `FORBIDDEN`.
- A Terminal: `CONFLICT`.
- An unknown id: `NOT_FOUND`.
- A malformed order: `INVALID_PARAMS`, with nothing changed.

A Clarification order whose question only the user can answer reaches the user only as a Decision (P3, `agent.ask`); holding the order alone never yields `needs-you`. `rup mcp <id>` offers `agent_set_order`, with `id` filled with its own Agent's id. Test: `o4_`.

**O5 an order survives.** Given an Agent with an order, when the Daemon reopens (A8, A12), the Agent is Resumed (A22), or it is moved to another Home (`rail.move`), then `rail.tree` shows the same order. A Resume sends no new order Steer. Discard and `rail.remove` drop it with the node. Test: `o5_`.

**O6 the user reads the order of an Agent.** Given a selected Agent in the App (a Workstream shows no order line, U467), then one line shows the order. For a Work order, the line is Q5's. For a Clarification order, it is `Clarifying:` and the question. The line is cut to one line, and activating it opens the full order in the Drawer under U111's layout rules and Q4's parts.

The line is present for every selected Agent, so moving between Agents never changes the Terminal's size (U5). It sits with U113's Card, which stays above it. A Terminal shows no line. Text meets U4, and the line uses only Tokens. Observers: `o6_` in Vitest and the U26 harness, and a native 1280×800 capture of a Work-order Agent and a Clarification-order Agent in one Workstream. The PR names the Checks it moves.

**O7 a Work order says when it is done, and its ask is short.** Contract change (rule 4, the Contract recipe of `.agents/builder.md`). `Order::Work` gains `done: Option<String>`, optional and absent from an old caller's JSON and from every stored order, generated into `contracts/generated/agent/`; GLOSSARY.md names it (Done condition). A present `done` is non-empty after trimming (O1). Every caller changes in the same PR: `crates/contracts`, O1's validation, O2's Steer, O4's `agent.setOrder`, the `agent_set_order` and `agent_spawn` schemas (generated from the same types), the Rail's persisted order, and every Rust fixture that builds `Order::Work` (`crates/perf`, `crates/rup`, `crates/rupd`). An explicit `order` of `agent.spawn`, `rail.createWorkstream` or `agent.setOrder` whose `ask` is over 200 characters after trimming (counted as Unicode scalar values) is `INVALID_PARAMS`, nothing changes, and the message names the cap (`order ask is over 200 characters`). The cap fits O6's one line, which is cut at the Rail's width (`apps/desktop/src/orders/styles.css:11`), with room for Q5's limits count. The prompt-only path of O2 is exempt: it stores the user's own words whole, and a stored order over the cap stays readable. Laws M1 to M10 are not touched. Tests: `o7_done_is_optional_and_stored` (a Work order with and without `done` round-trips `rail.tree`, and an old JSON without it parses), `o7_an_empty_done_is_invalid_params`, `o7_an_ask_over_the_cap_is_invalid_params_and_names_it` (200 passes, 201 fails, on spawn, `rail.createWorkstream` and `agent.setOrder`), `o7_the_prompt_only_path_is_not_capped` (a 2,400-character prompt is stored whole as the ask).

**O8 an Agent's spawn takes an order and a prompt together.** Contract change (rule 4): `agent.spawn`'s `SpawnParams` keeps `prompt` and `order`, and a new method `agent.spawnPrompt {id}` answers `{prompt: string | null}`, registered in `crates/contracts/src/methods.rs`; GLOSSARY.md names the Spawn prompt. Given `agent.spawn` by an Agent (F3, an Actor of kind Agent):
- With `order` and `prompt`, both are stored: the order as O2 says, the prompt exactly as written, in the Agent's persisted row beside the order (not on `RailNode`, so `rail.tree` and `rail.changed` stay as small as before; rule 7).
- With `order` and no `prompt`, the prompt is `null`.
- With `prompt` and no `order`, the spawn is `INVALID_PARAMS`, changes nothing, and the message says to add an `order` with the ask, the done condition and the limits. This is the refusal that fails loud; B25's measure still says whether Doors are refused too often, and if it fails, the refusal is lifted by an Issue that cites it.
A spawn by the user (the App's `SpawnPromptField`) keeps O2's prompt-only path and stores no Spawn prompt (`null`): the ask is the prompt. `agent.spawnPrompt` on an unknown id is `NOT_FOUND`; the prompt survives O5's cases, and Discard drops it with the node. Every caller changes in the same PR: the MCP tool `agent_spawn` (a28's test passes an `order`), the App seam's method list, and fixtures that build `SpawnParams`. Laws M1 to M10 are not touched. Tests: `o8_an_agents_spawn_stores_order_and_prompt`, `o8_an_agents_spawn_with_only_a_prompt_is_refused` (message holds `order`), `o8_a_users_prompt_only_spawn_is_unchanged`, `o8_the_prompt_survives_a_reopen_and_a_resume`, `o8_an_unknown_id_is_not_found`.

**O9 the child's first Steer carries every part, and the Door is told where each goes.** Given an Agent spawned by O8 with an order and a prompt, then at H19's gate the one Steer is, in order: the ask, `Done when:` and the done condition (left out when absent), `Limits:` and one line per limit (left out when none), then the prompt exactly as stored, under the heading `Details:`. Tests: `o9_the_first_steer_carries_the_ask_done_limits_and_prompt` with a fake `claude` recording the Steer, byte for byte against the fixture, and `o9_a_steer_without_a_prompt_is_o2s`. This amends B24, whose Brief stays otherwise as it is, and answers B25's `doneWhen` question for orders: the done condition is `order.done`, optional on the type and asked for by the Brief; B25 stays open for `owns` and `observer` only.

**O11 the Door writes the order for a prompt the user types.** Narrows U33 and O2's prompt-only path; changes no contract (rule 4): the App sends the existing `message.send`. Given a Project whose selected Workstream has a running Door (U467), when the user submits a non-empty prompt in `SpawnPromptField` (U33), then the App calls `message.send {to: <the Door's id>, kind: "note", body}` as the user (B1) and not `agent.spawn`. `body` is the typed words, trimmed as U33 trims them, and nothing else, so the Door reads the user's own words whole. The field closes, the Rail row count does not change, and U81's line `asking the Door…` takes the place of `starting agent…` until the call settles (all three asserted by `o11_a_typed_prompt_goes_to_the_door_as_a_note`). A failed send shows U9's `✕ <message>` line and keeps the field's text, as U33 does. The new row appears when the Door's `agent_spawn` (O12) lands, as any Rail change does, and this call selects nothing: the App has no way to tell which new row came from this note, so the selection stays where the user put it (policy). An empty or whitespace-only field keeps U33: `agent.spawn` with `prompt: null`, so the Agent holds a Clarification order and writes its own Work order (O2, O4). Tests: `o11_a_typed_prompt_goes_to_the_door_as_a_note` (the fake App seam records `message.send` with the exact body and no `agent.spawn`), `o11_a_failed_send_keeps_the_text`, `o11_an_empty_prompt_still_spawns_a_clarifying_agent`.

**O12 the Door spawns the Agent with the order it wrote.** Amended by F8 (`scenarios/door-terminal.md`) for direct Terminal conversation. **O13 a Door writes orders only for the Agents it spawns.** Narrows O4, whose Door clause now holds only as this says. **O16 the user edits the order in the Drawer.** Slice of the App (`apps/desktop/src/orders/`, the seam's `agent.setOrder` call, O4); it follows O14 and O15 on main.
