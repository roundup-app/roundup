# Todos and Pads over MCP

Module: `crates/rup` (the `rup mcp` subcommand), with `crates/rupd` (Reach, M7; `project.open`, M8) and `crates/contracts`. Ids: M1–M11.

ADR 0007: the Daemon serves MCP to Agents through a stdio shim, so every call is a Touch by the calling Agent. The shim is `rup mcp <agent-id>` in `crates/rup`. Build it on the official Rust MCP SDK (`rmcp`), not a hand-rolled protocol. Tests start the built `rup` (`CARGO_BIN_EXE_rup`) against an in-process Daemon on a temp socket, as `crates/rup/tests/ping.rs` does, and speak MCP to it over stdio. No `claude` is involved.

**M1 tools.** Given `rup mcp <agent-id>` started on stdio with a Daemon answering at `RUPD_SOCKET`, when an MCP client initializes and lists tools, then the server is named `roundup` and offers one tool for each of these methods: `todo.create`, `todo.get`, `todo.list`, `todo.update`, `todo.complete`, `todo.setBlockers`, `pad.create`, `pad.read`, `pad.list`, `pad.write`, `pad.append`, `pad.setOwner`, `pad.delete`, and, by B12, `message.send`, `message.get`, `message.list`, `message.pass`. A Door's list has one more, `agent.digest` (B20), and no other Agent's does. Each tool is named after its method with the dot replaced by `_` (`todo_setBlockers`). Each input schema is derived from the method's params type in `crates/contracts`, and none is written by hand. `todo.list` and `pad.list` take `null` params, so their schema is `{"type": "object"}`, and the shim sends `null` to the Daemon. `message.deliver`, `message.drop`, `route.set`, `takeover.begin` and `takeover.end` are the user's and not offered. `decision.list` and `decision.answer` are offered by H21 (#710), each judged by Reach (M7), and `decision.answer` is no longer left to the user. Four more methods are not offered. `todo.delete`: a Todo has no owner to guard its deletion. `todo.reorder`: the Todo order is the user's (T10). `pad.export`: it writes outside the Project. `pad.setStorage`: storage is the user's Project setting.

**M2 a call is a Touch by that Agent.** When the client calls `todo_create {title: "x"}`, then the Todo exists, its `wrote` Touch has actor `{kind: agent, id: <agent-id>, parent: null}`, and the tool result's text is the method's JSON result. A Daemon error, such as `pad_write` on a Pad another Agent owns, comes back as a tool result with `isError: true`. Its text is the Daemon's error as JSON, `{code, message}` (`-32002` is `FORBIDDEN`). The shim maps no code to a name, so it needs nothing new in `crates/rpc`. After such an error the server keeps serving.

**M3 no Daemon, no hang.** When no Daemon answers at start, `rup mcp` exits non-zero with one stderr line naming the socket path. When the Daemon goes away later, the next call makes it exit non-zero; it never waits forever. Claude Code then reports the server as failed instead of hanging a turn.

**M4 the tool list matches the real client's schema.** Given `rup mcp <agent-id>`, when a client lists tools, then every `tools/list` reply is `{ttlMs, cacheScope, tools, nextCursor?}` with `ttlMs` an integer of at least 0 and `cacheScope` either `public` or `private`: the schema of the interactive Claude Code 2.1.288, read from its binary (the headless 2.1.283 has the same schema and accepts the older reply). That client rejects a reply without them after `/mcp` reconnects: "Reconnected to roundup, but fetching tools failed: Invalid result for tools/list", with the issues `expected number, received undefined` at `ttlMs` and `invalid_value` with `values [ public, private ]` at `cacheScope`. Two checks prove it. `m4_` over stdio validates every reply (the full list, and the empty list a request with a cursor gets, since this server pages nothing) against that schema, which the test holds as a copy extracted from the installed binary, with the extraction command and `claude --version` in a comment that names what a changed schema would break. The interactive reconnect itself is a laptop check by QA or the user, as S7's window is: it needs a browser sign-in that a boxd VM's token does not satisfy. It runs `/mcp` against `rup mcp` on 2.1.288, shows the base binary rejected and the head accepted with `mcp__roundup__todo_list` listed, and is recorded in the PR. The same schema holds for every tool added later (`ask_user`, H14).

**M7 Reach: which nodes a call may act on.** Narrows M2. *Reach* (`GLOSSARY.md`) is the set of Rail nodes an Agent `m` may act on: the descendants of `m` in `rail.tree` (a Door is its Workstream's node, so a Door reaches its whole staff, A26), and every Workstream `m` created by `rail.createWorkstream` with all its descendants. The Daemon keeps the creating Actor beside the Workstream's `order` in the Rail's store (no wire field, a store written before it counts as created by the user), and it is gone with the Workstream. `m` is in no Reach of its own; a Subagent `s` of `m` is in `m`'s. A call by the user or an Extension has no Reach limit and is unchanged. For an Agent `m`:
- `agent_stop`, `agent_interrupt`, `agent_prompt`, `agent_resume`, `agent_discard`, `agent_land`, `rail_remove`: the node must be in `m`'s Reach, itself excluded, so `m` never stops, removes or lands itself. `rail_remove` of a Workstream `m` created removes it as A16 says.
- `rail_startDoor`: the Workstream must be one `m` created, or a Door in `m`'s Reach.
- `rail_rename`, `agent_worktreeState`: `m` itself or a node in its Reach. `rail_move`: the node in `m`'s Reach, with A6 and A26 unchanged (an Agent never moves under an Agent, a Workstream moves only to the root).
- `decision_answer` (H21): the Decision's Agent must be in `m`'s Reach, itself excluded, and not under a Takeover (`CONFLICT`). `decision_list` returns only the Decisions of Agents in `m`'s Reach.
- Project-wide, no node: `rail_tree`, `rail_createWorkstream`, `todo_*`, `pad_*`, `route_list`, `checkpoint_list`, `project_get`, `project_setWorktrees`, `project_open`, `project_rename`, `provenance_*`. A Todo, a Pad (its owner rules, P3) and a Project setting have no node.
A call whose node is outside the Reach is `FORBIDDEN` naming the node (M2), after `NOT_FOUND` for an unknown id, changes nothing, emits no event and logs no Touch. A call that succeeds logs a `wrote` Touch on `rail:<id>` by the Agent. Tests (`m7_`): `m7_a_door_stops_its_subagent`, `m7_a_door_cannot_stop_another_workstreams_agent`, `m7_an_agent_cannot_stop_or_remove_itself`, `m7_a_workstream_an_agent_created_is_in_its_reach`, `m7_a_sibling_subagent_is_outside_reach`, `m7_the_user_has_no_reach_limit`, `m7_a_forbidden_call_changes_nothing_and_logs_no_touch`, `m7_the_creator_survives_a_restart`.

**M10 a Door writes a checkpoint.** Found by the user's report #807: a Door's Thread was a chat log, and nothing condensed what had been achieved. Contract change (the Contract recipe of `.agents/builder.md`; `GLOSSARY.md` gains **Checkpoint** and **Block**, and `crates/contracts` gains `checkpoint.write`, `checkpoint.list` and the event `checkpoint.written`). A Checkpoint is not a Message: it has no Route, no status and no delivery, and `message.list` never returns one. Given a Door `d` and its `rup mcp d`, then:
- **Tool.** `tools/list` offers `checkpoint_write` to a Door and to no other Agent, and `checkpoint_list` to every Agent (as `agent.digest`, B20), its schema derived from the params type (M1). Asserted in `m10_only_a_door_is_offered_checkpoint_write`.
- **Shape.** `checkpoint.write {title, blocks}` takes a `title` of at most 80 characters and 1 to 8 Blocks. A Block is one of `{kind: "rows", title?, rows: [{label, value}]}` (at most 12 rows), `{kind: "table", title?, head: [string], rows: [[string]]}` (at most 6 columns and 12 rows), `{kind: "diagram", title?, mermaid}` (U148's source, at most 2000 characters) and `{kind: "text", title?, text}` (at most 400 characters). The Door chooses the Blocks, their number and their order; no part is required. The result is `{id, workstream, at, title, blocks}`, `id` the next integer of that Workstream (1, then 2), `workstream` the Door's own. Asserted in `m10_write_returns_the_next_id_in_the_doors_workstream` and, for each limit, `m10_a_block_over_its_limit_is_invalid_params` (a `title` of 81 characters, no Block, nine Blocks, an unknown `kind`, a 13th row, a 7th column, a 2001-character `mermaid` each fail with `INVALID_PARAMS` and write nothing).
- **Reach.** A call by an Agent that is not a Door is `FORBIDDEN` (M7, `-32002`) and writes nothing. Asserted in `m10_a_subagent_cannot_write_a_checkpoint`.
- **List and event.** `checkpoint.list {workstream}` returns that Workstream's Checkpoints, oldest first, and `checkpoint.written` carries the one written; both survive a Daemon restart as Messages do. A Touch `wrote` on `checkpoint:<workstream>:<id>` by the Door is logged (M2). Asserted in `m10_list_returns_checkpoints_in_order_after_a_restart` and `m10_write_emits_the_event_and_logs_a_touch`.
- **Brief.** A Door's Brief names `checkpoint_write`, says to write one when the work reaches a point worth marking (an Agent's work finished or merged, a change of direction, a decision made), to run `reduce` on every string and lay out Blocks the `show-me` way, and to put nothing the Thread's feed already shows (#688, Q1 to Q5 of #676). No other Agent's Brief names it (M9). Asserted in `m10_a_doors_brief_names_checkpoint_write_and_no_other_does`.

**M11 the roundup tools start deferred.** Found by the user's report #941: `/context` in an Agent roundup started showed MCP tools at 44.4k tokens (22.2% of 200k) with 151 tools loaded before any work; the 22 roundup tools are about 4.6k of it.
