# The user and the Project's program start an Agent with their own Claude Code settings (ST1–ST6)

Module: `crates/agents` (launch, merge, resume), `crates/contracts`, `contracts/generated/`, `crates/rupd` (who may send it) and `crates/rup`. Ids: ST1–ST6. Work order: [#7731](https://github.com/roundup-app/roundup/issues/7731), blocked by [#7730](https://github.com/roundup-app/roundup/issues/7730). Principles served: P8, P9 (`PRINCIPLES.md`). Amends A4 and A3507b (`scenarios/agents.md`: the file holds roundup's keys and the starter's) and U3801 (`scenarios/ui-app-settings.md`: the Project's program may set a permission mode through `settings`). Builds on PG1–PG6 (`scenarios/project-program.md`).

Decided by the owner (2026-11-20): `agent.spawn` takes `settings`, a JSON object roundup merges with its own keys into the Agent's `--settings` file, keeps with the Agent and writes again at each resume, whoever resumes it; roundup accepts `settings`, and a permission mode with them, only from the user or from the Project's program (PG1–PG6); roundup knows the program by something it gave the program at start, never by a name the caller claims; any other caller's `settings` is refused and no Agent starts. A design check that reads one of these as a defect changes how it is drawn, never the decision.

`GLOSSARY.md` gains **Start settings** (`SpawnParams.settings`: the Claude Code settings a starter sends with `agent.spawn`, kept with the Agent) in the implementing PR (Contract recipe of `.agents/builder.md`).

**ST1 the program or the user sends `settings`, and the file holds them beside roundup's.** Contract change (the Contract recipe). `agent.spawn`'s params gain `settings`, an optional JSON object (absent means none); anything but an object, or one over 64 KiB, is `INVALID_PARAMS`, writes nothing and starts nothing. No new RPC method, and `rup spawn` presents it as `--settings <json|@file>`. Given a launch whose `settings` hold `env`, `permissions.deny`, `enabledPlugins` and a `Stop` hook, when the caller is the user or the Project's program (ST3), then the Agent starts and its `<n>.settings.json` holds the merge of roundup's keys (A4's hooks, its permission rules, the bypass keys, `statusLine`, `env` of A43 and A3507b) and `settings`, by Claude Code's own rule for joining settings sources: an array joins, roundup's entries first, and an entry already there once is not repeated, so roundup's `STATE_EVENTS` hooks and permission rules always stay beside the `Stop` hook and the `deny` rules; an object merges key by key; a key both hold with a value that is not an array or an object, or with different shapes, keeps roundup's value, so `env.ROUNDUP_AGENT_ID` and the `PATH` of A43, A20's Attempt in the hook command and every bypass key are roundup's, and a key only `settings` holds is its own value. A3507b still holds for the user's own settings: no key of their `~/.claude` sources, Project settings or environment is copied in, and `settings` are the only starter keys. The file is written mode `0600`, and no error, log line, `rail.tree` row or Signal holds a `settings` value, since an `env` entry may be a secret. Tests (`st1_`, `crates/agents/tests/launch/`, through the production builders without starting a program): `st1_settings_join_roundups_keys_and_roundup_wins`, `st1_a_non_object_or_oversize_settings_is_invalid_and_writes_nothing`, `st1_no_user_key_enters_the_file`, `st1_the_file_is_private_and_no_value_is_logged`; in `crates/rup/tests/`, `st1_rup_spawn_sends_settings`.

**ST2 a resume writes the same file, whoever resumes.** Given an Agent started with `settings` (ST1), when it exits and `agent.resume {id}` is called by the user, by the program (ST3) or by the App's restart, then roundup keeps `settings` with the Agent's data beside A21's, survives a Daemon restart, and the new launch's `<n>.settings.json` is the merge of ST1 over the then-current roundup keys, equal to the first launch's except for A20's next Attempt in the hook command and the keys that follow the launch (`env.PATH` after a moved `rup`). `agent.resume`, `rail.startDoor` and every other method take no `settings` and send none: a stored value is neither replaced nor cleared by a resume, and a resume by an Agent or an Ext that A22's gate allows still sends nothing of its own, so it gives them no way to change or read the stored value. An Agent started without `settings` resumes without any. P9: settings change only at a launch, never during a running Attempt: a running Agent's file is not rewritten. Tests (`st2_`, `crates/agents/tests/scenarios/`): `st2_a_resume_writes_the_same_file_whoever_resumes`, `st2_the_settings_survive_a_daemon_restart`, `st2_a_resume_takes_and_changes_no_settings`.

**ST3 the Project's program is the process that descends from the Terminal roundup started for it.** Contract change in `crates/rupd`, no new method. Pick, and the reason: roundup identifies the program as it knows an Agent (H21), by the caller's process: a caller is the Project's program when its peer pid descends from the pid of that Project's program Terminal (PG2) that the Daemon started and still holds running, checked on each call by the same native parent walk as H21 (no process spawn, R3696a). No secret is made, handed out or stored, so none can leak into a child's environment, a log or a file, and none can be left from an earlier start. `--as`, `--agent`, `ROUNDUP_AGENT_ID` and a raw `daemon.identify` are read only to name an Ext or Agent; they never make a caller the program, and a caller below the program's pid that claims another name is still the program for ST4's gate. A caller that is below a running Agent's program is that Agent first (H21), so an Agent is never the program even when its Terminal lies in the program's tree. The program's pid is the Terminal's own as PG2 starts it, and after a Daemon restart (PG5) the pid the surviving owner reports once A12a's incarnation and program checks pass; a Terminal that has exited, been replaced by a restart (PG4), been stopped (PG3) or been dropped by PG5 is no program, so a process left from an earlier start of the program, now reparented to `init`/`launchd` or below a pid the Daemon no longer holds, is the Ext or User it claims and nothing more. The program's Terminal in another Project is no program here. What this pick cannot stop (policy): any process the program itself starts, since it is in the tree, including one that runs on text the program read; another program of the same macOS user that attaches to the program or the Daemon with the debugger rights the user holds (`task_for_pid`, `ptrace`) or writes the Daemon's store; and a detached process an Agent started, which is outside every tree and is the Ext it names or else the User exactly as `action_actor` decides today, so it can send `settings` only as the User. Who counts as the User stays as `action_actor` decides it. Tests (`st3_`, `crates/rupd/tests/`, a fake program whose child process calls through the socket): `st3_a_caller_below_the_programs_terminal_is_the_program`, `st3_a_claimed_name_is_never_the_program`, `st3_an_agent_below_the_program_is_the_agent`, `st3_an_earlier_start_and_a_gone_terminal_are_no_program`, `st3_a_surviving_program_is_known_after_a_daemon_restart`, `st3_the_programs_terminal_of_another_project_is_no_program`.

**ST4 any other caller's `settings` are refused, and nothing starts.** Given `agent.spawn` carrying `settings` (an empty object included), when the caller is an Agent (the MCP `agent_spawn` and `rup` from its shell), an Ext of any name, the Ext named after the program, `ext:<name>` or `--as` claims included, or a process outside every Agent's tree that claims the program's name and is not below the program's Terminal (ST3), then the call is `FORBIDDEN` and the message names `settings`; no Agent, Terminal, worktree, Pad, `<n>.settings.json` or stored value is made, and no Observation or Signal is recorded. The refusal is decided before any of them, from the caller's process (`action_actor`'s order: an Agent's process first), not from the connection's claim. The same call without `settings` is decided as today: nothing about spawning without them changes (`Gate::Spawn`). A permission mode is sent in `settings` as `permissions.defaultMode`, and the program's own `permissionMode` field stays the user's as U3801 says, so a call by the program with the field is `FORBIDDEN` as today. Tests (`st4_`, `crates/rupd/tests/`): `st4_an_agent_with_settings_is_forbidden_and_starts_nothing`, `st4_an_ext_with_settings_is_forbidden_and_starts_nothing`, `st4_a_claim_of_the_programs_name_is_forbidden`, `st4_a_spawn_without_settings_is_decided_as_before`, `st4_the_program_sending_permission_mode_is_forbidden`.

**ST5 a permission mode in `settings` reaches the launch.** Amends U3801 by name: the Project's program may set a permission mode, only through `settings`. Given `settings` whose `permissions.defaultMode` names a mode (`default`, `acceptEdits`, `plan`, `auto` or `bypassPermissions`), when the user or the program (ST3) starts an Agent with them, then the file holds it and the launch's argv carries the same `--permission-mode`, so the mode reaches Claude Code on both routes and the Agent starts in it. Given both the App-wide mode of U3801 and a `permissionMode` field on the user's call (the App sends one when the user chose a mode) and `settings.permissions.defaultMode`, then the field wins, as the command line wins over a settings file in Claude Code, and the file's `defaultMode` is rewritten to the same mode so the two never differ; policy: the user's choice made in the App is the later and more direct one than a program's. With no field, the program's mode stands and U3801's `Claude Code default` adds none over it. A resume (ST2) launches in the stored mode; the resume's own `permissionMode`, which only the user selects, wins over it as above. A YOLO start is unchanged and ignores both. An Agent still cannot choose a mode: ST4 refuses it, and an Agent that adds extras keeps the mode it started in. Tests (`st5_`, `crates/agents/tests/launch.rs`): `st5_a_settings_mode_rides_the_file_and_the_argv`, `st5_the_users_field_wins_over_settings_and_the_file_agrees`, `st5_a_resume_keeps_the_stored_mode`, `st5_yolo_ignores_settings_mode`.

**ST6 a credential from an earlier start is refused, and a refusal leaves no trace.** Given the program's Terminal killed and started again (PG4), a stopped (PG3) or cleared (PG1) program, or a Daemon restart (PG5) whose owner has gone, when a process left from the earlier start sends `agent.spawn` with `settings` and claims the program's name or none, then it is ST4's: the Ext it claims is `FORBIDDEN`, and one that claims none is the User exactly as `action_actor` decides today (ST3, policy). A caller below the new start's Terminal is accepted at once; the old start's pid and descendants are not. Given any ST4 refusal, then `rail.tree`, the Project's data and the Daemon's log hold no `settings` value, and a second identical call from the program afterwards starts the Agent as ST1 says (the refusal left no state behind). Tests (`st6_`, `crates/rupd/tests/`): `st6_a_process_left_from_an_earlier_start_is_refused`, `st6_a_restarted_program_is_accepted_at_once`, `st6_a_refusal_leaves_no_trace`.

## Gates

P8: Model and Effort keep A36's rules: an explicit choice is roundup's value and wins over a `settings` key of the same name, and `settings` sets neither otherwise (it is `settings`' own key then, as ST1 says). P9: settings change only at a launch (ST2); a refusal starts nothing (ST4). P11: a refusal says why, naming `settings`. The owner's decisions above hold; a design check never overrides them. Policy: the program's credential is its place in the process tree, which the scenario's ST3 states with what it cannot stop; the specifier's reading that the merge follows Claude Code's own joining of settings sources, and that the user's App-wide mode loses to nothing but a later explicit field, is stated in ST1 and ST5.
