# UI: dragging files to a target (U348)

Module: `apps/desktop` (the webview). Ids: U348, U415 (retired by U467), U420.

**U348 dragging files shows drop targets, a held drag opens one, a drop lands in it.** Found by the user's report #815: a File drop works only on the pane under the pointer, shows no target, and cannot reach an Agent, Workstream or Project that is not open; the user's model is Solo's. Narrows U162, U199 and U179; changes no contract, no Daemon method, no App seam command and no Token. The App seam's `onFileDrop` (U162) already reports `over`, `drop` and `leave` with `x` and `y`, so the position of a drag comes from it and no DOM `dragover` is read. Given the App with a Rail of Agents and Workstreams and two or more Project tabs (U179), then:

- **Targets appear.** On the first `over`, every Rail row of an Agent or a Workstream, every Project tab and the selected Terminal pane show a drop target: a 2 px `--accent` ring inside the element's edge, read from `--accent` (as U162's ring), and the row or tab under `x`,`y` also takes `--hover`'s background over `--ground` (as U112). `leave`, a `drop` or an `over` outside the window's webview clears every target in the same frame. Nothing animates (D6). Asserted in `u348_over_marks_every_target_and_leave_clears_them`.
- **Hold opens.** `over` positions inside one Rail row or one Project tab for 600 ms without leaving it select that row (U31's selection, as a click does) or switch to that tab (U179, as a click does); a move to another target restarts the 600 ms, and `leave` or a `drop` cancels it. The 600 ms is policy chosen by this spec: above a pass over a row at drag speed and below a wait the user reads as stuck. The held row stays selected after `leave`; hold opens, it never closes (the user closes with U64's own ways). Asserted in `u348_holding_over_a_row_selects_it_after_600_ms`, `u348_holding_over_a_tab_switches_to_it`, `u348_moving_to_another_row_restarts_the_hold` and `u348_leave_cancels_the_hold`, with fake timers.
- **A drop lands in the target under the pointer.** The target is the element under `x`,`y` at the `drop`, whether or not it was held open:
  - an Agent's Rail row or its open Terminal pane: the row is selected (U31) and its pane takes U162's paste of the paths, once, so `terminal.write` receives them exactly as U162 and U175 say. An Agent whose Terminal is exited (U25) takes nothing, shows no ring and the row is only selected. Asserted in `u348_a_drop_on_an_agent_row_pastes_into_its_pane` and `u348_a_drop_on_an_exited_agent_pastes_nothing`;
  - a Workstream's Rail row: the Workstream is selected (U467) and its Door's pane takes U162's paste of the paths, once; there is no Attachment (U467 removed the Thread's composer). Asserted in `u348_a_drop_on_a_workstream_row_pastes_into_its_door`;
  - a Project tab: **the drop opens the tab and delivers nothing.** A Project is not a place files can go: it has no Terminal until a row is chosen, and guessing one (its Door, or the last selected row) would send paths to an Agent the user did not point at. The tab switches as a hold does, every target clears and no `terminal.write` or Attachment results; the user drags again to a row now in view. Asserted in `u348_a_drop_on_a_project_tab_opens_it_and_delivers_nothing`;
  - any other place (the Shelf, a Drawer, the header outside the tabs): nothing, as U162 says, and the targets clear. Asserted in `u348_a_drop_elsewhere_does_nothing`.
- **U162 holds.** A drop on the selected Terminal pane pastes the quoted paths exactly once, not twice, though the pane is now also a target; U162's ring, and U174's same-task hand-off pass unchanged, and a `drop` with no paths shows no target and calls nothing. Asserted by the `u162_` and `u174_` tests passing unchanged, and `u348_a_drop_on_the_pane_pastes_once`.
- **Densest seed.** With 40 Rail rows and 8 Project tabs (the strip scrolled, U184), the row or tab under the pointer is found by its rectangle at `x`,`y` and a tab scrolled out of view is no target. Asserted in `u348_targets_are_found_by_rectangle_on_the_densest_seed`.

Observer: `u348_` Vitest cases in `apps/desktop/src/` against the fake App, whose `onFileDrop` the test drives with fake timers; `agent-browser` in the U26 harness captures the targets during `over` at 1280 by 800 to `artifacts/ux/U348/`. WKWebView's native drag is the one thing the harness cannot show, so the PR that implements this asks the user for a `macOS:` line with a real file dragged over a Rail row, held, and dropped.

**U415 retired by U467.** The Thread's composer is gone, so no drop lands on it and no Thread failure line says `Couldn't place the drop`; a drop on a Terminal pane is U162's.

**U420 a file dropped on a target lands in that target.** Found by the user's report #815 ("if they dropped we drop it into that target they selected like solo", for "an image or any file") and #1129: U348 narrows it twice and the user chose neither limit. Replaces U348's Project tab clause ("the drop opens the tab and delivers nothing") and its non-image refusal on a Workstream; U467 removed the Thread's composer and its Attachments, so a drop on a Workstream is a paste of its paths into the Door's Terminal; changes no contract, no Daemon method and no Token. Given the App with a Rail, two or more Project tabs (U179) and a drop whose `paths` are not empty, then:

- **A Project tab delivers to what the tab shows selected.** The tab opens as U348's drop does, then the drop lands in the row that tab has selected, by the clauses below, as if the drop had been on that row. A Project with no selected row, or whose selected row takes nothing (an exited Agent, U25), opens the tab and delivers nothing, and the targets clear; no failure line shows. No row is chosen for the user (no Door, no last-used guess). Asserted in `u420_a_drop_on_a_project_tab_lands_in_its_selected_agent`, `u420_a_drop_on_a_project_tab_lands_in_its_selected_workstream` and `u420_a_drop_on_a_project_tab_with_no_selection_delivers_nothing`.
- **A Workstream takes any file.** A drop on a Workstream's Rail row selects it and pastes the quoted path of each file, an image or not, into its Door's Terminal as U162 does, and no `<name> is not an image` line shows. A path that is a directory is a path like a file (U162). Asserted in `u420_a_non_image_dropped_on_a_workstream_pastes` and `u420_a_directory_dropped_on_a_workstream_pastes`.
- **Kept.** An Agent's row or pane pastes the quoted paths once (U162, `u348_a_drop_on_the_pane_pastes_once`), the Shelf, a Drawer and the header outside the tabs still deliver nothing (`u348_a_drop_elsewhere_does_nothing`). U348's tests that asserted the replaced clauses change to the clauses above; every other `u162_` and `u348_` test passes unchanged.

Observer: `u420_` Vitest cases in `apps/desktop/src/` against the fake App's `onFileDrop`; `agent-browser` in the U26 harness captures the paste of a non-image at 1280 by 800 to `artifacts/ux/U420/`. WKWebView's native drag is the one thing the harness cannot show, so the PR that implements this asks the user for a `macOS:` line with a real file dragged onto a Project tab and onto a Workstream's row.
