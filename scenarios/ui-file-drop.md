# UI: dragging files to a target (U348)

Module: `apps/desktop` (the webview). Ids: U348, U415, U420.

**U348 dragging files shows drop targets, a held drag opens one, a drop lands in it.** Found by the user's report #815: a File drop works only on the pane under the pointer, shows no target, and cannot reach an Agent, Workstream or Project that is not open; the user's model is Solo's. Narrows U162, U199 and U179; changes no contract, no Daemon method, no App seam command and no Token. The App seam's `onFileDrop` (U162) already reports `over`, `drop` and `leave` with `x` and `y`, so the position of a drag comes from it and no DOM `dragover` is read. Given the App with a Rail of Agents and Workstreams (U145) and two or more Project tabs (U179), then:

- **Targets appear.** On the first `over`, every Rail row of an Agent or a Workstream, every Project tab and the selected Terminal pane or the Thread's composer show a drop target: a 2 px `--accent` ring inside the element's edge, read from `--accent` (as U162's ring), and the row or tab under `x`,`y` also takes `--hover`'s background over `--ground` (as U112). `leave`, a `drop` or an `over` outside the window's webview clears every target in the same frame. Targets move no row, tab or pane and change no size (U5, U46); nothing animates (D6). Asserted in `u348_over_shows_every_target_and_leave_clears_them` and `u348_targets_move_no_rectangle`.
- **Hold opens.** `over` positions inside one Rail row or one Project tab for 600 ms without leaving it select that row (U31's selection, as a click does) or switch to that tab (U179, as a click does); a move to another target restarts the 600 ms, and `leave` or a `drop` cancels it. The 600 ms is policy chosen by this spec: above a pass over a row at drag speed and below a wait the user reads as stuck. The held row stays selected after `leave`; hold opens, it never closes (the user closes with U64's own ways). Asserted in `u348_holding_over_a_row_selects_it_after_600_ms`, `u348_holding_over_a_tab_switches_to_it`, `u348_moving_to_another_row_restarts_the_hold` and `u348_leave_cancels_the_hold`, with fake timers.
- **A drop lands in the target under the pointer.** The target is the element under `x`,`y` at the `drop`, whether or not it was held open:
  - an Agent's Rail row or its open Terminal pane: the row is selected (U31) and its pane takes U162's paste of the paths, once, so `terminal.write` receives them exactly as U162 and U175 say. An Agent whose Terminal is exited (U25) takes nothing, shows no ring and the row is only selected. Asserted in `u348_a_drop_on_an_agent_row_pastes_into_its_pane` and `u348_a_drop_on_an_exited_agent_pastes_nothing`;
  - a Workstream's Rail row or the Thread's composer: the Workstream is selected (U145) and U199's image drop applies, one Attachment per image path and U80's `<name> is not an image` line for another kind; a drop on the row of a Workstream that is not selected selects it first and puts the Attachments in its composer. Asserted in `u348_a_drop_on_a_workstream_row_attaches_images` and `u348_a_drop_on_a_workstream_row_refuses_a_non_image`;
  - a Project tab: **the drop opens the tab and delivers nothing.** A Project is not a place files can go: it has no Terminal and no composer until a row is chosen, and guessing one (its Door, or the last selected row) would send paths to an Agent the user did not point at. The tab switches as a hold does, every target clears and no `terminal.write` or Attachment results; the user drags again to a row now in view. Asserted in `u348_a_drop_on_a_project_tab_opens_it_and_delivers_nothing`;
  - any other place (the Shelf, a Drawer, the header outside the tabs): nothing, as U162 says, and the targets clear. Asserted in `u348_a_drop_elsewhere_does_nothing`.
- **U162 holds.** A drop on the selected Terminal pane pastes the quoted paths exactly once, not twice, though the pane is now also a target; U162's ring, U174's same-task hand-off and U199's composer drop pass unchanged, and a `drop` with no paths shows no target and calls nothing. Asserted by the `u162_`, `u174_` and `u199_` tests passing unchanged, and `u348_a_drop_on_the_pane_pastes_once`.
- **Densest seed.** With 40 Rail rows and 8 Project tabs (the strip scrolled, U184), the row or tab under the pointer is found by its rectangle at `x`,`y` and a tab scrolled out of view is no target. Asserted in `u348_targets_are_found_by_rectangle_on_the_densest_seed`.

Observer: `u348_` Vitest cases in `apps/desktop/src/` against the fake App, whose `onFileDrop` the test drives with fake timers; `agent-browser` in the U26 harness captures the targets during `over` at 1280 by 800 and 700 by 800 to `artifacts/ux/U348/`. WKWebView's native drag is the one thing the harness cannot show, so the PR that implements this asks the user for a `macOS:` line with a real file dragged over a Rail row, held, and dropped.

**U415 an image dropped on the Thread's composer becomes an Attachment, and a drop the App cannot place says so.** Found by the user's report #1113: an image dragged from Finder onto the composer left no chip and no failure line. Narrows U199's Image drop and U348's drop on the composer; changes no contract, no Daemon method and no Token; a new App seam command, if the cause needs one, follows the Contract recipe (rule 4). On `main` U199's listener (`apps/desktop/src/thread/Thread.tsx`, the `onFileDrop` call) returns without a word when the drop's point falls outside the composer's rectangle, and the point is Tauri's `onDragDropEvent` position divided by `devicePixelRatio` (`apps/desktop/src/app/tauri.ts`, `tauriFileDrop`) then U348's router; only the fake App's `dropFiles` has driven that path. Given a selected Workstream (U145) in Thread mode with the composer in view, then:

- **Cause.** The build run first reads, in the real App or the nearest observer of Tauri's webview (a `tauri dev` window on a Mac, else Tauri's own source and docs for the platform), the point reported for a drop at the composer's centre against `getBoundingClientRect()` of the composer, and names the cause (scale, origin, an inset, or the listener) in the PR. Policy: the cause is an engineering finding, not a scenario clause.
- **Placed.** A native drop of an image path at any point inside the composer's rectangle, with the point in the shape and scale the real App reports (physical pixels, the pixel ratios 1, 2 and 3, and the origin the cause names), adds one Attachment (U109) named by its last path segment. Asserted in `u415_a_real_scale_drop_on_the_composer_attaches_the_image` (one case per ratio, through `tauriFileDrop` and U348's router, not `dropFiles` alone).
- **Not placed.** A drop whose paths are not empty and whose point lies on neither a Rail row, a Project tab, the selected Terminal pane nor the composer, while a Workstream's Thread is selected, shows `couldn't place the drop` in the Thread's failure line (U80) and adds no Attachment; the line clears as U80's lines do. A drop that lands on the Shelf or a Drawer (U348) keeps doing nothing and shows no line. Asserted in `u415_an_unplaced_drop_says_so_in_the_failure_line` and `u415_a_drop_on_the_shelf_shows_no_line`.
- **Kept.** U199's `u199_` tests, U348's `u348_` tests and U162's `u162_` tests pass unchanged; a drop on an Agent's Terminal pane pastes once (`u348_a_drop_on_the_pane_pastes_once`), and a drop on a Rail row or a Project tab opens it.

Observer: `u415_` Vitest cases in `apps/desktop/src/thread/` and `apps/desktop/src/app/` against `tauriFileDrop` fed Tauri's payload shape at ratios 1, 2 and 3 and U348's router over the real Thread; `agent-browser` in the U26 harness at 1280 by 800 and 700 by 800 captures the chip and the failure line to `artifacts/ux/U415/`. WKWebView's native drag is the one thing the harness cannot show, so the PR that implements this asks the user for a `macOS:` line with a real image dragged from Finder onto the composer.

**U420 a file dropped on a target lands in that target.** Found by the user's report #815 ("if they dropped we drop it into that target they selected like solo", for "an image or any file") and #1129: U348 narrows it twice and the user chose neither limit. Replaces U348's Project tab clause ("the drop opens the tab and delivers nothing") and its non-image refusal on a Workstream (`u348_a_drop_on_a_workstream_row_refuses_a_non_image`); narrows U109, whose "a file that is not an image (refused with U80's one line)" no longer holds for a dropped file, U199's drop refusal and U145's Errors clause, whose list of U80's lines loses "U109's refusal of a dropped file that is not an image" (a pasted non-image is not a drop and U109 keeps refusing it); changes no contract, no Daemon method and no Token. Whether an Attachment (U109) may hold a non-image path is an engineering question the implementing run settles on the Issue by reading U419's path hand-off (`scenarios/ui-image-send.md`, merged in #1132); the clauses below hold either way. Given the App with a Rail, two or more Project tabs (U179) and a drop whose `paths` are not empty, then:

- **A Project tab delivers to what the tab shows selected.** The tab opens as U348's drop does, then the drop lands in the row that tab has selected, by the clauses below, as if the drop had been on that row. A Project with no selected row, or whose selected row takes nothing (an exited Agent, U25), opens the tab and delivers nothing, and the targets clear; the failure line of U415 does not show for it. No row is chosen for the user (no Door, no last-used guess). Asserted in `u420_a_drop_on_a_project_tab_lands_in_its_selected_agent`, `u420_a_drop_on_a_project_tab_lands_in_its_selected_workstream` and `u420_a_drop_on_a_project_tab_with_no_selection_delivers_nothing`.
- **A Workstream takes any file.** A drop on a Workstream's Rail row or its composer adds one Attachment per path, an image or not, named by its last path segment, and U80's `<name> is not an image` line no longer shows for a drop. A path that is a directory is a path like a file (U162). Asserted in `u420_a_non_image_dropped_on_a_workstream_attaches` and `u420_a_directory_dropped_on_a_workstream_attaches`.
- **Kept.** An Agent's row or pane pastes the quoted paths once (U162, `u348_a_drop_on_the_pane_pastes_once`), the Shelf, a Drawer and the header outside the tabs still do nothing (`u348_a_drop_elsewhere_does_nothing`), and U415's `couldn't place the drop` line and its Shelf exception hold. U348's tests that asserted the replaced clauses change to the clauses above, and so do `u199_a_native_drop_of_a_text_file_is_refused` and `u109_a_file_that_is_not_an_image_is_refused_with_one_failure_line`, which dropped `notes.txt` on the composer and now see one Attachment named `notes.txt` and no line; every other `u162_`, `u199_`, `u348_` and `u415_` test passes unchanged.

Observer: `u420_` Vitest cases in `apps/desktop/src/` against the fake App's `onFileDrop`; `agent-browser` in the U26 harness captures the Attachment of a non-image at 1280 by 800 and 700 by 800 to `artifacts/ux/U420/`. WKWebView's native drag is the one thing the harness cannot show, so the PR that implements this asks the user for a `macOS:` line with a real file dragged onto a Project tab and onto a Workstream's row.
