# UI: ⇧⌘⌫ removes the selected Rail item from anywhere

Module: `apps/desktop` (the webview). Ids: U6171a, U6171b, U6171c. Acceptance for [#6171](https://github.com/roundup-app/roundup/issues/6171). Journey: Intervene and Review. Changes no contract, RPC method, App seam command or Token.

Opening a Rail item moves focus to its Terminal, where U358's row-only `⌘⌫` never ran and U2242 sends `⌘⌫` as `\x15`. The owner chose `⇧⌘⌫` (2026-11-04), which no Terminal or text field uses. `⇧⌘⌫` was U165's chord and is free (`scenarios/ui-shortcuts.md`, retired table).

**U6171a ⇧⌘⌫ removes the selected Rail item wherever focus is.** Amends U358 and U5690d: their chord is `⇧⌘⌫`, not `⌘⌫`. Given an open Project with one or more Rail items selected and no dialog open, when the user presses `⇧⌘⌫` with focus on a Rail row, in the selected item's Terminal, or elsewhere in the App window, then the selection is removed by the path of the row menu's Remove (A16): one `rail.remove {id}` per selected item (one question for a set, U5690d), the same confirmation when the menu's `needsConfirmation` holds, and the same Undo. With no item selected, or while a dialog is open, the chord does nothing and calls nothing. A key repeat calls nothing more (U32). When focus was in a Terminal and the removal leaves it, the key reaches that Terminal's program as no bytes. Tests (`u6171a_`), in `apps/desktop/src/rail/u6171_remove_chord.test.tsx` against the fake App on `tree-40`: `u6171a_remove_chord_removes_the_selected_item_from_a_focused_terminal` (an item selected, its Terminal focused: `rail.remove` is called once for that item and `terminal.write` receives nothing), `u6171a_remove_chord_runs_from_a_row_and_from_elsewhere`, `u6171a_remove_chord_with_nothing_selected_or_a_dialog_open_calls_nothing`, and U5690d's and U358's tests edited to press `⇧⌘⌫` (their assertions otherwise unchanged).

**U6171b ⌘⌫ removes nothing and keeps its Terminal meaning.** Narrows U358: `⌘⌫` binds no roundup action. Given a Rail row focused or a Terminal focused, when the user presses `⌘⌫`, then `rail.remove` is not called and no roundup listener handles it; in a Terminal `terminal.write` receives `\x15` exactly once, as U2242 says. Test: `u6171b_cmd_backspace_removes_nothing_and_reaches_the_terminal_as_ctrl_u`, with `u358_other_modifier_sets_remove_nothing` edited so `⌘⌫` joins the set and `⇧⌘⌫` leaves it. The Rail row, its menu's Remove, Help (U54), the Quick jump list (`ui-quick-jump.md`) and every key chip show `⇧⌘⌫` for Remove, from the one `rail.remove` row of `CHORDS` (`apps/desktop/src/keys/chords.ts`); `u54_help` and the menu-accelerator drift tests cover it. No other Rail chord changes key.

**U6171c no App chord takes a Terminal editing key.** Narrows U2241: its kept-chord list gains `⇧⌘⌫` (`meta+shift+Backspace`) and nothing else; the sweep `u2241_no_other_chord_is_taken_at_app_scope` and `u2241_help_lists_exactly_the_kept_keys` are edited for that one press. Audit: every `CHORDS` row that binds while a Terminal has focus (rows without `inRail`, `inShelf`, `inEditor` or `inTriage`, plus the scoped `inTerminals` rows) has no press equal to a U2242 editing press: `meta+Backspace`, `meta+ArrowLeft`, `meta+ArrowRight`, `alt+Backspace`, `alt+ArrowLeft`, `alt+ArrowRight`. The build run records the audit of the rows in the PR. Test: `u6171c_no_terminal_scoped_chord_equals_a_terminal_editing_press`, in `apps/desktop/src/keys/u2241_nothing_else.test.tsx`, reading `CHORDS` only (no mount). Cheap CI guard; no process starts.
