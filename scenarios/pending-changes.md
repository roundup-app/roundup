# Pending changes

Module: `apps/desktop/src/app/` (the one helper), with its callers in `rail/`, `todos/` and `pads/`, and `crates/desktop` (the unchanged timeout). Ids: U5172a, U5172b. Acceptance for Issue #5172, found by the owner's report: "when I try to rename a workstream it doesn't succeed it fails and takes too long and it reverts than happens later!" This specification delivers no runtime behavior. It narrows U3791b (`scenarios/failure-handling.md`): `outcomeOf` already maps a timeout to `unknown`, but `apps/desktop/src/rail/RailRow.tsx` (`NameField`) still shows a failure and restores the old name. No contract, RPC method or native change is needed; `crates/desktop/src/state.rs`, `AppState::bounded` keeps failing a late call with INTERNAL. Refs #5159, whose Checkpoint writes made the Daemon slow.

**Pending change.** What the user asked for, shown in place of the old value and marked as still applying, from an `unknown` outcome until an event of the Daemon confirms or contradicts it, or a re-read of the Rail, Todos or Pads settles it.

**U5172a an unknown outcome keeps the asked value until the Daemon says.** Given a Rail row, Todo or Pad whose change (`rail.rename`, `rail.remove`, `rail.move`, a mode change, a Todo edit or a Pad rename) gets an `unknown` outcome (`outcomeOf`, U3791b), then:

- The row shows the asked value throughout, marked as applying, with no failure line, toast, attention or restored old value. A `failed` outcome (a known refusal) still restores the old value and shows why, once. Assert in planned `u5172a_unknown_rename_shows_the_asked_name_throughout` (a fake seam whose `rail.rename` rejects with INTERNAL, then emits `rail.renamed`: the name read at every step is the new one, and no failure role exists) and `u5172a_refused_rename_restores_and_shows_why` in `apps/desktop/src/rail/`.
- The Daemon's event that confirms the change (`rail.renamed` for the id) clears the mark and keeps the value. An event or re-read that contradicts it (the row holds another value) shows that value and one failure line saying the change did not apply; it never leaves the asked value in place. A change replaced by a newer one for the same item keeps only the newer mark. Assert in planned `u5172a_confirming_event_clears_the_mark` and `u5172a_contradicting_read_shows_the_daemon_value`.
- One shared helper in `apps/desktop/src/app/` runs a call, classifies the throw with `outcomeOf` and reports `applied`, `refused` or `pending`; every App call that changes Daemon state uses it, with no per-call classification. Audit every `app.rpc` caller of a mutating method (`rail.rename`, `rail.remove`, `rail.move`, the mode change, `todo.*` and `pad.*` writes) under `apps/desktop/src/`, not a fixed count. Calls with their own reconciliation keep it and call the helper for the classification (U3791b). Assert in planned `u5172a_every_mutation_goes_through_the_helper`, a source audit, and `u5172a_helper_maps_outcomes` covering a reply, a refusal code, INTERNAL, a timeout and a foreign throw.
- Policy: a pending change is a draft-like holder; it survives Rail re-render, never replays the call, and is dropped with its Project. Principles P11 gate: can the pending value be lost or shown as a success the Daemon did not confirm? Observer: the marked value is distinguishable from a confirmed one by role or attribute, never by prose or colour alone.

**U5172b a late application does not flip the screen.** Given a change with an `unknown` outcome that the Daemon then applies, when its event arrives after the App's bound, then the row never showed the old value after the asked one: the sequence read is old, asked (pending), asked (confirmed). Assert in planned `u5172b_late_event_does_not_flip_the_name` with fake time past the bound, in `apps/desktop/src/rail/`, and `u5172b_pending_remove_keeps_the_row_marked` for a removal, where the row stays, marked, until `rail.removed` or a re-read.
