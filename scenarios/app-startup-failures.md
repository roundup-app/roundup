# App startup failures

Acceptance for #5810; module: `crates/desktop`. Journey stage: Enter. This extends S1/S10 and U3787f's diagnostics without changing which local data N5467b refuses. It specifies reporting, not data repair, automatic deletion, migration or a new RPC/App seam command.

**S5810a a refused startup Project explains itself.** Given an isolated App profile and a Project whose rupd refuses to open with `Local data is incompatible with this build.`, when the App starts with that Project as its argument, then the user receives that refusal text and the Project's name in the App, or on stderr if no window opens. An exit code, RPC code or log file alone does not satisfy this clause. Before a fatal exit, the report reaches stderr or a native message whose dismissal precedes exit. The production `shell.log` entry contains the same refusal text, Project name and opening operation; a numeric code may accompany, never replace, the cause. Assert planned `s5810a_startup_refusal_reaches_user_and_log` through production startup with a real rupd refusal fixture and isolated data/log directories, observing the actual user-report destination and flushed log. An assertion on a formatter or returned `RpcError` alone is insufficient.

Parameterize the Project identity in that observer: a stored custom name different from the folder name, and no custom name (folder name). Both destinations identify the Project by that name, without adding its absolute path as its identifier; seed a distinct parent-path sentinel and assert its absence from the identifier. Existing rupd recovery instructions may name the data folder to repair; do not remove that instruction or confuse it with the Project's display name. Policy: reuse S10's name source even when the Daemon cannot open; do not ask the refusing Daemon for its name.

**S5810b saved Project refusals remain visible after restore.** Given three saved existing Project directories in saved order, with distinct names, when the middle Project is refused with S5810a's message during App startup, then the App reports that name and refusal to the user and logs the opening operation, name and refusal. The report remains available after the webview subscribes; an event emitted before its listener exists is not an observation. The failed Project remains listed with `running: false`, and the other two open in order; restore does not exit merely because one Project was refused. With every saved Project refused, each name and cause is reported and the App still launches. Assert planned `s5810b_restore_reports_each_refusal_without_losing_projects`, covering both mixtures through the production restore path and its user-report destination, and reading the production log. Reuse the S10 fixture/observer rather than duplicate its unrelated rename and vanished-directory proofs. Policy: S10's vanished-directory dropping and Reopen behavior remain unchanged.

**S5810c every fatal startup stage has a safe report.** Given a failure at each stage in the inventory below, when startup reaches that stage, then the user receives its operation and cause before termination, in the App if available or stderr when no window opens. Existing IO kinds, JSON categories/positions and typed Tauri causes are sufficient for foreign failures; an unexplained exit, only a numeric code, or only a file log is not. Where the log sink is installed, it records the operation and cause too. Assert planned `s5810c_fatal_startup_stages_report_before_exit`, a table of stage fixtures at the production startup boundary capturing the destination and exit ordering. Exercise pre-log failures without requiring a log that cannot yet exist; exercise initialized logging with the real sink. Policy: do not Debug/Display an arbitrary boxed, Tauri or plugin error to obtain richer text.

**S5810d reporting preserves the foreign-error boundary.** Given a foreign plugin initialization error containing credential, draft, Terminal and Project-path sentinels, plus a third-party log record containing those sentinels, when startup fails, then user feedback and stderr contain the safe operation/typed cause, and neither they nor `shell.log` contain those foreign sentinels or P14's prohibited usage fields. The App still reports failure, rather than pretending startup succeeded. Assert planned `s5810d_foreign_startup_errors_are_redacted` at the production startup/reporting boundary, extending U3787f's real log-sink fixture to observe user feedback and stderr as well. Policy: preserve the shell-target filter and existing private-content exclusions. S5810a authorizes rupd's own refusal message; it does not authorize dumping arbitrary plugin errors, all logs, raw RPC data or unrelated Terminal output.

## Startup reporting inventory

Policy: the implementation PR accounts for every row, naming the final reporting call/destination and its observer. This is an inventory of the existing paths on `origin/main`, not a requirement for new parallel error holders. Follow startup callees and add a row if another code-only failure is found; record engineering progress and failures on #5810, never in a scenario Work table.

| Existing path | Required report / observer |
|---|---|
| `main.rs`, `main`: `run` returns an error and the binary returns failure without text | Safe operation/cause to stderr when no window opens; retain the foreign-error exclusion. S5810c/d. |
| `lib.rs`, `run`: optional idle-perf guard, `Config::from_env`, `Config::context`, absolute startup-argument resolution, before `diagnostics::startup` | Each failure gets a safe stage/cause on stderr even before the sink exists; no arbitrary boxed-error print. S5810c. |
| `diagnostics.rs`, `startup`/`failure`: Tauri build/setup/plugin/runtime errors logged only to the shell sink | Keep typed redaction, additionally reach the user or stderr; do not require the log plugin to have initialized. S5810c/d. |
| `lib.rs`, `build` setup: `use_data_dir` / App data-folder resolution (`refuse Project preferences`) | App-owned cause and existing recovery guidance reach the user; log a safe cause rather than only RPC code. S5810c; preserve N5467b. |
| `lib.rs`, `build` setup: `state.restore` returns an error (`restore Project preferences`) | Report the App-owned preferences/restore cause before exit; no invented Project name when preferences could not be read. S5810c. |
| `lib.rs`, `build` setup: explicit `state.open_project` (`open startup Project`) | Project name and rupd cause in feedback and log before any fatal exit. S5810a. |
| `projects.rs`, `AppState::restore`: each failed saved `open` (`restore Project`) | Project name and rupd cause in feedback and log, retaining the failed entry and continuing restore. S5810b. |
| `daemon.rs`, `start`/`connect_after_bound`: spawn, bound-notification, connect/ping, readiness timeout or child exit produces the Project-opening error | Preserve the specific launch/readiness/refusal cause through the owning startup/restore report; existing IO-kind warnings remain safe. No replacement with only `INTERNAL` or an exit status. S5810a/b, plus S5810c's missing-executable fixture. |

Policy: inventory adjacent startup warnings (`daemon.rs` socket removal, refused-child stop, stderr-read and child-wait failures; `store.rs` reads/writes) as retained typed diagnostics, distinguishing them from fatal/open failures. Do not turn recoverable cleanup or S10's in-memory write retention into a new fatal exit. Do not start a Model turn or Agent to diagnose startup.
