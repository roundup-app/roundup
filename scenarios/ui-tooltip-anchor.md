**U2749a the Project root Kind owns its tooltip.** Given the U26 harness with `tree-40` at Project root and a Workstream whose Door has a Kind, when the pointer rests on that entry's Kind glyph, then one shared Tooltip opens, its text is the Kind label and its anchor box contains the pointer. The glyph's element carries the trigger; the full-width overview entry button does not own the Kind tooltip. Moving onto another control shows that control's own tip, not the Kind label. Test: `u2749a_project_root_kind_owns_its_tooltip`, through the mounted overview with the fake App, asserting the opened tooltip's text and anchor containment using controlled element rectangles and pointer events. Do not assert position, size or gap. Preserve U2567a's accessible name and U2567c's selection behavior; the state gains no button role or tab stop (policy).

**U2749b every tooltip uses one anchor rule.** Given a tooltip triggered by a pointer, when it opens, then `ui/Tooltip.tsx` anchors it to the box of the smallest element carrying that tooltip's trigger under the pointer, rather than an enclosing layout container (policy: inspect trigger ownership and the rendered observer below). Descendant SVG paths and decorative children do not become separate owners. The Rail row has no Tooltip (U2228c); `ui/Tooltip` has no explicit anchor option. Keyboard focus opens against the owning trigger without requiring pointer coordinates. Tests: `u2749b_focus_opens_without_a_pointer` (focus opens a shared Tooltip). Existing U521, U501 and U2228a behavior remains (policy).

Given a pointer-opened tooltip whose chosen anchor box excludes the opening pointer, when opening is attempted under `import.meta.env.DEV` or Vitest, then the Tooltip throws. Keyboard-only opening does not run this pointer assertion. Test: `u2749b_pointer_outside_anchor_throws`, exercising the actual Tooltip open path with controlled rectangles and pointer coordinates, in each environment branch. This contract checks ownership, not tooltip geometry; no production throw is required (policy).

**U2749c callers cannot bypass the shared Tooltip.** Given App tooltip callers, when migrated, then there is one `Tip` wrapper, backed by `ui/Tooltip.tsx`; `rail/Tip.tsx` and `ink/Tip.tsx` no longer define competing wrappers. Outside `apps/desktop/src/ui/` and the single selected wrapper file, no caller imports `@ark-ui/solid/tooltip` or renders `Tooltip.Root`. **U2749e a tooltip takes no press.** Given any App tooltip open over another control, when the pointer presses inside the tooltip's box, then the press reaches the element beneath: `document.elementFromPoint` there never names the tooltip's Positioner or Content, and the control beneath gets the press once. The fix goes through `ui/Tooltip.tsx` and the library's props or parts; it changes no anchor rule (U2749b, U6236a), delay or placement, and uses no `!important`, synthetic event or DOM clone (policy). Test: `u2749e_a_press_under_a_tooltip_reaches_the_control_beneath`, a real headless Chromium test on the `_browser.test` lane: open an `IconButton`'s tooltip over another control, press inside the overlap, and assert the hit target and one press on the control beneath. It asserts no position or size.

**U6236a a Tooltip anchors to the live element of its trigger.** Given a Tooltip whose trigger's element is replaced (a `Tip` child that re-renders) while the Tooltip waits to open or is open, then the Tooltip anchors to the replacement's box. Given the trigger leaves the document with no replacement, then the Tooltip closes. Test: `u6236a_replaced_trigger_keeps_the_tooltip_on_its_trigger`, through a mounted `Tip` whose child a signal swaps, with `getBoundingClientRect` mocked as a browser gives it (live nodes at a box, detached nodes at zero); it asserts the anchor box the Tooltip positions against and its open state, never the surface's position, size or gap. U2749a-d hold: the anchor contains the opening pointer and `u2749b_pointer_outside_anchor_throws` still throws.

**U6236b pickers and menus follow their anchor row.** Given the Todo home picker, the Todo owner picker, the Rail move picker, the Rail create menu or the Pad block handle open on an anchor, when a Todo update, Agent update or block re-render replaces the anchor's element, then the surface anchors to the replacement for the same Todo, Agent or block. Given that row is gone, then the surface closes and returns focus as it does today. Test: `u6236b_replaced_row_keeps_the_picker_on_its_row`, the owner picker open on a Todo while an update replaces the row's button, then the row's removal; it asserts anchor boxes and open state only. The other four surfaces share the one helper of U6236c and the same replacement lookup (policy).

**U6236c one helper reads every anchor box.** Given a floating surface's `getAnchorRect` or `getPosition`, then it reads the box through one helper in `apps/desktop/src/ui/`, which returns no box for an element outside the document or one whose `checkVisibility()` is false, so Ark falls back to the trigger it finds by id. A lint rule in `.oxlintrc.json`, implemented under `tools/oxlint/` as U2749c's is, rejects a `getAnchorRect` or `getPosition` that calls `getBoundingClientRect` outside that helper. Test: `u6236c_lint_rejects_raw_anchor_boxes`, running the configured linter on fixtures: a raw `getBoundingClientRect` in `getAnchorRect` exits nonzero, the helper's use exits zero. Do not test the configuration's text in place of running the linter. No surface stays open but hidden: `positioning.hideWhenDetached` alone leaves a Tooltip open, so it fails U6236a's close (policy).

Reuse direction (policy): Ark keeps positioning; no custom positioning engine. The implementation PR's Reuse section weighs Ark's `hideWhenDetached` and `@floating-ui/dom`'s `hide` middleware against the helper.

**U6640a a Rail row shows its status in the row.** Amends U5231a and U2228c's exception: a Rail row of Status Kind `blocked`, `needs-you`, `working` or `error` with a non-empty `Status.label` shows that label and its age (U5231b's text and ticking, joined by ` · `) in the row beside its name, and its status mark opens no Tooltip on hover, focus or selection. Every Rail row then opens no `role="tooltip"` element, whatever its Kind. Test: `u6640a_a_rail_row_holds_its_status_and_its_mark_has_no_tooltip` (jsdom, connected App, fake clock): each of the four Kinds shows label and age in the row, hover and focus on the mark open no tooltip, and the mark's accessible name still names the Kind. It retires U5231a's tooltip clause and `u5231a_reason_and_age_reveal_on_hover_and_focus`; `u5231b_age_ticks_while_shown` asserts the row's text instead.

**U6640b a long status keeps one line.** Given a row whose label is longer than its place (a `needs-you` question), then the status shows on one line cut with `…`, never wrapping and never growing the row; the full text is in that Agent's Terminal and the row adds no `title` (U2749c).
