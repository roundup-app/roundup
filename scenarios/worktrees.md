# Worktrees

Module: `crates/agents` (`src/worktree.rs`, which runs the `git` command; `git` on `PATH` is the one requirement), with end-to-end tests in `crates/rup/tests`. Terms: Worktree, Base, Landing (`GLOSSARY.md`). Principles served: P2 (`PRINCIPLES.md`), P4 (provisioning is vendor-neutral, in `crates/agents`, never in `claude_code/`) and P5. Design: `docs/worktrees.md`. Tests use a real `git` in a temporary repository, a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4), no network. Errors: no new `rpc::code` constant. Each code below is an existing constant (`INVALID_PARAMS` for `not_a_git_project`, `no_base` and `cwd_not_in_worktree`; `NOT_FOUND` for `no_worktree` and `worktree_missing`; `CONFLICT` for `worktree_unlanded`, `worktree_dirty`, `landing_conflict`, `check_failed`, `check_missing`, `base_moved` and `base_dirty`; `INTERNAL` for `worktree_failed`) whose message starts with the lowercase name, a colon and a space (`no_base: HEAD is detached`); a test asserts the constant and that prefix. Contract change (the committee approves it in its own PR, rule 4): the methods and fields named below are new, and the contract PR changes every caller of `RailNode`. Ids: G1–G9.

**G1 the `worktrees` setting.** Given a Project, when `project.setWorktrees {on, check}` arrives (`on` a boolean, `check` a command line or `null`), then the setting is stored and `project.get` returns it as `{worktrees: {on, check}}`; a Project that never had it set returns `{worktrees: {on: false, check: null}}`. It survives a Daemon restart. With `on: false`, `agent.spawn` behaves exactly as A4 says and the Agent's node has `worktree: null`. A `check` that is the empty string is `INVALID_PARAMS`. `on: true` with `check: null` is allowed, because isolation needs no check, but G4 then refuses to land.

**G2 spawn provisions a Worktree.** Given `worktrees` on and a Project that is a git repository on a branch with at least one commit, when `agent.spawn {cwd, prompt}` arrives (A4), or `rail.startDoor` first starts a Door in the Project folder (A7), then before the Agent starts the Daemon makes the branch `roundup/agent-<id>` at the Project's current commit and a git worktree for it at `<Project folder>/.roundup/worktrees/agent-<id>`, adds `.roundup/` to the repository's `.git/info/exclude` if it is not there, and starts the Agent with that Worktree as its working directory (the same subpath of it when `cwd` was a subfolder of the Project). The node's `worktree` is `{path, branch, base}` where `base` is the branch that was checked out in the Project. It is stored with the node and `rail.tree` returns it. Two Agents spawned back to back, and two Doors started back to back, have different working directories (P2's observer); a first Door start whose Worktree fails leaves the Workstream and its children where they were, and, like a failed spawn, leaves no branch and no worktree directory. A failed call emits no event. A Terminal opened with `terminal.open` (X12) is not given a Worktree. When any step fails, then `agent.spawn` fails with its own error code and nothing is left: no node, no branch, no worktree directory, and `git worktree list` and `git branch` equal what they were before the call. When `cwd` is a subfolder of the Project that does not exist in the fresh Worktree (it is untracked or ignored, which A4 allows), the call fails with `cwd_not_in_worktree` and leaves nothing. The codes are `not_a_git_project` (the folder is not a git work tree, or has no commit), `no_base` (HEAD is detached) and `worktree_failed` (git failed; the message holds git's own text) and `cwd_not_in_worktree`.

**G3 a Worktree's status.** Given an Agent with a Worktree, when `agent.worktreeState {id}` arrives, then it returns `{ahead, behind, dirty}`: `ahead` is the number of commits on the Agent's branch that the Base does not have, `behind` the number on the Base that the branch does not have, and `dirty` is true when the Worktree has any staged, unstaged or untracked change outside `.roundup/`. A fresh Worktree is `{0, 0, false}`. After one commit in it the result is `{1, 0, false}`, after one commit on the Base `{1, 1, false}`, and writing an untracked file makes `dirty` true with the counts unchanged. The call changes nothing: the branch, the Base and the files are the same after it. For an Agent or Terminal with `worktree: null` it fails with `no_worktree`; when the directory is gone from disk it fails with `worktree_missing` naming the path, and the node stays.

**G4 landing.** Given an Agent with a clean Worktree (`dirty` false), when `agent.land {id}` arrives, then the Daemon rebases the Agent's branch onto the Base's current commit, runs the Project's `check` command in the Worktree, and fast-forwards the Base to the branch; it returns `{base: <commit>}` and `agent.worktreeState` then returns `{0, 0, false}`. It never writes the Base any other way, and it never commits for the Agent: before the fast-forward it checks that the Project folder has the Base checked out, and when it has another branch checked out or the Base no longer exists the call fails with `base_moved` and changes nothing. The checks run in this order, so one code wins when several hold: `no_worktree`, `worktree_missing` (G3: the directory is gone; nothing ran), `check_missing`, `worktree_dirty`, `base_moved`, the rebase (`landing_conflict`), the check (`check_failed`), then the fast-forward (`base_dirty`). Each failure leaves the repository as it was before the call, and names its code: `check_missing` (the Project's `check` is `null`; nothing ran, because Landing without a check would break P5's "check green, then fast-forward"; the user sets one with `project.setWorktrees`), `worktree_dirty` (the Worktree has changes; nothing ran), `landing_conflict` (the rebase hit a conflict; the Daemon aborts it, the branch is where it was, and the error's message lists the conflicted paths; it never picks a side), `check_failed` (the check exited non-zero; the message holds its last 20 lines of output; the Base is unchanged and the Daemon resets the branch to the commit it had before the call and restores the Worktree's files; a check that leaves the Worktree dirty is also `check_failed`, with the message `check left changes`), `base_moved` (above), and `base_dirty` (the Project's own checkout has changes and the fast-forward would touch them; nothing changed). An Agent with `worktree: null` fails with `no_worktree`. The tests make a conflict between the Base and the branch, a failing check (`false`), a passing check (`true`) and a dirty Project checkout, and compare `git rev-parse` of both branches and `git status` before and after each failure.

**G5 removal never loses work.** Given an Agent with a Worktree, when `rail.remove {id}` arrives (A16), then if the Worktree is clean and the branch has no commit the Base lacks (`ahead` is 0), the Agent is stopped and removed as A16 says, and its worktree directory and its branch are deleted, so `git worktree list` and `git branch` equal their state before the spawn (P5's observer). If the Worktree is dirty, or the branch is ahead of the Base, then `rail.remove` fails with `worktree_unlanded` before it stops anything: the node, the Agent's status, the directory, the branch and every file are unchanged, and the message says `dirty`, `ahead` or both with the counts. The Daemon checks again after A16's stop, because the Agent may have written or committed until it ended: when the Worktree is then dirty or ahead the call fails with `worktree_unlanded` too, the Agent stays as a stopped node with status `done`, and the directory, the branch and every file are kept. The test has a fake `claude` that writes a file while it is being stopped. `agent.discard {id}` is the deliberate way to drop work: it stops the Agent, deletes the node, the directory and the branch whatever their state, and returns `null`, and for a Workstream it treats the children as A16 does; a Terminal or an Agent with `worktree: null` fails with `no_worktree`. A directory that is already gone from disk is not an error for either call: git's record of it is pruned, and the branch is judged as before: `rail.remove` still refuses with `worktree_unlanded` (`ahead` N) when the branch is ahead of the Base, and otherwise deletes the branch, then removes the node; `agent.discard` deletes both whatever their state. A Workstream removed with `rail.remove` follows A16 for its children and leaves their Worktrees alone; only the removed node's own Worktree is considered.

**G6 the Daemon finds its Worktrees again.** Given Agents with Worktrees, when the Daemon is stopped and started again on the same Project, then `rail.tree` returns each node's `worktree` as before, `agent.worktreeState` answers for each from the directories on disk, and no Worktree, branch or file changes. A Daemon killed between making the branch and starting the Agent must leave nothing a restart cannot clear: the node is stored before `git` runs and is marked unfinished until the Worktree exists and the Agent's Terminal is about to start, and on start a node still unfinished is rolled back: its directory and branch are deleted (they hold no commit of the Agent's), and the node is removed when it was made by `agent.spawn`, or leaves the Workstream with its Door stopped when provisioning was started by `rail.startDoor` (A7), with its children where they were, so `git worktree list` and `git branch` equal their state before the spawn. The test puts a `git` wrapper first on `PATH` that runs the real `git worktree add`, touches a marker file and then blocks (every other `git` command passes through to the real one); it waits for the marker, kills `rupd` with SIGKILL as D6 does, kills the blocked wrapper, starts `rupd` again with the real `PATH`, and compares both lists with their state before the spawn. A worktree that git lists but that no node names (made by the user or another tool) is never reported as an Agent's, never touched by G4 or G5, and never deleted. Each Agent's Worktree is found again by the `worktree_path` stored on its node, never by where the node sits in the Rail: the test starts the Daemon with the same nodes moved under other parents and gets the same results. A node whose directory the user deleted keeps its node and answers `worktree_missing` (G3).

**G7 a Rail move never touches a Worktree.** Given an Agent with a Worktree whose uncommitted edits, an untracked file and one commit are in place, and a running fake `claude` that has the Worktree as its working directory, when the Agent's node is moved with `rail.move` (A6) under another Workstream, or to another index under the same parent, then only the node's `parent` and `order` change. The node's `worktree` (`path`, `branch`, `base`), the Agent's working directory, the git worktree list, the branch and the Base's commit are the same bytes after the move; `git diff`, `git diff --cached` and `git status --porcelain=v2` run in the Worktree print the same bytes before and after; the fake `claude` (which logs its pid and working directory at start and again after the move) is not restarted and sees the same working directory and the same files. `agent.worktreeState` (G3) returns the same result. A move that A6 refuses (into the node's own descendant, or under a plain Agent or Terminal) is `CONFLICT` as before and changes nothing, Worktree included. A Rail has one Project, because each Daemon serves one Project and ids are per Project, so a move to a node of another Project cannot be asked: a `parent` that names no node here is `NOT_FOUND` with nothing changed, and a Worktree belongs to one repository for the same reason. When the Workstream an Agent sits under is removed (A16) its Agents move to the removed node's parent as A16 says and every Worktree is left as G7's first sentences require; there is no operation that merges Workstreams, so none is specified. Every file path, relative or absolute, in the Agent's working directory means the same file after a move as before.

**G8 the contract.** Given the Worktrees contract of `docs/worktrees.md`, then `crates/contracts` and `contracts/generated/` hold it with no hand edit, and each clause has a test.
- `project.setWorktrees` takes `{on, check}` and returns `null`; `project.get` takes `null` and returns `{worktrees: {on, check}}` with `check` a string or `null` (test `g8_project_methods_are_registered`).
- `agent.worktreeState {id}` returns `{ahead, behind, dirty}` and `agent.land {id}` returns `{base}` (test `g8_worktree_state_and_land_shapes`).
- `agent.discard {id}` takes a node id and returns `null` (test `g8_discard_is_registered`).
- `RailNode.worktree` is `{path, branch, base}` or `null` and is a required field, so a `RailNode` literal in the webview fixtures, `seeds.ts` or an e2e test without it fails `pnpm typecheck` (test `g8_rail_node_worktree_is_required`).
- The error codes of G1 to G7 add no `rpc::code` constant (test `g8_no_new_rpc_code`, which compares the constants with those of `main`'s `crates/rpc`).
- `loop/rules.sh vocab` passes with every new name in `GLOSSARY.md` (policy, checked by `just check`).

**Door restart boundary (G2/G6).** Given a stopped or reopened Door with a recorded Worktree, `rail.startDoor` reuses that path and branch without resetting commits or files, even if the Project setting changed since first start. A missing recorded directory fails `worktree_missing` and preserves the Workstream and record. A failed retry never deletes an existing Worktree. Only a first start without a recorded Worktree provisions under G2 and rolls back its newly created files on failure; G6 unfinished-provision recovery retains the Workstream and membership. Observe stop/start and cold reopen with an uncommitted file and commit in the Worktree, comparing ids, paths, branches and file bytes; inject launch failure and a missing path. Explicit Workstream removal retains G5 protection and A16 child lifting.


**G9 removing a Workstream retains Worktrees without copying on one filesystem.** Given A34's removal of a Workstream with clean, landed Worktrees, backup preparation and rollback obey the following clauses. Ownership: `crates/agents/src/worktree.rs` and scenario tests in `crates/agents/tests/scenarios/` and `crates/rup/tests/a34.rs`; a fallback dependency belongs in `crates/agents/Cargo.toml` and its generated `Cargo.lock`. No RPC, App seam or vocabulary change.

- **Retain by rename.** Before deleting a Worktree's git registration or branch, move its complete directory into a unique backup directory on the Worktree's filesystem using a directory rename. Until the coordinated storage commit succeeds, retain the directory and recorded branch tip. Then remove the backup. Test `g9_same_filesystem_backup_moves_the_directory` observes the original path absent, the saved directory and ignored file retaining their device and inode numbers, and no fallback copy invocation; `g9_success_removes_worktrees_branches_and_backups` asserts cleanup only after commit. Backup preparation must not redirect git commands into the saved directory or change the Base (same tests).
- **Copy only across filesystems.** If directory rename reports a cross-device error, copy through a maintained crate such as `fs_extra`; remove the source only after the complete backup succeeds. Other rename errors fail preparation without copying. Replace or delete the hand-written recursive `copy_tree`; it is not a fallback implementation (policy). Tests `g9_cross_device_backup_uses_copy_only_after_exdev`, `g9_other_rename_errors_do_not_copy` and `g9_failed_copy_keeps_the_original` inject the respective filesystem outcomes at the filesystem boundary. The copy observer compares nested file bytes, ignored files, permissions and symlinks (including a dangling link), without following links outside the Worktree. Unsupported file types fail without deleting their only copy (same copy-failure test).
- **Restore every moved directory.** A later preparation failure, git removal failure, branch deletion failure or coordinated storage failure restores every already moved directory, including ones whose git removal was not attempted. Rename a retained directory back on the same filesystem; use the maintained copy fallback only for a cross-device restore. Restore missing branch tips and git registrations so the original path is usable with git; never overwrite an externally advanced branch or files written by another process at the original path. Tests `g9_later_preparation_failure_restores_earlier_moves`, `g9_removal_failure_renames_back_ignored_files`, `g9_storage_failure_restores_all_moves` and `g9_restore_preserves_external_writes` compare original paths, ignored bytes, permissions, symlinks, branch tips, git registrations and the Rail; the rename-path tests also compare ignored-file device and inode numbers. Clear the injected failure and retry successfully (same tests).
- **Keep the only copy.** If restoration fails or the original path now contains external files, return `worktree_failed` with the retained backup path and keep every backup not yet safely restored. No error return or automatic temporary-directory cleanup deletes the only remaining copy of any ignored file. Test `g9_failed_restore_keeps_recoverable_backup` injects restoration failure, reads the ignored bytes from the reported path after the removal object is dropped, and verifies external files remain unchanged.

Observer: `g9_workstream_removal_with_one_gb_ignored_file_finishes_under_one_second` in `crates/rup/tests/a34.rs` uses a real git repository, a real Daemon and a finished fake Agent with a clean, landed Worktree. Before timing, write and flush an allocated 1,000,000,000-byte ignored regular file (not a sparse length-only fixture) under `target/` or `node_modules/`, verify its size and that git reports clean, and establish the client connection. Measure with a monotonic clock from sending `rail.remove` for the Workstream through receiving its successful reply, including backup cleanup; elapsed time must be strictly below 1,000 ms. Assert the Workstream, removed Agent, Worktree directory, branch and backup are gone. Do not time fixture creation or Daemon startup, mock git or filesystem operations, or relax the limit after a failure. Run on a local filesystem supporting directory rename; print elapsed time and filesystem identity on failure.

## Prepared directories (specification; implementation pending)

G2542a–G2542e extend G2, G5 and G6 only for explicitly enrolled directories in opt-in prepared-directory mode. G1–G9 retain their legacy meaning otherwise; Base and Landing are unchanged. For an enrolled directory, G9's removal/rollback must retain the directory and ignored files rather than deleting its backup after removal. A prepared Worktree is in the same repository and within the Project's allowed cwd boundary; external vendor-managed paths need a separate A4 trust-boundary specification.

Ownership: `crates/agents` owns Project configuration, exclusive assignment and durable recovery, using its existing git/worktree execution and storage. Every contract change and caller ships together. No UI, vendor orchestration, ecosystem detection, copy engine, automatic adoption or Terminal integration is added by this specification. Inspection/editor opening and Terminal integration remain separately owned; neither is a readiness prerequisite. New tests below are planned acceptance, not existing evidence.

Preparation uses the Project's explicit command before enrollment. Cold creation, exhaustion and incompatible dependencies require preparation and never silently install or copy on launch. Capacity is exactly the enrolled directories; no fixed pool count or replenishment process. An assignment keeps the enrolled path but uses `roundup/agent-<id>` at the captured Project commit.

**G2542a Project preparation and readiness.** Given prepared-directory mode and one explicitly enrolled git Worktree, when an Agent or first Door starts, reserve the directory before changing its branch; switch tracked files to the captured Project commit without force, then run the Project's explicitly configured readiness command there and wait for exit 0 before starting the Agent. Run that command on every assignment, including after a lockfile, toolchain or setup-command change. It must validate the current environment, not merely test that a folder exists. With an explicitly configured positive readiness timeout, nonzero exit, expiry of that timeout or cancellation starts no Agent, reports phase, path, exit status when available and the last 20 lines of diagnostic output, capped at 16 KiB and redacted by the Project command before emission, and leaves the directory unavailable pending successful preparation. No silent fallback to installation, copying or the primary checkout. Tests: `g2542a_readiness_precedes_launch` and `g2542a_changed_environment_and_failed_readiness_block_launch` in `crates/agents/tests/scenarios/worktrees.rs`. Cold setup is an explicit Project command invocation, outside the launch timing; it can take minutes and must not be called ready early (same failure/readiness test).

**G2542b Reuse without dependency writes.** Given an enrolled Worktree already prepared for the target commit, when assigned, run the Project's smoke test successfully without invoking its installer or recursively copying/cloning/linking dependency directories. Preserve ignored `node_modules/`, `target/`, `.venv/` and local `.env` at their existing paths, with the same device/inode and bytes. Use independent fixtures for Node, Rust and Python, including a Python environment whose executable refers to its absolute path, to catch relocation. Project commands supply ecosystem knowledge; roundup contains no special case for those folder names. Tests: `g2542b_prepared_ecosystems_run_without_install_or_copy` and `g2542b_reassignment_preserves_ignored_paths` in `crates/agents/tests/scenarios/worktrees.rs`. Actual ecosystem smoke commands belong in the integration observer, not fake executables that only claim readiness.

**G2542c Exclusive use and consent.** Given two simultaneous starts and one available directory, at most one Agent launches there; the other reports no prepared directory available and changes no files. A directory with a recorded Agent, running Terminal or preparation process is unavailable even when git reports clean. Enroll only with explicit local user configuration; never execute newly discovered repository commands or approve Worktrunk hooks automatically. `wt list --format=json` can discover candidates, but discovery grants no permission to switch, adopt or delete them. Validate canonical path, repository identity, git registration and branch ownership before assignment. Reject the primary checkout, duplicate canonical paths, symlink escapes and directories with staged, unstaged, untracked nonignored work, unlanded commits or an in-progress git operation. Test `g2542c_exclusive_assignment_and_enrollment_guards` in the same test file; it compares rejected directories' refs and file bytes before and after. Policy: no shared writable dependency symlinks between simultaneously active assignments.

**G2542d Release and crash recovery preserve work.** Release only after all roundup-managed users have stopped and a second clean/landed check passes. Keep dirty or ahead work attached to its stopped Agent, as G5 does; never reset, stash, clean or force-switch to make a directory available. A clean successful removal deletes the Agent branch and node but retains the enrolled directory and ignored files on a parked detached commit. Explicit discard may discard tracked/untracked Agent work, but returning to the pool never removes dependency directories; unenrollment does not delete the directory. A restarted Door reuses its existing assignment without switching or readiness writes over its work. Persist the reservation before branch changes; on restart, uncertain setup or assignment remains unavailable until reconciled, and a recorded running/stopped Agent retains ownership. Never apply G6's fresh-directory deletion to an enrolled directory. Tests `g2542d_release_keeps_work_and_ignored_files` and `g2542d_crash_recovery_never_deletes_or_double_assigns` in the same test file inject process death before/after reservation, checkout, readiness and launch; retry must preserve work and yield one owner. Failure to restore metadata retains the path and reports recovery instructions rather than deleting it.

**G2542e Seconds and managed-Mac observer.** Given two available, independently prepared directories, each with at least 10,000 ignored dependency files, after fixture creation and Daemon startup measure twenty sequential assignments to the same target commit, releasing between assignments. Time from start request through the launched test process reporting its first successful smoke-test result; p95 (the nineteenth sorted time, using nearest rank) must be at most 5,000 ms. Record all twenty times, OS, filesystem, tool versions, fixture counts and dependency file identities. Installer calls and creates/writes/renames/unlinks under the dependency roots must be zero during each timed assignment, observed at the filesystem/process boundary; inode equality alone is insufficient. Node, Rust and Python smoke tests must each pass. Observer `g2542e_warm_launch_observer` is an implementation delivery requirement, with Linux automation and the same documented procedure on a managed Mac with Defender enabled. Policy: Linux success proves reuse, not Defender latency. Record Mac results separately; do not claim Defender scans are bypassed, request antivirus exclusions or disable protection. Missing managed-Mac evidence leaves that claim unverified, without blocking the Linux implementation work.
