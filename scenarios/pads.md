# Pads

Module: `crates/pads`. Ids: every `P` heading in the file.

**P1 create.** Given an empty Project, when an Agent `a` calls `pad.create {name: "notes", text}`, then the Pad contains `text`; creating `notes` again fails with `CONFLICT`, and so does `Notes` (names are unique ignoring case, because the macOS file system is case-insensitive and file-backed Pads would otherwise share one file); `pad.changed {name}` is emitted and a `wrote` Touch on `pad:notes` is logged. Test `p1_create_stores_text_and_logs_a_write` (planned replacement in `crates/pads/tests/pads.rs`, retaining uniqueness/Event/Touch assertions).

**Pad**: A markdown note with a Home (P12). Removing its Workstream applies A34 by Home alone. It has a Revision (P15): a number that starts at 1 and rises with each change to its text, which `pad.write` and `pad.appendSection` can require atomically (`expectedRevision`) so two writers never interleave blindly. "Scratchpad" is the product word in prose only.

**P2 any Actor rewrites or appends.** Given Pad `notes` created by Agent `a`, when the user, `a` or another Agent `b` calls `pad.write`, then the text is replaced; each may also call `pad.append` to add text at the end. Each changed write emits `pad.changed` and logs a `wrote` Touch by its caller. Planned test `p2_any_actor_rewrites_and_appends` in `crates/pads/tests/pads.rs` replaces the former permission matrix while retaining text, Event and Touch assertions.

**P3 read and list.** Given three Pads, when `pad.list` is called, then all three come back ordered by name; `pad.read {name}` returns one and logs a `read` Touch; an unknown name is `NOT_FOUND`.

**P4 shared access.** Pads have no owner. Policy: a Pad belongs only to its Home, a Workstream or the Project root. Every Actor in that Project may read, write, append, rename, move and delete it; Project authentication, name validation, incarnation and Revision guards, file safety, Touches and Events remain. The storage setting and export-path rules stay P5/P6. The contract and public-tool observer is P16; no compatibility method or data migration is required for disposable pre-release data.

**P5 file-backed storage.** Given Pads `notes` and `plan`, when `pad.setStorage {files: true}` is called, then `pads/notes.md` and `plan.md` exist in the Project's data folder (N1) with the Pads' text, and later writes and appends update the files. When a file is edited on disk and `pad.setStorage {files: false}` is called, then the edit is imported into the Pad. Files are not added to any ignore list. In file mode the app database stays the source of truth and the files are a mirror: `pad.read` returns the database text, and edits made on disk are imported only when flipping back to app storage. Every file write is atomic (temp file then rename) and happens before the database change is committed, so a failure leaves nothing applied; `setStorage` records the new setting only after every file operation succeeded, so a retry redoes the work. A name the file system refuses is `INVALID_PARAMS`.

**P6 export.** Given a Pad, when `pad.export {name, path}` is called, then one `.md` file with the text is written to `path`, whatever the storage setting; a relative `path` is `INVALID_PARAMS` (the Daemon's working directory is not the caller's), and a path whose directory does not exist is an error, never a silent create.

**P7 persistence.** Given app-stored Pads, when `Pads::open` is called again on the same directory, then every Pad, its Home and text are intact. Test: `p7_pads_keep_home_and_text_after_reopening` (planned replacement in `crates/pads/tests/pads.rs`).

**P8 names.** A Pad name containing `/`, `\`, `..`, a leading dot, or an empty string fails with `INVALID_PARAMS` for every method that takes a name.

**P9 delete.** Given Pad `notes` created by `a`, when the user, `a` or another Agent calls `pad.delete {name}`, then the Pad is gone (`pad.read` is `NOT_FOUND`), its file is removed when file-backed, `pad.changed {name}` is emitted and a `wrote` Touch on `pad:notes` is logged; the name is validated like every other (P8). Planned test `p9_any_actor_deletes` in `crates/pads/tests/pads.rs` retains deletion, file, Event and Touch assertions for each caller.

**P10 a rejected call leaves no trace, in either storage mode.** Given Pad `notes` created by Agent `a` in app storage and again in file storage (P5), when `pad.create` of `Notes` fails with `CONFLICT` (P1), and `pad.read`, `pad.append` and `pad.delete` of `../x` fail with `INVALID_PARAMS` (P8), then after each call `pad.read {name: "notes"}` returns the same text, Home, incarnation and Revision, the Project's data folder `pads` (N1) holds exactly the files it held (none in app storage, no temp file left in file storage), no `pad.changed` arrived and no Touch was logged. A refused call to a Pad that is not there is `NOT_FOUND` and creates no file. Owns `crates/pads/**`. Test `p10_rejected_calls_leave_no_trace` (planned, both storage modes). It keeps P1, P2, P5, P8 and P9 green and narrows none.

**P2544a block editing in the existing Pad surface.** Given a Pad in its Drawer, when the user types `/` at an empty paragraph, then Crepe's `block-edit` slash menu opens; choosing a heading by pointer or by Arrow keys and Enter inserts that block, Escape dismisses without changing text, and typing resumes in the document (`p2544a_slash_menu_pointer_and_keys`, planned isolated headless browser test beside the Pads tests). When the user drags a paragraph by Crepe's block handle before another paragraph, then the paragraphs change order and the resulting saved text has that order (`p2544a_drag_reorders_and_saves`, planned browser test). Given a Pad created by an Agent, the same actions edit and save it (`p2544a_slash_menu_pointer_and_keys` and `p2544a_drag_reorders_and_saves`, parameterized by maker); the former readonly-only test is retired. Policy: retain Crepe (Milkdown), its library-owned block interactions and the one live-preview surface; no editor replacement, second editing mode or new visual-authoring capability. This adds to U147 retaining its lazy-loading rules.

**P2544b autosave acknowledges the latest draft.** Narrows U20, U36 and U147's blur-only timing: blur still flushes, but is no longer the only save trigger. Given a Pad with a changed document, when typing pauses for 500 ms, then one `pad.write` sends the latest reconciled source; another edit before the deadline restarts it, and an unchanged document or a document undone to its saved state sends nothing (`p2544b_pause_coalesces_latest_draft`, planned Vitest beside `PadDrawer`). Leaving the editor or closing its Drawer flushes a dirty draft immediately, cancels its timer, and never duplicates a write already sent for that draft; moving focus into an editor menu is not leaving the editor (`p2544b_blur_close_and_menu_focus`, planned Vitest). Given an in-flight save, when more edits arrive, then at most one write is in flight; its completion advances the saved baseline without replacing the newer draft or its selection, and the newest draft is sent after that completion if its pause or blur deadline has passed (`p2544b_inflight_edits_are_not_lost`, planned Vitest).

Given that a write has succeeded and its returned text equals the current draft, then a noninteractive `Saved` status beside the Pad name appears; a new edit, pending write, conflict or failure removes that mark, and a late response for an older draft cannot restore it (`p2544b_saved_means_current_draft_acknowledged`, planned Vitest asserting status semantics and call settlement, not exact copy or layout). A failed save retains the draft, exposes the error, shows no saved status and allows a later blur or edit/pause to retry; failure after closing reaches the Shelf's existing error line (`p2544b_failure_preserves_draft_and_retry`, planned Vitest). Switching Pads or Projects leaves no timer able to write a draft into another Pad, and deleting a Pad cancels its queued save (`p2544b_save_lifetime_is_pad_scoped`, planned Vitest).

**P2544c edits preserve the untouched source.** Given a loaded source and its initial editor document, when the document is unchanged, then its original bytes are returned and no save is sent (`p2544c_no_edit_preserves_bytes`, planned Vitest through the real Crepe binding). Given an edit, then the saved text changes only the blocks the user edited. An edited block may take Crepe's serialization whole (a table whose cell changed may lose its padding), and every block the user did not touch keeps its bytes: unchanged ranges remain byte-identical, including table padding, list markers, blank lines, line endings, final-newline presence, front matter, HTML, reference definitions and footnotes. Each fixture declares the exact expected full source; no whitespace normalization in the assertion (`p2544c_only_edited_ranges_change`, planned table-driven Vitest through Crepe). Fixtures cover insertion, deletion, formatting, paragraph split/join, two separated edits with untouched content between them, identical repeated paragraphs with only the second edited, non-ASCII text, CRLF and missing final newline, undo/redo, block insertion and drag reorder. A moved block retains its authored bytes except where the user's operation requires a delimiter change. Opaque syntax that Crepe cannot represent stays in its original relative position when editing neighbouring content. If the edited blocks cannot be matched to source blocks, saving fails visibly and retains the draft rather than replacing the file with a whole-document serialization (`p2544c_ambiguous_mapping_keeps_source_and_draft`, planned Vitest).

When two successive saves edit different paragraphs, then both edits remain and each acknowledged source becomes the baseline for later edits; replacing the loaded source after a clean external update or `Use theirs` establishes the same baseline (`p2544c_repeated_saves_and_reload_preserve_bytes`, planned Vitest). When creating a new unordered list, then its serialized marker is `-`; changing neighbouring prose leaves an existing `*` list unchanged (`p2544c_new_lists_use_dash_existing_markers_survive`, planned Vitest). Policy: source reconciliation belongs behind the editor's source interface, not in each save trigger; compare editor documents/serializations against their own baseline and reconcile into original source, never diff raw source against a normalized serialization and apply that normalization wholesale. Reuse maintained diff machinery where it covers the need; rule 9 applies to the implementation.

**P2544d concurrent changes remain explicit.** Given a dirty draft, when another Actor changes the Pad, then autosave and blur pause, the draft remains, and U36's conflict choices remain available; the user's own save echo does not create a conflict (`p2544d_external_change_pauses_autosave`, planned Vitest). `Use theirs` adopts the latest listed text and Revision without writing; `Keep mine` explicitly saves the current reconciled draft and clears the conflict only after success; typing while that save is in flight remains in the draft (`p2544d_conflict_choices_preserve_latest_draft`, planned Vitest). **P3557a ordinary editor actions always produce saveable source.** Extends P2544c; its failure clause applies only to an ambiguous relocation of authored source, not to an ordinary edit or a difference in paragraph/block counts. Given a Pad opened through the real Crepe binding, when the user performs any editor action, then the edited blocks map back to their source or use Crepe's serializer, while untouched blocks retain their original bytes. Empty paragraphs that have no remark block and Crepe's trailing caret target do not make saving fail. A whole-document serialization that changes untouched blocks does not satisfy this clause.

Guard: one table-driven or generated Vitest, `p3557a_ordinary_edits_preserve_source`, beside `apps/desktop/src/pads/p2544c_source.test.tsx`, uses the actual `PadRichEditor`/Crepe binding, its installed key commands and history, without mocking the parser, serializer, source reconciliation or editor handle. It runs in Vitest's headless DOM environment, starts no browser or Daemon, and stays within rule 10's five-second CI bound per test. Replacing the entire document with parsed fixture Markdown does not exercise an Enter or Backspace action. The matrix crosses each applicable action below with at least three fixture Pads: several one-line paragraphs; mixed blocks with a padded table and an authored `*` list untouched beside the edit; and non-ASCII CRLF source without a final newline. It includes an initially empty Pad and identical repeated paragraphs. Each row declares its selection and expected edited document, its untouched source ranges and their exact expected bytes.

| Action | Required positions and sequences |
|---|---|
| Enter | On an empty line; at the start, middle and end of a paragraph; twice in succession. |
| Empty paragraph | Create before, between and after existing blocks; edit it again after an acknowledged save and after loading that saved source in a fresh binding. |
| Shift+Enter | Inside a paragraph, creating a hard break and continuing to type after it. |
| Enter in structured blocks | Inside unordered and ordered list items, checked and unchecked task items, quotes and headings; include an empty item/quote and the resulting exit to prose. |
| Backspace | At a block boundary to join paragraphs; remove an empty paragraph before, between and after other blocks. |
| Undo and redo | Undo and redo every sequence above, including both successive Enters; save/read at each resulting state. |

After each action, undo, redo and subsequent text insertion, the guard asserts that `getText()` is non-null, that the edited content matches the expected document under Crepe's supported serialization, and that all declared untouched ranges are byte-identical, without trimming or whitespace normalization. It acknowledges the returned source through the existing handle, edits again and repeats those assertions, then opens the saved text in a fresh binding and repeats an edit/save. An unchanged or fully undone document returns its original bytes (P2544c). Empty paragraphs are tested as editor state as well as source: a serialization-only comparison cannot prove their actions ran. These assertions all belong to `p3557a_ordinary_edits_preserve_source`.

Given an edit whose alternatives would move or discard opaque authored syntax, when no source mapping can preserve that syntax's relative position, then saving still refuses, keeps the saved source and recoverable draft, and exposes the failure (`p2544c_ambiguous_mapping_keeps_source_and_draft`, existing real-binding Vitest). A failed match caused solely by blank paragraphs, generated heading ids or a normalized baseline is not that ambiguity. Policy: preserve P2544c's source interface, maintained library machinery and P2544b/P2544d's save ordering and conflict guards; no editor replacement or new RPC.
