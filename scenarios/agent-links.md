# A Door names an Agent with its link, and every Terminal makes the link clickable (AL1 to AL6)

Module: `crates/messages`, `crates/agents`, `crates/rup`, `apps/desktop/src`. Ids: AL1, AL2, AL3, AL4, AL5, AL6. Acceptance for [#6173](https://github.com/roundup-app/roundup/issues/6173). Terms: Door, Agent, Terminal, Rail, link (`GLOSSARY.md`). Source: the owner, 2026-11-04, on a Door that wrote "open the researcher-checks-free-routes pane" in plain text. No implementation is claimed by this specification.

Policy, Must not: no new link scheme, contract field or RPC method beyond what carrying the link in the digest needs (a contract change follows the Contract recipe of `.agents/builder.md`); `http(s)` and path links keep working as U365 says (`scenarios/ui-terminal-links.md`); LK1's form is the only link form (`scenarios/rup-ext.md`).

**AL1 a digest and a Door tool reply name an Agent with its link.** Given a Door whose Workstream holds the Agent `researcher-checks-free-routes`, when the Door reads `agent_digest`, or a digest is pushed to it (`entry_text`, `crates/messages/src/digest.rs`), or any other Door tool reply names an Agent, then each line that names that Agent also carries its LK1 link `roundup://agent/<id>?project=<key>`, `<id>` and `<key>` percent-encoded as LK1 says, and the line keeps the name. A reply that names no Agent is unchanged. Asserted in planned `al1_a_digest_entry_carries_the_agents_link` in `crates/messages/src/digest/tests.rs` and planned `al1_a_door_tool_reply_naming_an_agent_carries_its_link` in `crates/rup/tests/e2e.rs`. The Daemon already knows the key (`daemon.ping` `projectKey`, LK1); the digest takes it from there (policy; a new field is allowed only if the digest cannot be given the key otherwise, by the Contract recipe).

**AL2 the Door's brief tells it to give the link.** Given a Door's brief (`crates/agents/src/claude_code/brief.rs`), when it is built, then it says that when the user must act in an Agent (a permission ask, a question, a failure, a result to read) the Door names the Agent with its link, copied from the digest or tool reply and never made up. Asserted in planned `al2_the_door_brief_asks_for_the_agent_link` in `crates/agents/src/claude_code/brief.rs` tests, pinning the instruction token, not the whole text.

**AL3 a link in a Terminal is clickable and shows the name.** Given any Terminal (Door, Agent, shell, Bubble) that printed a `roundup://` link to an Agent, Workstream, Pad or Todo of this Project, plain or as an OSC 8 hyperlink, when the user plainly clicks it, then the object is selected and shown as the Rail shows it, by the route of an Overview Message's native anchor (`watchNativeOpen`, `link.read`, U365 amendment #5772); for an Agent that is its Terminal, focused as U5742c says, so a waiting permission ask is in view. An OSC 8 link shows its text (`researcher-checks-free-routes`), never the raw URL. The same hover, drag, double-click and mouse-reporting rules as U365 hold, and `findTargets` stays the one recogniser (`apps/desktop/src/terminal/links.ts`; the emulator gains OSC 8 handling through xterm's `linkHandler` option, no hand-written parser). A link of another Project or of another scheme opens nothing and says why, as U365 says. Asserted in planned `al3_an_osc8_agent_link_shows_its_text_and_selects_the_agent` and `al3_a_plain_roundup_link_selects_its_object` in `apps/desktop/src/terminal/al3_browser.test.ts` (mounted real emulator, fake App), and `al3_http_and_path_links_still_open` retaining the U365 proofs.

**AL4 a link to a missing object says so.** Given a link to an Agent, Workstream, Pad or Todo that no longer exists, when the user clicks it, then the existing not-found line of the native open route shows (the `link.read` error message shown by `fail` in `apps/desktop/src/app/nativeOpen.tsx`), and the centre is never a blank pane. Asserted in planned `al4_a_link_to_a_missing_agent_shows_not_found` in `apps/desktop/src/terminal/al3_browser.test.ts`.

**AL5 every surface that shows a Door's or an Agent's text makes the links clickable.** Given the Door and Agent Terminals, the Inbox, the Overview and notifications, when each shows text holding a LK1 link, then the link is clickable by AL3's route; a surface that cannot hold a link (a native notification) shows the object's name and its click opens that object. The PR records the audit as a table, one row per surface, with the test or the stated reason. Asserted in planned `al5_inbox_and_overview_text_links_open_the_object` in `apps/desktop/src/ask/u365_links.test.tsx`.

**AL6 a failed link lookup returns the reply without links.** Found by the review of PR #6182. Given a Door tool reply that succeeded and names an Agent, when the extra read AL1 needs for its links (`rail.tree`, or `daemon.ping` for the Project key) fails, times out within `CALL_TIMEOUT` or returns data that does not parse, then the Door gets the reply as the tool produced it, without links, and not an error; the call's effect is not reported as failed. A later reply, once the read answers, carries its links again. Asserted in planned `al6_a_failed_link_lookup_returns_the_reply_without_links` in `crates/rup/tests/e2e.rs`, with a fake Daemon whose `daemon.ping` never answers and a second run whose `rail.tree` errors; assert the reply text and `isError: false`, never timing beyond `CALL_TIMEOUT` plus a margin.

Observer: AL1 to AL6 in Vitest and cargo tests above, using the fake App and mounted real xterm in isolated headless Chromium (a dedicated agent-browser session, a fresh profile); test behaviour, selections, call counts and contracts only (AGENTS.md rule 10). One real run on this revision, by the user on the Mac (a logged-in real `claude`): a real Door whose Agent waits on a permission ask names it with a link, and clicking the link shows the ask.
