# Messages between Actors

Module: `crates/messages` (with the tools in `crates/rup`). Ids: every `B` heading in the file.

Messages let the user, Agents and Extensions send each other typed text. Design, contract and module split: `docs/messages.md`. Terms are in `GLOSSARY.md`. A Message's status is one of `pending`, `delivered` and `dropped`; a `dropped` Message also names why (`receiver gone`, `not accepted`, `removed` or `merged`). A Message to an Agent is written to the receiving Attempt's Claude inbox and is never typed into a Terminal (B3563c); nothing is held, and an undelivered Message is `pending`. Tests use a fake `claude`, the fake Terminal of `crates/terminal` and a fake clock; none needs a display or a network.

**B1 send.** Given an open Project with Agent `a`, when an Actor calls `message.send {to: "a", kind, body, replyTo?}`, then the result is a Message with the next id (1, then 2 and on, per Project), `from` the calling Actor (never a parameter, so nobody can forge it), `to` the Agent `a`, `kind`, `body`, `replyTo` or `null`, a `status` and `at`. The call emits `message.sent` and logs a `wrote` Touch (B11). `kind` is `note` or `question`; neither kind chooses transport: every Message to an Agent goes through the inbox (B50), and the receiver can identify the kind and Message id; any other `kind` is `INVALID_PARAMS`. A `to` that names no Actor is `NOT_FOUND`. A `to` that is a Terminal, a Group or the sender itself is `INVALID_PARAMS`; only an Agent or the user can be its own receiver, so an Extension may send to an Agent that has its id. An empty body, one larger than 8192 bytes, or a `replyTo` that names no Message is `INVALID_PARAMS`. A receiver whose Kind is `done`, or whose Attempt ended, is `CONFLICT` (B9); a live receiver in `error` follows B37. A receiver with 32 Messages in `pending` that are not pushed digests (B21) is `CONFLICT` naming the bound; pushed digests have their own bound (B22). A rejection before storage changes nothing: no id is used, no event is sent and no Touch is logged. B51(f) is the explicit post-storage exception: an unavailable inbox returns `INBOX_UNAVAILABLE` with a durable `pending` Message, not a rollback.

**Card**: Anything the user sees in the app (an Inbox Message, a status, a summary); it has a kind.

**B2 auto delivery.** Transport is B3563c's: every Message to an Agent, whatever its authenticated sender or kind, uses only the receiving Attempt's Claude inbox (B50), with B50–B52's receipt, failure and replay rules. Messages addressed to the user use B10 and have no Agent inbox destination. Given a Route from the sender to Agent `a` of `auto` (B5), when a Message is sent, then it is stored `pending`, `message.sent` is emitted, and at `a`'s existing eligible delivery time (Kind `idle`, or B37's live-error case) the Message is written to the inbox with its original id, kind, body, sender and reply identity, in id order (B7). It stays `pending` with its saved in-flight record (B39) and becomes `delivered`, and `message.delivered` is emitted, in that order, only when `a`'s transcript records that Message id (B50(c)). When `a` has any other Kind, nothing is written and the Message stays `pending` until the next eligible time. A receiver that is gone drops it with the reason `receiver gone` (B9). No Message write ever reaches a Terminal, `Agents::prompt` is never called for a Message, and the user's unsent Terminal bytes neither delay nor receive it (B3563c). Exactly once (B39): the Message is `delivered` once, by the receipt, and never written to a second turn. `<sender's name>` labels the entry's `from-name`: the Rail name for an Agent, `you` for the user, the Extension's id for an Extension and `rupd` for the Daemon. An Agent renamed between send and delivery uses its current Rail name; after removal it uses its last Rail name known to Messages, never its machine id (B2705a). Daemon rename notes follow B2704a.

**Terminal owner** (`TerminalOwner`, `TerminalOwners`, `with_terminal_owner`, internal `terminal_owner`): The Agent or Door attached to a Terminal as its Message receiver, with its Attempt, Status revision and receiver ending facts. A Run or the user's shell has no Message receiver, even when an Agent or Workstream owns its Terminal.

**B3 retired by #3563** (the ask-first Route and its hold). Routes have no ask-first value (B3563d), and `message.held` and `message.deliver` are removed with it: a Message to an Agent is never waiting on the user. `message.drop {id}` stays as the user's removal of one `pending` Message (B3563b, U3782): only the user may call it, any other Actor gets `FORBIDDEN`; it makes the Message `dropped` with the reason `removed` and emits `message.dropped`; a Message that is not `pending`, or whose in-flight record exists, is `CONFLICT`, naming the cause.

**B4 drop.** Given a Route of `drop`, when a Message is sent, then the call succeeds and returns the Message with the status `dropped`; nothing is sent, and `message.dropped` is emitted. The sender is not told it was dropped by an error.

**B5 Routes.** Given no Route for a sender and receiver, then the delivery is `auto`. `route.set {from, to, delivery}` stores a Route for that pair, `delivery` being `auto` or `drop`, and emits `route.changed`; `route.list` returns every stored Route. Any other `delivery` value is `INVALID_PARAMS` and stores nothing (B3563d). The user may call `route.set`; an Agent may only as M14 (`scenarios/mcp.md`) says, never with the user as `from`, to itself or over a Route the user set, so a user's choice is never overridden by an Agent. Any other call gets `FORBIDDEN`. A Route whose `to` is the user, or whose `from` equals its `to`, is `INVALID_PARAMS`. A change applies to Messages sent after it: one already `pending` stays `pending`.

**B6 retired by #3563** (Takeover, its holds, and the Door-action amendments that waited for it). `takeover.begin`, `takeover.end`, `takeover.changed` and every Takeover-based wait are removed. A Door action never waits for the user's input: prompt, interrupt, stop, resume, order, Terminal write, read, resize, close and kill, child rename, question and permission answers, and rewind plan and execution each perform their normal operation or return their normal error in that call (B3563d), and direct user Terminal input does not defer them. The one B6 amendment below that concerns Resume cleanup is kept, since it has no Takeover dependency.

B6 retirement keeps these tests and no others from its former Door-action families: the Reach and actor-identity tests (`b6_child_snapshots_keep_reach_restrictions` and its neighbours in `crates/rupd/tests/`) stay as they are, since B3563d reuses them rather than duplicating their proof.

Observer: real-Daemon integration tests under `crates/rupd/tests`, deterministic fake Claude and recording handlers; no real vendor or user's desktop is needed (B3563d's `b3563d_door_actions_return_their_effect_or_error_without_deferral`). Laws touched: M1 (at most once), M4 (order), M6 (no silent loss), M7 (receiver gone), M9 (restart replay), M10 (eligible-delivery liveness), as named in `scenarios/proofs.md`. M2's release obligation and M3's isolation are retired by #3563; M3 is replaced by zero Message writes to Terminal input (B3563c).

B6 amendment, Resume cleanup exit confirmation (source #1958), kept after B6's retirement. Given a failed Resume whose saved conversation cannot be promoted, then:

- While the failed Attempt's Terminal exit is unconfirmed after cleanup's kill and bounded wait, `agent.resume` returns `rpc::code::UNKNOWN_OUTCOME` (-32004), preserving the original save failure, the Terminal id, "exit not confirmed" and "do not retry Resume". A second Resume returns the identical error, allocates no Attempt, and leaves the failed Terminal attached with `can_resume: false`. An unconfirmed `agent.stop` also returns unknown and does not authorize Resume. Only confirmed exit and explicit resolution permit a later Resume. Test: `cleanup_completion::b6_unconfirmed_terminal_exit_preserves_the_resume_failure_and_blocks_a_blind_retry` in `crates/rupd/tests/b6_cleanup_completion.rs`, exercised on Linux and macOS with the same assertions.
- The unconfirmed-exit observer establishes that exit confirmation remains unavailable through the cleanup wait, independently of whether the host PTY reports EOF when its leader exits. Its readiness handshake precedes the failing acknowledgement; releasing its hold allows exit and resolution, and teardown releases every hold and reaps every descendant it created. Test: the same `b6_unconfirmed_terminal_exit_preserves_the_resume_failure_and_blocks_a_blind_retry`; policy: no platform skip, retry-until-green, longer sleep or relaxed error assertion substitutes for this precondition. It exercises the Daemon's confirmation branch rather than merely injecting an UNKNOWN_OUTCOME response.
- A confirmed cleanup preserves the original save failure without falsely reporting an unknown outcome, and a later Resume can succeed with a new Terminal. Test: `cleanup_completion::b6_resume_completion_waits_for_both_promotion_failure_cleanups` in `crates/rupd/tests/b6_cleanup_completion.rs`, extended to assert the confirmed error code. Cleanup refusal retains its distinct reason and the same retry fence. Test: `cleanup_completion::b6_cleanup_refusal_preserves_the_resume_failure_and_blocks_a_blind_retry` in that file.

Checks retained from main: (1) `crates/agents/src/resume.rs`, `Shared::confirm_terminal_exit`, rejects a Terminal still listed running; (2) `crates/agents/src/ending.rs`, `kill_or_already_gone`, subscribes before kill and bounds the exit wait; (3) `crates/terminal/src/lib.rs`, `pump`, waits for PTY read completion and program reaping before publishing exit; (4) `crates/rupd/tests/b6_cleanup_completion.rs`, `cleanup_completion::b6_resume_completion_waits_for_both_promotion_failure_cleanups`, keeps completion behind both cleanup paths. **B7 order.** Given several Messages to one Agent, then they are written to its inbox in the order in which they became deliverable, ties broken by id: id order (B3563c). A Message that cannot go yet (an unavailable inbox, B51) does not let a later Message overtake it; when the same Attempt's inbox becomes usable, the next eligible event retries the same ids in order.

**B8 restart.** Given a Project whose Daemon was killed without warning and is started again (D6), then Routes, every Message and its status survive, and the next Message id continues the sequence. Exactly once: no Message is lost and none is delivered twice (B39). The Daemon saves a Message's in-flight record (B39) in the same write that precedes the inbox write and records `delivered` only when the transcript receipt for that Message id arrives (B50(c)). A Daemon killed between the inbox write and the receipt leaves the Message `pending` with its in-flight record, and the same id is written again at the Agent's next eligible time under the same `msg_id` (B40, B52); the receiver's receipt is still one delivery. A Message to an Agent whose Terminal did not survive (A12), in the status `pending` and with no in-flight record, becomes `dropped` with the reason `receiver gone`; one with an in-flight record stays `pending` with the record cleared, and is written at the first eligible time of that Agent once `agent.resume` brings it back (B39), dropped `receiver gone` only if the Agent is removed or its Attempt cannot be resumed (B9). Messages to the user keep their status. The reasons are listed by `message.get`.

**B9 receiver gone.** Given Agent `a` whose Kind becomes `done` or whose Attempt ends (including an exit with Kind `error`, but excluding B37's live `error`), then every Message to `a` in the status `pending` becomes `dropped` with the reason `receiver gone`, one `message.dropped` each, in id order, and a later `message.send` to `a` is `CONFLICT`.

**B10 to the user.** Given a Message whose `to` is the user, then it is `delivered` at once, whatever Routes exist, no inbox entry is written, and `message.delivered` is emitted. Such a Message sends no `agent.status` event and changes no Agent's Kind (`PRINCIPLES.md` P3), and `message.list {to: "user"}` lists it. What the webview shows of it is the Inbox's scenario, not this series.

**B11 Touch.** Given a Message with id `n`, then `message.send` logs a `wrote` Touch on `message:<n>` by the sender, `message.drop` logs one by the user, `message.get {id}` logs a `read` Touch by its caller, and `message.list {to?, status?}` logs none; for an Agent it returns only the Messages that Agent sent or received, and for an Extension only the ones it sent. `provenance.history {item: "message:<n>"}` returns them in order, and `provenance.touched` lists them under each Actor. Reading is by Actor: an Agent may `message.get` a Message it sent or received, and any other Message is `FORBIDDEN`; the user may read any. `GLOSSARY.md` now says a Touch is of a Todo, a Pad or a Message.

**Touch**: One logged read or write of a Todo, a Pad or a Message by an Actor.

**Provenance**: The append-only log of Touches.

**B12 an Agent sends and reads.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `message_send`, `message_get` and `message_list` are offered besides M1's, named after their methods with the dot replaced by `_`, with input schemas derived from the params types in `crates/contracts`. A call is made as that Agent, so `from` is its id and B11's rule on reading applies; an Agent cannot name another sender. M1 lists the exact set of tools; this scenario narrows it by those three, and the test `m1_offers_one_tool_per_method_and_no_others` is amended to M1's methods plus the three, in the same PR as `scenarios/mcp.md`'s M1 text. `message_drop` and `route_set` are not offered: they are the user's. Each tool call and its result are exactly the Daemon's result or error for the method, as M1 says.

## Child digests: a Door learns what its children did

A Door has no shell and reads children only through tools, so a child's state reaches it as a small fixed envelope, asked for or pushed on change, and never as Terminal output. Every cut or merge is marked in the text; nothing is dropped without a sign. Tests use the fake clock, a Rail with Door `m` and children `a`, `b` and `c`, and a fake Terminal that prints a unique word.

**B19 the envelope.** Given a Door `m`, then the digest of a child is exactly `{name, kind, last, todos, pads}`: `name` the child's Rail name, `kind` its Kind, `last` one line of at most 120 bytes, `todos` the number of Todos satisfying `!done && creator.kind == "agent" && creator.id == child.id`, regardless of Home, and `pads` the names of the child's Pads written since the previous envelope about that child went to `m` (at most 4 names of at most 32 bytes each). `last` is the first line of the newest Message the child sent to `m`, or the child's Status label when it sent none; a line cut at 120 bytes, a name cut at 32 and a `pads` list cut at 4 each end in `[cut]`, and the whole entry is at most 512 bytes. No Terminal output is ever read: a fake Terminal that prints the word `ZEBRA` leaves it out of every envelope, whatever the child's Kind. Policy: Agent references in digest errors follow A2703a and B2705a; the envelope shape and bounds do not change.

Tests in `crates/messages`: `b19_todos_counts_only_open_todos_created_by_the_agent` counts two open Todos created by one Subagent and excludes done Todos and Todos created by another Agent, the user or an Extension in the same Workstream, including a non-Agent creator with the Subagent's id; `b19_completing_a_created_todo_reduces_the_count` asserts 1 after completing one of two; `b19_home_changes_keep_creator_attribution_until_completion` asserts the creating Agent's count after moving Home to another Workstream or the Project root, and its removal on completion. `b21_two_stopped_changes_release_one_newest_entry_of_weight_two` composes two separate open-Todo changes from creator-attributed Workstream Todos, asserts each changes the Subagent's entry, no send while stopped, and one newest entry with count 2 and weight 2 on start under B22. T13's rejection of Agent Homes and T14's automatic Workstream Home remain unchanged. B19's shape and bounds and B21/B22's waiting, counts and caps remain unchanged.

**Digest**: A Door's fixed-size envelope about one direct child, `{name, kind, last, todos, pads}`, asked for with `agent.digest`, or pushed to the Door as a Message when the child's Kind (an `idle` and `working` flip alone excepted, B35), Pads or open Todos change (B21), as plain text (B33), and never read from Terminal output (B19, B20). An `error` or `needs-you` child is the exception: its note goes to its parent at once, whoever the parent is (B43). The end note of a child carries its own summary, at most 600 bytes (B49).

**B20 asking.** Given `m` with children, when `agent.digest {id: "m"}` arrives, then the result is `{children: [...]}` with one entry per direct child in Rail order (B19's shape), at most 20 entries, and a last entry `{more: n}` when `m` has more than 20. A caller that is neither `m` nor the user gets `FORBIDDEN`; an id that names no Agent is `NOT_FOUND`; an Agent that is no Door is `CONFLICT`. Error text names each existing Agent reference by its current Rail name and describes a missing Agent without its id; B2705a names the error tests. Authorization is unchanged: another Agent remains forbidden even if the target is in its Reach. `rup mcp <m>` offers the tool `agent_digest` to Doors only, taking no input (the shim fills `id` with its own Agent's id), and no other Agent's tool list has it; this narrows M1's closed list of tools in `scenarios/mcp.md` by that one tool for a Door, and `m1_offers_one_tool_per_method_and_no_others` is amended in the same form as B12's.

**B21 pushed on change.** Given `m` and a child whose Kind changes (an `agent.status` event, except an `idle` and `working` flip alone, B35) or whose Pad or Todo count changes, then the Daemon sends `m` one Message from `rupd`, kind `note`, whose body is `[digest]` and that child's one entry (B19). Route and order are as for any Message (B2, B5, B7). No push is made for a child that has no Door, and none for a change that leaves the entry as it was. A stopped Door is a Workstream whose Door has no live program, including after the Daemon reopens the Project (A24); it is distinct from a Door removed with its Workstream. While stopped, its changed child entries wait in the Daemon without a `message.send` attempt or a refusal log. Further changes replace each waiting child's entry with its newest and retain their change count for B22(c). A successful `rail.startDoor` makes those entries eligible for push without requiring another child change; B22's caps still apply. A failed start leaves them waiting. This defers only Digests not yet sent: B9 still governs existing Messages and direct `message.send`, and a removed Door receives no push. A push refused for any reason other than the Door being stopped still logs its receiver and cause and remains eligible for retry at the next change.

Tests in `crates/rupd`, through the real Daemon with a deterministic fake `claude`, captured stderr and the fake clock: `b21_a_failed_start_keeps_the_entries_waiting` starts and stops a Door, creates two open Todos for one Subagent across a failed start, and asserts no Digest Message, no `message.send` attempt and no Digest refusal line while stopped; after a successful start, with no further child change, it finds exactly one Digest naming that Subagent with open Todo count 2 and weight 2. The observer waits for completion of each Digest comparison before its next input; absence assertions use that completed comparison, never a sleep. Policy: B2, B9, B22, B34 and B35 otherwise keep their rules; this changes neither the Message contract nor the finality of a Message already sent.

B21 test-cost observer (T2964a): `b21_a_reopened_door_waits_until_explicit_start` needs the Daemon process to exit and reopen its stored Project, and the child's actual startup to leave its Door stopped. `b21_a_failed_start_keeps_the_entries_waiting` needs an actual failed launcher invocation followed by a successful child startup: changing a fake Rail's live flag cannot detect a launcher that publishes eligibility too early. `b21_start_releases_each_changed_child_under_b22s_caps` needs the real Door's receipt-confirmed inbox delivery while the fake clock advances cap windows; its assertion combines startup without another child change, delivered weights and readable merged Messages. **B22 caps.** Given `m`, then (a) at most 8 pushes go to `m` in any window of 60 000 ms of the fake clock; the pushes after the eighth wait and, at the window's end, become one Message `[digest] [K updates rolled up]` with the newest entries of at most 8 affected children, newest change first (at most 4096 bytes), then one line `[+n more: <names>]` for the others, cut at 512 bytes and ending `[cut]` when longer; (b) at most 20 pushed digests are `pending` for `m` at once: when a twenty-first arrives, the oldest two merge into one Message beginning `[digest] [N earlier updates: #a #b]` with N their count (a merged one counts its own N), `a` and `b` the two merged Messages' ids, and the newest entry of each child they named; the two become `dropped` with the reason `merged` and stay readable by `m` through `message.get` (P7); (c) no cap loses a count: every pushed digest has a weight, 1 for a plain push and the sum of the weights it holds for a rollup (K) or a merge (N), and the total weight of the digests delivered or still waiting equals the number of changes that changed an entry (a change that leaves the entry as it was is not one, B21), which the test checks after a burst of 100 changes, with `m` busy for part of it, along with every pushed digest being delivered, still waiting, or named by a merge that is, and `message.get` opening each for `m`; (d) pushed digests count only against (b), not against B1's 32, so a push never gets `CONFLICT`, and `m` filled to B1's bound by other Messages (pending behind an unavailable inbox, B51) still receives its pushes; (e) the caps count Messages: delivery (B30) calls no prompt for a digest, so the 8 pushes of (a) cost `m` no prompt of its own.

**B23 survive and gone.** Given pushes and a rollup that were `pending` when the Daemon was killed (D6), then after a restart they are delivered (once, B39) or dropped as B8 says, and a push that was written to the inbox but not received is written again, never lost and never delivered twice, the K and N counts in their bodies are intact, and the 60 000 ms window starts again. A child that is removed or ends (`done`, or an exited Attempt including `error`) gets one last push with its Kind, and a Door that is gone gets none (B9).
