# UI: Settings › Updates

Acceptance for #7208, from the owner's request (2026-11-15) that App Settings hold an update section like Herdr's. Modules: `apps/desktop/src/` (`settings/`, `toasts/`, `state/`, `app/`) and `crates/desktop/src/` (`updates.rs`, `updater.rs`, `core_update.rs`, `menu.rs`). Ids: U7208a–U7208f. Builds on CH7077e (`scenarios/channels.md`), S5981a (`scenarios/app.md`), CH7077g's `MIN_CORE`, U3799's App Settings and U7192's top-right Toasts. Amends CH7077e: the application menu's "Update available" opens this page and no longer installs.

Contract (policy, by the Contract recipe of `.agents/builder.md`): `scenarios/app.md`'s seam table gains the commands `updates`, `install_update` and `update_core` and the event `updates-changed`, and `open-app-settings` takes an optional payload; `GLOSSARY.md` gains the _Updates_ row; `scenarios/ui-persist.md` names the new App family `roundup:updates-told`. Every caller changes in the same PR: the `App` type, its Tauri, fake and isolated-browser implementations, and M5's no-tool list for the three commands. The facts are one value, `{roundup, core}`: `roundup` is `{version, ready}` or `null` on a build with no update feed (the Source Channel, CH7077e), and `core` is `{version, ready}` or `null` when no `herdr-core` runs; `ready` is the newer version's text or `null`.

**U7208a Settings holds an Updates page.** Given App Settings, then the General list ends with `Updates`, which shows two rows and one line. The roundup row names `roundup <version>`. With a newer version ready it reads `<new> is ready. Your Agents keep running through it.` and holds the button `Update roundup`; with none, `Up to date` and no button. The herdr-core row names `herdr-core <version>`. With a newer version ready it reads `<new> is ready. Your Terminals keep running through it.` and holds the button `Update herdr-core`; with none, `Up to date` and no button; with no `herdr-core` running, `Not found` and no button. The line below reads `roundup looks for both every hour and tells you in the corner.`; it shows only beside the roundup row, and a build with no update feed shows neither. Each row is one Settings search result (U5243a) for its name, with its live button. Tests: `u7208a_updates_page_shows_both_rows_with_their_state`, `u7208a_search_finds_each_update_row_with_its_button` (`apps/desktop/src/settings/`). Observer: the design critic on `just capture U7208a` at 1512×950, dark, `tree-40`, with both versions ready and a failure line showing (no test asserts geometry, rule 10).

**U7208b Update roundup installs through the Update exit.** Given a ready roundup version, when the user presses `Update roundup`, then the App reads the feed again and installs the version it offers then, never one an earlier look offered (#7300): it downloads and installs it, leaves every Daemon through the Update exit (S5981a) so Agents and their Terminal owners keep running, and relaunches on the new bundle. When the feed then offers nothing newer, the click installs nothing: `install_update` answers `null`, `Update available` leaves the application menu and `updates-changed` names no ready roundup version, so the row reads `Up to date`. A download the server answers 404 or 410 (the `dev` release keeps only its newest build) reads the feed once more and installs the newer version it offers then; only when that fails too does the row show a failure. From the click until the App relaunches the button is busy (U170): it reads `Updating…` with an indeterminate mark and ignores clicks, so a second click starts no second install. The row shows the download's progress as the updater reports it (downloaded and total bytes): `Downloading 12 of 40 MB`, then `Installing…`; with no total it reads `Downloading…`. The App reports it with the event `update-progress` `{downloaded, total: number | null, stage: "downloading" | "installing"}` (`scenarios/app.md` gains its row), sent only while `install_update` runs. A failed install leaves the Daemons running and the version the click's last look found ready, sends `updates-changed`, and the row shows the cause in one line below it and the button returns to `Update roundup` with no progress line. The cause is the copy catalogue's sentence for the kind word that leads `install_update`'s failure, `<kind>: <cause>`, never the updater's text: `unreachable` (the feed or the download could not be reached), `no_build`, `replaced` (the build is gone and the feed offers no newer one), `broke_off` (the download broke off), `refused` (the server answered the download with another error), `signature` (the download did not match its signature) and `not_installed`; any other kind reads `Couldn't update roundup. Try again.` An HTTP answer never reads as no answer. `install_update` with no version ready fails `INTERNAL` `no update is ready`. Tests: `ch7077e_the_update_leaves_the_daemons_only_once_it_is_installed` (`crates/desktop/src/updater.rs`, unchanged), `u7208b_install_update_without_a_ready_version_fails` (`crates/desktop/tests/`), `u7208b_a_failed_install_shows_its_cause_and_keeps_the_button` (the catalogue's sentence for the kind, never the App's text), `u7208b_a_pending_install_shows_updating_and_its_progress_and_ignores_a_second_click` (a pending `install_update`: `aria-busy="true"`, `Updating…`, `Downloading 12 of 40 MB` after an `update-progress` event, `Installing…` after the next, one call after two clicks; once it settles the idle label), (`apps/desktop/src/settings/`); `u7208b_install_update_emits_progress_while_it_runs`, `u7208b_the_click_installs_what_the_feed_offers_then`, `u7208b_a_gone_build_reads_the_feed_again_and_installs_the_newer_one`, `u7208b_a_gone_build_with_nothing_newer_names_the_replacement`, `u7208b_with_nothing_newer_at_the_click_the_app_is_up_to_date` (`crates/desktop/tests/`, a fake feed whose answers a test changes; a test has no key to sign a package, so the signature check of the build the click fetched is what stops each install). The Toast of U7208e shows the same busy state if its button starts the update; its card only opens Updates, so no Toast starts it today (policy).

**U7208c Update herdr-core runs `herdr-core update`.** Given a ready herdr-core version, when the user presses `Update herdr-core`, then the App runs `herdr-core update` from the login-shell `PATH` (S6). When it exits 0 the row shows the version `herdr-core --version` then reports, `Up to date`, and no button. While it runs the button is busy as in U7208b, reading `Updating…` with an indeterminate mark (no progress line: `herdr-core update` reports none). When it fails the row keeps its version and an idle button and shows the last line the program printed on its error output, or its exit status when it printed none, in one line below it. Nothing runs `herdr-core update` on another Machine (Settings › Machines, #7206) or without the click (policy). Tests: `u7208c_update_core_runs_herdr_core_update_and_reads_the_new_version`, `u7208c_a_failed_core_update_names_its_last_line` (`crates/desktop/tests/`, a fake `herdr-core` on the App's `PATH`), `u7208c_a_failed_update_names_the_last_line_the_program_printed` (`crates/desktop/src/core_update.rs`), `u7208c_the_core_row_shows_the_new_version_or_the_failure`, `u7208c_a_pending_core_update_shows_updating_and_ignores_a_second_click` (`apps/desktop/src/settings/`).

**U7208d the App looks for both versions every hour.** Given the App at launch and every hour after, then it reads roundup's signed feed (CH7077e) and herdr-core's release feed, `<releases>/core/latest.json`, where `<releases>` is `HERDR_RELEASES_URL` when set and `https://releases.herdr.dev` otherwise: the feed `herdr-core update` reads, so a version this finds is one the update installs. A build with no update feed reads herdr-core's alone, and an App configured with no herdr-core feed (a test App) reads none. Neither read installs anything. A herdr-core version is ready when the feed's `version` is newer, by semantic versioning, than `herdr-core --version` reports; an equal or older one, an unreadable or unreachable feed, or an unreadable version is not. After each look the App emits `updates-changed` with the facts, and `updates` answers the same facts at any time. Each look keeps what roundup's feed offers then, a newer version or none, and the application menu holds `Update available` only while one is offered (#7300). A failed look is logged (`diagnostics`) and changes nothing; a herdr-core feed that answers an HTTP error is logged as one that answered with an error, never as one that did not answer. Tests (`crates/desktop/src/core_update.rs`, a local HTTP feed): `u7208d_a_newer_core_version_in_the_feed_is_ready` (newer, equal, older, a feed with no `version`, a 404, nothing listening), `u7208d_the_installed_version_is_the_one_the_program_prints`; (`crates/desktop/tests/`, a fake `herdr-core` and a local feed): `u7208d_updates_answers_the_versions_and_what_is_ready`. Policy, observer: on a Mac whose herdr-core is older than the feed's, the Updates page names the feed's version within a minute of launch.

**U7208e each new version raises one Toast.** Given facts that name a ready version not yet told, whether read at launch or sent as `updates-changed`, then one Toast (U7192) names it, `roundup <version> is ready` or `herdr-core <version> is ready`, and makes no sound. Pressing its card shows App Settings on Updates (U7208f). The same version raises no second Toast, however many hourly looks name it and across relaunches (told versions persist in `roundup:updates-told`); a newer version after it raises its own. Facts that name none raise none. Tests: `u7208e_each_new_version_raises_one_toast_that_opens_updates`, `u7208e_a_told_version_stays_told_across_looks_and_launches` (`apps/desktop/src/toasts/`).

**U7208f the application menu's Update available opens Updates.** Given a roundup version ready on an installed build, then the application menu holds `Update available` as CH7077e says, and choosing it installs nothing: it emits `open-app-settings` with the payload `updates`, and the webview shows App Settings on Updates, also when Settings is open on another page or a search is showing. `Settings…` emits it with no payload, as U3799 says. Tests: `u7208f_the_update_item_emits_open_app_settings_with_updates` (`crates/desktop/tests/settings.rs`), `u7208f_the_updates_payload_shows_the_updates_page` (`apps/desktop/src/settings/`).
