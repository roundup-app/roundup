# Lean child start

Module: `crates/agents` (the launch flags, settings and Brief under `claude_code/`, P4), with the extras check in `crates/rupd` and the `extras` field in `crates/contracts`. Terms: Role, Brief, Skill, Door, Subagent, Agent (`GLOSSARY.md`). Principles served: P9. Contract change (rule 4): `agent.spawn` gains `scout` and `extras`, and one tool lists the extras; the build adds `scout` to `GLOSSARY.md`'s Role entry. Supersedes the "keeps the user's own servers" note in `launch.rs`. Q11's plugin delivery holds for every child. Ids: LC1–LC14 and LC16–LC21. Evidence (Claude Code 2.1.302, Max login, haiku): a child started with 31.7k tokens, 149 tools, 109 skills and 13 plugins from the user's other work. Accepted tradeoff (owner): every child keeps the user's whole setup, and this start cost is expected.

Rule: a child's start is the user's whole setup (LC6) plus its Role's `--tools`, Brief and bundled plugins, plus the extras the Door named. roundup only adds: its MCP server, hooks, permission rules, Brief and plugins. It removes none of the user's settings, plugins, MCP servers, memory, output style or global instructions.

Terms of this file: the Door is Role `door`. A scout is a Subagent started with `scout: true` for reading and searching, with memory writes under LC19–LC20. The worker of the Issue is every other Subagent, Role `subagent` (`GLOSSARY.md` avoids "worker").

**LC1 one profile table per Role.** Given a child started by `rail.startDoor` (A7) or by `agent.spawn` (A4) from an Agent, then its launch follows this table, and `launch.rs` holds it as one table that the tests below read:

| Role | `--tools` | Skills | Plugins | MCP servers | Instruction files |
|---|---|---|---|---|---|
| Door | `Read,Grep,Glob,Write,Edit,ToolSearch,Skill,AskUserQuestion` | on (no `--disable-slash-commands`; a `/command` sent to a Door runs there, A41) | `hope`, `hunch`, `hold` (LC5, LC14), plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |
| scout | `Read,Grep,Glob,Bash,Write,Edit,ToolSearch,AskUserQuestion` | on (no `--disable-slash-commands`) | `hope`, `hunch`, `hold`, plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |
| worker | all | Project skills listed | `hope`, `hunch`, `hold` (LC5), plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |

Each cell is a launch fact, read from the recorded argv and files (`lc1_each_role_launches_as_its_row`, in `crates/agents/tests/launch.rs`). A Door without MCP (M2219) keeps `DOOR_TOOLS_NO_MCP` and has no ToolSearch row; every row, with or without MCP, lists `AskUserQuestion`, so the user answers an Agent's question natively in its Terminal (A3564a/b).

**LC2 every child extends the user's settings.** Given a child of any Role in the LC1 table, then it starts with the user's effective settings and environment under A3507a and A3507b (`scenarios/agents.md`), and every key is kept, `outputStyle`, `enabledPlugins`, `mcpServers`, `autoMemoryEnabled` and `autoMemoryDirectory` among them. Its argv holds no `--strict-mcp-config` and no `--setting-sources`. Its environment does not set `CLAUDE_CODE_DISABLE_AUTO_MEMORY`. roundup adds its `--mcp-config` server (when MCP is on), its hooks and its permission rules on top, and replaces no user hooks, permission fields or servers. LC7 still adds explicitly requested extras.

|---|---|

| none set | hold:Plain as its output style. roundup sets `"outputStyle": "hold:Plain"` in its generated settings as Q1 and Q11 require; the Brief carries no style body or hold:Plain instruction. |

**LC6 an agent the user starts keeps the user's full setup.** Given an Agent that the user starts from the Rail or a Terminal (`agent.spawn` with no `parent`, and a Terminal's own program), then none of `--setting-sources`, `--strict-mcp-config`, `--disable-slash-commands` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` is set, and no `--tools` list. roundup's `--settings` hooks and `--mcp-config` stay, so Status and the tools work (`lc6_a_user_started_agent_keeps_the_users_setup`).

**LC7 the Door names extras when it starts a child.** Given `agent_spawn` (F3) with `extras: {skills?, plugins?, mcp?}` each a list of names, then `crates/rupd` checks each name against what exists: a skill in the Project's `.claude/skills` or the user's skills folder, a plugin in the user's installed plugins, an MCP server in the user's configuration. A name that exists is added to the child's start (a skill listed, the plugin as `--plugin-dir`, the server in the `--mcp-config` file); any unknown name fails the call with `INVALID_PARAMS` naming each unknown one and its kind, and nothing starts (`lc7_a_known_extra_joins_the_start`, `lc7_an_unknown_extra_fails_the_start_and_is_named`). The tool `agent_extras` returns the available names by kind on demand; no name list is in the Door's Brief, settings, `tools/list` or start text (`lc7_the_extras_are_in_no_start_text`; the E9 same-bytes test holds).

**LC8 a missing extra relaunches with `--resume`.** Given a running child and `agent_extras_add {id, extras}` (LC7's shape) from its Door or parent, then the Agent is stopped and relaunched as A35 relaunches, with `--resume <conversation>`, its LC1 row plus the new extras and `--system-prompt-snapshot off`, so that a changed Brief applies; an unknown name is `INVALID_PARAMS` as in LC7 and the child keeps running. Any other `--resume` of a roundup child keeps the snapshot default (`lc8_a_missing_extra_relaunches_with_resume_and_snapshot_off`, `lc8_an_unknown_extra_leaves_the_child_running`).

Given `rail.startDoor`, then the recorded start's `--tools` and roundup's added `permissions.allow` rules hold no shell or Terminal-start tool: no `Bash`, `PowerShell`, `terminal_spawn`, `terminal_open` or `terminal_write`, with or without MCP (M2219) (`lc11_the_doors_start_allows_no_shell_or_terminal_start`). **LC12 a standing specialist stays alive per Workstream.** Folded from #2423; supports B20. A standing specialist is a scout (LC4) the Door keeps for one kind of reading, for example a repo scout for all GitHub and git reading; the Daemon keeps at most one live per Workstream and specialist name. Given a Door that calls `agent_spawn` with `scout: true` and `specialist: "<name>"` and a second call with the same name in the same Workstream while the first child lives, then the second returns the first child's id and starts nothing; the call with a different name, or in another Workstream, starts a child (`lc12_two_lookups_give_one_child_start`, on the real Daemon with the fake `claude`, counting starts in the recorded start log). When the child has ended, the same name starts a new one (`lc12_an_ended_specialist_is_started_again`). The Brief names `specialist` as the way to ask for one (`lc12_the_brief_names_the_specialist_field`). Contract change (rule 4): `SpawnParams` gains `specialist: Option<String>`, valid with `scout: true` only, else `INVALID_PARAMS` and no child starts (`lc12_a_specialist_requires_scout`).

**LC13 a specialist at 160k tokens is replaced with a handoff; a job-sized child fits under 160k.** Folded from #2424; supports B22. The Daemon reads a child's context size as the sum of `input_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` of the last `usage` in its Claude transcript, at each `Stop` Signal. Given a specialist (LC12) whose size crosses 160 000 at a `Stop`, then the Daemon sends it one Message asking for a summary of at most 600 bytes (B49's limit), and when the summary arrives stops it and starts one replacement of the same name, whose first input holds that summary under the heading `Handoff from the previous specialist`. Replayed counts of 90 000, 150 000 and 161 000 give one replacement, at the third; a count that stays under 160 000 gives none; a replacement whose first `Stop` reports 161 000 again is replaced once more only after a new summary (`lc13_a_specialist_crossing_160k_is_replaced_once_with_the_summary`, `lc13_under_160k_makes_no_replacement`). While that summary is pending, repeated `Stop` Signals reporting 161 000 send no additional summary request and start no replacement; after the summary arrives, those Signals still produce only one replacement (`lc13_repeated_stops_wait_for_one_handoff`). A job-sized child reporting 161 000 at a `Stop` gets no summary request or replacement (`lc13_a_job_sized_child_is_not_replaced`): the Brief tells the Door to give it a whole job that finishes under 160k tokens and to expect its summary at the end (B49); its size judgment is not tested, only the Brief tokens `160k` and `whole job` (`lc13_the_brief_sizes_a_job_under_160k`).

## Memory writes for Doors and scouts

From #5529. Scope: `crates/agents/src/claude_code/` and `crates/agents/tests/launch.rs` with its `launch/` fixtures and hook tests. Any additional hook entry point needed outside this scope must be named with its reason in the work Issue before implementation. No RPC, Message, Route or public domain name changes. This section amends LC1, LC3, LC4, LC16 and F2 (`scenarios/spawn-boundary.md`): a Door or scout gains `Write` and `Edit` for memory, not general file editing. Ordinary Subagents and user-started Agents already have those tools and are exempt from this new restriction; their ability to do implementation work stays intact (policy).

Applicable Gates and Observers:

1. P1: can a memory request force the user away from the Workstream's Door? LC21 observes the request and saved files from that Door.
2. P4: can this change replace user hooks, permissions, memory configuration or credentials, or move vendor logic outside the Adapter? LC19 checks generated settings alongside the carried setup; memory resolution and hook decisions belong under `claude_code/`.
3. P9/P10: can memory support change the settings, Brief or tool catalogue during a running session, add a Model turn to decide permission, or put per-Agent paths in the shared Brief? LC19 checks launch artifacts; LC20's hook decides without a Model. The memory rule is fixed Brief text; the resolved directory is launch data, not per-Agent Brief text (policy).

Checks retained from `origin/main`:

1. `scenarios/lean-child-start.md`, **LC11 the Door runs nothing and the Brief offers two children**, and `crates/agents/tests/launch/lean.rs`, `lc11_the_doors_start_allows_no_shell_or_terminal_start`, hold the Door's shell and Terminal boundary. `Agent` remains absent too; saving memory does not use a native subagent.
2. `scenarios/agents.md`, **A3507b settings are extended, with a closed lean exclusion list**, owns settings precedence and preservation; LC2 in this file keeps memory settings and user hooks.
3. `crates/agents/tests/launch/lean.rs`, `lc6_a_user_started_agent_keeps_the_users_setup`, holds the unrestricted user-started path; `crates/agents/tests/launch.rs`, `m2219_off_keeps_the_hooks_and_the_tools_without_toolsearch`, holds the no-roundup-MCP path.
4. `scenarios/spawn-boundary.md`, **F2 a Door has no shell (guarantee)**, limits its guarantee to Claude Code's built-in tools. LC20 adds no sandbox for user MCP servers or the scout's existing `Bash` (policy); the scout's Brief still delegates implementation work.

The test names below are implementation acceptance, not claims that these tests already exist on main.

**LC20 only the effective memory directory passes the guard.** Given LC19's generated hook, `Write` or `Edit` input, and either `default` or `bypassPermissions`, when the hook runs, then its decision follows the resolved filesystem target, not a string prefix:

| Target | Hook result | Implementation test in `crates/agents` |
|---|---|---|
| New topic file, existing topic file or `MEMORY.md` inside the effective Claude Code memory directory | No refusal by roundup's guard; normal user permissions still apply. A missing memory directory does not prevent the first write. | `lc20_memory_files_pass_the_guard` |
| A file in the Project checkout outside memory, or any other outside file | Denied before execution; the reason tells the Agent to hand the work to a child Agent; existing bytes stay unchanged and a new file stays absent. | `lc20_other_files_are_refused_even_in_bypass` |
| Sibling directory sharing the memory path's prefix; a `..` escape; a symlink inside memory pointing outside | Same denial as an outside file. Resolve existing ancestors when the final file does not yet exist. | `lc20_path_aliases_do_not_escape_memory` |
| Missing, malformed or unresolvable file path or memory root | Denied with the cause and child-Agent direction; never broadened to the checkout, home or config directory. | `lc20_unknown_paths_are_refused` |

Each test covers both tools and both permission modes. The hook tests feed the vendor-shaped input to the handler used by the generated hook and assert its blocking result and reason; checking only matcher text or permission rules is insufficient.
