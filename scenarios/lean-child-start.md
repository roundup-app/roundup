# Lean child start

Module: `crates/agents` (the launch flags, settings and Brief under `claude_code/`, P4), with the extras check in `crates/rupd` and the `extras` field in `crates/contracts`. Terms: Role, Brief, Skill, Door, Subagent, Agent (`GLOSSARY.md`). Principles served: P9. Contract change (rule 4): `agent.spawn` gains `scout` and `extras`, and one tool lists the extras; the build adds `scout` to `GLOSSARY.md`'s Role entry. Supersedes the "keeps the user's own servers" note in `launch.rs` and the plugin delivery of Q11 for every child, which Q1 (`scenarios/plain-text.md`) kept in the Brief. Ids: LC1–LC9. Evidence (Claude Code 2.1.302, Max login, haiku): a child started with 31.7k tokens, 149 tools, 109 skills and 13 plugins from the user's other work.

Rule: a child's start depends only on its Role, its Project and the extras the Door named. A cost in tokens enters only when every job of the Role needs it. A cost of none that spares an interruption always carries over: login, the user's permission rules, roundup's hooks (policy).

Terms of this file: the Door is Role `door`. A scout is a Subagent started with `scout: true` for reading and searching only. The worker of the Issue is every other Subagent, Role `subagent` (`GLOSSARY.md` avoids "worker").

**LC1 one profile table per Role.** Given a child started by `rail.startDoor` (A7) or by `agent.spawn` (A4) from an Agent, then its launch follows this table, and `launch.rs` holds it as one table that the tests below read:

| Role | `--tools` | Skills | Plugins | MCP servers | Instruction files |
|---|---|---|---|---|---|
| Door | `Read,Grep,Glob,ToolSearch` | off (`--disable-slash-commands`) | none | roundup's | the Brief; Project `CLAUDE.md` |
| scout | `Read,Grep,Glob,Bash,ToolSearch` | off | none | roundup's | the Brief; Project `CLAUDE.md` |
| worker | all | Project skills listed | `hope`, `hunch`, `hold` (LC5) | roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |

Each cell is a launch fact, read from the recorded argv and files (`lc1_each_role_launches_as_its_row`, in `crates/agents/tests/launch.rs`). A Door without MCP (M2219) keeps `DOOR_TOOLS_NO_MCP` and has no ToolSearch row.

**LC2 every child starts from its own settings.** Given a child of any Role in the LC1 table, then its argv holds `--setting-sources project`, `--strict-mcp-config` beside `--mcp-config` naming roundup's config, and its environment holds `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Its `--settings` file holds roundup's hooks and `mcp__roundup__*` allow (A4), and also the `permissions.allow` and `permissions.deny` rules of the user's settings file, copied at launch, merged after roundup's, a rule once. Nothing else of the user's settings, plugins, MCP servers, output style or memory reaches the child (`lc2_a_child_starts_from_its_own_settings`). Given a user settings fixture that sets an output style, a plugin, an MCP server and a permission rule, then the recorded start drops the first three and carries the rule (`lc2_the_users_output_style_never_shapes_a_child`; folded from #2422).

**LC3 the Door is lean and shaped by the Brief only.** Given `rail.startDoor`, then its argv holds `--tools Read,Grep,Glob,ToolSearch` and `--disable-slash-commands`, no `--plugin-dir` for `hold` and no `--setting-sources` value but `project`. Its Brief no longer inlines `hold-plain.md`'s body: it names Plain's rules in the Door's own words and leaves the user's own `CLAUDE.md` out (the Door reads none), so a Door neither ignores a Project `CLAUDE.md` nor forces status tables. This amends Q1 (`scenarios/plain-text.md`) and E1: Q1's vendored body is carried by the worker only (`lc3_the_door_launches_lean_and_its_brief_omits_the_plain_body`). Whether the Door then writes as Q3 lays out is observed in LC9's real run (policy).

**LC4 a scout reads and searches.** Given `agent.spawn` with `scout: true` from a Door or an Agent, then the child's argv holds `--tools Read,Grep,Glob,Bash,ToolSearch`, `--disable-slash-commands`, and no user `CLAUDE.md` (`lc4_a_scout_launches_with_read_tools_and_no_user_instructions`). It takes the Subagent's Model and Effort (A36); no Project setting is added. `scout` is absent from an old caller's JSON and false; a user's spawn that sets it is `INVALID_PARAMS`.

**LC5 a worker has what working needs, and plugins go only where used.** Given `agent.spawn` without `scout`, then the child has every tool, no `--disable-slash-commands`, and the user's global `CLAUDE.md` is appended to its Brief file at launch as read-only text under a heading. Project skills are listed by Claude Code from `.claude/skills`. roundup's `hope`, `hunch` and `hold` (Q11) are passed with `--plugin-dir` to a worker only; the Door and a scout get none, and `roundup-question` goes with `ask_user` to the Roles that have the tool (`lc5_a_worker_gets_the_plugins_and_global_instructions`, `lc5_the_door_and_scout_get_no_bundled_plugin`).

**LC6 an agent the user starts keeps the user's full setup.** Given an Agent that the user starts from the Rail or a Terminal (`agent.spawn` with no `parent`, and a Terminal's own program), then none of LC2's `--setting-sources`, `--strict-mcp-config`, `--disable-slash-commands` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` is set, and no `--tools` list. roundup's `--settings` hooks and `--mcp-config` stay, so Status and the tools work (`lc6_a_user_started_agent_keeps_the_users_setup`).

**LC7 the Door names extras when it starts a child.** Given `agent_spawn` (F3) with `extras: {skills?, plugins?, mcp?}` each a list of names, then `crates/rupd` checks each name against what exists: a skill in the Project's `.claude/skills` or the user's skills folder, a plugin in the user's installed plugins, an MCP server in the user's configuration. A name that exists is added to the child's start (a skill listed, the plugin as `--plugin-dir`, the server in the `--mcp-config` file); any unknown name fails the call with `INVALID_PARAMS` naming each unknown one and its kind, and nothing starts (`lc7_a_known_extra_joins_the_start`, `lc7_an_unknown_extra_fails_the_start_and_is_named`). The tool `agent_extras` returns the available names by kind on demand; no name list is in the Door's Brief, settings, `tools/list` or start text (`lc7_the_extras_are_in_no_start_text`; the E9 same-bytes test holds).

**LC8 a missing extra relaunches with `--resume`.** Given a running child and `agent_extras_add {id, extras}` (LC7's shape) from its Door or parent, then the Agent is stopped and relaunched as A35 relaunches, with `--resume <conversation>`, its LC1 row plus the new extras and `--system-prompt-snapshot off`, so that a changed Brief applies; an unknown name is `INVALID_PARAMS` as in LC7 and the child keeps running. Any other `--resume` of a roundup child keeps the snapshot default (`lc8_a_missing_extra_relaunches_with_resume_and_snapshot_off`, `lc8_an_unknown_extra_leaves_the_child_running`).

**LC9 the profile holds in the real TUI.** Given the real Brief and `crates/rup/tests/real_claude.rs`, then once, in the implementing PR, the Door's first request carries about 6.5k tokens and a worker's about 17k, and Claude Code's init event lists only the tools, skills, plugins and servers of the LC1 row. The two numbers go in the PR body as a measurement; there is no ongoing budget test (policy, by the user's choice).

**LC10 the forbidden switches.** Given any launch, then no argv holds `--bare`, `--safe-mode` or `--agent`: `--bare` fails a Max login, `--safe-mode` stops `--settings` hooks and `--agent` makes ToolSearch unusable (`lc10_no_launch_uses_bare_safe_mode_or_agent`). The note in `launch.rs` "No `--strict-mcp-config`: the Agent keeps the user's own servers." is deleted by the build, since LC2 replaces it (policy).
