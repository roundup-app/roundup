# Lean child start

Module: `crates/agents` (the launch flags, settings and Brief under `claude_code/`, P4), with the extras check in `crates/rupd` and the `extras` field in `crates/contracts`. Terms: Role, Brief, Skill, Door, Subagent, Agent (`GLOSSARY.md`). Principles served: P9. Contract change (rule 4): `agent.spawn` gains `scout` and `extras`, and one tool lists the extras; the build adds `scout` to `GLOSSARY.md`'s Role entry. Supersedes the "keeps the user's own servers" note in `launch.rs`. Q11's plugin delivery holds for every child. Ids: LC1–LC14 and LC16. Evidence (Claude Code 2.1.302, Max login, haiku): a child started with 31.7k tokens, 149 tools, 109 skills and 13 plugins from the user's other work. Accepted tradeoff (owner): every child keeps the user's whole setup, and this start cost is expected.

Rule: a child's start is the user's whole setup (LC6) plus its Role's `--tools`, Brief and bundled plugins, plus the extras the Door named. roundup only adds: its MCP server, hooks, permission rules, Brief and plugins. It removes none of the user's settings, plugins, MCP servers, memory, output style or global instructions.

Terms of this file: the Door is Role `door`. A scout is a Subagent started with `scout: true` for reading and searching only. The worker of the Issue is every other Subagent, Role `subagent` (`GLOSSARY.md` avoids "worker").

**LC1 one profile table per Role.** Given a child started by `rail.startDoor` (A7) or by `agent.spawn` (A4) from an Agent, then its launch follows this table, and `launch.rs` holds it as one table that the tests below read:

| Role | `--tools` | Skills | Plugins | MCP servers | Instruction files |
|---|---|---|---|---|---|
| Door | `Read,Grep,Glob,ToolSearch,Skill,AskUserQuestion` | on (no `--disable-slash-commands`; a `/command` sent to a Door runs there, A41) | `hope`, `hunch`, `hold` (LC5, LC14), plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |
| scout | `Read,Grep,Glob,Bash,ToolSearch,AskUserQuestion` | on (no `--disable-slash-commands`) | `hope`, `hunch`, `hold`, plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |
| worker | all | Project skills listed | `hope`, `hunch`, `hold` (LC5), plus the user's enabled plugins | the user's, plus roundup's | the Brief; Project `CLAUDE.md`; the user's global `CLAUDE.md` appended |

Each cell is a launch fact, read from the recorded argv and files (`lc1_each_role_launches_as_its_row`, in `crates/agents/tests/launch.rs`). A Door without MCP (M2219) keeps `DOOR_TOOLS_NO_MCP` and has no ToolSearch row; every row, with or without MCP, lists `AskUserQuestion`, so the user answers an Agent's question natively in its Terminal (A3564a/b).

**LC2 every child extends the user's settings.** Given a child of any Role in the LC1 table, then it starts with the user's effective settings and environment under A3507a and A3507b (`scenarios/agents.md`), and every key is kept, `outputStyle`, `enabledPlugins`, `mcpServers`, `autoMemoryEnabled` and `autoMemoryDirectory` among them. Its argv holds no `--strict-mcp-config` and no `--setting-sources`. Its environment does not set `CLAUDE_CODE_DISABLE_AUTO_MEMORY`. roundup adds its `--mcp-config` server (when MCP is on), its hooks and its permission rules on top, and replaces no user hooks, permission fields or servers. LC7 still adds explicitly requested extras.

Output style:

| User's settings | Child gets |
|---|---|
| `outputStyle` set | theirs; roundup never overrides it. The child's settings keep that value, and its Brief holds no hold:Plain instruction and no vendored `hold-plain.md` body. |
| none set | hold:Plain as its output style. roundup adds no `outputStyle` key, and the Brief carries hold:Plain as Q1 and Q11 require. |

Tests:
- `lc2_a_child_starts_from_its_own_settings` (updated to assert that every key is kept and nothing is excluded)
- `lc2_the_users_output_style_shapes_a_child` (set; replaces `lc2_the_users_output_style_never_shapes_a_child`, assertion reversed): for each LC1 row with a fixture `outputStyle`, the settings keep it and the Brief has neither `hold:Plain` nor the vendored body
- `lc2_no_user_output_style_gets_plain` (unset): for each LC1 row without one, the settings have no `outputStyle` and the Brief carries hold:Plain
- A3507a's shared guard

**LC3 the Door is shaped by the Brief and keeps the user's setup.** Given `rail.startDoor`, then its argv holds `--tools Read,Grep,Glob,ToolSearch,Skill` and no `--disable-slash-commands`, so a `/command` sent to a Door runs there (A41). It holds `--plugin-dir` for `hope`, `hunch` and `hold` (LC5), and its settings extend under LC2. Its Brief does not inline `hold-plain.md`'s body. When the user sets no `outputStyle` (LC2), it names Plain's rules in the Door's own words. It appends the user's global `CLAUDE.md` as read-only text under a heading, so a Door neither ignores a Project or user `CLAUDE.md` nor forces status tables. This amends Q1 (`scenarios/plain-text.md`) and E1: only the worker carries Q1's vendored body, and only when the user sets no `outputStyle` (LC2) (`lc3_the_door_launches_with_the_users_setup_and_its_brief_omits_the_plain_body`). Whether the Door then writes as Q3 lays out is observed in LC9's real run (policy).

**LC4 a scout reads and searches, inside the user's setup.** Given `agent.spawn` with `scout: true` from a Door or an Agent, then the child's argv holds `--tools Read,Grep,Glob,Bash,ToolSearch` and no `--disable-slash-commands`. It keeps the user's setup under LC2, gets `hope`, `hunch` and `hold` (LC5), and appends the user's global `CLAUDE.md` to its Brief (`lc4_a_scout_launches_with_read_tools_and_the_users_setup`). It takes the Subagent's Model and Effort (A36); no Project setting is added. `scout` is absent from an old caller's JSON and false; a user's spawn that sets it is `INVALID_PARAMS`.

**LC5 every child has hope, hunch and hold, and the user's global instructions.** Given `rail.startDoor` or `agent.spawn` (with or without `scout`), then roundup's `hope`, `hunch` and `hold` (Q11) are passed with `--plugin-dir`. The exception is a plugin of the same name that the user's `enabledPlugins` already enables: the user's install loads and the bundled copy is not passed. The user's global `CLAUDE.md` is appended to the Brief file at launch as read-only text under a heading. A worker also has every tool and no `--disable-slash-commands`, and Claude Code lists Project skills from `.claude/skills` (`lc5_every_child_gets_the_plugins_and_global_instructions`, `lc5_a_users_installed_plugin_replaces_its_bundled_copy`).

**LC6 an agent the user starts keeps the user's full setup.** Given an Agent that the user starts from the Rail or a Terminal (`agent.spawn` with no `parent`, and a Terminal's own program), then none of `--setting-sources`, `--strict-mcp-config`, `--disable-slash-commands` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` is set, and no `--tools` list. roundup's `--settings` hooks and `--mcp-config` stay, so Status and the tools work (`lc6_a_user_started_agent_keeps_the_users_setup`).

**LC7 the Door names extras when it starts a child.** Given `agent_spawn` (F3) with `extras: {skills?, plugins?, mcp?}` each a list of names, then `crates/rupd` checks each name against what exists: a skill in the Project's `.claude/skills` or the user's skills folder, a plugin in the user's installed plugins, an MCP server in the user's configuration. A name that exists is added to the child's start (a skill listed, the plugin as `--plugin-dir`, the server in the `--mcp-config` file); any unknown name fails the call with `INVALID_PARAMS` naming each unknown one and its kind, and nothing starts (`lc7_a_known_extra_joins_the_start`, `lc7_an_unknown_extra_fails_the_start_and_is_named`). The tool `agent_extras` returns the available names by kind on demand; no name list is in the Door's Brief, settings, `tools/list` or start text (`lc7_the_extras_are_in_no_start_text`; the E9 same-bytes test holds).

**LC8 a missing extra relaunches with `--resume`.** Given a running child and `agent_extras_add {id, extras}` (LC7's shape) from its Door or parent, then the Agent is stopped and relaunched as A35 relaunches, with `--resume <conversation>`, its LC1 row plus the new extras and `--system-prompt-snapshot off`, so that a changed Brief applies; an unknown name is `INVALID_PARAMS` as in LC7 and the child keeps running. Any other `--resume` of a roundup child keeps the snapshot default (`lc8_a_missing_extra_relaunches_with_resume_and_snapshot_off`, `lc8_an_unknown_extra_leaves_the_child_running`).

**LC9 the profile holds in the real TUI.** Given the real Brief and `crates/rup/tests/` real-Claude observers, then once, in the implementing PR, the Door's and a worker's first-request token counts are recorded, and Claude Code's init event lists the tools of the LC1 row with the user's skills, plugins and servers plus roundup's. The two numbers go in the PR body as a measurement; there is no ongoing budget test (policy, by the user's choice). E2962 retires the recurring `lc9_the_profile_holds_in_the_real_tui` observer, including its tool-list and relative-size assertions; the implementing-PR measurement remains one-time policy.

**LC10 the forbidden switches.** Given any launch, then no argv holds `--bare`, `--safe-mode` or `--agent`: `--bare` fails a Max login, `--safe-mode` stops `--settings` hooks and `--agent` makes ToolSearch unusable (`lc10_no_launch_uses_bare_safe_mode_or_agent`). The note in `launch.rs` "No `--strict-mcp-config`: the Agent keeps the user's own servers." is deleted by the build, since LC2 keeps the user's servers (policy).

**LC11 the Door runs nothing and the Brief offers two children.** Folded from #2422. Given `rail.startDoor`, then the recorded start's `--tools` and roundup's added `permissions.allow` rules hold no shell or Terminal-start tool: no `Bash`, `PowerShell`, `terminal_spawn`, `terminal_open` or `terminal_write`, with or without MCP (M2219) (`lc11_the_doors_start_allows_no_shell_or_terminal_start`). User-authored permission rules are preserved under A3507b; carrying a rule grants no absent built-in tool and bypasses no MCP authorization. The Door's Brief names, for each ask, two choices: a standing specialist child or a new job-sized child, and draws no fixed line between them; the Brief text holds the tokens `standing specialist` and `job-sized` (`lc11_the_brief_names_a_standing_specialist_and_a_job_sized_child`). Which one the Door picks is its judgment and no test pins it (policy).

**LC12 a standing specialist stays alive per Workstream.** Folded from #2423; supports B20 and A32. A standing specialist is a scout (LC4) the Door keeps for one kind of reading, for example a repo scout for all GitHub and git reading; the Daemon keeps at most one live per Workstream and specialist name. Given a Door that calls `agent_spawn` with `scout: true` and `specialist: "<name>"` and a second call with the same name in the same Workstream while the first child lives, then the second returns the first child's id and starts nothing; the call with a different name, or in another Workstream, starts a child (`lc12_two_lookups_give_one_child_start`, on the real Daemon with the fake `claude`, counting starts in the recorded start log). When the child has ended, the same name starts a new one (`lc12_an_ended_specialist_is_started_again`). The Brief names `specialist` as the way to ask for one (`lc12_the_brief_names_the_specialist_field`). Contract change (rule 4): `SpawnParams` gains `specialist: Option<String>`, valid with `scout: true` only, else `INVALID_PARAMS` and no child starts (`lc12_a_specialist_requires_scout`).

**LC13 a specialist at 160k tokens is replaced with a handoff; a job-sized child fits under 160k.** Folded from #2424; supports B22 and A32. The Daemon reads a child's context size as the sum of `input_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` of the last `usage` in its Claude transcript, at each `Stop` Signal. Given a specialist (LC12) whose size crosses 160 000 at a `Stop`, then the Daemon sends it one Message asking for a summary of at most 600 bytes (B49's limit), and when the summary arrives stops it and starts one replacement of the same name, whose first input holds that summary under the heading `Handoff from the previous specialist`. Replayed counts of 90 000, 150 000 and 161 000 give one replacement, at the third; a count that stays under 160 000 gives none; a replacement whose first `Stop` reports 161 000 again is replaced once more only after a new summary (`lc13_a_specialist_crossing_160k_is_replaced_once_with_the_summary`, `lc13_under_160k_makes_no_replacement`). While that summary is pending, repeated `Stop` Signals reporting 161 000 send no additional summary request and start no replacement; after the summary arrives, those Signals still produce only one replacement (`lc13_repeated_stops_wait_for_one_handoff`). A job-sized child reporting 161 000 at a `Stop` gets no summary request or replacement (`lc13_a_job_sized_child_is_not_replaced`): the Brief tells the Door to give it a whole job that finishes under 160k tokens and to expect its summary at the end (B49); its size judgment is not tested, only the Brief tokens `160k` and `whole job` (`lc13_the_brief_sizes_a_job_under_160k`).

Observer: argv and environment tests against the fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4) in `crates/agents/tests/launch.rs`, the recorded start read as in `a4_the_argv_runs_claude_with_a_per_agent_settings_file`; LC7 and LC8 through `crates/rupd`'s fake-Claude fixtures; LC9 by the one-time implementing-PR measurement (its recurring observer is retired under E2962). Existing tests that expect the old argv change in the same PR (`a4_the_argv_runs_claude_with_a_per_agent_settings_file`).

**LC14 the Door runs `hope:intent` on each new ask, from its Brief.** Given `rail.startDoor`, then the Door's Brief file holds the standing instruction: on each new ask from the user, run the `hope:intent` skill first and act on the work order it produces. The instruction travels in the Brief (`--append-system-prompt-file`) only: nothing is typed into the Door's Terminal for it and it costs no turn. The Door's `--tools` list holds `Skill` and its `--plugin-dir` list holds roundup's pinned `hope`, `hunch` and `hold` (Q11, LC5), and `hope` holds `skills/intent`. A scout and a worker get the same plugins but no such instruction, and an Agent the user starts keeps their own setup (LC6) and no instruction. A bundle without `hope`'s `intent` skill never fails the start: the Door starts without `hope` and without the instruction, and shows one line in Claude Code's status line for the whole session, `roundup: hope's intent skill is missing; this Door runs without it.`, set in its `--settings` file. A worker's start is unchanged (`lc14_a_door_without_the_intent_skill_starts_and_says_so`; the other proofs are `lc5_every_child_gets_the_plugins_and_global_instructions`). The bundle is `hope` 13.1.0. When the user's own enabled `hope` replaces the bundled one (LC5), the intent check reads the user's `hope`.

**LC16 every Agent the user can type into offers the `/` menu a plain `claude` offers.** Given an Agent of any Role (Door, scout, worker, or an Agent the user starts) in a Project with a user command under `~/.claude/commands` and a Project command under `.claude/commands`, then Claude Code's `/` menu lists the built-in commands, those two commands and the user's skills and plugins, as a plain `claude` in the same folder lists them. Measured on the installed `claude` 2.1.296 (`stream-json` init `slash_commands`, one user command and one Project command): a plain start lists 53 and both commands; `--disable-slash-commands` lists 0 (no commands, no skills); `--setting-sources ""` lists 51 and neither command; `--setting-sources user` lists the user command only; `--strict-mcp-config` and `--tools Read,Grep` hide nothing (53, both commands). So no argv of any Role holds `--disable-slash-commands`, and none holds `--setting-sources` with an empty value; a lean Role keeps `--tools`, which hides no command. LC2 keeps every user key, so the user's plugins and servers list too. This supersedes the scout's Skills "off" in LC1 and the `--disable-slash-commands` of LC4, and LC1's table keeps `--tools` as the scout's boundary: a scout with the `/` menu still has only `Read,Grep,Glob,Bash,ToolSearch,AskUserQuestion` to run. Tests, in `crates/agents/tests/launch/lean.rs` against the fake `claude`: `lc16_no_role_hides_slash_commands` (one argv per Role, from the production profile table so a new Role is checked too: none holds `--disable-slash-commands` or an empty `--setting-sources` value); `lc1_each_role_launches_as_its_row` and `lc4_a_scout_launches_with_read_tools_and_no_user_instructions` change in the same PR. Observer: a one-time headless run of the installed `claude` with each Role's recorded argv, its init `slash_commands` equal to a plain start's in the same folder except the five exclusions, the list in the implementing PR's body (policy; no Mac window needed, and no recurring real-Claude test under E2962).

**LC17 a lean child reads each `CLAUDE.md` only as LC1 lists it.** Given a Door or scout (LC1) started in a Project whose folder holds a `CLAUDE.md`, with a `~/.claude/CLAUDE.md` present, and no `--setting-sources` (LC16), then the child's context holds the Project `CLAUDE.md` text exactly once, in the Brief's `The Project's instructions` section, and the user's global `CLAUDE.md` text exactly once, appended under LC5's heading. A worker holds both once the same way. A user-started Agent keeps Claude Code's own loading (LC6). So a lean launch stops Claude Code from loading `CLAUDE.md` files by its own sources (the vendor's switch for that, such as `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, set in the child's environment only for the lean Roles; the build picks the mechanism by the observer below, and a user-started Agent's environment gets none). Tests, in `crates/agents/tests/launch/lean.rs` against the fake `claude`: `lc17_a_lean_child_loads_no_claude_md_by_itself` (one launch per lean Role from the production profile table, so a new Role is checked too: the environment or argv that stops the vendor's loading is set, and the Brief file holds the Project text once and the global text once) and `lc17_a_user_started_agent_leaves_claude_md_loading_alone` (none of that switch). `lc4_a_scout_launches_with_read_tools_and_no_user_instructions` also asserts the switch. Observer: a one-time headless `claude -p` run with each lean Role's recorded argv and environment in a folder with a `CLAUDE.md` and a fixture `CLAUDE_CONFIG_DIR` holding a global `CLAUDE.md`, each carrying a distinct token, asking the model to quote any instruction file it was given: the Project token and the global token each appear once for the Door and scout; the transcript goes in the implementing PR's body (policy; a run needs a logged-in `claude`, so a Mac observation, and no recurring real-Claude test under E2962).
