# Perf gate

Module: `crates/perf`, and the keystroke probe in `apps/desktop`. Ids: every `R` and `K` heading in the file.

`just perf` measures a fresh Daemon `runs` times (default 11) and compares the median of each metric with `crates/perf/budgets.json`. A metric fails when it is above its `limit` (rule 7's absolute budget), or above its OS's `baseline` by more than 10% plus the metric's `noise` allowance (R13 qualifies this). A metric with neither is reported only. On Linux two metrics (`cold_start_ms`, `rail_tree_10_p95_ms`) vary too much between identical runs for a 10% test and carry a limit only; on macOS `cold_start_ms` is stable and gated, and `ping_p95_ms` and `rail_tree_10_p95_ms` have no baseline: a gross tripwire, not rule 7's regression test (`docs/perf.md`). The result, the per-run values and each run's load average are written to `target/perf.json` and printed, so a noisy machine is visible. The keystroke-to-render budget is measured by `just perf-keystroke` in the real App's webview (K1 to K3, R11); its budget file is `crates/perf/keystroke-budgets.json`, separate because `just perf` fails on a budget it did not measure (R7). `hook_loop_ms` (H15, `scenarios/control.md`) is limit-only the same way, on every OS: it has no committed baseline at all, so it names no `max_load_per_cpu` either (R13's threshold only ever qualifies a baseline's regression test) and its `limit` alone must hold under whatever load the run sees.

**R1 within budget.** Given a baseline of 100 and no noise allowance, then a value of 109 passes and exactly 110 passes.

**R2 regression.** Given the same baseline, then a value of 111 fails as a regression from 100.

**R3 limit.** Given a limit of 300 and a baseline of 400 for the OS, then 350 fails as over the limit, whatever the baseline.

**R4 noise.** Given a baseline of 0.03 ms and a noise allowance of 0.3 ms, then 0.2 ms passes and 0.4 ms fails.

**R5 median.** Given the values `[9, 1000, 11]`, the median is 11; given `[1, 2, 3, 4]`, 2.5.

**R6 other platforms.** Given a baseline only for `linux`, then on `macos` only the limit applies.

**R7 no silent gate.** Given a budget for a metric the run did not measure, then the comparison is an error, not a pass.

**R13 load-aware comparison.** The 10% regression test compares a run with a baseline recorded on a quiet-enough machine; a busy machine moves latencies far more than 10% and moves memory not at all. Found: at load 7.5, `just perf` failed write-to-output by 0.001 ms with no regression, and under 8 busy loops latencies moved 2x to 8x while RSS did not.

Schema: a metric's entry in `crates/perf/budgets.json` may carry `max_load_per_cpu`, shaped like `baseline` (OS name to number):

```json
"write_to_output_p95_ms": { "limit": 16, "noise": 0.001,
  "baseline": { "linux": 0.066, "macos": 0.056 },
  "max_load_per_cpu": { "linux": 2.0, "macos": 0.45 } },
"rss_extra_mb": { "limit": 150, "noise": 0.05, "baseline": { "linux": 1.6, "macos": 3.14 } }
```

Given a metric with a `max_load_per_cpu` for this OS, when the run's load per cpu is above it, then that metric's regression test is skipped, its `limit` still applies, and the output says `not compared: load <x> per cpu, above <max>` for it. The run's load per cpu is the median of the per-run 1-minute load averages `just perf` already samples at the start of each run (`loads`), divided by the CPU count; it includes the load the earlier runs put on the machine themselves, as the baselines' did. A metric with a baseline but no `max_load_per_cpu` for this OS is always compared: absence is the rule, so the memory metric, `rss_extra_mb`, is exempt by leaving the field out, and a test over the committed budgets (R8) checks that every time metric with a baseline names a threshold for each OS it has a baseline for and that `rss_extra_mb` names none. Cold start is a time metric like the others and counts as latency now that it has a macOS baseline.

The thresholds are the highest per-cpu load each OS's baselines were recorded under, so a run no busier than the baseline is compared and a busier one is not. Linux is 2.0 (load 2 to 4 on 2 vCPUs, `docs/perf.md`); macOS is 0.45 (load 4 to 7 on 16 cores is 0.25 to 0.44, recorded in #95), which skips the false fail seen at 0.47. The margin over 0.44 is only 0.01 on purpose: a run busier than every baseline run is skipped by definition, and widening it to 0.5 would compare the 0.47 false fail again. A metric with no baseline for the OS, on macOS `ping_p95_ms` and `rail_tree_10_p95_ms`, has no regression test and so nothing to skip. R6's rule, that an OS without a baseline is held to the limit only, is unchanged. The Builder adds the fields to `budgets.json` once the baselines they sit beside are on main.

Output: whenever at least one regression test was skipped, the last line reads `skipped <n> regression tests: load <x> per cpu`, with `<x>` the load per cpu defined above, and `target/perf.json` has a `skipped` key holding one `{metric, load_per_cpu, max_load_per_cpu}` object per skipped metric (an empty list when none), which a test asserts. Skipping is not failing: a run in which every time metric was skipped still exits 0 if no limit was exceeded, but it can never read as a clean regression gate. A run with no load figures at all exits 2 naming that, as R10's missing-input errors do.

The PR that builds R13 also amends, in the same PR, AGENTS.md rule 7 and the "What is enforced" section of `docs/perf.md`, whose "a regression above 10% fails" becomes "...fails, except that a time metric's regression test is skipped, loudly, when the machine is busier than its baseline's load (R13)", on top of whatever wording #95 has put there by then.

**R8 the committed budgets.** Given `crates/perf/budgets.json`, then the limits are 300 ms cold start, 150 MB extra RSS and 16 ms write-to-output; every metric with a baseline has a regression ceiling within 15% of it; every metric without a baseline has a limit or, on macOS, none (`ping_p95_ms`, `rail_tree_10_p95_ms`); and the committed baselines are exactly those recorded (R8 pins each value, so deleting or doubling one fails).

**R9 boundaries.** A value exactly at a limit passes and the next representable value above it fails; the same holds for the regression ceiling, including 110.00000000000001 against a baseline of 100.

**R10 exit codes.** `perf` exits 2 when the budgets file or the `rupd` binary is missing, naming it.

**R14 binary paths.** `perf` resolves its `rupd` and `rup` paths to absolute before launching, because the launcher refuses a relative `rup` (`rup not found at target/release/rup`). Given no `--rupd` or `--rup`, then each is the current directory joined with its default (`target/release/rupd`, `target/release/rup`); given a relative `--rup bin/rup`, then it is the current directory joined with `bin/rup`; given an absolute path, then it is unchanged. The path is not required to exist, so R10 still names a missing `rupd`.

**R15 paced writes.** A Terminal refuses a write while 16 earlier ones are unread (`terminal <id> is not reading its input`), so `terminal_write_p95_ms` sends each `terminal.write` only after the `cat` Terminal's output event for the one before it. Given 1000 writes to a Terminal that refuses at 16 unread and echoes each write 1 ms later, then all 1000 are timed, at most one is ever unread, and no write's time includes its 1 ms echo wait: the metric is the `terminal.write` call alone.

**R16 Linux Builder regression observer.** `just perf` selects a measured Linux machine class before comparing baselines. The supported Builder classes are GitHub Actions' Ubuntu 24.04 x86_64 VMs with four online and available CPUs and unrestricted affinity, with exact CPU model `AMD EPYC 9V45 96-Core Processor`, `AMD EPYC 7763 64-Core Processor`, `AMD EPYC 9V74 80-Core Processor` or `INTEL(R) XEON(R) PLATINUM 8573C`. Each CPU model is a distinct class with its own measured baseline and provenance; the two-vCPU boxd VM remains a fifth class. Builder selection requires exact OS identity (`ID=ubuntu`, `VERSION_ID=24.04`), architecture (`x86_64`), CPU model, online CPU set (`0-3`), available CPU count (4) and affinity (`Cpus_allowed_list: 0-3`). The release build and login-shell workload remain those used by `just perf`; kernel, toolchain and shell are recorded for diagnosis rather than treated as CPU identity. CPU affinity does not turn any class into another. Ownership stays in `crates/perf/`, `docs/perf.md` and this file.

Checks on main: rule 7's absolute budgets and regression rule (`AGENTS.md:30`); R8's pinned limits and baselines (`scenarios/perf.md:40`); R13's load qualification and loud skipping (`scenarios/perf.md:32`, `scenarios/perf.md:36`); R10's missing-input exit (`scenarios/perf.md:44`). R16 qualifies Linux baseline selection; R1–R15, macOS selection and the real App's keystroke observer keep their existing behavior.

Observer: release `just perf` on each newly measured supported Linux Builder class, plus the tests below. The implementation commits its measurement evidence under `crates/perf/` and gives the exact commands and reference commits in `docs/perf.md`; tests alone cannot complete the observer. Specification policy: the Intel identity amendment uses `Refs #1303` and closes #1303 only when its specification acceptance holds; the 9V74 identity amendment uses `Refs #1313` and closes #1313 only when its specification acceptance holds; #1251 remains open for implementation and all retained measurements. Supporting an identity supplies no baseline and proves no absence of a Daemon or probe regression.

- Given any supported Builder machine and a measured baseline for its exact class, when `just perf` runs without extra selection flags, then it selects that class's baseline, never the boxd baseline or another Builder CPU model's baseline. The printed output and `target/perf.json` identify the selected class and baseline reference, OS and distribution version, architecture, CPU model, online and available CPU counts, affinity, kernel, release toolchain/build settings, shell, and binary hashes. `r16_builder_selects_its_measured_class` asserts selection and report metadata for all four exact CPU identities and rejects reuse of another class’s baseline or provenance; `r16_affinity_does_not_reclassify_the_host` asserts that narrowing four CPUs to two cannot select boxd.
- Given a Linux baseline configured for a machine class, when the observed machine does not match any measured class or required class metadata is absent, then the observer exits 2 naming the mismatch or missing input, rather than silently comparing across classes or reporting a clean pass. `r16_unknown_or_incomplete_linux_class_is_an_observer_error` asserts this, including a supported identity with no measured baseline, missing baseline provenance, and CPU model strings differing from any exact supported identity. R6 still holds for an OS with no configured baseline; it is not a fallback for an unrecognized Linux class.
- Given a selected class and its baseline, then values exactly at `baseline * 1.10 + noise` pass and the next representable values above fail with exit 1, including RSS at high load. Every absolute limit still applies to every measured class. `r16_selected_class_keeps_regression_and_limit_edges` asserts each baseline's boundary and the 300 ms, 150 MB and 16 ms limits; `r16_memory_is_compared_at_any_load` asserts a memory regression cannot be skipped. R13 latency skips retain their per-metric reason, JSON entries and final summary; `r16_load_skip_is_not_a_clean_observation` asserts that a skipped run cannot satisfy R16's completion evidence even when its R13 exit code is 0.

Baseline establishment and diagnosis (policy, reviewed against committed reports): every step below applies independently to each newly measured class. Boxd, AMD 9V45, AMD 7763, AMD 9V74 and Intel 8573C keep separate baselines and provenance. AMD measurements establish no Intel baseline, and neither boxd nor 7763 observations establish a 9V45 baseline; no other class can establish a 9V74 baseline or supply its provenance. The same-host diagnosis, nine alternating eleven-Daemon invocations per reference, nine clean calibration invocations and three separate clean implementation observations below apply independently to 9V74; identical OS and CPU counts do not make different CPU models interchangeable.

1. Identify the commit that supplied the original Linux baseline from repository history, and the unchanged main reference used to reproduce the reported misses. Record both full commit ids and the perf measurement/build changes between them. Build each revision's `rupd` and `rup` in release mode with the same toolchain and build settings, measure both with the same probe and workload, and record binary hashes. Changes to the probe are isolated from changes to the Daemon by measuring the same binaries with the old and new probes. A build or protocol incompatibility is recorded as a failed observation and repaired or given a scoped prerequisite; it is not evidence of a machine mismatch.
2. On each newly measured supported Builder class, collect nine invocations of eleven fresh Daemons per reference, alternating the references on the same VM. Retain every report, per-run metric and load, exit code and machine metadata. Use invocations at or below the existing Linux R13 load threshold (2.0 per CPU); retain busy invocations with their skip reasons and repeat them, never count them as clean observations. No report or metric is discarded solely because it misses a ceiling. RSS is always compared.
3. Compare the historical and current references on that same class using the existing 10% plus noise ceilings. An increase above a ceiling in three clean paired invocations is a Daemon or probe regression to investigate and repair before accepting new baselines. If the historical reference itself misses the boxd ceilings on the Builder class while every clean current invocation stays within `historical median * 1.10 + existing noise`, the evidence supports a class mismatch. Record the conclusion per failing metric; a memory mismatch alone does not settle latency, and a class mismatch does not excuse a simultaneous regression. If results do not settle the cause, continue observation or file a scoped prerequisite; do not raise baselines to make them pass. User settlement for `rail_tree_40_p95_ms` only (2026-10-13): asked "Should the loop accept 0.71 ms as the new Rail reply baseline?", the user answered "q1: yes". After the repairs in #1368, #1373, #1375 and #1476, the remaining increase is the measured cost of Rail rows carrying 17 fields instead of 8: the 40-row reply grew from 5,285 to 11,045 bytes ([#1374](https://github.com/saadshahd/roundup/issues/1374#issuecomment-6136937092)). Step 3's historical comparison no longer blocks this metric; each class's Rail-40 baseline comes from step 4 on the repaired reference, never from a value measured on another class. `ping_p95_ms`, `terminal_write_p95_ms` and `write_to_output_p95_ms` keep step 3 in full.
4. Only after that diagnosis, establish the Builder class's baseline from the median of nine clean invocation medians of the repaired reference, preserving the existing noise allowances and 10% rule. All nine must fit their resulting ceilings. If that repeatability check fails, repair the measurement or runner isolation and repeat; do not remove a metric, increase noise, widen the load threshold or substitute an absolute-only gate. Retain the original boxd values and provenance under their own class, and keep each Builder class’s values and provenance separate. Update R8's asserting tests in the same implementation PR to pin every class's values, provenance and load thresholds; `r16_class_baselines_have_pinned_provenance` asserts that missing, added, removed or changed pins fail. Do not derive a baseline from the candidate being judged, auto-update it during `just perf`, or rescale it from CPU count.
5. With the baseline fixed, run three further clean `just perf` invocations of eleven Daemons on the implementation head on the supported Builder class. Each must exit 0, compare all five Linux baseline metrics, carry an empty `skipped` list and meet every absolute limit. Commit the reports and exact reproduction commands separately from the nine calibration invocations. Demonstrate a genuine regression with a fixture for every selected-class baseline metric above its ceiling, while below any absolute limit: `r16_each_class_metric_can_fail_as_a_regression` asserts exit 1 and a regression naming that metric and selected baseline. A fixture cannot replace the three real observations.

## Keystroke-to-render in the App (`apps/desktop`, run by `crates/perf`)

**K1 opt-in.** Given a normal build, then its bundle holds no trace of the keystroke probe (the string `roundup-keystroke-probe` is absent). A build made with `VITE_ROUNDUP_PERF` carries it. The probe is chosen when the bundle is built, so a normal run pays nothing and no query or flag can switch it on.

**K2 a sample.** The time of a key is from its `keydown` to the first render after the emulator has parsed the typed character itself as output. A render before that echo does not count, and neither does other output of the program. A key whose echo is not rendered within 500 ms is dropped and counted. The first 100 keys are discarded; the rest give `n`, `dropped`, p50, p95, p99 and max by nearest rank.

**K3 the run.** Given the App built with the probe on a Project, when the webview mounts, it presses `+ Workstream` (U191), then `⌘T` (U165), waits for the program's `ready` line in the focused bubble (the Door that U191 starts is not expected to run under the perf `SHELL` and K3 neither waits for it nor reads it), then types 1000 keys one at a time, 20 to 40 ms apart, and writes one line `PERF <json>` through that Terminal. The JSON carries the K2 numbers, the renderer used (`webgl` or `dom`), the mean frame time, the timer resolution (1 ms in WKWebView), the pixel ratio and the user agent. A failure in any step is written as `{"error": ...}` the same way. Its observer is the real run (`just perf-keystroke`), not a test: the webview is the thing under test and no fake has one.

**R11 what the runner accepts.** `perf-keystroke` starts the App with `SHELL` set to a script that makes its tty raw, prints `ready` and runs `cat`, reads the `PERF` line from `terminal.output` on the Daemon's socket, and refuses (exit 2) a report that proves nothing: the webview's own error, a mean frame time above 25 ms (the window was covered or napped; the perf build's window is always on top and on every Space so that it is not), or more than 5% of keys dropped. Otherwise `keystroke_p95_ms` (median over `--runs`, default 3) is compared with `keystroke-budgets.json`: limit 16 ms.

**R12 the window needs a yes.** `perf-keystroke` and `just perf-keystroke` open a window over the user's screen, kept on top for about 40 s per run, and type into it. Without `ROUNDUP_ALLOW_WINDOW=1` in the environment they print why and exit 2 before building, starting or opening anything. The variable is set only by someone the user asked to run it; no agent, Reviewer, CI job, boxd VM or `just check` sets it.
