# One database per Project

Module: store opens and migrations in `crates/agents`, `crates/todos`, `crates/pads`, `crates/provenance`, `crates/messages`, `crates/checkpoints`; storage wiring and removal in `crates/rupd`. Terms: Project data, Daemon, Workstream, Todo, Pad, Touch (`GLOSSARY.md`). Specification for #1642; implementation remains open in #1929, blocked by #1642. No RPC or App seam change, no Message delivery change; M1–M10 remain unchanged. `crates/agents/src/lib.rs` changes only for store wiring. Pad files, launch files, Git objects and Worktrees remain outside SQLite.

## Baseline and decision

Policy: the implementation records its fetched main SHA and measures before editing. At `ea24f557`, seven production databases open per Project: `agents.db` (`crates/agents/src/store.rs`, `Agents::open_in`), `todos.db` (`crates/todos/src/lib.rs`, `Todos::open`), `pads.db` (`crates/pads/src/lib.rs`, `Pads::open`), `provenance.db` and `digest.db` (`crates/rupd/src/lib.rs`, `Daemon::open_with_proof`), `messages.db` (`crates/messages/src/lib.rs`, `Messages::open_with`) and `checkpoints.db` (`crates/checkpoints/src/lib.rs`, `Checkpoints::open`). Count SQLite main files separately from WAL/SHM companions. `touches.db` is a test filename, not an eighth production store.

The implementation PR inventories every cross-file consistency mechanism and lock use, with file and function references: `Daemon::storage_calls`, its initialization and Todo/Pad read acquisition in `Daemon::route`, the write acquisition and attachment list in `Daemon::remove_workstream` (`crates/rupd/src/removal.rs`), attachment forwarding and deferred publication in `crates/agents/src/removal.rs`, `Rail::remove_workstream`'s ATTACH/DETACH and transaction in `crates/agents/src/rail.rs`, and the qualified removal SQL in `crates/todos/src/store.rs` and `crates/pads/src/store.rs`. Include Todo history's Provenance read during open, and distinguish file rollback guards from database coordination. Search for additional mechanisms at the recorded SHA rather than treating this list as exhaustive (policy).

Consolidate when all database attachment coordination and the storage-call lock can be replaced by one Project-local SQLite transaction. Otherwise publish the inventory, the exact mechanism a single database cannot replace, and a reproducible failing probe; close the implementation only with that measurement, without claiming N16–N19 pass (policy). SQLite cannot transact Pad files, Git or Terminal effects: preserving A34's existing staging/rollback is required, not a reason to reject database consolidation.

Reuse (policy): use existing [rusqlite transactions](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html) and the adopted [rusqlite_migration](https://docs.rs/rusqlite_migration/latest/rusqlite_migration/) versioned SQL. [refinery](https://docs.rs/refinery/latest/refinery/) is the alternative migration library; switching requires a concrete capability missing from the installed library. The implementation records current release evidence and rule 9's two-candidate comparison before adding machinery. No custom transaction or migration engine.

**N16 one live database holds all concerns.** Given a new Project, when its Daemon opens and each store writes and reopens, then all seven concerns' application tables live in one `project.db` under N1's data directory, with one migration sequence and no table-name collision; all store reads return the written values (`n16_all_stores_share_one_project_database`). Multiple connections are allowed; no connection, transaction or write lock is shared across Projects. The test enumerates actual database paths and persisted tables, including Digest state and Checkpoints, rather than checking only path constants (`n16_all_stores_share_one_project_database`). Fresh Projects create one main database instead of seven; WAL/SHM are companions (policy). Store callers change together. N9–N11 are retired; N20 governs pre-release schema cleanup (policy).

**N17 old per-store databases never block startup.** Given a data folder that still holds per-store databases from before `project.db` (an `agents.db` in a column order no current build writes, a `todos.db` that is not a database), when the Project opens, then it opens with a fresh `project.db` that holds none of their rows, and the old files are left byte for byte as they were (`n17_old_store_files_never_block_the_open`). Nothing imports them: roundup has not shipped release 0, so no local data has to survive an upgrade (owner direction: "haven't even did release 0 yet"; data does not matter at this stage). N3 still moves legacy `.roundup/` data before this open; its copy-conflict and Worktree guarantees remain (policy).

**N18 removal commits across concerns once.** Given A34's mixed removed/kept Agents, Todos and Pads, when removal succeeds, then Rail, Todo, blocker, Pad metadata and removal Touch changes commit in one transaction in `project.db`, without attached databases; observers receive removal events only after commit (`n18_removal_commits_all_concerns_once`). Inject a SQL failure after earlier concern writes and before commit: persisted rows and Touches remain unchanged, no success events escape, staged files are restored, and retry produces the A34 result exactly once (`n18_failed_removal_rolls_back_all_concerns`). Killing the Daemon before and after SQLite commit leaves database rows entirely before or entirely after removal on reopen (`n18_removal_commit_survives_restart`). Preserve A34's external-effect guarantees and tests; do not claim SQLite makes Git, Pad files or Terminals transactional (policy). Delete `storage_calls` and removal-only ATTACH/DETACH/qualified schema coordination; retain necessary file rollback and deferred publication (policy).

**N19 removal does not stop unrelated calls.** Given two Projects with independent Daemons, when Project A's removal is paused at an acknowledged pre-transaction Door-stop gate, then Project B's Todo write completes and reads back before that gate is released (`n19_other_project_writes_during_removal`). Given two Workstreams in one Project, the same pause permits a Todo write in the other Workstream to complete before release (`n19_same_project_writes_while_door_stops`). Use deterministic gate-entry/release acknowledgements and a bounded completion timeout, not sleeps or elapsed-time comparisons. The same-Project test must fail with main's `storage_calls` exclusion restored. Contention during an actual SQLite write transaction is permitted; holding a database writer or replacement storage-call mutex while awaiting Door stop is not (policy).

## Pre-release storage cleanup

**N20 current schemas need no pre-release adoption.** Given a fresh Project, when every store writes and the Daemon reopens the current `project.db`, then its written values remain readable (`n16_all_stores_share_one_project_database`, retained in `crates/rupd/src/storage.rs`). Given a fresh standalone or in-memory store used by current callers, when it writes and reopens where persistence applies, then its current schema supports the same store operations (`n20_current_store_opens`, parameterized over Agents, Todos, Pads, Provenance, Messages, Digest and Checkpoints; no historical-schema fixtures).

Policy: until release 0, no local application data needs to survive an upgrade. Delete each store's pre-release schema adoption: bootstrap hooks, historical table/column probes and transformations, adoption-only SQL, baseline fixtures and their unused support. Keep current-schema creation for live standalone/in-memory callers and the shared Project database; use the installed migration library without adding a replacement migration engine. This does not request automatic deletion, repair or import of an old `project.db`; no outcome for opening an obsolete schema is promised. This policy also retires the historical-schema upgrade clauses of T8, T10, T12, T15, P12, B8 and B29, and P14’s “From before” binding recovery; their current-schema behaviours remain required. N14’s Marks content-format compatibility is unchanged; it is not schema adoption.

Policy: delete the Pads `scribes` recovery end to end: `Store::take_old_bindings` in `crates/pads/src/store.rs`, its Pads wrapper, the Daemon's `old_bound` state, initialization and calls, and `crates/rupd/src/old_bindings.rs`. Remove tests and fixtures proving only that recovery or retired N9–N11 guarantees. A test that also proves current behaviour keeps that assertion under its live scenario; do not delete current startup recovery such as stale Terminal cleanup. N9's versioned-SQL requirement, N10's adoption/idempotence/invalid-old-schema preservation requirements and N11's historical migration rollback requirement are retired, including their incorporation above.

## Message sender name storage

**N2705a last observed sender names persist in the Project schema.** Specification for #2735, the Project-schema prerequisite for #2705's B2705a in `scenarios/messages.md`. Implementation owns only `crates/rupd/**`: one added SQL migration under `crates/rupd/migrations/project/` and applied-schema behaviour tests in the existing `crates/rupd/src/storage.rs` test module (policy).

- **Fresh creation.** Given an empty Project data directory, when `storage::open` applies the production migration sequence, then `message_sender_names` is empty and inserting `('7013', 'sad')` permits reading `sad` by the `agent` key (`n2705a_a_fresh_project_stores_a_sender_name`).
- **Schema constraints.** The table has `agent TEXT PRIMARY KEY NOT NULL` and `name TEXT NOT NULL` (policy). Given the applied Project schema, when inserts attempt a null identity, a null name or a duplicate identity, then each is rejected by SQLite (`n2705a_sender_names_reject_nulls_and_duplicate_identities`, parameterized over those constraint violations).
- **Durable identity.** Given `('7013', 'sad')`, when that identity's name is updated to `glad` and another identity `7014` is inserted with name `glad`, then closing every connection and reopening through `storage::open` preserves exactly one row for `7013` with name `glad` and a distinct row for `7014` with name `glad` (`n2705a_updated_names_survive_project_reopen`). Equal names do not merge identities (policy).
- **Added migration.** Given a file-backed Project database initialized by the production migration sequence through the version immediately preceding the new migration, holding an existing Message and Route, when the full current sequence is applied through `storage::open`, then the new table exists and is empty, and all column values of the existing Message and Route are unchanged. After inserting `('7013', 'sad')`, closing every connection and reopening the current schema through `storage::open`, that name and the unchanged Message and Route remain readable (`n2705a_an_added_migration_preserves_messages_and_routes`). Build the fixture with the installed `rusqlite_migration` sequence, not a copied historical schema (policy).

Policy: use installed `rusqlite` and `rusqlite_migration`; add no store, migration engine or database. N21's discovered SQL file is the migration: do not edit the frozen ten-migration head or register this file in Rust. The existing N16 schema assertion may account for the new Project-only table without weakening its single-database or persisted-store assertions. This scenario requires preservation across this added migration only; it does not restore N20's retired pre-release adoption guarantees.

Policy: `agent` is a machine identity used only as a storage key. Do not derive names from historical Message bodies or invent names for absent Agents. #2705 owns observing Rail names, writing them, delivery rendering, standalone Messages migration registration and digest/Route error changes. This schema prerequisite changes no Message delivery or M1–M10 law and does not complete B2705a or close #2705.
