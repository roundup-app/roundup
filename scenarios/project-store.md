# One database per Project

Module: store opens and migrations in `crates/agents`, `crates/todos`, `crates/pads`, `crates/provenance`, `crates/messages`, `crates/checkpoints`; storage wiring and removal in `crates/rupd`. Terms: Project data, Daemon, Workstream, Todo, Pad, Touch (`GLOSSARY.md`). Specification for #1642; implementation remains open in #1929, blocked by #1642. No RPC or App seam change, no Message delivery change; M1–M10 remain unchanged. `crates/agents/src/lib.rs` changes only for store wiring. Pad files, launch files, Git objects and Worktrees remain outside SQLite.

## Baseline and decision

Policy: the implementation records its fetched main SHA and measures before editing. At `ea24f557`, seven production databases open per Project: `agents.db` (`crates/agents/src/store.rs`, `Agents::open_in`), `todos.db` (`crates/todos/src/lib.rs`, `Todos::open`), `pads.db` (`crates/pads/src/lib.rs`, `Pads::open`), `provenance.db` and `digest.db` (`crates/rupd/src/lib.rs`, `Daemon::open_with_proof`), `messages.db` (`crates/messages/src/lib.rs`, `Messages::open_with`) and `checkpoints.db` (`crates/checkpoints/src/lib.rs`, `Checkpoints::open`). Count SQLite main files separately from WAL/SHM companions. `touches.db` is a test filename, not an eighth production store.

The implementation PR inventories every cross-file consistency mechanism and lock use, with file and function references: `Daemon::storage_calls`, its initialization and Todo/Pad read acquisition in `Daemon::route`, the write acquisition and attachment list in `Daemon::remove_workstream` (`crates/rupd/src/removal.rs`), attachment forwarding and deferred publication in `crates/agents/src/removal.rs`, `Rail::remove_workstream`'s ATTACH/DETACH and transaction in `crates/agents/src/rail.rs`, and the qualified removal SQL in `crates/todos/src/store.rs` and `crates/pads/src/store.rs`. Include Todo history's Provenance read during open, and distinguish file rollback guards from database coordination. Search for additional mechanisms at the recorded SHA rather than treating this list as exhaustive (policy).

Consolidate when all database attachment coordination and the storage-call lock can be replaced by one Project-local SQLite transaction. Otherwise publish the inventory, the exact mechanism a single database cannot replace, and a reproducible failing probe; close the implementation only with that measurement, without claiming N16–N19 pass (policy). SQLite cannot transact Pad files, Git or Terminal effects: preserving A34's existing staging/rollback is required, not a reason to reject database consolidation.

Reuse (policy): use existing [rusqlite transactions](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html) and the adopted [rusqlite_migration](https://docs.rs/rusqlite_migration/latest/rusqlite_migration/) versioned SQL. [refinery](https://docs.rs/refinery/latest/refinery/) is the alternative migration library; switching requires a concrete capability missing from the installed library. The implementation records current release evidence and rule 9's two-candidate comparison before adding machinery. No custom transaction or migration engine.

**N16 one live database holds all concerns.** Given a new Project, when its Daemon opens and each store writes and reopens, then all seven concerns' application tables live in one `project.db` under N1's data directory, with one migration sequence and no table-name collision; all store reads return the written values (`n16_all_stores_share_one_project_database`). Multiple connections are allowed; no connection, transaction or write lock is shared across Projects. The test enumerates actual database paths and persisted tables, including Digest state and Checkpoints, rather than checking only path constants (`n16_all_stores_share_one_project_database`). Fresh Projects create one main database instead of seven; WAL/SHM are companions (policy). Store callers change together; N9–N11's migration guarantees continue for the consolidated schema (policy).

**N17 old per-store databases never block startup.** Given a data folder that still holds per-store databases from before `project.db` (an `agents.db` in a column order no current build writes, a `todos.db` that is not a database), when the Project opens, then it opens with a fresh `project.db` that holds none of their rows, and the old files are left byte for byte as they were (`n17_old_store_files_never_block_the_open`). Nothing imports them: roundup has not shipped release 0, so no local data has to survive an upgrade (owner direction: "haven't even did release 0 yet"; data does not matter at this stage). N3 still moves legacy `.roundup/` data before this open; its copy-conflict and Worktree guarantees remain (policy).

**N18 removal commits across concerns once.** Given A34's mixed removed/kept Agents, Todos and Pads, when removal succeeds, then Rail, Todo, blocker, Pad metadata and removal Touch changes commit in one transaction in `project.db`, without attached databases; observers receive removal events only after commit (`n18_removal_commits_all_concerns_once`). Inject a SQL failure after earlier concern writes and before commit: persisted rows and Touches remain unchanged, no success events escape, staged files are restored, and retry produces the A34 result exactly once (`n18_failed_removal_rolls_back_all_concerns`). Killing the Daemon before and after SQLite commit leaves database rows entirely before or entirely after removal on reopen (`n18_removal_commit_survives_restart`). Preserve A34's external-effect guarantees and tests; do not claim SQLite makes Git, Pad files or Terminals transactional (policy). Delete `storage_calls` and removal-only ATTACH/DETACH/qualified schema coordination; retain necessary file rollback and deferred publication (policy).

**N19 removal does not stop unrelated calls.** Given two Projects with independent Daemons, when Project A's removal is paused at an acknowledged pre-transaction Door-stop gate, then Project B's Todo write completes and reads back before that gate is released (`n19_other_project_writes_during_removal`). Given two Workstreams in one Project, the same pause permits a Todo write in the other Workstream to complete before release (`n19_same_project_writes_while_door_stops`). Use deterministic gate-entry/release acknowledgements and a bounded completion timeout, not sleeps or elapsed-time comparisons. The same-Project test must fail with main's `storage_calls` exclusion restored. Contention during an actual SQLite write transaction is permitted; holding a database writer or replacement storage-call mutex while awaiting Door stop is not (policy).
