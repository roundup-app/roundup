# Plain text

**Q5561 every Pad-writing Agent separates the reader's result from Agent details.** Extends Q6/Q7's Pad guidance. Given an ordinary Agent or Door, using MCP or the `rup` CLI, when its E1 Brief is prepared, then the Brief says: a Pad holds notes and depth, verdict first, for a reader who opened it from a link (Q12); put details needed only by Agents, including paths, commands, ids, logs and raw evidence, in one final folded section named `For Agents`, stored as `<details><summary>For Agents</summary>` with its Markdown content and closing `</details>`, without `open`. The instruction covers creating, rewriting and appending to a Pad (`pad_create`, `pad_write`, `pad_append` and `pad_appendSection`, or their CLI equivalents); subsequent edits keep Agent-only details inside the same trailing section rather than adding them after it. A fact the user needs to decide or act also goes in the message that points to the Pad; a Pad never carries it alone, and a path or command that is part of the action goes in the message too (policy: placement follows the reader's need, not a ban on those characters). U5561a–c are unchanged.

Planned `q5561_pad_guidance_reaches_each_writer` in `crates/agents/tests/launch/guidance.rs` reads prepared Briefs for both writing roles and both tool modes, asserting the reader-first/verdict-first instruction, exact `For Agents` name, trailing folded Markdown form, detail categories and update guidance in each. Assert delivered instructions, not a live Model's compliance or a duplicated source constant. Whether an Agent follows them is model behavior (policy), as for Q6. Preserve E9's role-shared bytes and P9's session-stable Brief; no per-Agent details enter the shared file. The read-only Scout gains no write tool or authority (policy).

Policy — U5561a–c in `scenarios/ui-item-view.md` own display, insertion, round-trip and public-tool observers. Q7's no-HTML-artifact rule remains: a details block in Pad Markdown is no HTML file or `open` action. Existing checks on `main` to retain:

1. Shared instruction delivery: `crates/agents/tests/launch/guidance.rs`, `q6_brief`.
2. Supported views and no HTML file: the same file, `q7_brief_names_each_view_and_its_place` and `q7_brief_forbids_html`.

Policy — P9/P10 gate: does this instruction vary the Brief within a session or by Agent identity? Observe prepared Brief byte equality through the existing E1/E9 tests; this is fixed guidance shared by each writing role. Scope: the Pad clauses above, `crates/agents/src/claude_code/brief.rs`, its launch-guidance tests, and U5561a–c's existing Pad/editor, read-only renderer and public-seam test owners. No loop, contract, glossary or unrelated renderer change is ordered. This specification delivers acceptance only and leaves implementation work open.

Module: `crates/agents` (the output-style setting and bundled plugin, under `claude_code/`, P4), `apps/desktop` (Drawer and Rail text). Terms: Brief, Work order, Digest, Message, Pad (`GLOSSARY.md`); `hold:Plain` is the output style `hold/output-styles/plain.md` of `saadshahd/moo.md`. Principles served: P3, P6. No contract change: a Work order holds only `ask` and `limits`; the Steer of O2 and the Drawer change. Reported in #676, #688 and #726. Ids: Q1–Q12.

**Q8 reduce drops no fact the reader needs.** Given a fixture of an Agent's long Message to `you` and its reduced form, then (a) the reduced text is shorter than the original in characters; (b) each fact of the fixture's fact list appears in the original and in the reduced text; (c) none of the fixture's padding phrases appears in the reduced text. The fixture is `crates/agents/tests/fixtures/reduce/door-question.md` (original), `door-question.reduced.md` (reduced) and `door-question.facts` (one fact per line, each a literal string the reader needs: a name, a number, a choice, a path). Its original is shaped like the Door's questions to `you` in #729: it opens "On it.", guesses "My guess is that this Workstream is for finishing that, but tell me if it's something else", introduces its list with "Separately:", and holds a list item of about 110 characters that restates the question above it. Its padding phrases are exactly those four. The reduced text keeps every question, each choice offered and each fact the answer needs, and drops what only repeats or fills. The comparison is a check on a stored pair, not a call to a model, so it is deterministic and costs no tokens. Tests: `q8_reduced_is_shorter`, `q8_every_fact_survives`, `q8_no_padding_phrase_survives`, and `q8_the_check_rejects_a_dropped_fact` (a copy of the reduced text with one fact removed fails (b)), so the check is shown able to fail. The pair is refreshed only with a human-read diff of the facts: policy.

**Q10 the App renders the Markdown an Agent writes.** Found by the user's report #726: a Door's question to `you` showed `**Driftech:**`, `` `story/` `` and `1. ` as typed. Narrows Q3; changes no contract, App seam command or Token. Not the text's length (#688, Q1). Given text of Q2 from an Agent, then every surface of Q2 renders its Markdown through one renderer, `renderMarkdown`, a library the App already ships or one that loads lazily (rule 7), never one renderer per surface:
- **Elements.** Bold, italics, ordered and unordered lists, inline code, code fences, links and tables become `strong`, `em`, `ol`, `ul`, `code`, `pre`, `a` and `table`; no `**`, backtick or list marker shows as a character. Asserted in `q10_markdown_becomes_elements`, which renders the body quoted in #726 in a surface of Q2 and finds in it a `strong`, a `code` and an `ol` of three `li`, no `**`, backtick or `1. ` text node.
- **Safe.** An Agent's HTML is shown as text and never runs or injects markup: a body holding `<img src=x onerror=alert(1)>` renders no `img` element and no `onerror` attribute, and a link whose target is `javascript:` has no `href`. Asserted in `q10_html_is_text`.
- **One renderer.** Each surface of Q2 that exists calls `renderMarkdown` and none draws a generated body as a raw string, except `OrderLine`, which is exempt: O6 and Q5 cut it to one line of plain text, so it renders no Markdown and shows no element. Asserted in `q10_one_renderer`, which renders the same body in each surface but `OrderLine` and finds equal markup for it.
- **Weight.** A heavy renderer is not in the entry bundle: cold start stays under 300 ms (rule 7, policy, checked by `just perf`).

**Q12 a Door message stands on its own.** Found by the user asking "show me" after a Door asked "matches?" or "start the build?" and left the facts in a Pad. Changes no contract, App seam command or Token. Given the Door's Brief (B24), then it says that every Door message the user reads: (a) holds each fact the user needs to follow it, and to answer it when it asks; (b) shows each choice as what the user would see or get (a sketch, a wireframe, rows), never a bare title; (c) puts each term the user has not used into plain words; (d) says what each answer starts. It may lean only on what the user and the Door already said to each other in this conversation, or on a place the user chose to read. A Pad, Todo, Issue, PR, child Terminal or link adds depth or is where the act happens; it never carries a fact the user needs. Both roles' Todo guidance follows: `todo_addRef` says to link a Todo to a Pad or one of its headings, and a Todo comment is where the user answers or acts, the message holding the same question. The Door's direction to a child's Terminal stays: the Terminal is where the act happens. The rule is fixed text per role (P9, P10): the Agent Brief holds none of it, and no Project key or per-Agent text enters the Brief.
