# UI: keyboard focus rings (U2770)

Module: `apps/desktop` (webview). Work Issue: #2770. Journey stages: Enter and Intervene (`.agents/data/journey.md`, heading “What must work”).

**U2770 pointer presses never draw focus rings.** Given the App with focusable controls, when the user changes input method, then ring drawing follows the last user input, including focus moved by code after that input:

- **Pointer.** A mouse or trackpad pointer press selects pointer mode. No focused control draws a ring in that mode, including the first focus on a fresh page, a click after keyboard focus, a clicked Shelf tab whose handler prevents default focus, and a dialog's first control focused by code after its opener is clicked. Terminal inputs focused after Add Workstream or New Terminal also draw no ring. Test: `u2770_pointer_and_keyboard_focus` (planned real-browser observer below).
- **Keyboard.** A key press selects keyboard mode, including Tab, arrows and shortcuts that move focus. Keyboard focus shows the shared ring, including after a pointer interaction and when focus is moved by code. macOS Full Keyboard Access also shows keyboard focus. Test: `u2770_pointer_and_keyboard_focus` for browser-delivered keys; native Full Keyboard Access is the Mac observation policy below.
- **Focus destinations.** Focus still lands on the same element as before this change; do not remove `.focus()` calls or `preventDefault` to hide a ring. Drawer, Bubble and Decision focus return remains as U40, U111, U113 and U2742 specify. The observer `u2770_pointer_and_keyboard_focus` asserts the active element at each interaction; retain those scenarios' independent interaction tests (policy).
- **Text fields.** Text carets and the existing Todo/Ask accent bars stay as U353 and U388 specify, subject to their later amendments (U433 retires the Pad Ask field). The design critic judges their unchanged appearance (policy); no retired field is recreated.

One source of input modality controls the shared ring in `apps/desktop/src/styles.css`. Component styles defer to it: migrate every per-component `:focus-visible` ring, the `flat-tab` `:focus:not(:focus-visible)` pair, and Tree/tree-library ring Tokens. Ark's per-control `data-focus-visible` is not an independent authority for drawing rings. Prefer the installed Ark/Zag modality support; the implementation PR's `Reuse:` section weighs `@zag-js/focus-visible`, `what-input`, then custom listeners only if both fail rule 9. Inventory every production `.focus(` call under `apps/desktop/src`, excluding tests and fixtures, and classify each as pointer-reachable or keyboard-only in the implementation PR, rather than assuming the Issue's historical count is current (policy).

## Browser observer

One behavior test, `u2770_pointer_and_keyboard_focus`, under `apps/desktop/src/testing/`, runs the rendered App through the existing real browser observer, not jsdom or a focus test double. Use isolated headless Chromium with a dedicated agent-browser session and a fresh profile, at 1512×950 in light and dark. Optional captures and critic Check readings use dark only. Existing harness seeds `tree-40`, `tabs-8`, `bubbles` and `decisions` provide controls; drive real menus and dialogs rather than replacing them with synthetic elements (policy).

For each kind—tab, Rail row, button, IconButton, Project tab, Terminal tab, menu item, dialog's first control and Shelf tab—click the actual control or its opener, wait for the intended focus destination, assert that destination is active and its computed `outline-style` is `none`. Then reach the control by Tab or the component's arrow navigation and assert a ring is present. Include keyboard shortcuts that move focus and pointer→keyboard→pointer switching, both with existing focus and on a fresh page. Include the scripted Terminal-input cases above. All these behavior clauses are asserted by `u2770_pointer_and_keyboard_focus`; it checks ring presence, not colour, width, position or contrast. Those are the design critic's under D5 and D6 (policy). Cut any test rendered redundant by this observer, naming the surviving test that proves its then-clause, or the retired scenario (policy, rule 10).

## Enforcement and design policy

The following clauses are policy acceptance of the implementation PR, not tests of configuration text:

- `pnpm lint:styles` rejects a ring (`outline` or a `box-shadow` used as a ring) under `:focus`, `:focus-within` or `[data-focus]` instead of the shared keyboard-mode ring. It also rejects a per-component `:focus-visible` ring outside the shared ring file. Non-ring focus behavior, such as revealing a Rail row action, stays allowed. The implementation supplies the Stylelint enforcement; this specification adds no lint machinery.
- `docs/design-system.md`, heading “Click targets”, changes the focus row's condition from `:focus-visible` to “keyboard focus only; a pointer press never draws it”. D6, under “The checks”, names U2770 and this condition. U133, U523, U388, U441, U182 and the Decision and Project-root Ask specifications defer to U2770 for input modality; their other acceptance remains unchanged.
- Moves: D5 and D6. Definitions on main: `docs/design-system.md`, heading “The checks”; current observer: `apps/desktop/src/testing/checks.ts`, function `runChecks`. D2 from the same heading also holds. Use Tokens only; no Check passing on main regresses. The design critic rejects any capture showing a ring after a click and judges the shared `--accent` keyboard ring, its contrast and clipping, plus unchanged text-field bars/carets.
- At 1512×950 in dark, publish paired main/head captures and Check readings under `artifacts/ux/pointer-no-ring/`, linked from the implementation PR, following `.agents/data/harness.md`, heading “Captures”. Show the Shelf tab after a click and after Tab, a clicked Rail row, button and Terminal tab. Include the densest `tree-40` screen with injected failure text visible. Record immutable SHAs and matching seed, scheme and observer; this scenario-only PR claims no rendered change.
- In the native App built from the implementation head, click each Shelf tab, then press Tab: a ring appears only for keyboard focus. Repeat with macOS Full Keyboard Access enabled and keyboard navigation. Record the build commit, steps and results; Chromium evidence makes no WKWebView claim. If only this observation remains, follow the Builder's Mac-observation procedure.

Scope (policy): ring drawing only. No focus destination, keyboard navigation, restoration, selection, contract, App seam or Token value changes. Rule 3's one-module-directory restriction is waived for this cross-cutting `apps/desktop/src` change; state the waiver in the implementation PR. Stylelint configuration/enforcement and design documentation needed above are in scope. This specification lands separately before implementation and leaves #2770 open.
