# UI: no focus rings or click-press flashes

Module: `apps/desktop` (webview). Work Issue: #3528. Journey stages: Enter, Understand and Intervene (`.agents/data/journey.md`, heading “What must work”).

**U2770 retired: input modality no longer draws a ring.** Policy: U3528 replaces this scenario in full, including its keyboard-mode state, ring Tokens, ring-presence tests, Stylelint requirement and native ring observation. No keyboard-only ring exception remains.

**U3528 controls never draw focus rings or pressed backgrounds.** Given a fresh App page with the main workspace, when the user starts the App, clicks, presses a modifier alone, uses a registered shortcut, navigates the Rail with arrows, or presses Tab or Shift-Tab, then no control, row, pane, text field or dialog draws a focus outline or focus box-shadow. The browser observer `u3528_keys_and_pointer_never_draw_rings_or_pressed_backgrounds` below asserts this acceptance on real controls. Policy: it applies to every App-owned surface, including library components, pseudo-elements and the Diff reader's shadow root; lists and trees use only their selection highlight, and text fields keep their caret.

## Browser observer

Implement exactly one guard, `u3528_keys_and_pointer_never_draw_rings_or_pressed_backgrounds`, under `apps/desktop/src/testing/`, replacing `u2770_pointer_and_keyboard_focus`. Use the existing rendered-App browser lane, isolated headless Chromium, a dedicated agent-browser session and a fresh profile at 1512×950. Run behavioral observations in light and dark; captures and critic Check readings use dark only (policy).

1. Load a fresh page and inspect the initial active element before any input. Then click a real focusable control, assert it is active, and keep it focused throughout the modifier sequence. Press and release Control, Command (`Meta`), Option (`Alt`) and Shift individually, with no other key held. After each release, inspect the active element; also inspect while each modifier is held, so a keydown-only ring fails. Assert no computed outline and no focus box-shadow at every checkpoint. A body-focused initial page is allowed, but the later navigation checkpoints must focus real controls.
2. Use a registered App shortcut that moves focus, such as `Meta+t`; wait for its intended real focus destination and assert that destination is active and ring-free. Click a real Rail row, use ArrowUp and ArrowDown between visible rows, then Tab and Shift-Tab. Assert the expected focus destination and absence of a ring after each action. The Rail still selects by Enter and retains its selection highlight (behavior asserted by existing U31 tests; rendering is policy for the design critic).
3. Exercise the existing real-control paths of the retired U2770 observer: Project tab, Rail row, button, IconButton, Terminal tab, Shelf tab, menu item and a dialog's first control, including a dialog opened by pointer and by keyboard. Check the intended active element and no ring after pointer, keyboard and scripted focus. Open the Bubble and the Import dialog through their real controls; their containers and focused controls also have no ring. Use existing harness seeds and real openers; no replacement elements or synthetic focus to simulate navigation (policy).
4. In the Todo board, locate its Auto switch and record its resting computed background colour and background image. Move the pointer over it, press the mouse and hold before release: both computed backgrounds equal their resting values, on the visible switch and its painted label/mark. Release and assert the switch changes its checked state and calls its existing action once. The held-press checkpoint must run before pointerup, so testing only the final checked state cannot pass this clause.

All numbered steps are asserted by that one browser test. “No outline” means computed `outline-style` is `none` or computed `outline-width` is zero. “No focus box-shadow” means no focus-added shadow on the focused element, its painted wrapper or pseudo-elements: controls with no resting shadow compute `none`; an opaque floating panel retains only its unchanged resting depth shadow. Inspect these painted sites as well as the active input, including visually hidden library inputs (policy). This guard is the Issue's explicit computed-style CI exception; other UI tests remain behavioral under rule 10.

## Removal and class audit
