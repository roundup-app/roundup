# UI: focus indicators and no click-press flashes

Module: `apps/desktop` (webview). Work Issue: #3528. Journey stages: Enter, Understand and Intervene (`.agents/data/journey.md`, heading “What must work”).

Policy amendment for #4382: `scenarios/ui-form-controls.md`, heading “Acceptance”, requires frames and focus rings for shared form controls. That narrow exception supersedes the no-ring and removal clauses below for those controls only; unrelated surfaces and the prohibition on transient pressed backgrounds retain this scenario's acceptance.

Policy amendment for #4685: U4685a and U4685b below require an indicator on the focused Terminal, Rail, Shelf or Drawer region, for pointer and keyboard focus. This exception supersedes the pane prohibition and removal clauses only for region paint; it adds no ring to a row, button, tab or dialog. U4382a's shared-form-control exception remains in force.

**U2770 retired: input modality no longer draws a ring.** Policy: U3528 replaces this scenario in full, including its keyboard-mode state, ring Tokens, ring-presence tests, Stylelint requirement and native ring observation. No keyboard-only ring exception remains.

**U3528 controls never draw focus rings or pressed backgrounds.** Given a fresh App page with the main workspace, when the user starts the App, clicks, presses a modifier alone, uses a registered shortcut, navigates the Rail with arrows, or presses Tab or Shift-Tab, then no control, row, pane, text field or dialog draws a focus outline or focus box-shadow, except shared form controls under U4382a and region indicators under U4685a/b. The design critic judges this look acceptance through D5, D6 and D7 (AGENTS.md rule 10); the browser observer `u3528_keys_and_pointer_never_draw_rings_or_pressed_backgrounds` is retired as a computed-style test. Policy: it applies to every App-owned surface, including library components, pseudo-elements and the Diff reader's shadow root; lists and trees use only their selection highlight, and text fields keep their caret.

## Focused regions (#4685)

Module: `apps/desktop` (webview). Journey stages: Understand (where keyboard input goes) and Intervene (answer in the selected Agent's Terminal). Policy: this specification changes acceptance only; implementation and rendered evidence follow on #4685. Use the existing GLOSSARY.md terms Terminal, Rail, Shelf (user label: work items) and Drawer. No new domain term, RPC, App seam command or persisted focus setting is required.

**U4685a the focused region is visible for either input path.** Given an open Project with a running Agent selected and its centre Terminal shown, and the Rail, Shelf and Drawer available, when the user clicks the Terminal input, then that Terminal's region has a visible focus indicator (policy; rendered observer below). When the user moves keyboard focus to Rail, Shelf and Drawer in turn, then only the region containing actual focus has the indicator, and the previous region loses it (policy; rendered observer). Moving between descendants of the same region keeps its one indicator; selection, hover and a modifier pressed alone do not give an unfocused region an indicator (policy; rendered observer). When focus leaves these regions for Help or another existing dialog, none of the four retains an indicator; dismissing it restores the indicator to whichever region actually regains focus (policy; rendered observer). A hidden region draws nothing. Existing focus destinations, layer ownership and focus-return permissions are unchanged (policy).

Policy: start with the centre Terminal, then apply the same region language to Rail, Shelf and Drawer in the same implementation. `apps/desktop/src/keys/places.ts`, function `placeOf`, currently distinguishes Rail, the Terminal pane, Drawer, Help and other; it does not name Shelf. Shelf is nevertheless required by this work order: use its existing registered keyboard owner and production opening, without changing shortcut scope to satisfy appearance. Help and other dialogs do not gain region indicators. A region indicator encloses the region once, never each focused row or control. Shared form controls may retain their own U4382a keyboard ring inside that region; unrelated controls retain U3528's no-ring and no-pressed-background policy.

Behavioral observer: retired by the owner's flaky-test cut (#4892, 2026-10-29). The cross-region focus proof has no automated test; the per-region focus tests stand. Indicator presence and absence are rendered policy, never computed-style assertions.

**U4685b changing region focus moves no content and refits no Terminal.** Given the same selected running Agent, settled Terminal output, and Shelf and Drawer already open, when focus moves Terminal → Rail → Shelf → Drawer → Terminal without opening, closing or resizing a surface, then the Terminal, its text, region edges and neighbouring content keep their positions and dimensions in every state, and the indicator covers no Terminal glyph or caret, including the first and last visible lines (policy; rendered observer). Repeat Terminal entry by pointer and by the existing keyboard path. The indicator's drawing never changes border width, padding or size (policy; source review). Focus movement alone calls neither the emulator's fit nor `terminal.resize`; test: planned `u4685b_focus_changes_never_refit_or_resize_the_terminal`, using the existing App/pane harness, after initial mount/fit has settled, asserting fit and RPC call-count deltas for the same cross-region sequence. Keep the actual browser RPC count in the rendered run too, so a mocked fit cannot hide a focus-triggered resize.

**U4685c the Drawer indicator stays in view while its content scrolls.** Found by Issue #4779, which U4685a and U4685b do not name. Given a Drawer whose content is taller than its panel and keyboard focus on a control inside it, when the user scrolls the content down and back, then the indicator still encloses the Drawer's visible panel edges and moves with neither the scroll offset nor the content (policy; rendered observer: the Todo Drawer on `tree-40` at 1280×400, scrolled to the bottom, with a control focused). Scrolling alone leaves focus, the scroll offset and the content unchanged, and the indicator's drawing still changes no border width, padding or size, so U4685b holds (policy; source review of `.drawer` in `apps/desktop/src/styles.css` and the indicator rule in `apps/desktop/src/tokens.css`). A Drawer whose content fits keeps U4685a's indicator unchanged. Policy: use the installed platform's own paint (a fixed or sticky region the Drawer's scroll does not move, or an outline on a non-scrolling parent) and add no scroll listener, measurement or second focus state; Tokens only (U4685's policy). No behavioural test is added: indicator presence and position are the rendered observer's. Run `just capture U4685c` at 1280×400, dark, and leave the scrolled-bottom capture under `artifacts/ux/U4685c/`. Moves: D2, D5 and D6; no other Check passing on main regresses.

Policy: all indicator colour, thickness, offsets and any shadows use Tokens only; any Token change updates all its callers under the Contract recipe. An outline, inset shadow or other platform paint that consumes no layout is permitted. Solo's thin accent-blue top and bottom rules are a reference for the critic, not a requirement for a new blue Token or literal. The critic decides exact shape, thickness and colour. The indicator follows focus without a delayed ownership state; no new animation is commissioned. It cannot intercept pointer input or obscure failure feedback. Controls keep U3528 behavior and U4382a's existing narrow exception; no replacement input-modality state is introduced.
