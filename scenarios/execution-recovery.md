# Resume unfinished work

Module: `crates/agents` (Work order and Attempt identity), `crates/messages` (retained evidence and continuation-to-Message acceptance), `crates/rupd` (reconciliation and public registration), `crates/rup` (public CLI/MCP observers), `apps/desktop` (existing work surface). Ids: U3078a–U3078j. Work order: #3078. Baseline: `de22e186d` on `origin/main`.

Acceptance specification, not feature delivery. The user's direction is recovery above opaque vendor Agents on their subscription: see confirmed progress, what remains and what needs checking, then explicitly resume unfinished work. Implement → review → repair → check is one example, not a mandatory sequence or a restriction to coding. #3078 stays open until implementation and observation meet this acceptance.

## Ownership and evidence

Policy: extend existing Work orders, Messages, reactions and Attempts in their existing Project holders and delivery paths. No parallel workflow store, mandatory pipeline editor, new dashboard, vendor reasoning/tool reconstruction, additional Adapter, API-key prerequisite or custom Model loop. Reuse published Deliverable identities for evidence of published results; do not republish or copy them into a second catalogue. #3021 owns unsent draft presentation; #3024 owns idle owned-Todo selection and handoff. Neither owns execution recovery. A handed Todo or idle Agent proves no successful result. Do not create a second Todo scheduler.

Policy: retain the exact Project, Home, original Workstream and Agent identity, affected Attempt, Work order/instruction revision and bytes (including Done condition and limits), target/output identity and revision, accepted result/evidence, and declared pending next action. Instructions carried by Messages retain their Message identity and exact instruction, not just the mutable current Order. Historical records remain attached to their original identities; a user Home move wins. A revision distinguishes replacement and change-away-and-back, even when the text or filename becomes equal again. Names, timestamps alone and current paths are not revision identities.

Policy: separate delivery, an Agent's completion report, user acceptance and independent verification. An authenticated public CLI/MCP report records its author and Attempt, claimed result and exact version; it proves only that report. User acceptance records who accepted which version and evidence, without claiming independent verification. Independent verification records a declared authoritative source, exact version, observation revision and verdict. An unavailable/unsupported source cannot verify success. Delivery acknowledgements, idle/done/error/needs-you, exit codes alone and Terminal prose cannot upgrade these facts. A successful verifier of one declared condition proves that condition only, never all work.

Policy: no new RPC or public type name is prescribed by this specification. Implementation records any new names in `GLOSSARY.md`, regenerates contracts and changes every caller in the same PR. Keep vendor interpretation inside existing Adapter seams (P4); expose unsupported facts with weaker guarantees and a cause/action. Use existing method registration to expose reports and reconciliation through public CLI/MCP rather than private test-only writes. A report cannot forge a verifier, another Actor's acceptance or another Attempt's authorship.

## Behavioral acceptance

Every test named below is a planned observer, not a claim that it exists or passes on main. Use real temporary Project data through the real Daemon and public CLI/MCP, deterministic fake vendor observations, and fake-vendor argv/prompt counts. Extend existing E2E suites where possible. Only transaction cut points need lower store fault injection; exercise their public recovery separately. App tests use the existing App seam for clicks, keys, focus, identity and call counts, never appearance assertions.

**U3078a retain exact accepted progress.** Given a Work order “Fix login”, its instruction revision I1, Agent A/Attempt 1, implementation output V1, an acceptance of V1, and an independent review of V1, when repair is interrupted and the Project and Daemon reopen, then the original instruction bytes, accepted result, review source/verdict/revision, Agent/Attempt and pending repair/final-check actions remain readable with their original identities. No result is silently upgraded or lost. Opening does not start a program, deliver a Message or use a Model turn. Planned test: `u3078a_reopen_retains_exact_progress_without_starting`, including interruption immediately after instruction delivery and after result acceptance. Policy: evidence follows P6 user Home moves and remains discoverable after its maker stops; explicit removal and access revocation remain effective.

**U3078b reports are not verification.** Given an instruction delivered to A, when fake vendor observations separately show idle, done, error, needs-you, exit, a delivery acknowledgement or Terminal text saying “complete”, then none establishes successful work. An authenticated public report establishes reported completion only; user acceptance and an authoritative check remain separately attributed. A failed/missing/unsupported observation shows its cause and an action to inspect evidence or retry verification, without claiming success. A stale or wrong-version passing check cannot verify the current result. Planned tests: `u3078b_delivery_report_acceptance_and_verification_are_distinct` and `u3078b_public_reports_cannot_forge_authority`, the latter also refusing wrong Project/Reach, another Agent/Attempt and forged verifier/acceptor authority without mutation.

**U3078c changed work cannot borrow success.** Given accepted/reviewed I1/V1 and pending repair, when instruction, Done condition, limits, target or output changes, then the old acceptance stays readable as historical evidence but is not completion of the changed work; reconciliation identifies what needs checking before continuation. Changing I1→I2→equal I1 bytes or replacing a target with the same name does not revive acceptance for the replacement. An unrelated unchanged accepted result remains accepted for its exact version. Missing/revoked published evidence is explicitly unavailable, never substituted with current bytes or another Deliverable. Planned test: `u3078c_changed_revisions_and_unavailable_evidence_do_not_inherit_completion`.

**U3078d resume reconciles unfinished work.** Given U3078a's reopened work and a live eligible receiver, when the user explicitly chooses Resume unfinished work, then the Daemon reconciles current instruction, target, accepted evidence and next-action identities before acceptance; one successor Message carries the eligible unfinished repair, retained confirmed context and pending checks, without ordering implementation or accepted review to run again. Final checks stay pending until their own evidence arrives. When repair produces V2, V1's accepted review does not verify V2. With everything complete, repeated resume reports no unfinished work and creates no Message or Attempt. Planned test: `u3078d_explicit_resume_continues_only_eligible_unfinished_work`. Repeat with a non-code task: an accepted source outline and reviewed document revision, interrupted diagram preparation and pending export validation; no prescribed coding-stage names or four-stage sequence is required. Planned test: `u3078d_document_work_uses_the_same_recovery_path`.

**U3078e one accepted decision has one successor.** Given one reconciled pending action for exact instruction/target/output versions, when resume is repeated with the same request identity, retried with a fresh client request after an unknown reply, replayed after reopen or observed concurrently, then at most one accepted continuation decision and one successor Message exist for that pending action. A client-generated retry id alone cannot authorize a second successor. Same-id conflicting payload refuses without changing the accepted record. A later genuine unfinished action has a distinct retained identity; old accepted decisions cannot consume it. If an existing reaction firing already accepted that same continuation, explicit resume reconciles to its Message rather than making another. Planned test: `u3078e_resume_replay_and_reactions_share_one_successor`, asserting durable decision/firing/Message ids and bodies, not just prompt counts.

**U3078f acceptance and Message commit together.** Given faults immediately before and after the continuation transaction commit, when the Daemon restarts and the user reconciles/retries resume, then pre-commit state contains neither accepted decision nor successor and a retry may accept both once; post-commit state retains both original identities and retry returns them without another Message. There is no accepted decision without its Message, and no orphan successor. A failed write exposes its cause and retry action without claiming acceptance. Planned store test: `u3078f_decision_and_successor_are_one_commit`; planned real-Daemon test: `u3078f_reopen_reconciles_unknown_acceptance`. Together with U3078a these interrupt after delivery, after result acceptance and on both sides of successor commit.

**U3078g normal authority and delivery guards win.** Given unfinished work, when the Project reopens, then it sends nothing and starts no program. Resume with a busy receiver, changed permissions/Reach or changed Attempt never injects past the existing guards; Message provenance, pending/delivered/dropped reasons, inbox delivery and batching remain the existing contracts. A stopped Agent or stopped reaction stays stopped: Resume unfinished work does not authorize restart or revive a reaction. Show the separate existing explicit start/resume action where available; only that action may launch the saved conversation through A22/A23, followed by revalidation. A removed/replaced target refuses with its cause and no substitution, even when another Agent has the same name. Resume never starts a fresh conversation as fallback, repeats the original start prompt or overlaps Attempts. Planned tests: `u3078g_resume_preserves_stop_holds_authority_and_attempts` and `u3078g_removed_targets_are_never_substituted`, reusing existing delivery/resume proofs and adding only execution-recovery assertions. Policy: M1–M10 remain unchanged; an implementation changing Message/Route contracts names the touched laws and keeps `docs/messages.md` and `proofs/messages` agreeing.

**U3078h unknown external effects are not retried.** Given deployment, payment and push fixtures in turn, each issued before interruption without authoritative acknowledgement, when reopening, reporting completion, resuming repeatedly or replaying Message delivery, then the effect remains unknown and no continuation orders that effect again. A next action may inspect/reconcile authoritative external evidence; it must not repeat the uncertain effect. Evidence of completion for the exact target/version records that completion; authoritative evidence that it did not happen may make that unfinished action eligible for an explicit resume. Unavailable, stale or inconclusive evidence leaves it unknown with the cause and useful checking action. Planned test: `u3078h_unknown_external_effects_require_authoritative_resolution`, counting fake external calls as well as Messages. Policy: this guarantees accepted-decision-to-Message identity, never exactly-once external effects; existing Message transport replay remains in force and replayed instructions must preserve the check-before-effect requirement.

**U3078i open the same work and resume.** Given U3078a's interruption among ten Agents, when the user opens the same Workstream/work detail in the existing App surface, then they can read which exact results were accepted, which were independently checked, where work was interrupted and what remains. Older-version evidence is distinguishable from current progress; unavailable evidence and unknown effects show cause and next action. Selecting evidence opens its exact existing target or explicit unavailable result. Opening, reloading and switching Projects sends nothing. Choosing Resume unfinished work invokes U3078d–h against the original identity without requiring the user to recreate the request, including an unknown RPC response reconciled by identity before retry. Keyboard and pointer both work; leaving and returning preserves unsent input and focus returns to the initiating control after an action. Planned App tests: `u3078i_open_inspect_resume_and_reconcile` and `u3078i_navigation_preserves_input_and_original_identity`; planned real-Daemon journey observer: `u3078i_real_daemon_reopen_and_resume`, including failure and repeat-resume cases. No native rendering or vendor-internal state is claimed by this observer.

Policy: U3078i moves D2, D5 and D6 and regresses no passing Check. Reuse existing Ark-backed primitives and Tokens on the Workstream/work detail; no separate recovery dashboard or unsent-draft catalogue. Observe the Understand, Intervene and Review stages at 1512×950 in an isolated headless session, dark mode, with long/overlapping names, ten Agents, confirmed/interrupted/pending results, old versions, pending work, unavailable evidence, unknown effects and failed resume visible on the densest seed. Run `just capture U3078i`; leave before/after PNGs, video of open→inspect→resume and Check readings under `artifacts/ux/U3078i/` for design-critic review; never commit images/videos. No motion clause. Layout, copy fit, contrast and clipping belong to that critic, not App behavior assertions.

**U3078j passive recovery spends no turns and composes with handoff.** Given retained progress, deterministic event notifications and no explicit resume, when time passes, status/reaction events replay, a Project opens or the user inspects evidence, then remembering/waiting/reconciliation uses no Model call or vendor prompt and launches no program. Deterministic verification may consume compute, never a Model poll for already observable facts. Explicit continuation uses normal subscription usage, unchanged Brief/settings/tool bytes and existing batching. An owned-Todo handoff remains owned by #3024: recovery attaches to that work's existing identities, does not select another Todo or duplicate its accepted handoff Message. Planned test: `u3078j_passive_recovery_and_owned_handoff_do_not_duplicate_usage`, using fake-vendor calls, public Todo/Message history and captured launch configuration. Policy: no Pi, new vendor Adapter, Model-loop runtime or API key is a prerequisite.

**U3078k a Resume request belongs to one Agent and one set of actions.** Narrows U3078i, whose request-identity clause it completes; changes no contract (rule 4). Given a failed or unknown-reply Resume on Agent A in the work detail, then: (1) when the user shows Agent B in the same surface, B's progress starts with no request id and no `failed` or `unknown` phase from A, and choosing Resume on B sends a fresh request id for B's own actions (`u3078k_a_new_agent_starts_without_the_old_request`); (2) when the actions the Resume would carry for the same Agent change between the failure and the retry, the retry sends a fresh request id, so the Daemon never sees one id with two payloads (`u3078k_changed_actions_drop_the_old_request`); (3) with the same Agent and the same actions, a retry after a failure or unknown reply keeps its request id, as U3078e and U3078i say (`u3078k_the_same_actions_keep_their_request`). Tests (`u3078k_`, Vitest in `apps/desktop/src/orders/`, fake App seam recording `message.reconcileWork` calls). Policy: the work detail is keyed by the shown Agent's id; the PR names the Checks it moves (rule 8) and a looks change is the design critic's.

## Specification boundary

Policy: independent review checks every acceptance heading has named observers and every numbered baseline reference exists on main. No implementation, contract name, schema or generic workflow engine is delivered here. Implementation extends the existing holders; any new machinery must first satisfy rule 9's library research. Fleet cancellation, admission/budgets, additional vendors and unattended restart authorization stay out of scope. Implementation is split into reviewable work Issues only after this specification merges, using native blocked-by dependencies for genuine prerequisites. Progress, split decisions and unresolved engineering questions live on #3078, never in a scenario Work table. A specification-only PR uses Refs #3078 and never closes it.
