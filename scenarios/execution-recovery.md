# Resume unfinished work

Module: `crates/agents` (Work order and Attempt identity), `crates/messages` (retained evidence and continuation-to-Message acceptance), `crates/rupd` (reconciliation and public registration), `crates/rup` (public CLI/MCP observers), `apps/desktop/src/continuation` (the App's Resume line and command, U7211). Ids: U3078a–U3078j; U3078i and U3078k retired (#7190); U7211a–U7211d (#7211). Work order: #3078; #7211 for the App. Baseline: `de22e186d` on `origin/main`.

Acceptance specification, not feature delivery. The user's direction is recovery above opaque vendor Agents on their subscription: see confirmed progress, what remains and what needs checking, then explicitly resume unfinished work. Implement → review → repair → check is one example, not a mandatory sequence or a restriction to coding. #3078 stays open until implementation and observation meet this acceptance.

## Ownership and evidence

Policy: extend existing Work orders, Messages and Attempts in their existing Project holders and delivery paths. No parallel workflow store, mandatory pipeline editor, new dashboard, vendor reasoning/tool reconstruction, additional Adapter, API-key prerequisite or custom Model loop. Reuse published Deliverable identities for evidence of published results; do not republish or copy them into a second catalogue. #3021 owns unsent draft presentation; #3024 owns idle owned-Todo selection and handoff. Neither owns execution recovery. A handed Todo or idle Agent proves no successful result. Do not create a second Todo scheduler.

Policy: retain the exact Project, Home, original Workstream and Agent identity, affected Attempt, Work order/instruction revision and bytes (including Done condition and limits), target/output identity and revision, accepted result/evidence, and declared pending next action. Instructions carried by Messages retain their Message identity and exact instruction, not just the mutable current Order. Historical records remain attached to their original identities; a user Home move wins. A revision distinguishes replacement and change-away-and-back, even when the text or filename becomes equal again. Names, timestamps alone and current paths are not revision identities.

Policy: separate delivery, an Agent's completion report, user acceptance and independent verification. An authenticated public CLI/MCP report records its author and Attempt, claimed result and exact version; it proves only that report. User acceptance records who accepted which version and evidence, without claiming independent verification. Independent verification records a declared authoritative source, exact version, observation revision and verdict. An unavailable/unsupported source cannot verify success. Delivery acknowledgements, idle/done/error/needs-you, exit codes alone and Terminal prose cannot upgrade these facts. A successful verifier of one declared condition proves that condition only, never all work.

Policy: no new RPC or public type name is prescribed by this specification. Implementation records any new names in `GLOSSARY.md`, regenerates contracts and changes every caller in the same PR. Keep vendor interpretation inside existing Adapter seams (P4); expose unsupported facts with weaker guarantees and a cause/action. Use existing method registration to expose reports and reconciliation through public CLI/MCP rather than private test-only writes. A report cannot forge a verifier, another Actor's acceptance or another Attempt's authorship.

## Behavioral acceptance

Every test named below is a planned observer, not a claim that it exists or passes on main. Use real temporary Project data through the real Daemon and public CLI/MCP, deterministic fake vendor observations, and fake-vendor argv/prompt counts. Extend existing E2E suites where possible. Only transaction cut points need lower store fault injection; exercise their public recovery separately. App tests use the existing App seam for clicks, keys, focus, identity and call counts, never appearance assertions.

**U3078a retain exact accepted progress.** Given a Work order “Fix login”, its instruction revision I1, Agent A/Attempt 1, implementation output V1, an acceptance of V1, and an independent review of V1, when repair is interrupted and the Project and Daemon reopen, then the original instruction bytes, accepted result, review source/verdict/revision, Agent/Attempt and pending repair/final-check actions remain readable with their original identities. No result is silently upgraded or lost. Opening does not start a program, deliver a Message or use a Model turn. Planned test: `u3078a_reopen_retains_exact_progress_without_starting`, including interruption immediately after instruction delivery and after result acceptance. Policy: evidence follows P6 user Home moves and remains discoverable after its maker stops; explicit removal and access revocation remain effective.

**Instruction** (`Instruction`, `InstructionRevision`, `Instructions`, `agent.instructions`, `agent_instructions`): Exact Work order values or a Message's identity and body, retained under a never-reused Project revision with its original Agent and Workstream. A replacement is a new revision even with equal bytes; Home follows the user's placement while historical attribution stays fixed.

**U3078b reports are not verification.** Given an instruction delivered to A, when fake vendor observations separately show idle, done, error, needs-you, exit, a delivery acknowledgement or Terminal text saying “complete”, then none establishes successful work. An authenticated public report establishes reported completion only; user acceptance and an authoritative check remain separately attributed. A failed/missing/unsupported observation shows its cause and an action to inspect evidence or retry verification, without claiming success. A stale or wrong-version passing check cannot verify the current result. Planned tests: `u3078b_delivery_report_acceptance_and_verification_are_distinct` and `u3078b_public_reports_cannot_forge_authority`, the latter also refusing wrong Project/Reach, another Agent/Attempt and forged verifier/acceptor authority without mutation.

**Instruction delivery** (`InstructionDelivery`, `InstructionState`): An instruction revision's exact words and original Attempt: `prepared` before writer admission, `uncertain` without authoritative receipt, `submitted` after the existing prompt/inbox acknowledgement, or `refused` after an unwritten refusal or Message drop. These are delivery facts, never work completion, acceptance, verification or authority to replay.

**Result report** (`ResultReport`, `ReportParams`, `message.report`): An authenticated Agent's claim about its own Attempt's submitted Instruction delivery, retained in the Project Message holder with exact instruction, original Workstream, Home at report, pending next action and published Deliverable identity. A report key reconciles equal retries and refuses conflicting ones. It never proves acceptance or verification. `ResultTarget` names the claimed target identity and revision; `ResultState` distinguishes reported work from an unknown external effect.

**Result acceptance** (`ResultAcceptance`, `AcceptResultParams`, `message.acceptResult`): The user's acceptance and evidence for one exact Result report, without independent verification. `ResultId` selects that report within its original Project and Agent.

**Result check** (`ResultCheck`, `ResultObservation`, `message.verifyResult`): A declared authoritative condition observed by the Daemon, retaining its source revision and verdict separately from claims and acceptance. Publication checks prove only retained-byte integrity; PR checks use fresh, complete forge evidence for the exact declared repository/PR/head. Unsupported sources and uncertain external effects remain unknown with a cause and checking action. Agent status and Terminal prose supply no verification authority.

**U3078c changed work cannot borrow success.** Given accepted/reviewed I1/V1 and pending repair, when instruction, Done condition, limits, target or output changes, then the old acceptance stays readable as historical evidence but is not completion of the changed work; reconciliation identifies what needs checking before continuation. Changing I1→I2→equal I1 bytes or replacing a target with the same name does not revive acceptance for the replacement. An unrelated unchanged accepted result remains accepted for its exact version. Missing/revoked published evidence is explicitly unavailable, never substituted with current bytes or another Deliverable. Planned test: `u3078c_changed_revisions_and_unavailable_evidence_do_not_inherit_completion`.

**U3078d resume reconciles unfinished work.** Given U3078a's reopened work and a live eligible receiver, when the user explicitly chooses Resume unfinished work, then the Daemon reconciles current instruction, target, accepted evidence and next-action identities before acceptance; one successor Message carries the eligible unfinished repair, retained confirmed context and pending checks, without ordering implementation or accepted review to run again. Final checks stay pending until their own evidence arrives. When repair produces V2, V1's accepted review does not verify V2. With everything complete, repeated resume reports no unfinished work and creates no Message or Attempt. Planned test: `u3078d_explicit_resume_continues_only_eligible_unfinished_work`. Repeat with a non-code task: an accepted source outline and reviewed document revision, interrupted diagram preparation and pending export validation; no prescribed coding-stage names or four-stage sequence is required. Planned test: `u3078d_document_work_uses_the_same_recovery_path`.

**Continuation** (`ContinuationAction`, `ContinuationChoice`, `Reconciliation`, `ResumeWorkParams`, `message.reconcileWork`, `message.resumeWork`): The user's explicit choice to resume one Agent's unfinished work. Reconciliation reads retained Result reports, acceptance and observations and changes nothing; an action is a current report's pending next step, identified by its Agent, instruction, target, output and next step, never by a report key or client request id. A choice accepts its actions once and makes one successor Message in the same write; a stopped Agent, a removed target, an unknown external effect or a completed result never yields one.

**U3078e one accepted decision has one successor.** Given one reconciled pending action for exact instruction/target/output versions, when resume is repeated with the same request identity, retried with a fresh client request after an unknown reply, replayed after reopen or observed concurrently, then at most one accepted continuation decision and one successor Message exist for that pending action. A client-generated retry id alone cannot authorize a second successor. Same-id conflicting payload refuses without changing the accepted record. A later genuine unfinished action has a distinct retained identity; old accepted decisions cannot consume it. Planned test: `u3078e_resume_replay_shares_one_successor`, asserting durable decision/Message ids and bodies, not just prompt counts.

**U3078f acceptance and Message commit together.** Given faults immediately before and after the continuation transaction commit, when the Daemon restarts and the user reconciles/retries resume, then pre-commit state contains neither accepted decision nor successor and a retry may accept both once; post-commit state retains both original identities and retry returns them without another Message. There is no accepted decision without its Message, and no orphan successor. A failed write exposes its cause and retry action without claiming acceptance. Planned store test: `u3078f_decision_and_successor_are_one_commit`; planned real-Daemon test: `u3078f_reopen_reconciles_unknown_acceptance`. Together with U3078a these interrupt after delivery, after result acceptance and on both sides of successor commit.

**U3078g normal authority and delivery guards win.** Given unfinished work, when the Project reopens, then it sends nothing and starts no program. Resume with a busy receiver, changed permissions/Reach or changed Attempt never injects past the existing guards; Message provenance, pending/delivered/dropped reasons, inbox delivery and batching remain the existing contracts. A stopped Agent stays stopped: Resume unfinished work does not authorize restart. Show the separate existing explicit start/resume action where available; only that action may launch the saved conversation through A22/A23, followed by revalidation. A removed/replaced target refuses with its cause and no substitution, even when another Agent has the same name. Resume never starts a fresh conversation as fallback, repeats the original start prompt or overlaps Attempts. Planned tests: `u3078g_resume_preserves_stop_holds_authority_and_attempts` and `u3078g_removed_targets_are_never_substituted`, reusing existing delivery/resume proofs and adding only execution-recovery assertions. Policy: M1–M10 remain unchanged; an implementation changing Message/Route contracts names the touched laws and keeps `docs/messages.md` and `proofs/messages` agreeing.

**U3078h unknown external effects are not retried.** Given deployment, payment and push fixtures in turn, each issued before interruption without authoritative acknowledgement, when reopening, reporting completion, resuming repeatedly or replaying Message delivery, then the effect remains unknown and no continuation orders that effect again. A next action may inspect/reconcile authoritative external evidence; it must not repeat the uncertain effect. Evidence of completion for the exact target/version records that completion; authoritative evidence that it did not happen may make that unfinished action eligible for an explicit resume. Unavailable, stale or inconclusive evidence leaves it unknown with the cause and useful checking action. Planned test: `u3078h_unknown_external_effects_require_authoritative_resolution`, counting fake external calls as well as Messages. Policy: this guarantees accepted-decision-to-Message identity, never exactly-once external effects; existing Message transport replay remains in force and replayed instructions must preserve the check-before-effect requirement.

**Result resolution** (`ResultResolution`, `ResultOutcome`, `ResolveResultParams`, `message.resolveResult`): A Daemon GET of an authoritative receipt source explicitly chosen by the user, never by an Agent. The receipt names the exact `ResultTarget`, an opaque source revision, Unix observation seconds and a completed, not-performed or inconclusive outcome. HTTPS (or literal loopback HTTP), a five-second deadline, no redirects and a 64 KiB response bound apply. A receipt older than 60 seconds, more than five seconds ahead, without a source revision, for another target/version, unavailable or inconclusive records an unknown cause and checking action. A conclusive receipt is retained as a resolved `ResultObservation` with source and authorizing Actor. It resolves only that unknown-effect report; acceptance and publication integrity cannot resolve it. No effect or continuation is issued by resolution. The receipt endpoint is a declared read-only source; choosing it grants no Agent permission to choose another source.

**Progress** (`Progress`, `ProgressParams`, `ResultProgress`, `message.progress`): Passive inspection of retained instructions, Result reports, acceptance, source observations and exact publication availability. Opening or inspecting Progress starts nothing and sends no Message.

**U3078j passive recovery spends no turns and composes with handoff.** Given retained progress, deterministic event notifications and no explicit resume, when time passes, status events replay, a Project opens or the user inspects evidence, then remembering/waiting/reconciliation uses no Model call or vendor prompt and launches no program. Deterministic verification may consume compute, never a Model poll for already observable facts. Explicit continuation uses normal subscription usage, unchanged Brief/settings/tool bytes and existing batching. An owned-Todo handoff remains owned by #3024: recovery attaches to that work's existing identities, does not select another Todo or duplicate its accepted handoff Message. Planned test: `u3078j_passive_recovery_and_owned_handoff_do_not_duplicate_usage`, using fake-vendor calls, public Todo/Message history and captured launch configuration. **U3078l a receipt read names the failure it met.** Narrows U3078h's "unavailable evidence leaves it unknown with the cause"; changes no contract (rule 4). Given the authoritative receipt source answers over `http` and the Daemon reads it with one bounded GET, then the unknown cause is: (1) a reply whose status is not 2xx says "the authoritative source returned HTTP <code>", whatever the body size, including a body over 64 KiB (`u3078l_a_non_success_status_wins_over_an_oversized_body`); (2) a 2xx reply whose body is cut off mid-transfer says "the authoritative receipt could not be read completely", not "unavailable or did not answer within five seconds" (`u3078l_a_truncated_body_is_not_reported_as_unavailable`); (3) a 2xx body over 64 KiB says "the authoritative receipt exceeds 64 KiB"; no reply within five seconds or no connection says "unavailable or did not answer within five seconds" (`u3078l_other_failures_keep_their_causes`). In every case the outcome stays unknown and no effect is retried. Tests: `u3078l_` in `crates/rupd/src/evidence.rs`, against a local socket server that sends each reply; a test that starts `curl` is allowed here because the causes come from its exit and `%{http_code}`. Policy: no new RPC, type or `contracts/` change.

**U7287a a report carries a confidence only below its check.** Owner, 2026-11-16, #7287, after Anthropic's single-agent-loop-kit: a child's result may say how far to trust it, only where that informs. `ReportParams` may carry one `confidence` (`ResultConfidence`): a `level` (`ConfidenceLevel`), `medium` or `low`, and a non-blank `reason`. A Job sets it only when the result rests on something it could not check; a report without it stands on its `check`. `high` cannot be written, and a blank or missing reason is refused at parse. Absent by default. Test: `u7287a_confidence_is_medium_or_low_with_a_reason` (`crates/contracts/src/message.rs`).

**U7287b a report carries caveats only for limits that change the next step.** `ReportParams` may carry `caveats`: short texts (non-blank, at most 256 bytes), each naming one limit of the result that changes what the Door or the user does next. A report without such a limit carries none: an absent or empty list reads and writes with no `caveats` field, never an empty list. Test: `u7287b_a_report_without_a_limit_carries_no_caveats`.

**U7287c a report stored before U7287a still reads.** A report stored without `confidence` and `caveats` reads and writes back its own bytes, so an equal retry under its key still reconciles (U3078 Result report). Test: `u7287c_a_report_stored_before_still_reads`.

**U7287d the Briefs say when both fields inform.** The Agent Brief's `message_report` line, the same bytes for every Agent, tells an Agent to leave out `confidence` and `caveats` by default, to give `confidence` only when the result rests on something it could not check, to give one caveat per limit that changes what its coordinator or the user does next, and that no note, question or other Message carries either. The Door Brief tells the Door, where it reads a child's report, to read both fields before it reads the child's Terminal. Test: the golden Briefs `crates/agents/tests/fixtures/brief/agent.md` and `door.md` (`m2219_on_brief_is_unchanged`); rule 10 adds no test that repeats them. Message laws: M1–M10 untouched; a report changes no delivery (`docs/messages.md`).

## Specification boundary

Policy: independent review checks every acceptance heading has named observers and every numbered baseline reference exists on main. No implementation, contract name, schema or generic workflow engine is delivered here. Implementation extends the existing holders; any new machinery must first satisfy rule 9's library research. Fleet cancellation, admission/budgets, additional vendors and unattended restart authorization stay out of scope. Implementation is split into reviewable work Issues only after this specification merges, using native blocked-by dependencies for genuine prerequisites. Progress, split decisions and unresolved engineering questions live on #3078, never in a scenario Work table. A specification-only PR uses Refs #3078 and never closes it.
