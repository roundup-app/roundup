# UI: maximise the Shelf and act on its focused row by key (U3721 to U3724, U3721a, U3721b)

Module: `apps/desktop` (the webview). Acceptance for #2899. Webview only: no App command, no Daemon method and nothing under `contracts/` changes; `todo.delete`, `pad.delete` and `pad.export` are the existing calls. Extends U370 (open state per Project), U373 (frame), U460 (delete confirmation) and U21 (export); obeys U2241 and U2541b.

**U3721 the Shelf can be maximised to fill the centre.** Given an open Shelf in reserved-width mode (U369), when the user presses the Shelf head's `Maximise` button or the plain key `m` with focus inside the Shelf, then the Shelf's box spans the whole centre: its left edge meets the Rail's right edge and its right edge meets the window's, the Rail keeps its width and stays operable, and the centre's own content is hidden, not unmounted (U138's focus return still lands). The same press again restores the width the Shelf had (`--shelf-width`, U390), and the button's accessible name flips between `Maximise` and `Restore`. The state is kept per Project beside U370's open state in `shelf/frame.ts`, restored in the frame the Project first shows without animating, and a Project that never maximised opens at its stored width. Closing the Shelf from a maximised state and reopening it opens maximised; resizing (U390) is inert while maximised. In overlay mode (U369) the button is absent and `m` does nothing, since the Shelf already covers the centre. Motion follows U369's slide and respects reduced motion. Tests (`u3721_`): `u3721_maximise_fills_the_centre_and_restore_returns_the_width`, `u3721_the_state_is_kept_per_project_and_restored_unanimated`, `u3721_maximise_keeps_the_centre_mounted` (the name flips), `u3721_overlay_mode_has_no_maximise_button_and_m_does_nothing`, and the design critic judges the span from Rail edge to window edge at 1512×950 (AGENTS.md rule 10).

**U3721a `⌘K` then `B` rotates the Bench through four sizes.** Source: the owner's request of 2026-11-07 (#6795). Amends U2239's `B` row (`leader.shelf`), which toggled; no new chord is added (U2239, U2241). Given an open Project and no modal layer, when the user presses `⌘K` then `B`, then the Bench steps one size, in this order:

- **Order.** closed → list (at its stored width, U390) → list with the open item → full → closed. The "list with the open item" step opens the Bench's selected row in today's Drawer (U430), which covers the Bench; it adds no side-by-side layout. With several rows selected it opens the focused one. With no row selected the list steps straight to full. "Full" maximises the open item's Drawer (U4458), or the list (U3721) when no item is open. From full, the press closes the Bench and the Drawer, and the next press opens the list at its stored width.
- **Overlay mode (U371).** Nothing maximises, so the cycle skips full: closed → list → list with the open item → closed, and with no selection closed → list → closed.
- **Kept.** Esc closes from any size, the Drawer before the Bench (U371). The stored state per Project follows each step (U3721, U370), the stored widths do not change, the peek (U6224) is unchanged, and a tab switch stays instant (U373). The `B` row's name and hint name the rotation, not "open".

Tests (`u3721a_`): `u3721a_the_leader_b_steps_closed_list_item_full_closed_in_reserved_mode`, `u3721a_overlay_mode_skips_full`, `u3721a_with_no_selection_the_list_steps_straight_to_full`, `u3721a_the_state_per_project_follows_each_step_and_esc_still_closes`. The old tests that pin `B` as a plain toggle are cut; `u3721a_the_leader_b_steps_closed_list_item_full_closed_in_reserved_mode` proves their closed-to-list and list-to-closed then-clauses.

**U3721b every Bench and Drawer size change moves, on `transform` only.** Source: #6795. Extends U6837a (the key duration, one running motion, reduced motion) to every change, and amends U3721's and U4458's maximise and restore, which snapped the width behind a faked `translateX`. Given an open Project, reduced motion off, then each of open, close, list to item, maximise, restore and each U3721a step, by key or by pointer:

- **Real motion.** The panel slides through `transform` (or `opacity`, or `clip-path`) and the width snap is gone; `width` and `grid-template-columns` never interpolate, on the Bench, the Drawer or the centre (M5, M11, and the `.columns` width transitions are deleted).
- **Once.** The centre takes its final width once, at the end, and a visible Terminal receives exactly one `terminal.resize` per change (U371, U430, U6228a, U6418b), with no frame showing it blank or half-drawn. This holds for a key-started change as for a pointer one: a Bench open, close and maximise and a Drawer maximise and restore, each by key, send exactly one `terminal.resize`, and none while `sliding` is true. `u3721b_each_size_change_sends_exactly_one_terminal_resize` (`apps/desktop/src/shelf/u3721b_motion.test.ts`) runs those five changes with the Terminal visible and counts the RPC calls. Bench and Drawer text does not reflow during the slide.
- **Duration.** A pointer change uses `--duration-drawer` and `--easing-out`; a key change uses `--duration-key` (U6837a).
- **Retarget.** A press during a motion retargets it from where the panel is drawn and leaves one running motion.
- **Reduced motion.** A change takes M10's opacity preset, with the final geometry at once.

Tests (`u3721b_`): `u3721b_each_size_change_starts_one_transform_motion_and_no_width_motion`, `u3721b_each_size_change_sends_exactly_one_terminal_resize`, `u3721b_maximise_and_restore_move_by_key_and_by_pointer`, `u3721b_a_press_during_a_motion_leaves_one_running_motion`. Observer: the design critic with `review-animations`, on frame-by-frame dark captures of `tree-40` at 1512x950 with 20 Todos and a long Pad, of each `⌘K` then `B` step and each pointer change (`artifacts/ux/U3721b/`, `.agents/data/harness.md`, **Captures**); a performance trace of one maximise shows no layout pass between its first and last frame. Moves D2, D5, D6. Policy: reuse `shelf/frame.ts`, the motion tokens and helpers, with no new library; scope `apps/desktop/src/shelf/`, `drawer/`, `resize/`, the App layout and `keys/chords.ts`.

**U3722 Maximise and Close name their key on hover and focus.** Given the Shelf head, when the pointer rests on or keyboard focus reaches `Maximise` (or `Restore`) or `Close`, then `ui/Tooltip` shows the action's name and its key as a `keys/KeyChip` through the tooltip's `chord`: `Maximise` with `M`, `Restore` with `M`, `Close` with `Esc`. The chip is derived from the same registry row the key runs from, never typed twice. A tooltip never takes focus or changes the head's layout (U112). Tests (`u3722_`): `u3722_the_chip_comes_from_the_registry_row`.

**U3723 plain keys delete and export the focused row.** Narrows U152 (every action has a keyboard path) and obeys U2241. Given the Shelf's Todos or Pads tab with a row button focused, then the plain key `d` (no `⌘`, `⌃`, `⌥`, no `⇧`) asks to delete that row through U460's one question (`Delete 1 Todo?` or `Delete 1 Pad?`, with `Delete` and `Keep`), selecting nothing else and calling nothing before confirmation, and the plain key `e` on a Pad row opens U21's save chooser for that Pad and calls `pad.export {name, path}` only once a path is chosen. `e` does nothing on a Todo row, and `d` and `e` do nothing while focus is in a text field, the Drawer's editor, a naming field or a dialog, with a modifier held (`⌘D`, `⌃E`, `⌥D` reach their existing owners unprevented) or on a repeated keydown. Both are registered once in the registry's Shelf scope, never a local `keydown` listener (policy), so they fire only while focus is inside the Shelf and add no `⌘`, `⌃` or `⌥` key at app scope; the Terminal's keys are untouched (U2241). A row also keeps its pointer paths. Tests (`u3723_`): `u3723_d_asks_once_to_delete_the_focused_row_and_calls_nothing_first`, `u3723_e_exports_the_focused_pad_and_is_inert_on_a_todo`, `u3723_keys_are_inert_in_text_fields_dialogs_modifiers_and_repeats`, `u3723_keys_are_shelf_scoped_and_leave_the_terminal_alone`.

**U3724 every new key is listed.** Given U3721 and U3723, then `m`, `d` and `e` each have one row in `CHORDS` (scope Shelf), one in `HELP_ROWS` and an entry in the key hints of U2541b for the Shelf place, and no key is listed that is not registered. Tests (`u3724_`): `u3724_each_new_key_is_in_chords_help_and_the_hint_line` (the U2241 sweep and the Help tests keep passing with the new rows).

Policy: implementation boundary is `apps/desktop/src/shelf/`, `keys/`, `copy.ts` and the explicitly named regression callers; reuse `ui/Tooltip`, `keys/KeyChip` and U460's confirmation, add no state machine. `m`, `d` and `e` are chosen to collide with no Shelf key on `main` (U3720 owns `o`, U460 owns Backspace).

Observer: the named Vitest cases against the fake App; one headless U26 Chromium session at 1512×950, dark and light (captures and critic Check readings use dark only, U3725), on `tree-40`. Moves: D2, D5, D6. Linux/Chromium is the rendered observer; the user reports what they meet on the Mac.
