# A migration the previous build cannot read fails the change (MG1–MG4)

Module: `crates/rupd` (`build.rs`, `src/storage.rs`, `migrations/project/`). Ids: MG1–MG4. Work order: #5983. Adds no RPC, public type or Token and touches no law M1 to M10. Refines N20 (`scenarios/project-store.md`): its "no historical schema has to survive" holds for data written before the Fork direction; from the head named below on, every migration is additive.

Why: a Fork runs a branch's build on a copy of the live data, and the owner can fall back to the previous build (deleting the Fork). Zero work loss needs the previous build to open what the new build wrote.

**MG1 an additive migration is the only kind that merges.** Given a migration file in `crates/storage/migrations/project/` that is on the change and not on `origin/main`, when the check parses its statements, then it passes only when every statement is `CREATE TABLE`, `CREATE INDEX`, `CREATE VIEW` (each `IF NOT EXISTS` or not), or `ALTER TABLE … ADD COLUMN` whose column is nullable or has a default. It fails, naming the file and statement, on `DROP`, `ALTER TABLE … RENAME` (table or column), `ALTER TABLE … DROP COLUMN`, and `UPDATE` or `DELETE` of a table that exists on `origin/main` (those change a meaning the previous build still reads). A migration file already on `origin/main` is never judged again. Asserted in `mg1_only_additive_statements_pass` and `mg1_dropping_renaming_or_rewriting_fails_naming_the_statement`. Policy: a migration that must change a meaning adds a new column or table the new build writes and reads, leaves the old one filled, and a later change removes it only after no build that reads it is kept.

**MG2 the previous schema is still there.** Given the database `origin/main`'s migrations build and the one the change's migrations build, when the check compares them, then every table, column (with its declared type) and index of the first exists in the second; the check fails naming each one missing or retyped. This catches what MG1's statement parse cannot see (a rebuilt table copied under its old name). Asserted in `mg2_a_table_rebuilt_without_a_column_fails` and `mg2_new_tables_columns_and_indexes_pass`. The comparison reuses the reference database `refuse_divergent` already builds (`reference`, `apply`); no second schema reader.

**MG3 the previous build opens a database one migration ahead.** Given a `project.db` written by a build whose sequence extends the previous build's, when the previous build opens it, then it opens, reads and writes every table it knows, and leaves the added tables and columns as they are. This replaces `refuse_divergent`'s refusal of `stored > known` with one that opens it when MG2 holds between the previous sequence and the stored one: the stored schema is a superset of the known schema, compared as MG2 does. A database that lacks something the build knows, or whose version is above `known` and fails that comparison, still refuses with the message it has. Asserted in `mg3_a_database_ahead_by_additive_migrations_opens` and `mg3_a_database_ahead_with_a_missing_column_still_refuses`; `user_version` is not lowered by the open (policy).

**MG4 the change's own migrations pass MG2.** Given the migration files on the change and not on `origin/main`, when the MG1 test builds the previous schema from the migrations without them and a second database from all migrations, then it asserts the MG2 comparison of the previous schema against the full one finds nothing missing, so a new migration that retypes or drops a table, column or index in a way MG1's statement parse misses fails the change naming it. Asserted by one test in the MG1 test file that holds the MG2 call; no second schema reader. Work order: #6001.

Observer: `cargo nextest run -p rupd mg1 mg2 mg3` on Linux, run by `check`'s Rust lane against the PR's own head, with `origin/main`'s migrations read through `git show` (the lane fetches `main`); cold start holds rule 7's 300 ms (the MG3 comparison runs only when `stored > known`).

Not in this scenario: the Fork copy, its name, colour, port or icons (their own Issues); other databases than `project.db`.
