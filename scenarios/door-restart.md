# Retry a failed fresh Door start (A4665)

A user-requested Restart can be retried with the same request after its fresh Door fails to start. This is a coordinator repair under the existing lifecycle contract, independent of the proposed lifecycle laws in `scenarios/agent-lifecycle.md`; it introduces no new RPC, public type or launch authority.

## Checks on main

1. `crates/rupd/src/restart.rs`, `Daemon::restart_session`: `workstream.restart` reserves the original Opening prompt before stopping the Door and persists `Starting` before calling `Agents::restart_door`.
2. `crates/agents/src/door.rs`, `Agents::restart_door`: a fresh conversation waits at most 15 s for its matching `SessionStart`; on timeout it attempts to stop that Door and returns the cause. A timeout alone is not proof that cleanup succeeded.
3. `crates/rupd/tests/support/opening_prompt.rs`, `a4452c_restart_sends_exactly_the_saved_prompt_once` and `a4452c_no_saved_prompt_starts_idle`: successful restart retains Workstream contents, types only its saved prompt once, or starts idle without one; completed-request replay keeps the same Attempt.
4. `crates/rupd/tests/support/opening_prompt.rs`, `a4452c_failed_recording_retries_without_another_physical_write` and `a4452c_unknown_input_outcome_never_retypes_on_retry`: recording retry does not type again, and an uncertain physical write is never replayed.

**A4665 a failed fresh start keeps the request retryable.** Given a Workstream and a user restart request, after its Opening prompt is reserved and `Starting` is persisted, make the fresh start fail either before any program starts or because its matching `SessionStart` does not arrive within the existing 15 s bound. Establish that no program from that failed start remains before allowing another launch. When the first call returns, then it reports the start failure, no Opening prompt has been typed or recorded as delivered, and the same request retains its original reserved text (planned test: `a4665_failed_start_retries_same_request`).

Given that failed request, when the start failure is removed and the user retries `workstream.restart` with the identical Workstream id and request id, then the call starts one fresh Attempt and completes instead of remaining stuck in an unknown outcome. It requires neither another Restart action nor a new request id. After matching `SessionStart`, a reserved prompt is typed byte for byte once and recorded as one delivered user note; without a reserved prompt, the Door starts idle and receives no typed input. A subsequent replay of the completed request returns the same successful Attempt, starts no program and types or records nothing again (same planned test).

Observer: extend the existing real-Daemon test harness in `crates/rupd/tests/support/opening_prompt.rs`, using its fake vendor and public `workstream.restart`. Parameterize the planned test over pre-launch refusal and missing `SessionStart`, each with a whitespace-sensitive multiline prompt and no prompt. For the timeout case, observe the failed program's termination before the successful retry; missing `SessionStart` must reach the real lifecycle wait and cleanup path, not a fabricated coordinator error. In the saved-prompt cases, change the Workstream's configured prompt after failure and before retry, and assert that the original reserved bytes, not the new setting, are typed and recorded. Count launches, live programs, Terminal input and delivered prompt notes across failure, successful retry and completed replay; assert at most one live Door at every observed launch. Use the existing harness bounds and event observers; no real vendor, browser or new public seam is required. The named test asserts every behavioral then-clause above; existing Checks 3–4 retain their independent proofs.

Policy: the initial user request authorizes this explicit retry (P9); failure never schedules an automatic launch. A persisted `Starting` record alone, a lost reply or a cleanup failure is not evidence that starting another program is safe. Unknown launch liveness remains an unknown outcome until authoritative reconciliation establishes no program remains; never reset all `Starting` records to retryable merely on reopen. `Typing` remains fenced as Check 4 requires. Preserve the original reservation until successful release, the Workstream and its children/Todos/Pads (P6), existing user-only authority and all Message ordering and Attempt guards. M1–M10 remain unchanged; any implementation changing Message contracts names affected laws and keeps `docs/messages.md` and `proofs/messages` agreeing. No UI change, automatic retry policy or general crash-recovery scheduler is requested.
