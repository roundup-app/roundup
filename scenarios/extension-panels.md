# An Extension draws a panel at the centre of its own Mode, and only the owner's click in roundup's window reaches it (EP1–EP21)

Module: `crates/rupd` (`src/extensions/`, `attention.rs`, `route/`), `crates/contracts` (`src/extension.rs`), `crates/agents` (the Rail node, the Ask store), `crates/perf`, `contracts/generated/`, `contracts/extension/history/`. Ids: EP1–EP21. Principles: P3, P14 and P16 (`PRINCIPLES.md`); MC46 (`scenarios/machine-custom.md`). Work order: [#8049](https://github.com/roundup-app/roundup/issues/8049); implementation follows in #8050 to #8058 and #8061, each naming its ids. This file is specification only: every test named here ships with its implementing Issue, and no App UI for the panel or the approval prompt is specified (the owner has not picked the draft).

Decided by the owner (2026-11-27):

- hum (`@moo.md/hum`) runs a queue of work items through Agents and needs the owner's answers. An Extension draws a panel in roundup's own components, at the centre of its own Mode on the Rail, and a click on it carries roundup's proof that it came through roundup's window.
- The interface only grows: no field, call or event is removed or renamed; an Extension declares the capabilities it uses (`uses`), roundup states what it offers (`hello`); no v2.
- A panel is data with actions as links, drawn by roundup's own components; no webview or iframe.
- The Extension host supervises `service` Extensions; health shows only on the Extension's own Rail node; a wait shows only in its panel: no Inbox row, count, Toast or badge from an Extension.
- The Project Program (PG1–PG6) is removed everywhere in one PR (EP16).
- `agents.settings` only by the owner's approval per Extension, made with an attested click; an approval pins folder, name and capabilities (no module hash); a new capability asks again.
- Stay unsigned (no Apple Developer ID). Agents editing Extension files is by design out of roundup's scope (harnesses manage Agent access). GUI automation is out of scope: roundup proves a click came through roundup's window, not that your hand made it: any program you allowed to control your computer can click hum's buttons for you.
- An Extension's panel shows no token, cost or cap numbers; P14 stays as is.
- The Ask bar is the one place to write to an Extension (EP19–EP21).
- Precedence: when a design check reads one of these as a defect, change how it is drawn, never the decision. When two cannot both hold, the run asks the user (`flag:needs-user`).

New terms (Panel, Render, Attested connection, Extension capability) enter `GLOSSARY.md` in the implementing PRs (Contract recipe of `.agents/builder.md`).

## The proof that a click came through roundup's window

**EP1 the App's connection is attested by a secret only it holds.** Contract change (the Contract recipe). Given `rupd --attached --notify-bound`, when it starts, then it writes `rupd-bound <secret>` on its stdout, a fresh 32-byte random secret per start in hex, and the secret appears in no log, file, environment variable or child's argv. The App keeps it in memory and sends `app.attest {secret}` as the first call on every connection it opens; rupd compares in constant time and marks that connection attested. A method behind the new `Gate::Attested` is `FORBIDDEN` on a connection that did not attest; a connection that sent no secret, a wrong one, or the previous start's gets `FORBIDDEN` from `app.attest` and stays unattested. No existing `UserOnly` method moves to the new gate, so the `rup` commands the owner types keep working. Tests: `ep1_an_attested_connection_reaches_an_attested_method`, `ep1_no_secret_a_wrong_one_or_an_old_one_is_forbidden`, `ep1_the_secret_is_logged_nowhere_and_passed_to_no_child`, and, in `crates/desktop`, `ep1_the_client_attests_first_after_parsing_the_bound_line`.

**EP2 `daemon.identify` refuses a `user` claim.** Contract change (the Contract recipe). Given `daemon.identify {kind: "user"}` on any connection, then it is `FORBIDDEN` and the next call on that connection runs as the Actor it ran as before; `agent` and `ext` claims work as they do today (EP16 refuses `ext`). Every caller in the repository that claims `user` changes in the same PR. Threat-model row closed: an Agent connecting to the socket and claiming the user. Test: `ep2_identify_refuses_a_user_claim`.

## The contract only grows

**EP3 the Extension contract is one schema that only grows.** Contract change (the Contract recipe). Given `crates/contracts/src/extension.rs`, it defines every frame between rupd and an Extension and the `Panel`, and rupd's `extensions/` code reads and writes frames through its types, so no second definition stays. Extension to roundup: `registered`, `call`, `result`, `failed` (unchanged), `show {ask, panel}` and `health {note}` (at most 80 characters). Roundup to Extension: `run`, `callResult` (unchanged), `hello {offers, granted, components}`, `shown {ask, render}` or `shown {ask, refused: {code, cause}}`, `click {id, render, element, action, args, inputs, by: "user", via: "app"}` and `stop {reason: "user" | "reload" | "rupd"}`. A `Panel` is `{root, elements: {id: element}}`; the first components are `stack`, `heading`, `text`, `row`, `chip` (tone `neutral`, `waiting` or `fault`), `button` (action `{name, args}`) and `input` (label, name), and the set only grows; text is plain, with no markup, link or image, and labels are capped. The capabilities are `panel`, `service`, `agents.place` and `agents.settings`. The generated schema is written to `contracts/generated/extension/` and its snapshots are kept append-only in `contracts/extension/history/`. Allowed on the Extension-to-roundup side: a new optional field, enum value or frame; refused: removing or renaming a field, value or frame, making an optional field required, narrowing a type. Allowed on the roundup-to-Extension side: a new field, and a new frame or enum value sent only to an Extension that declared its capability; refused: removing or renaming a field, value or frame, changing a field's type. Tests: `ep3_the_generated_schema_equals_the_newest_snapshot`, `ep3_a_snapshot_that_drops_a_field_fails_naming_the_field_and_direction`, `ep3_a_snapshot_that_adds_an_optional_field_passes` (`crates/contracts/tests/ext_accretion.rs`). Policy: a PR that edits an old snapshot is rejected in review, since the test cannot see it; no v2 and no deprecation layer.

**EP4 an Extension ignores what it does not know.** Given an Extension registering an event other than `action`, then its actions are still published and nothing throws during registration; given a frame, field or enum value the SDK does not know, then it is ignored. This amends UA's load-failure clause: an unknown event is no longer a load failure. Tests: `ep4_an_unknown_event_does_not_stop_the_actions_publishing`, `ep4_the_sdk_ignores_unknown_frames_and_fields`.

## Capabilities

**EP5 a capability is granted only by the owner's attested approval.** Contract change (the Contract recipe). Given a manifest with `uses: [capability]` beside `permissions`, read before the Extension starts, then rupd sends `hello {offers, granted, components}` first on its stdin. `service` is granted on declaration. `panel`, `agents.place` and `agents.settings` are granted only when the owner approved them: an approval method behind `Gate::Attested` records the folder, the name and the set of capabilities asked, and a read method lists each Extension's asked, granted and waiting capabilities. The approval holds while folder, name and set all match; a manifest that adds a capability or changes its name is granted none of the three until approved again. No module hash is pinned. A frame or field that needs a capability is sent only to an Extension granted it. Tests: `ep5_an_extension_asking_panel_is_granted_it_only_after_an_attested_approval`, `ep5_the_approval_call_on_an_unattested_connection_is_forbidden`, `ep5_adding_a_capability_asks_again_for_all_three`, `ep5_service_is_granted_on_declaration`.

**EP6 an Extension's store and Actor are keyed by its folder.** Given two folders whose manifests share one `name`, then they are two Extensions: each has its own `$.store`, its own `ext:<folder>` Actor and its own approval, and neither gets the other's. Threat-model row closed: an Agent writing a folder that reuses an approved Extension's name. Policy: an Agent can still edit an approved Extension's own files, since it runs as the owner; harnesses, not roundup, manage that. Test: `ep6_a_second_folder_with_the_same_name_gets_its_own_store_actor_and_no_approval`.

**EP7 `agents.settings` starts an Agent with Claude Code settings only for an approved Extension.** Given `agent.spawn` carrying `settings` on the stdio of an Extension granted `agents.settings`, then the Agent starts; from an Extension not granted it, the call is `FORBIDDEN` and nothing starts. ST1, ST4 and ST5 (`scenarios/start-settings.md`) gain "or an Extension you approved for `agents.settings`" beside the user and the Project's program, so such an Extension may also set a permission mode through `settings`; the program clauses stay until EP16 deletes them. Tests: `ep7_spawn_with_settings_starts_for_an_extension_granted_agents_settings`, `ep7_spawn_with_settings_from_an_ungranted_extension_is_forbidden_and_starts_nothing`.

## The panel and its click

**EP8 render ids never repeat.** Given an Extension sending `show {ask, panel}`, then rupd validates the panel against the component set, mints a render id from a counter kept in the Project DB, answers `shown {ask, render}` (or `shown {ask, refused: {code, cause}}`) on the Extension's stdin and emits `panel.changed {folder, render}`; a read method returns the current panel for the App. One `show` is unanswered at a time. The counter survives a rupd restart, an Extension restart and a hot reload. Tests: `ep8_a_show_is_answered_with_a_render_and_panel_changed`, `ep8_an_invalid_panel_is_refused_with_a_cause`, `ep8_render_ids_after_a_rupd_restart_exceed_every_earlier_one`, `ep8_render_ids_keep_counting_across_an_extension_restart`.

**EP9 one click per render, only from the attested App.** Contract change (the Contract recipe). Given `panel.click {render, element, inputs}`, behind `Gate::Attested`, then rupd passes it only for the render it holds now and only once, reads `action` and `args` from the render it stored, and writes `click {id, render, element, action, args, inputs, by: "user", via: "app"}` with a fresh click id to the Extension. A click on an unattested connection, on a replaced render (including one sent across an Extension restart) or on a spent render is refused, naming `not attested`, `stale` or `used`, and no `click` frame is written. Only rupd's Extension host writes a `click` frame: `action.run`, `action.list`, `rup do` and MCP tools never make one. The Extension's SDK acts only when the render is its newest, no newer `show` is unanswered and the click id is unseen. Threat-model rows closed: a click fired through RPC, `rup do`, an MCP tool or `action.*`; a stale click; a replayed click. Tests: `ep9_a_click_on_an_unattested_connection_is_refused_and_writes_no_frame`, `ep9_a_second_click_on_one_render_is_refused_used`, `ep9_a_click_on_a_replaced_render_or_across_a_restart_is_refused_stale`, `ep9_the_click_frame_carries_the_stored_action_and_args`, `ep9_no_other_path_writes_a_click_frame`, `ep9_the_sdk_acts_only_on_its_newest_render_and_a_new_click_id`.

**EP10 a panel pulls no attention.** Given an Extension granted `panel` that sends `show`, then `attention.rs` lets the `panel` path through only for that capability; a `show` moves no selection, focus or unread mark and raises no `extension.problem`, Toast, alert, badge, count or Inbox row; a panel beside the centre, a Toast or a badge from outside stay refused (MC46). `health {note}` is kept for the Extension's node and raises nothing. An Extension's panel shows no token, cost or cap numbers: rupd draws only what the Extension sends, so this is policy for what roundup itself adds to a panel, enforced in review (P14 stays as is). Tests: `ep10_a_show_raises_no_problem_toast_or_alert_event`, `ep10_panel_passes_attention_only_for_the_panel_capability`.

**EP11 the first fixture runs on rupd.** Given `crates/rupd/tests/extensions/2026-12-echo-<hash6>/`, an Extension written against this interface that shows a panel, takes a click and shows the next one, then `crates/rupd/tests/ext_fixtures.rs` lists every folder there and runs each on rupd as a case named by its manifest `name`, the echo fixture's being `ep11_echo`. A folder's name ends in the first six hex digits of the SHA-256 of its content, and the test fails when they differ, so a fixture is never edited in place. Tests: `ep11_echo`, `ep11_a_fixture_whose_name_hash_differs_from_its_content_fails`. Policy (review): a PR that deletes a fixture folder is rejected.

## The Extension's Mode on the Rail

**EP12 an Extension's Mode is a node on the Rail.** Contract change (the Contract recipe). Given an Extension granted `panel` or `service`, then `rail.tree` lists one Mode node for it among the Modes, keyed by its folder, carrying its name, its health state and latest `health` note, and whether a panel is current; it has no Agent and no Terminal, and selecting it shows the panel at the centre (App drawing is a later UI Issue). An Extension granted neither has no node. The node raises no alert, Toast, badge, count or Inbox row; a `health` frame changes only what the node shows. A4452c gains the Extension's Mode: a Mode is an Agent holding one saved Mode prompt, or an Extension's Mode, which holds its panel instead. Tests: `ep12_a_panel_extension_appears_once_in_the_rail_as_a_mode_keyed_by_its_folder`, `ep12_an_extension_granted_nothing_has_no_node`, `ep12_a_health_frame_changes_the_nodes_note_and_raises_no_alert`.

**EP13 `agents.place` puts the Agents an Extension starts under its Mode.** Given `agent.spawn` on the stdio of an Extension granted `agents.place`, then the Agent sits under that Extension's node, whatever parent the call names; rupd takes the parent from the stdio the call came on, never from a caller field. Without the grant the Agent goes where it goes today (the Project root). The Agents stay the owner's (P6) and their Provenance names the Extension as starter. Tests: `ep13_a_spawn_from_an_extension_granted_agents_place_sits_under_its_node`, `ep13_without_the_grant_the_agent_goes_to_the_project_root`.

## Supervision

**EP14 rupd supervises `service` Extensions.** Contract change (the Contract recipe). Given an Extension granted `service`, then rupd starts it when the Project opens with `node --disable-sigusr1`, no `NODE_OPTIONS`, stdin and stdout as the protocol and stderr to a capped log; when it exits without the owner's asking, it restarts after 1 s, doubling to 30 s with no jitter, and 60 s alive resets the wait; one timer runs at a time. A hot reload is a stop and a start, and render ids keep counting. Restart, Stop and Start methods take the Extension's folder and sit behind `Gate::Attested`. The node's health reads `Running`, `Restarting in N s, exited (code)`, `Stopped by you` or `Refused: cause`, plus its `health` note, and raises no Toast, badge, count, Inbox row or alert. An Extension without `service` is not restarted: UA6 holds for it. Tests: `ep14_a_killed_service_restarts_after_1_s_then_2_s`, `ep14_sixty_seconds_alive_resets_the_wait`, `ep14_the_node_health_reads_each_state_and_raises_no_alert`, `ep14_an_extension_without_service_is_not_restarted`, `ep14_restart_stop_and_start_are_forbidden_unattested`.

**EP15 a Stop holds.** Given the owner's Stop, then rupd sends `stop {reason}`, closes stdin, waits 5 s, then kills; nothing restarts the Extension afterwards, and the hold survives a rupd restart until the owner's Start. Tests: `ep15_stop_sends_stop_and_kills_a_child_that_ignores_it_after_5_s`, `ep15_after_stop_nothing_restarts_it_also_across_a_rupd_restart_until_start`.

## Writing to an Extension

**EP19 an Ask to an Extension's Mode reaches it as an `ask` frame, only from the attested App.** Contract change (the Contract recipe). Given `ask.send {text}` where an `@<name>` token names a loaded Extension's Mode node and no Workstream has that name, then no Placement call runs, the part's Placement names that Extension (a new variant beside `routed`), and rupd writes `ask {id, text, item?, by: "user", via: "app"}` on the Extension's stdin, `text` being the part's text with the `@<name>` token and the item token cut (a leading `@<name> ` as A40 cuts it; mid-text, the token and one adjoining space), `item` the token after `#` directly following `@<name>` (absent when none), and `id` a fresh ask id the SDK drops when seen twice; the part reads `typed` (Sent) once the frame is written. A name that is also a Workstream's names the Workstream. With a second `@` naming a different Workstream or Extension, A40's Placement rule holds and a part placed on an Extension is delivered the same way. rupd writes the frame only when the call came on an attested connection and the Extension is running and granted `asks`; otherwise it writes nothing and the part is `failed` with a cause naming which of the three failed. Only rupd's Extension host writes an `ask` frame: `rup`, an MCP tool, `action.run` and an unattested RPC never make one, and `ask.send` stays the user's call (A40, M2). A40's "Naming a Workstream skips the call" also holds for an Extension's Mode. Tests: `ep19_an_ask_to_a_mode_reaches_its_extension`, `ep19_only_an_attested_ask_reaches_an_extension`, `ep19_no_other_path_writes_an_ask_frame`.

**EP20 a panel button may open the Ask bar on an item.** Given a button whose action is `{ask: {item}}` (an `ask` field beside `name` and `args`, optional and added; when `ext_accretion` refuses making `name` optional, it carries `name: "ask"` and `args: {}`), then the App opens the Ask bar on `@<mode> #<item> ` with the cursor after it; clicking it sends no `panel.click`, spends no render and writes no `click` frame. rupd answers a `show` holding an ask action with `shown {refused}` when the Extension is not granted `asks`. The panel keeps no text field of its own: `@hum` in the Ask bar files a new hum item, and Write a note / Request changes in hum's panel open the same Ask bar aimed at the open item. Test: `ep20_a_button_may_open_the_ask_bar`.

**EP21 `asks` is offered to every Extension and granted by approval.** Given the capability `asks` (an Ask to the Extension's Mode), then `hello.offers` holds it for every Extension and `hello.granted` holds it only after the attested approval of EP5; adding `asks` to an approved manifest grants none of the approved set until approved again. Test: `ep21_asks_is_offered_and_granted_by_approval`.

Policy, out of scope: GUI automation (see the owner's sentence above); Agents editing Extension files; a replaced rupd or a hand-run Extension, since an Agent running as the owner can start any process. Observer: `loop/rules.sh vocab` exits 0.
