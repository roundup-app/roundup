# Terminals

Module: `crates/terminal`. Ids: X1–X10, X13, X17.

**X1 output.** Given a Project, when `terminal.spawn {command: ["/bin/sh","-c","echo hi"]}` is called and a client is subscribed, then a `terminal.output` event whose base64 `data` decodes to bytes containing `hi` is emitted.

**X2 input.** Given a Terminal running `cat`, when `terminal.write` sends `"ping\n"` (base64), then `terminal.output` events carry `ping` back.

**X3 exit.** Given a Terminal running a command that exits with code 3, then `terminal.exited {code: 3}` is emitted and `terminal.list` shows `running: false, exit_code: 3`. A program killed by a signal has `code: null`.

**X4 title.** Given a Terminal whose program prints the OSC sequence `ESC ] 0 ; hello BEL`, then `terminal.title {title: "hello"}` is emitted and `terminal.list` shows `title: "hello"`. A later title replaces it.

**X5 resize.** Given a Terminal spawned at 80x24, when `terminal.resize {cols: 100, rows: 30}` is called, then a program that prints its size (`stty size`) reports `30 100`.

**X6 kill.** Given a running Terminal, when `terminal.kill` is called, then the program stops, `terminal.exited` is emitted, and the Terminal stays in `terminal.list` as exited. Killing an exited or unknown Terminal is `NOT_FOUND`.

**X7 cwd and env.** Given `cwd` and `env` in `SpawnParams`, then the program runs in that directory and sees those variables (and the parent's, minus nothing).

**X8 in-process API.** The same operations (spawn, write, resize, kill, subscribe to a Terminal's events) are plain async Rust methods on `Terminals`, usable without a socket; the agents module calls them. Output events keep arriving to a subscriber in order, and a slow subscriber never blocks the PTY reader.

**X9 a stuck write never blocks kill.** Given a Terminal whose program never reads its input, when more writes are issued than the blocking pool has threads and then `terminal.kill` is called, then `kill` returns within `PATIENCE`. A write that cannot be queued is `CONFLICT`, never an unbounded wait. After `terminal.kill` has returned, the program is gone and a second kill is `NOT_FOUND`.

**X10 spawn errors and titles.** A program that cannot be found or run, and an id that is not the canonical form of a Terminal id (`+5`, `05`), are `INVALID_PARAMS` whose message names only `argv[0]` or the id, never the Daemon's `PATH`; a real fork or exec failure stays `INTERNAL`. A title such as `ESC ] 0 ; build; test BEL` is emitted whole, `build; test`.

**X13 read a Terminal's output.** Found by the user's report #814: an Agent started a Run and could not read what it printed. Contract change (the Contract recipe of `.agents/builder.md`, rule 4): new Daemon methods `terminal.screen`, `terminal.read` and `terminal.search`, with every caller (`crates/rup`'s tools, M13) in the same PR; `GLOSSARY.md` gains **Output log**. Each takes a Terminal `id` and only reads. Decided here, each a numbered engineering call changed only by a later scenario:
1. **Output log.** Each Terminal keeps its last 1 MiB (1 048 576) of output bytes, the same bytes the `terminal.output` events carry, and an offset is the same running byte count as `terminal.output`'s `offset` and `Snapshot.after`. Older bytes are dropped. The log ends with its Terminal (X11, X12) and an exited Terminal's stays readable until `terminal.close`.
2. **Plain text.** Every reply is UTF-8 text with escape sequences (CSI, OSC, other `ESC` forms) removed, `\r\n` as `\n`, and a bare `\r` redraw kept as the line's final form; an invalid byte is U+FFFD. An Agent never receives a colour code.
3. **Caps.** Every reply is at most 16 384 bytes of text, cut on a character boundary, and says when it was cut (`truncated: true`) and where to continue. A request's own `max` may only lower the cap; a `max` of 0 or above the cap is `INVALID_PARAMS`.

- `terminal.screen {id}` returns `{cols, rows, offset, lines}`: the screen as it is now, one string per row, trailing blanks trimmed and trailing empty rows dropped, `offset` the log's end when the screen was copied. A screen larger than the cap keeps its top rows and sets `truncated: true`. Test: `x13_screen_returns_the_visible_rows_as_plain_text_and_the_offset`, `x13_screen_over_the_cap_is_cut_and_says_so`.
- `terminal.read {id, after, max?}` returns `{from, next, text, truncated}`: the output from offset `after` on. `after` equal to the log's end returns `text: ""` and `next: after`; reading again from `next` returns exactly the bytes printed since, no byte twice and none missed, also when a multi-byte character straddles the cap. An `after` older than the log's start begins at the start: `from` is that start and exceeds `after` (the gap is visible). An `after` beyond the log's end is `INVALID_PARAMS`. Test: `x13_read_from_next_returns_only_what_is_new`, `x13_read_at_the_end_is_empty`, `x13_read_never_splits_a_character_or_repeats_a_byte`, `x13_read_older_than_the_log_starts_at_the_log_start`, `x13_read_past_the_end_is_refused`.
- `terminal.search {id, pattern, after?, max?}` returns `{matches, truncated, next}`; `matches` are `{offset, text}`, one per matching line in order, `offset` the byte offset of that line's start and `text` the line cut at 400 characters. `pattern` is a regular expression of Rust's `regex` crate (linear time, compiled at most 64 KiB) and an invalid or oversized one is `INVALID_PARAMS`; `after` defaults to the log's start. At most 50 matches are returned and the reply is under the cap; when more exist `truncated` is true and `next` is the offset to search from for the rest, else `next` is the log's end. Test: `x13_search_returns_only_matching_lines_with_their_offsets`, `x13_search_resumes_from_next_without_a_repeat`, `x13_search_caps_matches_and_line_length`, `x13_an_invalid_pattern_is_refused_and_a_match_free_log_gives_none`.
- Reading changes nothing: after any of the three, the Terminal's screen (`terminal.snapshot`), its running or exited state and its log are what they were, no byte is written to the program, and no `terminal.output`, `terminal.changed` or `rail.changed` is emitted. An unknown id is `NOT_FOUND`. Test: `x13_reading_writes_nothing_and_changes_no_screen_state_or_event`, `x13_an_unknown_terminal_is_not_found`.
- A 1 MiB log is searched within `PATIENCE` and holds no lock while it is, so the program's output and `terminal.kill` are never blocked (X9). Test: `x13_searching_a_full_log_does_not_block_output_or_kill`.

Tests (`x13_`, Rust, in `crates/terminal/tests/` and `crates/rup/tests/`), plus a generated-contract case that regenerating changes nothing. Observer: `just check` and the real-Daemon run (the U144 harness) that runs `printf` lines in a Terminal, reads from an offset, searches and sees the same result as the Rust tests.

**X17 a program's colour query is answered from the App's scheme.** Found by the owner's report: Claude Code asks for the background colour (OSC 11) about 0.3 s after it starts and keeps its dark palette for the session when nothing answers, so a Terminal in the light scheme showed dark colours (U59). The App's emulator is not attached then, or at all for a Door's child that is not shown, so the Daemon answers. Contract change (the Contract recipe of `.agents/builder.md`, rule 4): new method `terminal.scheme {scheme: "light" | "dark", background, foreground}` (the two colours as `#rrggbb`, taken from the emulator's theme so they have one source), with its caller, the fake App and `contracts/generated/` in the same PR; `GLOSSARY.md` gains **Terminal scheme**. Decided here:
1. **Answer.** Once `terminal.scheme` has been called, a program's OSC 10 or 11 query `?` gets one reply of the current colour (`rgb:rrrr/gggg/bbbb`, ST-terminated), DA1 (`ESC [ c`) gets one reply, and DSR 996 (`ESC [ ? 996 n`) gets `ESC [ ? 997 ; 1 n` for dark or `2` for light, for every running Terminal, shown or not, in the order asked. Before the first call nothing is answered. A colour that is not `#rrggbb` is `INVALID_PARAMS`. Tests: `x17_a_colour_query_gets_one_reply_in_the_current_scheme`, `x17_no_scheme_set_means_no_reply`, `x17_a_colour_that_is_not_hex_is_refused`.
2. **Notice.** A program that turned on mode 2031 (`ESC [ ? 2031 h`) and not turned it off gets `ESC [ ? 997 ; Nn` once each time the scheme changes, and a program that did not gets nothing; the same scheme sent again changes nothing. Test: `x17_a_switch_sends_one_notice_to_programs_that_asked_for_them`.
3. **App.** The App calls `terminal.scheme` when it connects to a Project's Daemon, before any Terminal is spawned, and again whenever the window's scheme switches, with the colours of `terminalThemeFor` (U59). Its emulator answers none of OSC 10, OSC 11 or DA1 itself, so no program gets two replies. Tests: `x17_connecting_tells_the_daemon_the_scheme_and_each_switch_tells_it_again`, `x17_the_emulator_leaves_a_colour_query_and_da1_to_the_daemon` in `apps/desktop/src/terminal/`.

Tests are `x17_`. Observer: `just check`, and a real `claude` on the mock model whose palette is read from its first screen in each scheme and after a live switch (artifacts in `artifacts/ux/terminal-colour-query/`). Policy: the reply format and DA1's answer are chosen here; a later scenario changes them.
