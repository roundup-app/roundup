# Rust and test libraries: measured adoption

Work order: #3802. This specification defines seven independent keep-or-drop decisions. It adds no library and claims no implementation or performance pass. Implementation Issues depend natively on #3802; each row may land in its own crate/module PR without waiting for another row. Progress, measurements and engineering questions belong on the implementation Issues, not in scenario Work tables.

## Shared acceptance

Policy: each row finishes with either a merged implementation meeting its keep condition or a drop record on its implementation Issue, linked from #3802. A drop record names the library/version, measured value and failed threshold (or the specific missing capability and reproducible probe), exact command, exit status, reference commit and primary source. No improvement, an unavailable release or a demonstrated capability failure permits dropping the candidate; inability to access a measurement host does not. File/reuse a measurement prerequisite for unavailable hardware under `docs/perf.md`, heading `Execution hosts`. Do not install a rejected candidate or leave its spike/dead dependencies in production.

Policy: every row's PR carries a `Reuse:` section comparing at least two candidates with crates.io/npm source links, versions, last release dates and download counts dated at observation time. Read installed Cargo/pnpm dependencies, patches and platform features first. Reject a candidate by a demonstrated missing capability, licence, measured size/performance cost or lack of recent releases, never implementation effort. Keep the owner-approved candidates below as the first candidates; alternatives are comparisons, not authorization to broaden the batch. `tauri-specta`, `anyhow`, Quint and Shader Gradient are excluded.

Policy: split by owning crate/module (AGENTS rule 3); include shared dependency/lockfile edits with their owning change. Preserve contracts, permissions, persisted data and existing scenario behavior. Add no RPC or App seam command. Retain tests that prove distinct behavior and remove redundant ones under rule 10 when editing their file, recording which remaining test proves each removed clause. New behavioral tests use the lowercase scenario id; names below are planned tests, not claims they already exist. Measurements and diff inventories are policy evidence, not tests that reread source/configuration. Run `just lint-web`, `just lint-rust` and tests reached by changed files; CI judges the complete push.

Policy: performance pairs use one physical host and one observation session, the same observer/workload and release settings, with only the candidate code/dependency changed. Record full before/after commits, binary hashes, toolchain, profile, lockfiles, host identity, load, all samples, units, exit statuses and retained reports. Use `just perf`'s eleven-sample medians, absolute limits, class baselines and load qualification unchanged. Retain failed/busy/skipped runs and repeat them; a skipped comparison proves no keep condition. No baseline increase, budget relaxation or changed observer can establish a saving. This is the Issue's same-host evidence requirement; P2 separately protects concurrent Worktree isolation.

## Gates and observers

Policy: P2 asks whether concurrent Agents can share a cwd; all implementation/measurement work uses isolated Worktrees, observed by `git worktree list` and each process's cwd. P4/P9 ask whether changed paths read vendor details outside the Adapter, replace user setup, start an Agent or type an unauthorized prompt; inspect the changed production callers and run their existing launch/delivery observers. P11 asks whether a changed reducer loses, sends or retargets unfinished work; exercise its existing continuity observer when that surface changes. P14 asks whether diagnostics read/store/send usage or money; spans contain method identity and outcome, no request/reply bodies, Terminal input, credentials or vendor usage. Observe actual captured tracing fields in Z3802a. No visual or native-window change is ordered.

These numbered checks identify current constraints; they are not proof of future adoption.
