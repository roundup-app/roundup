# UI: the Fork sheet

Module: `apps/desktop` (a new `fork/` directory, `ui/TreeView.tsx`, the application menu's event in `App.tsx`) and the two App seam commands below, whose host side is `crates/desktop`. Ids: FS5979a–FS5979e. Work order: [#5979](https://github.com/roundup-app/roundup/issues/5979). Terms: Fork, Project, Door, Agent, Rail, Tokens (`GLOSSARY.md`). Principles served: P5 (`PRINCIPLES.md`). Needs `scenarios/data-fork.md` (FK5977a–f), which owns `data.fork` and the colour set, and the Fork colour Tokens of `apps/desktop/src/tokens.css` (U130). Contract change (rule 4): two new App seam commands, `fork_branch` and `fork_make`, each with the sheet as its one caller; `scenarios/app.md`'s seam table and every host and fake caller change in the same PR; no Daemon method is added. Tests use the App against its fake App seam and a fixture `rail.tree`; no Daemon, `claude`, network or display. All tests below are planned observers, not passing claims.

**FS5979a the application menu offers "Fork for development…".** Given the mounted App with any Project open, when the application menu's `Fork for development…` item is chosen, then one sheet opens, centred by `ui/Dialog.tsx`; choosing it again while open opens no second sheet. With no Project open the item is present and disabled. Policy: the sheet is the only Fork control and adds no Rail control. Tests (`fs5979a_`): the menu event through the seam opens one sheet with role `dialog`; a second event leaves one; no Project leaves the item disabled and opens none.

**FS5979b the sheet is the Rail tree with every row ticked.** Given a Rail holding two Projects, a Door with child Agents and Agents under a Project, when the sheet opens, then it shows that tree as `ui/TreeView.tsx` over Ark UI's `TreeView` with `NodeCheckbox`, in the Rail's order and nesting, each row labelled with the Rail's name, and every row is ticked, every time it opens, whatever the last sheet left unticked. Unticking a Project, a Door or an Agent unticks every row under it; a parent with some rows ticked shows the mixed state; ticking a row ticks the rows above it, so no Agent is kept without its Door and Project. Tests (`fs5979b_`): the opened tree matches the fixture's nesting and every checkbox is checked; unticking each kind clears its descendants; a part-ticked parent reports `indeterminate`; ticking an Agent re-ticks its Door and Project; closing after unticking and opening again shows all ticked.

**FS5979c the name and the colour.** Given the open sheet, then its name field holds the branch name returned by `fork_branch`, selected so typing replaces it, and a row of eight swatches, one per Fork colour (`red`, `orange`, `amber`, `green`, `teal`, `blue`, `violet`, `pink`), each drawn from that colour's Token and named by its colour word, forms one radio group with `teal` chosen first. Arrow keys move the choice; a swatch uses no value outside Tokens (rule 8). A name of 0 or over 40 characters, or holding a control character, marks the field invalid and Enter makes no Fork. Tests (`fs5979c_`): the field's initial value and selection from a fake `fork_branch`; the radio group's eight roles, names and arrow movement; each invalid name leaves `fork_make` uncalled. The design critic judges looks and the Token use at 1512×950 (rule 10).

**FS5979d Enter makes the Fork and opens its App.** Given the sheet with some rows unticked, a name and a colour, when the user presses Enter in the name field (or presses the sheet's `Make Fork` button), then `fork_make` is called once with `{name, colour, projects}` where `projects` holds one `{key, agents}` per ticked Project, `agents` being `all` when every Agent under it is ticked, `none` when none is, else the ticked Agent ids; an unticked Project is absent, and no pick for Todos, Pads, Messages or History is sent (FK5977b defaults them to true). The seam command makes the Fork (`data.fork`, FK5977a–f) and opens the branch's App on it, then the sheet closes. While the call runs the button is disabled and a second Enter sends nothing. Tests (`fs5979d_`): the params for all ticked, one Project unticked, one Agent unticked and an Agent-less Project; one call for two Enters; the sheet closes only after the call resolves.

**FS5979e a failed Fork stays on the sheet.** Given `fork_make` rejects, when the call returns, then the sheet stays open with the ticks, name and colour as the user left them, shows the rejection's text beside the button and as a `role="alert"`, and enables the button for another try; nothing else opens. Tests (`fs5979e_`): a rejecting fake seam keeps every choice and shows the text; a retry that resolves closes the sheet.

**Seam.** `fork_branch`: none → the name of the git branch the live App's source checkout is on, or `fork` when it has none. `fork_make`: `{name, colour, projects}` → `null`; the host chooses the Fork's folder under `$ROUNDUP_HOME`, makes it with `data.fork`, starts the branch's App on it (its own port, `.app` and identity are #5980's and the launcher's work) and rejects with the failure's text. It touches no running Agent, Terminal or Worktree of the live App (FK5977e). Policy, Mac observer: the user reports the branch's App opening on the Fork after a real `Fork for development…`; Chromium cannot show the native menu or the second App.

**FS6102a the Fork's folder is its own subfolder whatever the name.** Given `fork_make` with a name holding no ASCII letter or digit (such as `日本`) and no `forks` folder under `$ROUNDUP_HOME`, when the host chooses the Fork's folder, then the folder is a new subfolder of `$ROUNDUP_HOME/forks` named `fork`, never `$ROUNDUP_HOME/forks` itself; a second such name gets `fork-2`, never `-2`. A name with ASCII letters or digits keeps its slug, and a taken folder name still gets the next `-N` suffix. Tests (`fs6102a_`, Rust, on the host's folder-choosing function): `日本` on an empty home returns `forks/fork`; two such names return `forks/fork` and `forks/fork-2`; `my fix` returns `forks/my-fix`.

**U6266a Make Fork opens the Fork's window.** Given a live App started by `just app`, so `ROUNDUP_DEV_PORT` and the live App's other per-instance variables are set in the host's environment, when `fork_make` starts the Fork's App, then the start's environment holds the Fork's own dev port and `ROUNDUP_DATA_DIR` set to the Fork's folder, and none of the live App's per-instance variables (`ROUNDUP_DEV_PORT`, `ROUNDUP_RUPD_BIN`). `fork_make` resolves, and the sheet closes, only once the Fork's App has started; when the start's program exits non-zero before it is up, `fork_make` rejects with that program's last error line and nothing else, and the sheet stays open showing that line (FS5979e). Tests (`u6266a_`, Rust, on `fork::open`): the built command's environment, read without starting anything, carries none of the live App's variables when they are set in the parent and carries the Fork's folder; a program that prints an error and exits 1 makes `fork_make` fail with that last line. The Mac observer: Make Fork opens a second window titled with the Fork's name within the first build's time while the live App keeps running (policy; Chromium cannot show the second App).

**U6266b a Fork's .app opens its own Fork.** Given the `.app` that `fork_app::make` writes for a Fork (FA5980b), when it is opened from Finder or the Dock with no `ROUNDUP_DATA_DIR`, then the binary resolves the Fork's folder as its data folder, shows the Fork's name, colour and icon, and uses neither the live App's data folder nor its single-instance socket. Tests (`u6266b_`, Rust): the `.app` read back from disk makes the binary's data folder resolve to the Fork's folder; the live App's folder is not chosen.

**U6266c the whole Fork path works end to end.** Given a real App started by `just app`, when the user makes a Fork with no Agents and one with all Agents, opens each, resumes a forked Agent, closes the Fork, reopens it from its `.app` and makes a second Fork while one runs, then every step succeeds and the live App's processes, data and Agents are untouched. Policy, Mac observer: the PR body lists each step with its result; Chromium cannot run the second App.
