**Machine page** (`Machines` in App Settings): the Settings page that lists the Machines, opens the Add dialog and removes one. It is not a sidebar, a Rail level or a dispatch panel.

**MC70 App Settings has a Machines page.** Amends MC2 and MC3; the design is Herdr's Settings › Machines (#7260). Given App Settings (U3799), then its page list holds **Machines**, and the page shows, top to bottom: one line saying these are the user's computers, reached over ssh, with terminals that keep running; the **This computer** row (MC74); each other Machine herdr-core lists in the order it lists them; **No other machines yet.** when it lists none; and an **Add a machine** button. Each other Machine row holds its name, **Online** or **Offline** with a status dot (MC74), **Remove** (MC71) and **Update** only under MC75. **This computer** has no action. The page holds no Add field: **Add a machine** opens a Dialog (`ui/Dialog.tsx`) that Escape closes, and that holds one line saying what adding does, **From your ssh config** (MC73) and **Or type how ssh reaches it**, a field with **Add**. A Machine shows on this page and as a chip or status on an Agent, and nowhere else: no sidebar, no Rail level, no dispatch panel (P16 holds). `machine.add` stays callable by the App as well as a Door (MC2). The page's buttons use the App's UI font and the button kinds of the rest of Settings (policy; the design critic judges it against Herdr's page). Tests: `mc70_machines_page_lists_this_computer_first_then_the_others` (by role: the first row is This computer with no button, the next rows are the listed Machines in order, each with **Remove**); `mc70_no_other_machines_reads_the_empty_line` (by text, with none listed); `mc70_the_page_has_no_add_field_and_the_button_opens_the_dialog` (by role: no textbox on the page, **Add a machine** opens a dialog, Escape closes it and focus returns to the button); `mc70_no_machine_sidebar_rail_level_or_panel` (by role, with the page open and closed: no sidebar, Rail level or panel names a Machine); `mc70_machine_add_is_callable_by_the_app_and_a_door` (the method's caller list in `crates/contracts`). Observer: the design critic on `just capture MC70` at 1512×950, dark, `tree-40`, against Herdr's page, with the failure sentence visible on the densest seed (no test asserts geometry or font, rule 10).

**MC71 Remove forgets the Machine in herdr-core, and every Machine action fails in one plain sentence.** Given a Machine row, when the user activates **Remove**, then roundup calls herdr-core's `machine.rm` for that name through the App method `machine.remove` with the params the pinned schema names (#7261 owns the param clauses), the row leaves the page, and no Agent, Terminal, Project or Spool of roundup is deleted: Agents on it show offline (MC15) and its Spool stays (MC26). The user is asked once to confirm, naming the Machine, because the action cannot be undone from the App; cancelling changes nothing. **This computer** has no **Remove**, and `machine.remove` of this Mac's name returns a coded error (`this_mac`). Given any failure of Add, Remove, Update, the list, or a missing or too-old core, then the page shows one plain sentence saying what failed and what to do, beside the row, the dialog field or the page's head, and never a core error text, a code, `-32602`, `invalid_params`, JSON or `see hc schema`. One table in the App maps each failure's kind to its sentence: the core's `data.kind` (`name_taken`, `already_added`, `unreachable`, `hc_missing`, `incompatible`, `machine_unknown`, `needs_update`, `unavailable`, `invalid_params`) and the Daemon's own codes (`core_missing`, `core_too_old`, `core_closed`, `core_silent`, `update_failed`, `this_mac`); a kind the table lacks reads "Couldn't {action} {name}. Try again." A failing `machine.list` shows its sentence in place of the list and never an empty page. Tests: `mc71_remove_calls_machine_rm_after_confirm_and_drops_the_row` (against a fake herdr-core: one `machine.rm`, name equal, row gone); `mc71_cancel_removes_nothing` (no call); `mc71_remove_keeps_agents_and_their_projects` (the Agent's row stays, offline); `mc71_this_computer_cannot_be_removed` (no button; the method returns `this_mac` and calls nothing); `mc71_a_failed_action_shows_the_mapped_sentence_and_no_core_text` (for each kind in the table, the sentence is the mapped one and the page text holds none of `-32602`, `invalid_params`, `{`, `see hc schema` or the core's message); `mc71_an_unmapped_kind_reads_the_fallback_sentence`; `mc71_a_failing_list_shows_a_sentence_not_an_empty_page` (`machine.list` rejects with `core_missing`: the sentence shows and **No other machines yet.** does not).

**MC72 the schema names every method the page calls.** Given the checked-in schema (MC55), then the pinned version's schema holds `machine.rm`, and the page's Update (MC75) is served by the herdr-core CLI `herdr-core machine update <name>` (0.1.21), which `connect` has no method for. The gap is named here: roundup calls no `machine.update` over `connect` until a schema holds one (policy), and runs the CLI on this Mac, through the user's own ssh and no other path (P15). The implementation bumps the pinned herdr-core and its schema to 0.1.21 and every MC55 check still holds. The CLI's stderr is one JSON line `{"error":{"kind":…}}`: roundup reads its `kind` for MC71's table and never shows the line. Tests: `mc72_remove_uses_a_method_in_the_pinned_schema` (the method name `machine.remove` sends appears in the checked-in schema's methods); `mc72_update_runs_the_cli_with_the_machine_name` (a fake `herdr-core` binary on a temp path records `machine update <name>`, and nothing else is run); `mc72_the_cli_json_error_line_yields_its_kind` (a fake CLI exiting 1 with `{"error":{"kind":"machine_unknown"}}` gives that kind; an unparsable line gives `update_failed`).

**MC73 adding takes an ssh host from the dialog and fails inline.** Given the **Add a machine** dialog (MC70), then **From your ssh config** holds one row per concrete `Host` name of this Mac's ssh config, each with **Add**, with no `*` or `?` pattern and no Machine already added; a missing or unreadable config, or no such Host, leaves the section out and the typed field alone. The names come from a read-only App method `machine.sshHosts` that reads the Hosts of the ssh config of the user on this Mac, through a maintained ssh_config parser (rule 9: research `ssh2-config` and others before parsing by hand), and changes nothing; reading the user's own ssh config is P15's own-ssh path. A Host row's **Add** and the field's **Add** both call `machine.add` (MC2) with that name or the typed text; an empty or whitespace-only entry submits nothing. On success the dialog closes and the Machine appears as a row. On failure the dialog stays open and shows MC71's sentence, keeping the typed text, adds no row, and raises no alert or toast. Tests: `mc73_ssh_hosts_lists_concrete_hosts_without_patterns_or_added_machines` (`crates/rupd/tests/` over a temp config; a missing file gives an empty list); `mc73_the_dialog_lists_the_hosts_and_a_row_add_calls_machine_add`; `mc73_the_typed_add_calls_machine_add_closes_the_dialog_and_shows_the_row`; `mc73_empty_entry_submits_nothing`; `mc73_a_failing_add_keeps_the_dialog_the_text_and_shows_the_sentence` (by role, no alert, no row); `mc73_no_ssh_config_shows_the_typed_field_alone`.

**MC74 a Machine's state is a dot, and an unreachable one is no Machine for a rule that needs another.** Amends MC33 and MC34, and MC15's status. Given a Machine whose `reachable` is false (MC15), then its row shows **Offline** with an off dot and keeps **Remove**; a Machine with `reachable` true or absent shows **Online** with an on dot. Given the Daemon's core connection, then **This computer** shows an on dot and "Connected · hc {version}" with the `hello.version` the Daemon already holds (`listed_now`), carried to the page by a field on the `machine.list` reply (a contract change: every caller changes in the same PR); with no core, or one too old, it shows an off dot and "Not connected" with MC71's sentence for `core_missing` or `core_too_old`. A rule worded "only when another Machine exists", "when a Machine is online" or "at least one other Machine" counts only the reachable ones: an unreachable Machine adds no chip to an Agent on this Mac, no choice in the start form's Machine field (MC76), and no pick for MC33; a named but unreachable Machine still fails the start as MC34 says. Tests: `mc74_unreachable_machine_is_offline_and_removable`; `mc74_this_computer_shows_connected_with_the_core_version` (a reply carrying `0.1.21` reads "Connected · hc 0.1.21"); `mc74_this_computer_without_a_core_reads_not_connected_and_why` (`core_missing` and `core_too_old`); `mc74_the_list_reply_carries_the_hello_version` (`crates/rupd/`, fake core); `mc74_an_unreachable_only_machine_leaves_no_chip_on_a_local_agent` (against `createMachines`: one unreachable Machine, `any()` is false); `mc74_a_reachable_machine_brings_the_chip_back`.

**MC75 Update shows only for an older herdr-core, and runs against an older one.** Given a Machine whose herdr-core `version` (its hello, read when roundup connects) is older than this Mac's, then its row offers **Update**; a Machine at the same or a newer version, or one whose version is unknown, or an offline one, offers none. Activating it runs MC72's CLI for that Machine, which works for a core older than the Daemon's (the CLI run is the one MC72 names, with no `machine.update` over `connect`), shows **Updating…** on the row and disables the action meanwhile; on success the row reads the new version and the action is gone; on failure the row shows MC71's sentence for the CLI's `kind` (`update_failed` when unreadable) and offers **Update** again, with no alert and never the CLI's line. Tests: `mc75_update_shows_only_when_the_machine_is_older` (older, equal, newer, unknown and offline); `mc75_update_runs_once_and_clears_on_success` (a double activation runs one CLI); `mc75_a_failed_update_shows_the_sentence_not_the_json_and_offers_it_again` (a `machine_unknown` line reads its sentence; the row text holds no `{`).

**MC76 the start form's machine pick shows only while another Machine is online.** Amends MC34; re-proved through the dialog. Given the start form, then its **Machine** field shows only while at least one other Machine is online (MC74); with none, the field is absent and the start is as MC33 says. Adding a reachable Machine from the Add dialog (MC73) shows the field without a reload; removing the last one, or every other Machine going offline, hides it and clears any name the user had chosen. Tests: `mc76_the_start_machine_field_needs_an_online_machine` (by role: absent with none, with only an offline one, present with one online); `mc76_a_chosen_machine_clears_when_it_goes_away` (`nameStart` is empty after the removal); `mc76_adding_through_the_dialog_shows_the_field` (the dialog's Add against a fake core).
