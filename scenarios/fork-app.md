# The Fork's own App

Module: `crates/desktop` (a new `fork_app` module beside `fork.rs`, `menu_bar.rs`, `window.rs`, `crates/desktop/icons/`). Terms: Fork, App, Daemon, Project (`GLOSSARY.md`). Principles served: P5 (`PRINCIPLES.md`). Work order: [#5980](https://github.com/roundup-app/roundup/issues/5980). Needs `scenarios/data-fork.md` (FK5977d, `fork.json`, `ForkColour`) and `scenarios/ui-fork-sheet.md` (FS5979d, which opens the Fork's App). Tests render files and images in a temporary folder; no Dock, menu bar, display, `claude` or network. Adds no RPC and no public type. Ids: FA5980a–FA5980e.

## Checks on main

1. `scenarios/data-fork.md`, FK5977d: `<path>/fork.json` holds `name` and `colour`, one of the eight `ForkColour` words.
2. `crates/desktop/icons/artwork.png`: the live Dock icon, 1024 px, plate `#e8572a` (S12, `scenarios/app.md`).
3. `docs/design-system.md`, "Fork colour accents": the Hue column of each `ForkColour`.
4. `crates/desktop/src/menu_bar.rs`: the live menu-bar mark, a template image (U5502).
5. `crates/desktop/src/window.rs`, `set_window_title`: the one window-title writer.

**FA5980a the icon recolours only the plate.** Given `artwork.png` and a `ForkColour`, when the Fork icon is rendered, then every pixel of the plate (the pixels within a fixed tolerance of `#e8572a`, the shading of its edge included) takes a tone of the Fork colour's hue, within 6° of the Hue column of `docs/design-system.md`, with the saturation and lightness of the plate's own tone; every other pixel (the hand, cuff, outline, scars and transparent corners) is byte-equal to `artwork.png`, so the hand stays a cutout over the plate. The output is 1024 px square, and `orange` renders the plate within a visible-colour tolerance of the source. Tests (`fa5980a_`): for each of the eight colours, the plate's mean hue, the count of changed pixels outside the plate mask (zero) and the alpha channel (equal); `fa5980a_the_live_icon_is_not_touched` reads `icon.png` and `artwork.png` before and after.

**FA5980b the small .app.** Given a Fork (`fork.json`, FK5977d) and the built App binary, when the Fork's App is made, then `<fork>/<name>.app` holds `Contents/Info.plist`, `Contents/Resources/<icon>.icns` (the FA5980a icon, every size an `.icns` takes) and `Contents/MacOS/<exec>`, a link to the built App binary and not a copy. The plist holds `CFBundleName` and `CFBundleDisplayName` equal to the Fork name, `CFBundleExecutable`, `CFBundleIconFile`, `CFBundlePackageType` `APPL` and a `CFBundleIdentifier` of `app.roundup.fork.<slug>` that differs from the live App's and from every other Fork's. Making it again for the same Fork replaces the files and keeps the identifier; a Fork whose name is changed in `fork.json` is renamed in the plist on the next make. The bundle is made before the App starts (FS5979d), and a make that fails leaves no half-made `.app` and does not stop the Fork from opening in a plain run. Tests (`fa5980b_`): the plist read back, the link's target, the icon's sizes, two Forks with distinct identifiers, the idempotent second make, a forced failure leaving no bundle.

**FA5980c a Fork App shows its name and colour in the Dock and ⌘-Tab.** Given the App opened on a data folder holding `fork.json`, when it starts, then it sets `NSApplication`'s icon (`setApplicationIconImage`) to the FA5980a image for the Fork's colour, so the Dock and ⌘-Tab show it, whether it started from the Fork's `.app` or from a plain run. Given a data folder with no `fork.json`, the App sets no icon and keeps the live one. The decision is a pure function of the folder's `fork.json`, `fork_icon(folder) -> Option<Image>`; the native call is the sole FFI owner's (`crates/native`) and receives only that image. Tests (`fa5980c_`): `fork_icon` returns the image for a Fork and `None` for the live folder and for an unreadable `fork.json`; the native call is proven on the Mac (policy observer below).

**FA5980d the menu bar mark and window title.** Given a Fork App, then its menu-bar icon is the live mark drawn in the Fork colour's Token (the light `--accent` of `docs/design-system.md`) and is not a template image, so it keeps its colour in light and dark menu bars; the state dot, rows and commands are U5502's and U5959's, unchanged. Its window title is `roundup — <Fork name>` (an em dash, one space either side), set at start and again after `set_window_title` is called, which never drops the suffix. Given the live App, the mark stays the monochrome template image and the title stays `roundup`. Tests (`fa5980d_`): the mark builder returns a template image for the live folder and a non-template image whose opaque pixels carry the Fork colour for each Fork colour; the title function for a Fork name of 1 and 40 characters, an emoji name and the live folder.

**FA5980e the Fork never touches the live App.** Given the live App running, when a Fork's `.app` is made and its App started, then the live App's bundle, icon, menu-bar mark, window title, data folder and Daemon are unchanged: the make writes only under the Fork's folder, and the Fork App sets its icon, mark and title on its own process. Tests (`fa5980e_`): a checksum of the live data folder, `icon.png` and `artwork.png` before and after a make; the make's writes are all under `<fork>/`.

Policy: the Mac observation is the user's, in light and dark: the Fork's `.app` pinned in the Dock shows its name and the tinted plate with the hand cut out; the running Fork shows the same in the Dock and ⌘-Tab, a coloured menu-bar mark and `roundup — <Fork name>` in its title, beside the live App with its plain icon and monochrome mark. Chromium cannot show these, so no test claims them. No webview path changes, so no capture is required.

Policy, Reuse (rule 9): candidates for the `.icns` and image work are `icns` and `image` on crates.io and the macOS `iconutil` and `sips`; for the native icon, `objc2-app-kit` already installed in `crates/native`. The implementation PR carries the `Reuse:` section with release evidence.
