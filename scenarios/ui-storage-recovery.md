# Recover past invalid saved work

Acceptance for #4086. Extends U3787f in `scenarios/ui-mac-expectations.md`: invalid legacy records remain recoverable with their cause, and the user can continue without the selected record. Implementation follows the validated plugin-storage migration owned by #4023; this specification adds no runtime behavior.

Journey: Enter and Review. A damaged preference or draft must not permanently prevent opening the App and finding other saved work. The production storage initialization and App recovery surface are the behavioral seams; the isolated headless App is the rendered observer. No new RPC, App seam command or native-only observation is required (policy).

## Checks on main

1. `scenarios/ui-mac-expectations.md`, **U3787f shell capabilities use maintained plugins and preserve stored work**: the nine legacy families, schema validation, acknowledged migration/readback, idempotence, newer-plugin precedence and recoverable invalid bytes remain requirements. This is acceptance, not evidence that migration has landed.
2. `apps/desktop/src/state/storage.ts`, `storedValue` and `draftStorage`: distinguish absent, invalid and unreadable records; preserve recoverable drafts and original identities rather than overwriting an invalid record.
3. `apps/desktop/src/state/u2773_storage.test.ts`, `u2773e_storage_failure_keeps_memory_distinguishes_missing_from_invalid`, `u2773b_storage_pending_reopens_as_unknown_without_resubmission`, `u2773a_storage_restoration_writes_nothing` and `u2773e_credentials_keep_existing_policy`: existing behavioral regression proofs.
4. `PRINCIPLES.md`, **P11 Unfinished input**, and `.agents/data/journey.md`, **What must work** and **The viewport**: retained original work, actionable restoration failure and a 1512×950 rendered observer.

## Acceptance

**U4086a a damaged record offers a way forward.** Given legacy `roundup:shelf:/p` containing the exact string `{"open":`, or valid JSON `{"open":"yes"}` which fails the Shelf schema, and valid saved records in another family and another Project, when production initialization encounters it, then the recovery surface explains that saved Shelf settings could not be restored because their format is invalid, and offers Retry and Continue without settings. Before that choice, the original string is unchanged, no quarantine or migration-complete claim exists for it, and editors cannot overwrite it. Retry revalidates; unchanged invalid input keeps the same recovery choices, while a repaired valid record restores normally. Parameterize equivalent parse/schema failures across all nine U3787f families, using each family's existing schema. For unfinished work, the consequence names unavailable saved unfinished work rather than settings, and the action is Continue. Assert roles, action availability, captured record identity and storage effects in planned `u4086a_invalid_legacy_record_has_retry_and_continue` in `apps/desktop/src/state/u4086_storage_recovery.test.tsx`.

**U4086b continuing preserves the selected bytes and opens valid work.** Given U4086a's failure, when the user chooses Continue without settings (or Continue for unfinished work), then durably quarantine that exact record's original key and raw string through the existing plugin store, acknowledge the save and read back the exact pair before removing its legacy source or excluding it from migration. Continue initializes the App using the normal missing-record default for only that record; migrate and restore all other valid records with their original values and Project/object/recipient/revision identities. Existing valid plugin data always wins over legacy data, including at the selected key. No draft is submitted, Agent started or Terminal written by recovery. A full initialization/reopen reads the retained quarantine and opens successfully without presenting that same invalid record as a new launch blocker. The App exposes the retained failure with an action to copy the original key and exact raw string for recovery, including after reopen; it never claims the damaged contents were restored. Assert these effects in planned `u4086b_continue_quarantines_one_record_and_reopens` in the same test file, parameterized over the nine families and both failure classes; use the existing production adapter for storage tests and the App seam for copy and opening behavior.

**Storage recovery** (`StorageRecovery`, `storageRecovery`, `retainedStorage`): The startup gate and explicit per-record choice to retain invalid legacy bytes in the existing store before excluding them from migration. Retained records preserve their original key and exact string for explicit copy after reopening; they never become live settings or submitted drafts. An unreadable record grants no continuation.

**U4086c failed recovery keeps the original and can retry.** Given an invalid record and its recovery action, when quarantine persistence fails, readback fails or returns different bytes, then keep the original legacy value, keep the App's restoration gate and both recovery choices, and show the failure cause with retry; do not mark that record migrated or offer a successful continuation. When the store answers normally and the user retries continuation, quarantine and continue as U4086b. An interruption after durable quarantine but before source cleanup is also recoverable: repeated initialization/continuation recognizes the same retained key/string, preserves its bytes, completes cleanup and opens without accumulating duplicate quarantine entries. Duplicate activations while an operation is pending perform no second operation. Assert the failure, retry and interruption paths in planned `u4086c_quarantine_failure_and_interruption_preserve_recovery` in the same test file, using controlled storage replies and recreating the production holder after each interruption.

**U4086d each invalid record needs its own choice.** Given two invalid legacy records (`roundup:shelf:/p` with U4086a's truncated string and `roundup:rail:/q` with truncated JSON), plus valid drafts and preferences in both Projects, when the user continues past the Shelf failure, then only the Shelf record is quarantined; the Rail failure remains visible with its own cause and recovery choices and its original bytes unchanged. Continuing past Rail opens both Projects with the valid work restored, while each quarantine remains separately recoverable after reopen. Never clear a whole family, Project, localStorage or plugin store. A storage enumeration/read failure whose original bytes are unavailable offers Retry with its cause and grants no permission to delete or fabricate a quarantine. Assert exact before/after key/value maps, sequential choices, reopen and unreadable-store refusal in planned `u4086d_recovery_is_per_record_and_never_clears_other_work` in the same test file.

## Implementation policies and observers

Policy: use the existing validated storage interface, plugin adapter, schema catalogue and shared UI primitives. Keep quarantine in the existing durable store, separate from live family values, and exclude it from legacy-family enumeration; add no parallel persistence service or parser. Quarantined raw values are recovery data, never trusted live values or inputs to submission. Copy is an explicit user action; raw bytes, Project paths, storage keys and draft content never enter logs or routine diagnostics. App errors name the affected content and cause; machine identity belongs in the explicit recovery copy, not ordinary rendered copy. Never discard a quarantine automatically. This action preserves data and requires no destructive confirmation. Any future discard or re-import UI is outside this Issue.

Policy: retain Checks 1–3 and their reached tests. Reuse surviving proofs before adding tests; the planned tests above cover the new continuation behavior, not duplicate generic draft restoration. Implementation changes storage initialization, its App startup/recovery caller, the copy catalogue and reached tests/styles; expand the Issue Scope for necessary companions under the Code recipe. Public names introduced by implementation follow `GLOSSARY.md` and the Contract recipe. Apply rule 9 before adding machinery; this specification selects no new library.

Policy/Gates: P11 rejects losing invalid bytes or other drafts, wrong original identities, automatic submission and hidden retention failures. P3 rejects routine attention from this recovery; P9 rejects automatic Agent starts; P14 rejects usage/cost collection; Check 1 retains the private-content logging prohibition.
