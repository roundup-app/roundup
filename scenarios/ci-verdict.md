# CI verdict time

Module: `.github/workflows/check.yml`, `.github/actions/setup/action.yml`, `apps/desktop/src/testing/shardSequencer.ts`, `loop/affected.py`

Scope: `check` gives a PR its verdict within 5 minutes of the push. Source: #7295, where a web-only PR waited 16 min: each of its 9 web lanes spent 351–375 s in setup and 523–568 s in tests (run 43959571073). It covers every lane of `check`: the web lanes (#7296), the Rust and macOS lanes and fail fast across lanes (#7298), and the whole run (#7297). Inside the web matrix, a failing shard leaves the other shards running, so one run reports every failing web test (L89); only a newer push cancels a run.

**CI7295a web shards by measured time.** Given a PR whose diff selects web tests, when `plan` sizes the web matrix, then it picks the fewest shards, at most `MAX_SHARDS` (the count a full run uses), whose longest measured time, heavy files counted whole, stays within its budget; the number of files decides nothing. A file's measured time is its mean over the full runs `just web-durations` reads, since one run's time swings up to half again, and a shard's parallel files count as two at once, not L89's 2.8: in 24 shards, App files beside Chromium ran no faster (test: `ci7295a_web_runs_get_the_fewest_shards_within_the_time_budget`).

**CI7295b lane time budget on `main`.** Given a web, `rust` or `mac` lane of a `main` run, when its setup takes over 90 s or its test step over 300 s, then the lane fails; when its test step takes over 240 s, it warns. Either way its log names the lane, the step, its seconds and the bound, so timing noise alone never fails `main` (policy; observer: the `CI7295b lane time budget` step of each lane).

**CI7295c web lanes compile nothing.** Given a web lane, when it sets up, then it installs no Rust toolchain and builds nothing: it restores the `rupd`, `rup` and test core that the `daemon` job built once for the run's Rust source tree, and a PR that changes no Rust restores the build `main` saved (policy; observer: the job log, where `daemon` reports a cache hit and the lane runs no `cargo`).

**CI7295d setup waits on no slow step.** Given a hosted Linux lane, when setup frees the runner's disk or installs U26's tracer packages, then each runs in the background; only a job that restores the Rust cache waits for the disk, before the restore, so CI5330e still holds (policy; observer: the job log).

**CI7295f no web test file runs over 100 s.** Given a web test file, when a full run measures it, then it takes at most about 100 s, since no shard ends sooner than its slowest file: a longer file is split by the clauses its tests prove, its tests moved whole and none cut (policy; observer: `apps/desktop/src/testing/shardDurations.json` after `just web-durations` on a full run; #7295 split the nine files over 100 s).

**CI7295e `check` turns red at the first failed job.** Given a `check` run, when any of its jobs fails or times out, then `check` fails within about 30 s, while every other lane runs to its end, so the run's `completed` event hands one fix run every failure; `check` passes only when `lanes`, which needs every lane, succeeds (policy; observer: the run's job list; run 43979217018 failed `check` at 224 s, 8 s after `observers` failed, while `rust 5` ran to 645 s).

**CI7295g a Rust lane builds only its own tests.** Given a `rust` or `mac` lane, when it builds, then it builds only the test binaries its nextest profile selects, plus the binaries those tests start, under `--workspace` so its features match the shared Rust cache, and a profile the diff misses builds nothing (test: the `test_ci7295g_` cases of `loop/affected.test.py`).

**CI7295h the two macOS jobs share the work.** Given a `check` run whose diff selects Rust tests, when the macOS jobs run, then `mac` runs the macOS tests and R24's measurement, and `mac-clippy` runs clippy, then the `rup ping` round trip and the N7/N8 guard observers, so each meets CI7297d with no third macOS job: two runs at once already take four of the org's five macOS runners (policy; observer: the run's job list; run 43990431351 spent 123 s of `mac`'s 515 s on the round trip, while `mac-clippy` took 130 s warm in run 43985742752).

**CI7297a `check` ends within 5 minutes.** Given a PR push, when `check` runs, then it concludes within 300 s of the push whatever the diff reaches, the sum of its slowest path counting: `plan`, the longest lane's setup (CI7295b's 90 s) and test step (240 s), and the verdict job of CI7295e; a lane that cannot fit splits into more shards before the budget grows. `main` logs the run's seconds in `check`'s summary, so a run over 300 s names the lane that made it long (policy; observer: the run's job list beside CI5330's `df` readings and E14's lane measurements).

**CI7297b the changed tests run first.** Given a PR whose diff changes test files, when `check` starts, then one `first` lane runs those files and only those, at once after `plan` and before the shard lanes' setup ends, in at most 60 s; its failure fails `check` at CI7295e's 30 s while the other lanes run to their end, so the author reads the failure of their own test before the full verdict. A PR changing no test file has no `first` lane (test: a `test_ci7297b_` case of `loop/affected.test.py` that the changed test files, and none else, reach the lane).

**CI7297c the Rust lanes set up and shard by time.** Given the `rust` lanes of a PR, when they set up, then each restores the Rust cache and the `daemon` build without compiling, in at most 90 s, and the `ciN` profiles of `.config/nextest.toml` give every lane a measured test time within 240 s, the ten partitions within 30 s of each other, so a lane over its time is moved to a lighter profile, not given a longer budget (policy; observer: the `CI7295b lane time budget` step of each `rust` lane, with E14's measurements for the partition times).

**CI7297d the macOS lanes keep their times.** Given the `mac` and `mac-clippy` lanes of a PR, when they run, then each ends within 300 s of its start, its setup within 90 s and its test step within 240 s, which CI7295b measures for `mac`; `mac-clippy` and `mac` start with `plan`, not after another lane, and `mac-package` runs on `main` pushes only, never in a PR's verdict (policy; observer: the run's job list and the `CI7295b lane time budget` step of `mac`).
