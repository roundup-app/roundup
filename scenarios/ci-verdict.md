# CI verdict time

Module: `.github/workflows/check.yml`, `.github/actions/setup/action.yml`, `apps/desktop/src/testing/shardSequencer.ts`, `loop/affected.py`

Scope: `check` gives a PR its verdict within 5 minutes of the push. Source: #7295, where a web-only PR waited 16 min: each of its 9 web lanes spent 351–375 s in setup and 523–568 s in tests (run 43959571073). It covers every lane of `check`: the web lanes (#7296), the Rust and macOS lanes and fail fast across lanes (#7298), and the whole run (#7297). Inside the web matrix, a failing shard leaves the other shards running, so one run reports every failing web test (L89); only a newer push cancels a run.

**CI7295a web shards by measured time.** Given a PR whose diff selects web tests, when `plan` sizes the web matrix, then it picks the fewest shards, at most `MAX_SHARDS` (the count a full run uses), whose longest measured time, heavy files counted whole, stays within its budget; the number of files decides nothing. A file's measured time is its mean over the full runs `just web-durations` reads, since one run's time swings up to half again, and a shard's parallel files count as two at once, not L89's 2.8: in 24 shards, App files beside Chromium ran no faster (test: `ci7295a_web_runs_get_the_fewest_shards_within_the_time_budget`).

**CI7295b lane time budget on `main`.** Given a web, `rust` or `mac` lane of a `main` run, when its setup takes over 90 s or its test step over 240 s, then it warns, naming the lane, the step, its seconds and the bound in `check`'s summary; no time budget fails `main`. Setup is cache restore and runner network, which no PR controls, and the same macOS build takes 33 s on one runner and 198 s on another, so timing noise never turns `main` red (policy; observer: the `CI7295b lane time budget` step of each lane; main run 44046436794 failed `rust 1` at 91 s of setup before this rule).

**CI7295c web lanes compile nothing.** Given a web lane, when it sets up, then it installs no Rust toolchain and builds nothing: it restores the `rupd`, `rup` and test core that the `daemon` job built once for the run's Rust source tree, and a PR that changes no Rust restores the build `main` saved (policy; observer: the job log, where `daemon` reports a cache hit and the lane runs no `cargo`).

**CI7295d setup waits on no slow step.** Given a hosted Linux lane, when setup frees the runner's disk or installs U26's tracer packages, then each runs in the background; only a job that restores the Rust cache waits for the disk, before the restore, so CI5330e still holds (policy; observer: the job log).

**CI7295f no web test file runs over 100 s.** Given a web test file, when a full run measures it, then it takes at most about 100 s, since no shard ends sooner than its slowest file: a longer file is split by the clauses its tests prove, its tests moved whole and none cut (policy; observer: `apps/desktop/src/testing/shardDurations.json` after `just web-durations` on a full run; #7295 split the nine files over 100 s).

**CI7295e `check` turns red at the first failed job.** Given a `check` run, when any of its jobs fails or times out, then `check` fails within about 30 s, while every other lane runs to its end, so the run's `completed` event hands one fix run every failure; `check` passes only when `lanes`, which needs every lane, succeeds (policy; observer: the run's job list; run 43979217018 failed `check` at 224 s, 8 s after `observers` failed, while `rust 5` ran to 645 s).

**CI7295g a Rust lane builds only its own tests.** Given a `rust` or `mac` lane, when it builds, then it builds only the test binaries its nextest profile selects, plus the binaries those tests start, under `--workspace` so its features match the shared Rust cache, and a profile the diff misses builds nothing (test: the `test_ci7295g_` cases of `loop/affected.test.py`).

**CI7295h `mac-clippy` pings only what a PR reaches.** Given a PR, when `plan` reads its diff, then `mac-clippy` runs the `rup ping` round trip and the N7/N8 guard observers after it only when the diff reaches the `rupd`, `rup` or `desktop` crates, a crate they depend on, or a file those steps read; every `main` push runs them (test: `test_ci7295h_the_ping_runs_when_the_diff_reaches_a_crate_it_starts_or_a_file_it_reads`).

**CI7295o a changed build plan refreshes the macOS Rust cache.** Given a `main` push that changes `.github/workflows/check.yml` or `.config/nextest.toml`, when `mac` saves the macOS Rust cache, then it saves a fresh entry, while a PR's macOS jobs still restore the newest entry `main` saved; a push that changes neither restores its own entry and saves nothing (policy; observer: the rust-cache restore and post lines of `mac`; after #7298 changed the plan, the entry of 11-16 restored as a full match, its post step logged `Cache up-to-date.`, and `mac-clippy` re-checked 426 crates in run 43992723908).

**CI7295j a failing web test turns `check` red within 3 minutes.** Given a PR whose diff adds a failing web test, when it is pushed, then `check` concludes red within 180 s of the push, since the `first` lane of CI7297b fails first and `check` follows within about 30 s (CI7295e); the run is recorded, then the test removed (policy; observer: the run's job list, push time to the `check` conclusion).

**CI7295m no test is cut to save time.** Given a PR of #7295, when a test leaves the suite to shorten a lane, then rule 10 holds for it: the PR names the test that still proves its then-clause, and no test is skipped or deleted otherwise (policy; observer: the review of the PR's diff).

**CI7295n the 5 minutes cost nothing.** Given `check`, when its lanes run, then they use standard GitHub-hosted runners only, no larger paid runner and no new paid service, and the run's concurrent jobs leave the org's runner limit room for loop runs to start (policy; observer: the `runs-on` labels of `.github/workflows/check.yml`).

**CI7295i support tests run once a run.** Given a run that tests the web, when its lanes run, then the support tests (`apps/desktop`'s `test:support`: the copy guard, reporting and R3800 startup budget tests) run once, in the `chromium` lane, and no web shard runs them: in each of 24 shards they cost about 10 s (policy; observer: the `chromium` job log and a web lane's log).

**CI7297a `check` ends within 5 minutes.** Given a PR push, when `check` runs, then it concludes within 300 s of the push whatever the diff reaches, the sum of its slowest path counting: `plan`, the longest lane's setup (CI7295b's 90 s) and test step (240 s), and the verdict job of CI7295e; a lane that cannot fit splits into more shards before the budget grows. `main` logs the run's seconds in `check`'s summary, so a run over 300 s names the lane that made it long (policy; observer: the run's job list beside CI5330's `df` readings and E14's lane measurements).

**CI7297b the changed tests run first.** Given a PR whose diff changes test files, when `check` starts, then one `first` lane runs those files and only those, at once after `plan` and before the shard lanes' setup ends, in at most 60 s; its failure fails `check` at CI7295e's 30 s while the other lanes run to their end, so the author reads the failure of their own test before the full verdict. A PR changing no test file has no `first` lane (test: a `test_ci7297b_` case of `loop/affected.test.py` that the changed test files, and none else, reach the lane).

**CI7297c the Rust lanes set up and shard by time.** Given the `rust` lanes of a PR, when they set up, then each restores the Rust cache and the `daemon` build without compiling, in at most 90 s, and the `ciN` profiles of `.config/nextest.toml` give every lane a measured test time within 240 s, the ten partitions within 30 s of each other, so a lane over its time is moved to a lighter profile, not given a longer budget (policy; observer: the `CI7295b lane time budget` step of each `rust` lane, with E14's measurements for the partition times).

**CI7297d the macOS lanes keep their times.** Given the `mac` and `mac-clippy` lanes of a PR, when they run, then each ends within 300 s of its start, its setup within 90 s and its test step within 240 s, which CI7295b measures for `mac`; `mac-clippy` and `mac` start with `plan`, not after another lane, and `mac-package` runs on `main` pushes only, never in a PR's verdict (policy; observer: the run's job list and the `CI7295b lane time budget` step of `mac`).

**CI7324a `apps/desktop` typechecks with TypeScript 7.** Given `apps/desktop`, when `typecheck` runs, then it runs TypeScript 7.x's compiler and finishes within 5 s on the CI runner (10.6 s on 6.0.3), while `typescript-analysis` stays installed for `apps/desktop/copy/types.mjs` only; a type error planted in `apps/desktop/src` fails it with the message TypeScript 6 gave (test: `test_ci7324a_` case of `loop/ci-lint-time.test.py` running `typecheck` on a planted error; policy for the 5 s, observer: the `typecheck` line of the `lint-web` log in a `pre` run).

**CI7324b every lint line logs its seconds.** Given a `lint` or `lint-web` job, when `loop/keep-going.sh` runs the recipe, then each recipe line logs its name and seconds, and the job summary lists the slowest lines, slowest first; a failing line keeps its exit code and the run still continues to the next line (test: `test_ci7324b_` case of `loop/ci-lint-time.test.py`).

**CI7324c the lint jobs name their top costs and drop no lint.** Given one `pre` run, when its `lint` and `lint-web` logs are read, then the PR body names each job's slowest three lines from it, `lint`'s setup and running time fall below the 71 s and 147 s p50 the Issue measured wherever the rule allows (selection never changes how a lint builds, and a cache is keyed by a hash of all its inputs), and no lint is dropped, weakened or made optional: `tools/lint/debt.json` judges what it judged, and `.github/workflows/pre.yml` is not edited (policy; observer: the `lint` and `lint-web` job logs of the PR's `pre` run, and the diff of `pre.yml`).

**CI7323a the macOS lanes restore the vendored crates' build.** Given `mac`, `mac-clippy` or `mac-package`, when it sets up, then it restores the build output of the path crates in `vendor/` and `crates/desktop/vendor/` for the profile and command that lane builds with, which `main` saves, so the lane compiles only what its PR changes; the build stays `--workspace` with `main`'s features (CI7295g), and a miss builds as today and passes (policy; observer: the restore line in the `mac` job log, and the build seconds of its test step against run 44050661193's 267).

**CI7323b the vendored cache key hashes every input.** Given the cache of CI7323a, when any vendored source, `Cargo.lock`, the pinned toolchain, the profile or command, or a cargo config that changes output (the line-tables entries the setup action writes to `$CARGO_HOME/config.toml`) changes, then the key changes and the lane builds the crates afresh; a change to none of them restores the same entry (policy; observer: the key in `.github/workflows/check.yml` and the restore line of two runs).

**CI7323c the vendored cache fits the repository's budget.** Given a `main` push that saves the cache of CI7323a, when it saves, then the entry's size is logged by the save step and the repository's caches stay under GitHub's 10 GB, so no Rust cache that lanes restore is evicted by it; each entry the change makes dead is named in the PR (policy; observer: the save log, and `gh cache list` before and after).

**CI7323d the cache changes no verdict and costs nothing.** Given `mac` and `mac-clippy` on a restored or missed cache, when they run, then they report the same tests and diagnostics as `main`, no test is skipped, weakened or deleted (CI7295m), no retry is added and no timeout widened, and no failing time budget or paid runner is added (CI7295n, CI7295b) (policy; observer: the review of the PR's diff and the lanes' test lists).
