# First journey: keep the next work ready

Module: `scenarios/` and `.agents/data/journey.md`. Ids: J1, J2, J3, J4, J5, J6, J7, J8, J9, J10, J11, J12, J13, J14. The destination and acceptance evidence are defined once in `.agents/data/journey.md`; this row makes its existing next-gap rule runnable.

**J1 audit the journey and queue its next missing behavior (policy).** Given current `origin/main` and the open PRs, inspect the five stages of `.agents/data/journey.md` in order. Audit the current UI even while prerequisite implementation is running. Run the applicable existing behavioral and rendered observers; record the main SHA, commands and artifact paths or run links for what actually passed. A test name, declared RPC, screenshot of a seeded success, or merged PR alone is not proof of a stage. State the first unproved behavior and the exact missing implementation or observer. Keep unobserved stages unproved. For each stage, inspect the rendered App at both journey viewports against the accepted product and design documents; show the failing interaction or screen and its user consequence. A missing backend capability does not prevent inspecting the UI already present.

Use an existing scenario and work Issue when they cover a gap. Correct a stale dependency or missing Issue using only prerequisites whose implementation exists on main. For each other gap it observes, specify one bounded missing behavior, its real observer and one implementation work Issue, in the file that owns the behavior. Set native blocked-by dependencies on each Issue's actual prerequisite Issues, including Issues this audit files; a missing implementation that a contract test happens to name is still a prerequisite. Keep implementation out of this audit PR. Settled product/design documents decide engineering choices; only a consequential product choice those documents do not settle is a question for the user.

The audit files one work Issue per uncovered gap, so the queue builds every independent gap at once; it never duplicates owned work: a gap with an open PR or a running build job keeps that owner. It also leaves exactly one next audit Issue with the next unused J id, referring to this policy. Its native blocked-by dependencies name the implementation Issues whose delivery will let that audit make new observations. If all observed gaps already have owners, add no implementation Issue and make the successor wait on their Issues. Do not add an immediately-ready audit successor that would merely repeat this report. When all five stages have the required behavioral and rendered evidence on one main revision, record that evidence and leave no successor.

Observer: independent review compares the cited evidence with the stage acceptance conditions and the actual proposed work Issue. `loop/orders.py ready` must print each new implementation Issue's correct ready/waiting/in-flight state and the successor audit as waiting until its prerequisites exist. This is an evidence/specification task, so no test that merely searches this document counts as its completion. A later implementation's tests establish behavior; this policy claims no implementation or native observation.
