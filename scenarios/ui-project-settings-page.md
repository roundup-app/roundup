# UI: Project settings are a Project page of Settings (U7887a–U7887d)

Work order: [#7887](https://github.com/roundup-app/roundup/issues/7887). Module: `apps/desktop/src/` (`settings/`, `rail/ProjectSettings.tsx`, `state/settingsView.ts`, `App.tsx`) and `crates/desktop/src/menu.rs`. No new Daemon method, nothing under `contracts/`, no new Token. Decided by the owner (2026-11-22): the Project's settings are a **Project** page of Settings; the Project menu keeps the ten actions of #5919 and gains none. Replaces the centre page of U3764–U3766 (`scenarios/ui-project-settings.md`) and the `Project Settings…` entry of U3813/U3814 (`scenarios/ui-project-menu.md`), which no menu item has sent since #5919. `Import Claude Code Work…` is out of scope: its lost entry needs its own Issue.

**U7887a Settings has a Project page for the Project it is about.** Given App Settings opened through `Roundup ▸ Settings…` or `⌘,` with Project A selected, then the page list holds a `Project` page, and choosing it shows two groups in this order: **Workstreams** (U3765's cap field and `No limit`) and **Program** (PG6's `Command`, `Folder`, `Worktree path` and `Clear`), each reading `project.get` of A when the page opens. With no Project selected and no link naming one, the list holds no `Project` page. Selecting Project B while the page is open makes it show B's values, never A's. Tests: `u7887a_settings_lists_a_project_page_for_the_selected_project`, `u7887a_the_project_page_holds_workstreams_then_program`. Observer: the design critic on `just capture U7887a` at 1512×950, dark, `tree-40`, with failure text visible on the densest seed (no test asserts geometry, rule 10). Policy: it moves D2, D5 and D6 and uses Tokens only.

**U7887b The cap and the program behave as they did.** Given the Project page, then every clause of U3765 (one `project.setWorkstreamCap {cap}` per commit, `null` for `No limit`, a bad entry refused in the field with `✕ <message>`) and of PG6 (one `project.setProgram {argv, dir}` per changed commit, refusals calling nothing, one `project.clearProgram` for `Clear`, the change failure keeping the form's text) holds with the call carrying the key of the Project the page shows. Tests: the existing `u3745_a_commit_sets_the_cap_once_and_no_limit_sets_null`, `u3745_a_bad_entry_calls_nothing_and_keeps_the_cap`, `u3745_no_limit_shows_when_the_project_has_no_cap` and `pg6_a_commit_sets_the_program_once_and_clear_clears_it`, `pg6_a_bad_command_or_folder_calls_nothing_and_keeps_the_entry`, `pg6_the_section_reads_what_the_daemon_stores`, retargeted at the page; `u7887b_a_commit_names_the_project_the_page_shows`.

**U7887c A settings link opens the Project page at its control.** Extends PL2: `<page>` also takes `project`, and `<control>` an `id` of `settingsEntries` on it: `workstreams` (the cap field), `program` (`Command`), `program-folder`, `program-worktree` (`Folder` and `Worktree path`). Given `roundup://settings/project?project=<key>#program` with that Project open, when the user clicks it, then Settings opens on the Project page for that Project and focuses `Command`, scrolled into view, its value unchanged, whether or not that Project is the selected one; it changes no selection and no setting. A link without `?project=` names the selected Project. Given a Project page already open for another Project, then it shows the named one. Given a `project` that is no open Project, or no `project` and no selected Project, or a control not on the page, then Settings keeps its state and the App shows one failure line naming the Project or the control, as PL2 shows it. Tests: `u7887c_a_project_settings_link_focuses_the_program_command`, `u7887c_a_link_names_a_project_that_is_open_but_not_selected`, `u7887c_a_link_with_no_project_or_an_unknown_one_fails_visibly`, each beside `pl2_a_settings_link_opens_its_page_and_focuses_the_control`. `PL2`'s list of pages gains `project`; `PL3`'s Brief tokens are unchanged (policy).

**U7887d Project settings have one home.** Given the build, then no centre page `project-settings`, no `onProjectPage` path to it and no `project-settings` id in `crates/desktop/src/menu.rs` or in the `open-project-page` command of `scenarios/app.md` remain: that command's only value is `import-work`. The Project menu holds exactly #5919's ten actions (it adds nothing back). Tests: `u7887d_the_project_menu_holds_the_ten_actions_and_no_settings_id` (host, mock runtime, replacing `s_u3813_project_menu_tracks_the_selected_project`'s settings clause), `u7887d_no_project_settings_page_opens_in_the_centre`; the U3764–U3766 tests in `apps/desktop/src/rail/u3764_project_settings_view.test.tsx` and the U3814 clauses for Project Settings are retired, and the tests of U7887b take their proof. Policy: this edit retires those clauses in `ui-project-settings.md`, `ui-project-menu.md` and `app.md` in the implementing PR.
