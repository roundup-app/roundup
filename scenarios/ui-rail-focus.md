# Choosing work focuses its Terminal

Acceptance for [#5742](https://github.com/roundup-app/roundup/issues/5742). Journey: Intervene — choose the requesting Agent and type into its Terminal without another click. This specification changes acceptance only; every test named below as planned belongs to implementation.

## Precedence

Policy: U5742a replaces U3789a/U3789e's plain-click row-focus rule only for Workstream, Door, Agent and Mode rows in the Rail. Shelf and owned Todo/Pad interactions, explicit rename, drag, disclosure, context-menu and destructive-action contracts retain their existing behavior. U520's tree navigation and U31's arrow guards remain; Enter opens as before. U64 still closes a Drawer only when selection changes to a different row. U3756a–d's newer-focus-wins rule applies through Terminal readiness, including a return to the original control or a temporary body focus. This work changes no shortcut binding.

## Acceptance

**U5742a a plain Rail choice focuses the chosen Terminal.** Given an open Project with live Terminals for a Workstream, its Door, an Agent and a Mode, when the user plain-primary-clicks each row's non-control content, then the row is selected and keyboard focus reaches that destination's centre Terminal, exactly as Enter on that row does. A second plain click on the selected row also focuses its Terminal. A plain click after a modifier-built selection replaces that set with the chosen destination. For a Workstream whose own status is not needs-you and which contains a needs-you descendant, click and Enter select and focus the same requesting descendant that the existing `openRow` resolves; a Workstream itself needing the user remains the destination. Test: planned `u5742a_plain_rail_choice_focuses_terminal` at the mounted App seam, parameterized over these row kinds, already-selected/multi-selected origins and redirect/no-redirect cases. Assert selected identity and exact Terminal identity as well as `document.activeElement` inside its `.pane-screen`; a focus spy alone is insufficient. A subsequent typed marker reaches only that Terminal once.

Given a different selected row and an open Drawer, when the same choice runs, then U64 closes the Drawer and focus finishes in the chosen Terminal rather than returning to the Drawer opener. Choosing the already-selected row retains U64's no-close rule; this specification adds no permission to focus a hidden/inert Terminal. Planned `u5742a_choice_closes_drawer_and_focuses_terminal` asserts changed-selection close and destination focus, plus unchanged-selection no-close. Policy: choosing work starts/resumes no Agent, creates no Terminal or Bubble, opens no additional view and writes no input before the user's marker. A row without a live Terminal retains its existing empty/stopped/start/retry behavior; focus readiness is not permission to launch it.

**U5742b selecting several rows and walking the Rail keep Rail focus.** Given visible rows A, B, C and D, when the user ⌘-clicks nonadjacent rows or ⇧-clicks a range, then the existing toggle/range identities are retained and focus stays in the Rail, with no Terminal focus request. Repeating either gesture can extend or reduce the set without opening a Terminal. When ↑ or ↓ runs on a focused row, focus moves to the adjacent visible row under U31 without leaving the Rail; Enter then selects and focuses that row's Terminal. Planned `u5742b_modifier_selection_and_arrows_keep_rail_focus` asserts selected identities, active element after each gesture/key, zero activation/lifecycle calls and Enter's destination. Keep U5690a's selected/unselected context-click targeting and native Ctrl-click compatibility behavior green.

Given a fold chevron, `+ Agent`, Door action or row-menu trigger, when that control is clicked, then only its existing action runs, with no additional row-choice selection or focus transfer to the centre. Its own dialog/editor/creation focus behavior remains unchanged; “no transfer” does not disable a control's own focus contract. Planned `u5742b_controls_do_not_activate_the_row`, parameterized over these controls, compares selection, action identities/counts and active element against that control's existing outcome. Policy: row drag/release, rename and section/fold headings gain no Terminal activation.

**U5742c every way of choosing work has the same focus result.** Given a destination with a live Terminal in an open Project, when the user chooses an Agent or Workstream through each path below, then the intended destination is selected and `document.activeElement` is inside that exact centre Terminal's `.pane-screen` after readiness. A typed marker reaches only that Terminal once. Test the actual App and production path using the fake App and a focusable emulator, never a replacement selection/focus implementation. Each path has its own named proving test; the implementation PR lists the paths and tests, including any existing proof reused instead of duplicated.

**U5742d readiness never steals a newer focus choice.** Given each independently scheduled choice path in U5742a/c with its selected Terminal not ready yet, when that Terminal becomes ready and no newer user action has occurred, then the exact requested Terminal receives focus and a typed marker once. When instead the user focuses the Ask field, a Drawer editor, another Rail row or a Bubble before readiness, then that exact newer element retains focus and its input/destination, and the late Terminal receives no marker. Test: planned parameterized `u5742d_choice_readiness_respects_newer_focus`, using controlled fake-App readiness at the actual scheduled boundary, covering each distinct scheduling owner rather than duplicating identical scheduling proofs. U3756c's away-and-back/body cases remain required; reselecting an available destination after an older request lost permission works as a new choice. Reuse U3756a–d's existing proofs where their assertions cover the clause; add only missing choice-path coverage. Policy: no fixed delay, background refresh or older queued row-focus callback grants focus permission.
