# Repeat scan

Module: `crates/agents` (the scan, read-only), `crates/contracts` and `contracts/generated/` (one Daemon method), `crates/rupd` (wiring), the fake App's handler. Ids: C7684a, C7684b, C7684c, C7684d, C7684e, C7684f. Work Issue: #7684; #7685 draws the result and #7704 generalises it into the mark with a source. Found by the owner (2026-11-18): "I do sanity check for code repetitions and logic". Terms: Agent, Worktree, Base, Tree (`GLOSSARY.md`).

Policy, owner's decisions (2026-11-18): the scan finds repeats of the changed lines in the repo, with no model, so it costs no tokens (P14); it reports for each repeat the changed lines and the other file and lines (the App shows "Repeats owned.ts 12-30"); it runs when the view opens and never blocks a key (rule 7). When a design check reads one as a defect, change how it is drawn, never the decision. The scan adds no refactor suggestion, no auto-fix and no Landing gate.

Policy, the exception to "no new Daemon method": the App reaches no repo file other than the changed ones (`agent.changedFiles`, `agent.compareFile`), and a repeat's other place may be in an unchanged file, so one read-only method is added, `agent.repeatScan`, by the Contract recipe. Names: the method and its result `ScanSpots {spots, complete}` with `Spot {source, path, start, end, message?, other?, stale}` (C7704a; lines 1-based, inclusive, in the working copy), a repeat being a `Spot` whose `source` is `{kind: "repeats"}` and whose `other` is `{path, start, end}`; no `Repeat` type, field or method names the result. Params are `ChangedFilesParams`'s (`id`, optional `from` and `to`). Each new name goes in `GLOSSARY.md` with the PR.

**C7684a a hunk that copies a block is reported with the other place.** Given a temporary Git repo with an Agent's Worktree whose Base holds `owned.rs` and whose working tree adds `new.rs` containing a 20-line block copied from `owned.rs` lines 12-31 (identifiers and literals equal, indentation and trailing spaces differing), when `agent.repeatScan {id}` runs, then `spots` holds one `Spot` of source `repeats` with `path` `new.rs`, the lines of the copied block, and `other` `{path: "owned.rs", start: 12, end: 31}`. The other place is found in a file the diff does not touch. A copy inside one changed file, away from the changed lines, is reported the same way, and a block repeated in two changed files is reported once from each file with the other's place. Tests: `c7684a_a_copied_block_is_reported_with_the_other_file_and_lines`, `c7684a_a_copy_between_two_changed_files_is_reported_from_each`.

**C7684b only a real repeat counts.** Given the same repo, then a changed hunk that repeats nothing yields no hit, and neither does a repeat shorter than the minimum: 8 consecutive lines of at least 40 non-whitespace tokens in all, counted after blank lines and lines of only brackets or punctuation are dropped. A hit never names its own lines as `other`, and one changed range reports one other place, the first by path then line. A generated or binary file, a file over 1 MiB and a path under `.roundup/` are neither scanned nor reported. Policy: the minimum is set on this repo; the implementing PR records the scan over its last 50 merged PRs on the Issue, with a median of at most one hit a PR and the dense `tree-40` fixture showing few hits, and changes the constants (named `MIN_LINES`, `MIN_TOKENS`) when it does not. Tests: `c7684b_a_hunk_that_repeats_nothing_has_no_hit`, `c7684b_a_repeat_under_the_minimum_is_not_reported`, `c7684b_an_unscanned_file_is_neither_scanned_nor_reported`.

**C7684c the scan is read-only.** Given the same repo, when the scan runs, then no file in the Worktree or the repo changes, the index and refs are as before, git runs with `--no-optional-locks`, and the scan holds no lock an Agent's own git call needs: a `git commit` in the Worktree during a scan succeeds. Tests: `c7684c_the_scan_changes_no_file_or_ref`, `c7684c_a_commit_during_the_scan_succeeds`.

**C7684d the scan is bounded and never blocks a key.** Given a repo larger than the bound, then the scan reads at most 5000 files and stops after 5 s, answering the spots found with `complete: false`; with the bound not reached, `complete` is true. It runs off the async runtime, so a `rail.tree` call made during a scan of that repo answers without waiting for it. When its call is dropped (the App closed the view or its connection ended) the scan stops within 250 ms and reads no further file. Tests: `c7684d_a_large_repo_answers_partial_at_the_bound`, `c7684d_another_call_answers_during_a_scan`, `c7684d_a_dropped_call_stops_the_scan`. Observer: `just perf` (rule 7) holds with the scan not running at idle, and its first-paint and keystroke budgets are unchanged because the App asks after the first paint (#7685).

**C7684e the method is the user's and fails as U2539a does.** Given an Agent actor, when it calls `agent.repeatScan`, then it is refused with `FORBIDDEN` and no file is read; the method is declared `none("…")` in `declarations.rs`, so `rup mcp` `tools/list` does not gain it. An Agent with `worktree: null` fails `no_worktree`; a Worktree directory gone from disk fails `worktree_missing`. Tests: `c7684e_an_agent_call_is_refused_and_the_tool_list_does_not_move`, `c7684e_no_worktree_and_missing_worktree_fail_as_u2539a_does`. The fake App answers `agent.repeatScan` from a fixture with hits, none, partial and a failure, so #7685's tests run without a Daemon.

**C7684f the minimum is measured on this repo.** Given `MIN_LINES` and `MIN_TOKENS` as C7684b sets them, when the scan runs over each of the last 50 PRs merged to `main` (each PR's merge-base to its head, in a checkout of its merge parent), then a comment on Issue #7684 holds the hit count per PR, the median and the `tree-40` fixture's count, and the median is at most one hit a PR and `tree-40` shows at most 3 hits (policy: the comment is the record, and a run reads it from the Issue). When either bound fails, the same PR raises `MIN_LINES` or `MIN_TOKENS` until both hold and the comment names the values it kept, with the C7684b test still passing. The scan runs from a test marked `#[ignore]` or a small example in `crates/agents`, so the count needs no model and no new Daemon method. Tests: `c7684f_the_tree_40_fixture_has_at_most_three_hits`.

Reuse (rule 9), required in the implementing PR. Candidates with evidence found on 2026-11-20, to be re-verified in the PR with release dates and measurements: `fallow` 3.34.0 (installed; a native Rust binary shipped through npm, [source](https://github.com/fallow-rs/fallow)) finds duplicates in JavaScript and TypeScript only, runs as a whole-project CLI with no hunk-against-repo input, and would be a second binary to ship; `jscpd` 5.x ([source](https://github.com/kucherenko/jscpd), Node, with a Rust engine as `jscpd-rs` on [crates.io](https://crates.io/crates/jscpd-rs)) and its library crates `cpd-core` and `cpd-tokenizer`; `polydup-core` ([crates.io](https://crates.io/crates/polydup-core), Tree-sitter and Rabin-Karp, cross-language); `dupes-core` ([crates.io](https://crates.io/crates/dupes-core), Rust only). The shipped App starts no Node of its own (`node` is only an optional Extension runtime, `crates/rupd/src/extensions/mod.rs`, and ADR 0002 rejects a bundled Node), so a Node tool cannot run on a user's machine. The PR measures C9b's native size and the rule 7 budgets for the Rust library candidates, takes the first that fits and takes hunk-against-repo input, and otherwise builds the bounded scan: line hashing over the changed hunks against each other and against the other tracked files. Each rejection cites a specific missing capability, size or release age.

Observers: `cargo nextest` on Linux (every test above); `just perf`. No test checks layout or looks (rule 10); the critic judges #7685's drawing. Line budget: about 550 changed lines (scan 250, Contract and wiring 150, tests 150).
