# The live App builds the new main beside itself (SU5982a–SU5982e)

Module: `justfile` (recipe `update`), `tools/update/` (the helper, `update.sh`), `crates/desktop` (`src/update.rs` and its app-menu item). Terms: Build slot and `good` (`GLOSSARY.md`; this file adds Build slot: a directory under `$ROUNDUP_HOME/slots/` holding one build of main from source, and `good`: the file `$ROUNDUP_HOME/slots/good` naming the one slot the App may restart into), Fork, Project, Daemon (`GLOSSARY.md`). Principles served: P5, P11 (`PRINCIPLES.md`). Design: the owner's direction of 2026-11-03 on #5982: the live App runs main from source in dev mode and takes a new build only on "Restart to update". Needs `scenarios/data-fork.md` (FK5977a–e) and `scenarios/migration-additive.md` (MG1–MG4) on `main`; implement after #5977 and #5983. Adds no RPC method: the check calls `data.fork`, `daemon.ping` and `project.open`. Contract change (rule 4): none beyond the `GLOSSARY.md` rows; the App's one new seam command (`update.status`, read by the menu item) is declared in `crates/desktop` and has the menu item as its one caller. Tests use a throwaway git repository as "main", a fake build command, an in-process Daemon on a temporary data folder and a temporary `$ROUNDUP_HOME`; no `claude`, network or display. Ids: SU5982a–SU5982e.

**SU5982a main moving starts a build in a spare slot.** Given the live App running slot `A` and `good` naming `A`, when `origin/main` of the App's source checkout moves to a commit no slot holds, then `just update` checks the commit out into the spare slot `B` (never `A`) and builds it there, while `A`'s files, its running Daemon and its window are untouched; a further move during the build restarts the build on the newer commit and never leaves two builds running. A commit already built in a slot is not built again. Tests (`su5982a_`): the helper against a throwaway repository, asserting `B` holds the new commit, `A`'s tree hashes before and after are equal and a second move supersedes the first; the `A` Daemon answers `daemon.ping` through the build.

**SU5982b the check is a Fork the new build opens.** Given a finished build in slot `B`, when the helper checks it, then it makes a fresh Fork of the live data folder (`rup data fork`, all Projects, FK5977a) in a temporary path, starts `B`'s Daemon on that Fork and a spare socket, requires `daemon.ping` to answer and `project.open` to succeed for every Project the Fork holds, then stops that Daemon and deletes the temporary Fork; the live data folder's checksums (FK5977e) and the live Daemon's Agents, Terminals and Worktrees are untouched, and the check never opens the live folder with `B`. Tests (`su5982b_`): a passing build opens a Fork with two Projects and the helper's log names each opened; the live folder's checksum before and after; a Project that fails to open fails the check (SU5982c).

**SU5982c only a passing build becomes good.** Given the check of SU5982b, when `daemon.ping` answers and every Project opens, then `good` is rewritten to name `B` by one atomic rename, after the check ended and never before; when the build exits non-zero, the Daemon does not answer `daemon.ping` within 30 s, any Project fails to open or the Fork cannot be made, then `good` is unchanged, `B` holds `failed.json` with `commit`, `step` (`build`, `fork`, `ping` or `open`) and `cause` (the failing command's last 20 lines or the Project key and its `project.open` error), and the exit code is 1 (build), 2 (fork), 3 (ping), 4 (open). A new check clears `failed.json` of the slot it reuses. Tests (`su5982c_`): one test per failing step asserting the exit code, `failed.json` and `good` bytes unchanged; the passing case asserting `good` names `B` only after the check's last log line; a kill of the helper mid-check leaves `good` as it was.

**SU5982d the previous build stays.** Given `good` naming `B` after a pass, when the next main moves, then the spare slot is `A` only when `B` is `good` and `A` is not the running App's slot; the helper never writes into the slot the running App runs from or the slot `good` names, whichever it is. A failed check of the new build leaves both slots as they were and `good` naming the build the App can restart into. The previous build still opens the data the new one wrote (MG3), so the owner can restart back into it by pointing `good` at it (`just update --rollback`, which names the slot that held `good` before). Tests (`su5982d_`): three consecutive moves with a pass, a failure and a pass, asserting which slot each build used and that neither the running slot nor `good`'s slot was written; `--rollback` restores the earlier `good`.

**SU5982e the App offers "Restart to update", and says why not.** Given the App running slot `A`, when `good` names a slot other than `A`, then the application menu holds an enabled item "Restart to update"; choosing it quits the App after the Daemon has no running Agent being started and relaunches into that slot on the same data folder; an Agent, Terminal or Worktree running at that moment is neither signalled nor ended by the quit, since the Daemon outlives the App (the launch recorded in `crates/desktop/src/daemon.rs`). Given `good` names `A` and the spare slot holds `failed.json` for a newer commit, then the item is disabled and its text is "Update failed: <step>"; its tooltip shows `cause`. Given neither, no item is shown. The App never restarts by itself: no timer, no dialog and no native attention is raised by a new build (P3). Tests (`su5982e_`): the item's state as a table over the three conditions, through `update.status` read from a temporary `$ROUNDUP_HOME`; choosing the item calls the relaunch with the `good` slot and sends no signal to any child the Daemon holds. Native look is the user's Mac report (L46).
