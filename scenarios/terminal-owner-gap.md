# Terminal output while no Daemon is attached

Module: `crates/terminal`; tests in `crates/terminal/tests/` and `crates/rupd/tests/`. Work order: #6014. Observer for the byte-loss clause of S5981a (`scenarios/app.md`); X8 (`scenarios/terminal.md`) and X5639a/b (`scenarios/terminal-output-memory.md`) keep their contracts.

**X6014a output written while no client is attached is kept and replayed in order.** Refs #5981. Given a Terminal owner (X8) whose program prints one numbered line per tick, when its client detaches (a Daemon left by `exit_for_update`, S5981a) and a new client attaches after a gap of several ticks, then the attached Terminal's snapshot and catch-up output (X14) hold every number the program printed since the first, once each and in order, with no duplicate across the gap and no `terminal.gap` naming bytes the owner still holds. The owner buffers the output itself, in the bounded Output log (X5639a), so no Daemon is needed to keep it; output beyond that bound is dropped oldest first and reported as a gap by offset, never silently. Tests: `x6014a_output_written_while_detached_is_replayed_in_order` (`crates/terminal/tests/`; a real owner and a counting program, the client process ends and a second attaches), and `s5981a_output_written_between_exit_and_reopen_is_replayed_in_order` (`crates/rupd/tests/`; the same through a real `rupd` reopening the Project, A12a).

**X6014b the buffer is bounded and reports what it dropped.** Given the Terminal of X6014a and a gap in which the program prints more than `LOG_BYTES` bytes, when a client attaches, then its snapshot holds the newest `LOG_BYTES` bytes and the first offset it reports equals the number of bytes dropped before them, so the client can tell what is missing (X5639b). Owner memory stays within X5639a's bound (rule 7). Test: `x6014b_a_long_gap_drops_oldest_bytes_and_names_the_offset` (`crates/terminal/tests/`).
