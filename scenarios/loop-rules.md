# Loop rules

Module: `loop/rules.sh`, `loop/builder.py`, `loop/orders.py`, `loop/stall.py` for L94, `loop/percy.sh` for L36, `loop/scenario_ids.py` for L97, and the workflows each id names. Each id's cases are its `L<n>` tests in `loop/rules.test.sh`, `loop/builder.test.py`, `loop/workflows.test.py`, `loop/orders.test.py`, `loop/stall.test.py`, `loop/scenario_ids.test.py` and `loop/percy.test.sh`.

| Exit | Means |
|---|---|
| 0 | holds |
| 1 | a rule is broken; stderr names it |
| 2 | bad input or usage, before any network call |
| 4 | `gh` or `git` failed, or `gh` exceeded `LOOP_GH_TIMEOUT` (20 s, fractions allowed); never read as a pass |

**L2 authorship.** `ci-trailers <pr>` passes when every commit carries `Author-Agent`, except a clean merge of `main` (L54) or a Copilot Autofix commit (L37), and no commit carries `Reviewed-by-Agent`: an approval is a verdict comment.

**L3 vocabulary.** `vocab` fails naming the word when a public Rust item, TS export or `contracts/` name holds a `GLOSSARY.md` _Avoid_ word, except under `crates/agents/claude_code/`.

**L23 Builder runs.** `build.yml` runs when `check` ends on `main` (claude-code-action rejects push events), hourly, on dispatch, and when an Issue adds work: a new or reopened Issue from the user (`saadshahd`) or a loop App, or a removed `flag:needs-user` or `flag:needs-mac`. Its `pick` job runs one at a time: `builder.py pick` first starts a fix run (L82) for each open same-repository `build/` PR that conflicts with `main` while its head awaits no review verdict (L82), failed `check`, `rules` or `review` on its head (for `check` and `rules`, in its latest result there, L82), or stayed a draft with no `Stopped:` line for three hours; then it takes L34's ready rows that no queued or running `build #<issue> / build` job holds, in Priority order, until sixteen build jobs hold Issues. Each row calls `build-issue.yml`, whose `build` job runs one job per Issue at a time, on Sonnet, for at most two hours. `orders.py task` checks the Issue again before any model call; a refusal (exit 3) ends the job with no run and no strike. The prompt is `.agents/builder.md` byte for byte, a `## Task` heading, then the task, its delimiter on its own line even when the task has no trailing newline. A run worked when its model used a tool, read from the action's execution file; a usage limit or setup failure is a run that did not work and records nothing. The run answers `{ask}`, empty unless only the user can act (`.agents/builder.md`). After a run that worked, `builder.py built` hands an open `build/<Key>` PR to L81; with none, it reads the Issue. One a person closed, one closed after its `build/<Key>` PR merged, one whose Key starts `stall-` (L94 closes it on any merge), or one `flag:needs-user` or `flag:needs-mac` holds, records nothing; one a bot closed without such a PR reopens and is struck. Otherwise a non-empty `ask` goes where its screen sends it (L79), and one a dependency or PR holds records nothing. One still ready gets a `<!-- strike -->` comment linking the run, and so does the Issue of a Builder PR that used its three fix runs (L82), linking that PR; strikes ask nobody, and L34 holds an Issue struck three times in 24 hours. Each Issue's own `after` job in `build-issue.yml` runs `builder.py built` as soon as that Issue's build job ends, and when its model worked dispatches `build.yml` on `main` with its workflow token, so a freed slot fills without waiting on the run's other jobs, the next merge or the hour; a job whose model did not work dispatches nothing, so a usage limit ends the chain. Build and fix runs request `workflows: write` from the installed Claude App, plus `actions: read` and `checks: read` for CI evidence; the action keeps its standard contents, pull-request and Issue publication rights. They request no check, status, administration or Actions write authority. Review runs keep their separate read-only workflow token. The App's token lasts an hour and a run may not, so the model step ends after 105 minutes, and an always-run step then runs `main`'s `builder.py keep`: when the run's branch holds commits the run did not push, or a build run's branch holds commits and its still-ready Issue no open PR, it trades the job's OIDC token for a fresh App token, as the action does, pushes the branch and, for that Issue, opens a draft PR naming `Refs #<issue>`, which `built` hands to L81 like any draft, then revokes the token. Builder checkouts install hooks from `main` (`author.sh`): a prepare-commit-msg hook that supplies a missing `Author-Agent` trailer and keeps existing attribution, and L97's pre-push hook. A build run reads every comment on its Issue starting `<!-- fix-exhausted` as an approach already tried (`.agents/builder.md`) and takes another (policy). A build run that finds its Issue's acceptance already met by other merged PRs opens its `build/<Key>` PR with one empty commit and `Closes #<issue>`; its review run runs a test that asserts each then-clause, and the merge closes the Issue, so work already done ends in no strike (policy). Tests: `l23` and `l79` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L24 review.** `check` skips a draft's heads, so a Builder's red pushes hold no macOS runner, and runs on push to `main`. When `check` succeeds on a same-repository PR head, `review.yml` runs from `main`'s definition, so no PR edits its own review; a newer head of the branch cancels an older head's review. `builder.py review-task <pr> <head>` prints the review run's task only when the PR is open at that head and not a draft, else exits 3 and no model starts. The task holds the body's `Scenarios:` and `Moves:` lines; for `apps/desktop/src/`, `percy-review` on the head's Percy build (`percy.sh build <sha>`, waiting up to 10 minutes; none is a `NOTE`, a Percy API failure exits 4) against the scenarios' then-clauses and the `Moves:` checks, never the author's intent; and earlier verdicts; never the rest of the body. The review run is a Builder run, `.agents/builder.md` byte for byte and then the task, on Opus with a read-only token, answering `{verdict, findings}`. Its checkout of the head holds `main`'s `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.agents/` and `loop/` in place of the head's, and no other `CLAUDE.md` or `AGENTS.md`, so no PR instructs its own review; it reads the PR's changes to them through `gh pr diff`. `builder.py review-post` posts the answer as `VERDICT:`, `Head:`, the findings and `Reviewed-by-Agent: reviewer-<run id>`, drops any findings line that would forge one of those fields, and sets the commit status `review` on the head: `success` for approve, `failure` for reject. A reject on a `build/` PR starts a fix run (L82). A head that moved since posts nothing. A run whose model used no tool (L23) leaves `review` pending; each `pick` reruns that review run once it has ended, and after six attempts asks the user (L79) instead. A run that worked with no verdict sets `review` to `error`, asks the user and fails. Tests: `l24` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L33 base.** `base <pr>` passes only when the PR's base is `main`.

**L34 Issue queue.** Work orders are open GitHub Issues, in the format of `.agents/data/work.md`, that the user (`saadshahd`) or a loop App (`claude[bot]` for a Builder's prerequisite, `github-actions[bot]` for a stall Issue) filed. Anyone else's Issue, a collaborator's included, is unspecified and never runs whatever its labels, since the repository is public. `orders.py ready` reads all pages and prints each Issue and its derived state; `--json` exposes structured records. Existing same-repository open `build/<Key>` PRs, or PRs explicitly naming the Issue with Refs/Closes/Fixes/Resolves, are in flight. An open work order is ready only when every native blocked-by dependency is closed as completed and it lacks `flag:needs-user` and `flag:needs-mac` (L79), either of which holds it unless its Key starts `stall-`; cancelled dependencies still block. Three `github-actions[bot]` comments starting `<!-- strike -->` (L23) in the last 24 hours hold an Issue whose Key does not start `stall-` until the oldest of the three is 24 hours old; the row names that time, nobody is asked, and L94 still counts the Issue as waiting work. No intake label is needed. Invalid fields, duplicate Keys and dependency cycles block visibly. API errors or timeouts exit 4, never an empty queue. Test names and file tables have no scheduling or completion authority. A specification Issue may introduce its named scenario. An implementation Issue whose Specification file or a named scenario heading is absent from the checkout, or whose Scenarios line names no ID, runs as Mode `specify` first: its task asks for the scenarios and an Issue that names their IDs and keeps Mode `implement`, so the queue implements it once they merge. An Issue with no `Key:` line is a request, such as a bug report: Mode `specify`, Key `issue-<n>`, Priority 50, so a Builder specifies it before the queue builds it. Tests: `loop/orders.test.py`.

**L36 Percy build.** The `visual` workflow's `percy` job reports on every PR, so it can be required, and passes at once when the PR changes nothing under `apps/desktop/src/`. On a PR that does, and on each such push to `main` as Percy's baseline, it runs `percy.sh snapshot`, which pins the build's commit to the PR head (`PERCY_COMMIT`), so L24 finds it by that SHA, serves `just harness` and runs `percy snapshot` on each seed of `.agents/data/harness.md` at 1280 px wide in Chrome only; it fails without `PERCY_TOKEN`, when the harness never answers, when Percy fails, or when its output has no build link, and writes that link to the job summary. When Percy refuses the build because the account is over its plan's limit, the job passes and its summary says the head has no visual proof; the review then checks the code alone (L24). (The user's call, 2026-10-11.)

**L37 Copilot attribution.** A commit with no `Author-Agent` is authored by `copilot` when it has the Copilot Autofix `Co-authored-by` trailer, GitHub committed it, and its signature verifies against GitHub's web-flow key in `loop/web-flow.asc` and no other key; anything short of all three still needs `Author-Agent`, and `copilot` can never be the approver.

**L41 tokens.** `tokens` scans every `.css` file and every `.ts` and `.tsx` file under `apps/desktop/src/` except `tokens.css`, `terminal/emulator.ts` and test files (`*.test.*`, `testing/`), and fails naming `<file>:<line> <property>` for each look literal. A look literal is a value that sets one of these without `var(--…)`: a colour (`color`, `background`, `background-color`, `border*`, `outline*`, `fill`, `stroke`, `caret-color`, `text-decoration-color`) holding a `#` hex, an `rgb(`, `rgba(`, `hsl(`, `hsla(`, `oklch(`, `color-mix(` or a bare colour name other than `transparent`, `inherit`, `currentColor`, `none`, `initial` or `unset`; a `font-size` or `border-radius` holding a number with a unit; a `box-shadow` other than `none`; or a `transition*` or `animation*` duration holding a number with `ms` or `s` other than `0s`. In a `.ts` or `.tsx` file only the text of `style={{…}}` objects is read, where `fontSize`, `borderRadius`, `boxShadow`, `color`, `background`, `backgroundColor` and `borderColor` hold the same values. A comment is not read. Exit 0 and no output when nothing is found, 1 with one line per literal, 2 with an argument. Tests (`l41_`, in `loop/rules.test.sh`, on a temporary tree whose `apps/desktop/src/` the script reads from `$PWD` the way `vocab` reads its tree): `l41_a_hex_colour_fails_naming_file_line_and_property`; `l41_rgba_hsl_and_a_bare_colour_name_fail`; `l41_a_unit_font_size_and_radius_fail`; `l41_a_box_shadow_and_a_duration_fail`; `l41_var_reads_pass`; `l41_transparent_inherit_currentcolor_none_and_0s_pass`; `l41_tokens_css_is_not_read`; `l41_emulator_ts_and_test_files_are_not_read`; `l41_an_inline_style_literal_fails_and_a_var_passes`; `l41_a_literal_in_a_comment_passes`; `l41_an_argument_exits_2`. `u130_` (`scenarios/ui-visual.md`) adds the `tokens` step to `.github/workflows/loop.yml` in the PR that leaves no literal.

**L42 delta.** `delta <base-dir> <head-dir>` prints `<step> <id> fixed|regressed|still-failing|still-passing` per check and fails on any `regressed`; a check missing on one side is exit 2, never a pass.

**L46 merge gates.** GitHub auto-merge merges a PR once ruleset `main-2` sees `check`, `rules`, `review`, `percy` and `critic` succeed on its head, each pinned to GitHub Actions, so no other app or person can post them; the ruleset has no bypass (policy). A Builder that leaves a ready PR arms auto-merge. No gate waits on the user's Mac: agents verify on Linux, the user reports a Mac problem when they see one, and only a problem that needs a Mac gets a Mac CI job or a `flag:needs-mac` ask (L79). Tests: `l46` in `loop/workflows.test.py`.

**L54 clean merge.** `clean-merge <commit>` passes for a merge of `main` that conflicts nowhere and changes nothing beyond the trial merge; such a merge needs no `Author-Agent`, and an approve of its first parent still covers it, so a human can merge `main` in from GitHub.

**L79 needs the user.** A PR or Issue waits on the user through the label `flag:needs-user` and one `github-actions[bot]` comment marked `<!-- needs-user -->` saying what to decide; `builder.py` and `stall.py` (L94) add both once and ask nothing more while the label is on. Four things ask: (1) a draft's `Stopped:` question (L81) and (2) a build run's `ask` (L23), each when its screen judges it `user`, (3) a review run with no verdict or six that did no model work (L24) and (4) a six-hour stall (L94). The job that ran the model screens what the run asks the user, the `Stopped:` paragraph of the open draft a build or fix run left or, with no PR, a build run's non-empty `ask`, with `claude-haiku-5-5`, no tools, against `.agents/screen.md`, answering `{verdict, reason, preview}`: `user` (a product choice no scenario settles, or a judgment of how something looks or feels) gets `flag:needs-user` with the preview above the question; `mac` (a check whose pass or fail only the user's Mac can produce: a logged-in real `claude`, or the `just app` window's native behaviour no Chromium check covers; a check `check`'s `macos-latest` jobs already run, or a native look-and-feel check whose Issue's observer is a Linux or Chromium check, or the native behaviour of work `main` already merged whose Linux or Chromium tests pass on `main`, is `loop`) gets the label `flag:needs-mac` and one comment marked `<!-- needs-mac -->`, which an agent on that Mac answers and takes off; `loop` strikes the Issue with the reason (L23), which the next build run reads as an answered ask (`.agents/builder.md`), or sends a draft back to work (L81). `.agents/screen.md` names the run's own GitHub token, push or job (an expired token, a failed push, a re-run) a `loop` fault, which `keep` (L23) or a later run repairs and no user can; Haiku still screens the whole question, so a product or Mac ask beside such a fault keeps its `user` or `mac` verdict. With no valid verdict the question goes to the user, marked unscreened, so a screen outage hides no question. Open items labelled `flag:needs-user` are the whole list; the queue builds no Issue either label holds but a stall Issue (L34), and removing either label returns an Issue to the queue and starts a pick (L23). Only `stall.py` (when a merge lands, L94) takes its own label off; the user takes off the other `flag:needs-user` labels. Tests: `l79` in `loop/builder.test.py`, `loop/orders.test.py` and `loop/workflows.test.py`. Every run executes ordinary engineering choices without approach confirmation; only these reasons wait for the user (policy).

**L81 stopped.** A Builder that stops on a product question leaves a draft with `Stopped: <the question>`, its consequence and a recommendation; after the run, `builder.py` sends that paragraph where its screen says (L79). `loop` replaces the paragraph with the run's link, the question and the screen's reason, so the draft no longer counts as stopped, posts the same text as a PR comment and starts an `unfinished` fix run, which reads it as an answered question (`.agents/builder.md`); L82's three fix runs bound the round trips. After a build or fix run that worked (L23), a draft without a `Stopped:` line gets an `unfinished` fix run (L82), and so does one no run touched for three hours. A ready PR goes on to `check` and review. Tests: `l81` in `loop/builder.test.py`.

**L82 fix runs.** `fix.yml` runs from `main`'s definition when `check` or `loop` fails on a same-repository `build/` PR, and on dispatch with a PR, its head and a cause: `check`, `rules`, `review` (a reject), `critic` (L103), `conflict` or `unfinished`. One fix run per PR runs at a time. A `check` or `rules` cause counts only from the latest result on the PR's head: once no run of its workflow is still going there, the check run of that name that ended last decides, so a newer run on the same head supersedes an older run's failure; `pick` dispatches no such cause, and `fix-task` exits 3 for it and counts no attempt. `check`'s gate job runs unless its run was cancelled, so in a run that concurrency cancels (a push and `gh pr ready` start two runs on one head) it ends `cancelled`, which blocks merge and starts no fix run. `builder.py fix-task` prints the task only when the PR is open at that head on a `build/` branch, else exits 3 and no model starts; so does a `check` or `rules` cause that `main` caused, so a fix run never answers `main`'s failure and the PR counts no attempt for it. `builder.py` reads the jobs that failed the cause on the head (`rust` and `web`, or `rules`) and, for each, its result on every push to `main` from the head's merge base until the job started, the pushes the PR's run could have merged. Each push to `main` keeps its `check` and `loop` runs, so `web`, `linux` and `rules` end on every push; a newer push cancels only an older push's Mac `rust`, and then that run's gate job skips, so a superseded commit shows no red `main`. A cancelled job gives no result. A job that failed on one of those pushes, while `main`'s latest result for it still fails, or a push among them whose job has not ended, starts no run; `pick` dispatches the cause again when `check` ends on `main` and each hour (L23). Once `main` passes that job again, the fix run only merges `origin/main` into the PR and pushes, once per head: it first posts a `<!-- fix-refresh <head> -->` comment linking the run and counts no attempt, and the merged head's runs decide; a refresh run that did not work (L23) deletes that comment, so the head keeps its refresh. A failing job that passed on each of those pushes, a refreshed head that fails again and a conflicting PR get their fix run. So does a `review` cause when the PR's last `<!-- fix-attempt -->` is newer than its last `VERDICT:` and under three hours old, since a review of that fix is on its way and the new verdict decides; the task names the cause, where the failed run's log is, the last verdict for a reject, and how the run ends. Whatever the cause, the task also names a conflict with `main`, first, and the last verdict when it rejects that head and is newer than the last `<!-- fix-attempt -->`, so a conflict and a reject cost one fix run and one attempt. A task that names only a conflict counts no attempt, since `main` moved, not the PR, even while the head fails `check` or `rules` (the merged head's runs decide those) and after three attempts: it asks for the merge and nothing the merge does not need, and the run first posts a `<!-- fix-conflict <head> -->` comment linking the run. A PR gets three such runs, then a conflict counts its attempt, so a PR gets at most six fix runs besides refreshes: `pick` holds each conflict until its head's verdict, so each such run follows a reviewed head, and #870 spent two of its three attempts on conflicts. A conflict run that did not work (L23) deletes its comment, as a refresh run does. `pick` holds a `conflict` cause while the head awaits its review verdict: its `check` has not ended, or passed under three hours ago and the head holds no `review` status other than a pending one. The reject then reaches the run that merges `main`, never lands while that run works. A fix run that worked and counts an attempt posts a `<!-- fix-attempt -->` comment on the PR; with three there, the next cause that would count one starts no run and hands the PR to its Issue instead: `builder.py` posts one comment on the PR's work Issue marked `<!-- fix-exhausted #<pr> -->` holding the PR link, a line per attempt's cause (`check`, `rules`, `review`, `conflict` or `unfinished`) with its failing check or the review finding, and the commit subjects its run pushed after it started, so a run that counted no attempt is no line, then closes the PR unmerged, deletes `build/<Key>` and strikes the Issue as L23 does. It posts, closes and strikes once per PR, so a repeat of the cause adds nothing, and it sets no `flag:needs-user`. The closed PR keeps its diff at its link and in `refs/pull/<pr>/head`, and the comment names the head commit. The closed PR leaves the Issue with no open `build/<Key>` PR, so L34's ready row starts at most one fresh build run from `main` (L23; policy, as `pick` holds one job per Issue); the Issue stays ready unless the strike is its third in 24 hours (L34). The close, the branch deletion and the strike bypass no required check or review status: nothing merges. The fix run pushes with the Claude App's token, so its push or its `gh pr ready` starts `check` and then review again (L24); a fix run that outlives that token keeps its commits through `keep` (L23), and its draft goes on through L81. A `review` fix run that worked and left the PR ready with neither (it only edited the body or title) starts no `check`, so `builder.py fixed` reruns the review run behind the head's failed `review` status, unless a `check` run is still going on that head; each such rerun counts toward L24's six attempts of that run. No retry bypasses a required check or the review status. Tests: `l82` in `loop/builder.test.py`: a fourth cause makes the comment, closes the PR, deletes the branch and strikes the Issue with no `flag:needs-user`, and a repeat does nothing more; a reject a fix run already answered starts no run until three hours pass; a reject answered with no push reruns its review run, and none is rerun for a draft, a moved head, a running `check` or another cause; a `check` or `rules` failure `main` caused starts no run and closes no PR, even at three attempts, while `main` still fails that job or has not ended it on a push the PR merged; once `main` passes, the run only merges `main`, once per head, and counts no attempt, and one that did no work leaves the refresh to the next run; a refreshed head, a conflicting PR, a failure no merged push shares, a cancelled `main` job and other causes get their run; a conflict task on a rejected head asks for the merge, then the findings, a reject of another head, one a fix run answered or one an approval follows adds nothing, and a reject task on a conflicting PR asks for the merge first; a task naming only a conflict counts no attempt, while `check` fails and after three attempts too, and one that did no work deletes its comment; a conflict with a reject or a failing `check` counts one; past three such runs a conflict counts its attempt and, after three attempts, closes the PR; the Issue's record shows no such run's merge under an attempt; `pick` holds a conflict while the head's `check` runs or its review has not posted, and starts it once a verdict is in, three hours pass or `check` failed; a `check` or `rules` failure that a newer run on the same head superseded, or a cancelled one, starts no run and counts no attempt, while one the latest run failed gets its run; and `loop/workflows.test.py`: `loop` runs on push to `main`, the fix task may read check runs and Actions jobs, `check`'s gate job runs neither in a cancelled run nor on a `main` push whose `rust` a newer push cancelled, and each push to `main` ends its `web`, `linux` and `rules` jobs.

**L84 Linux Builders.** Build and fix runs move to `ubuntu-latest` once a push to `main` passes `just check` there. `.github/actions/setup` installs Tauri's Linux packages (`libwebkit2gtk-4.1-dev`, `build-essential`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`) on Linux and GNU coreutils on macOS, and keys the Rust cache by the runner's OS. Each push to `main` also runs `just check` on `ubuntu-latest`, which saves the Linux cache. `check` on a PR stays on `macos-latest`, where the App ships, so no Linux green merges alone.

**L98 pipefail.** Every workflow under `.github/workflows/` sets `defaults.run.shell: bash`, so GitHub runs each `run` step under `bash -eo pipefail` and a failing command left of a pipe fails the step.

**L86 journey priority.** GitHub work Issues hold a numeric Priority from 0 (first) to 100 (last). Eligible Issues sort by Priority then Issue number before capacity limits apply. Native dependencies, an open PR and a running build job are never overridden. `.agents/data/journey.md` retains the goal and required rendered/behavioral evidence, not a duplicate priority list. Tests: `loop/orders.test.py` and `loop/builder.test.py`.

**L89 parallel CI.** `just check` remains the union of `check-rust` and `check-web`. CI runs those recipes concurrently, keeps Rust and the daemon smoke test on macOS, and runs web checks on Linux. The required `check` job succeeds only if both lanes succeed, and a draft invokes neither. Motivation: run 37831870531 spent about 105 seconds in Rust checks followed by 93 seconds in frontend tests. Tests: `loop/workflows.test.py`; observer: both CI lanes and the final gate on the PR.

**L93 run explanation.** Every workflow ends with an always-run Actions summary (`summary.yml`) naming its purpose, trigger, job results, the run link and the next automatic step, from the supplied job results without a checkout or GitHub API call. A run whose agent jobs all skipped says no agent work ran; a green workflow is not delivery (policy).

**L94 stall.** `stall.yml` runs `loop/stall.py` from `main` hourly and on dispatch. It calls no model, does not depend on `build.yml`, and holds `issues: write` and `contents: read` and `pull-requests: read` and `actions: read` and nothing else. Work waits when an open work Issue (L34) other than a stall Issue, or an open same-repository `build/` PR, lacks `flag:needs-user`; one `flag:needs-mac` holds still waits, so a queue that only Mac checks hold ends in a stall. A stall is work waiting while no PR merged to `main` in the last 3 hours. The script exits 0 whether or not a stall exists, and 4 when `gh` fails, never reading that as no stall.
- *No work waits.* Nothing is opened or commented, however long `main` has been quiet (`l94_no_issue_when_no_work_waits`). A stall Issue open when this holds stays open until a merge (`l94_no_work_leaves_an_open_stall_open`).
- *A stall, none open.* It opens one Issue labelled `loop:work` with `Scenarios: L94`, `Specification: [scenarios/loop-rules.md](https://github.com/saadshahd/roundup/blob/main/scenarios/loop-rules.md)`, `Key: stall-<yyyymmdd-hh>` (UTC), `Priority: 0` and `Mode: implement`, so `orders.py ready` classifies it ready (L34) and a build run repairs the loop, never specifies (`l94_first_stall_opens_one_implement_issue`, which asserts that classification). Its body lists the last merge (PR, time), each waiting Issue and PR, and every build, fix and review run since that merge with its workflow, link, result and, for a run that ended on a usage limit or did no model work (L23), that cause (`l94_body_lists_merge_waiting_work_and_runs`).
- *A stall, one open.* The next hourly run comments on that Issue with the same lists and opens no second Issue, so at most one open `loop:work` Issue has a Key starting `stall-` (`l94_next_run_comments_not_a_second_issue`).
- *Six hours.* When the last merge is 6 hours old or more, the Issue gets `flag:needs-user` and one `<!-- needs-user -->` comment naming the stall, its age and the failing runs, and asks nothing more while the label is on (L79; `l94_six_hours_asks_the_user_once`). Before 6 hours it sets no `flag:needs-user` (`l94_before_six_hours_does_not_ask`).
- *A merge lands.* The first run after a PR merges to `main` since the Issue opened closes it as completed with a comment naming that PR, and removes `flag:needs-user` (`l94_first_run_after_a_merge_closes_the_issue`). A merge from before the Issue opened never closes it.
- *Independence.* The workflow file names no `build.yml`, `claude-code-action` or model, and its token grants are those above (`l94_workflow_calls_no_model_and_holds_only_issue_writes`).

- *One helper decides.* `apps/desktop/src/testing/captures.ts` exports `captureDir(id)`. It returns the absolute path of `artifacts/ux/<id>/` when the environment variable `ROUNDUP_CAPTURES`, a comma-separated list of ids, names `<id>`, and `null` otherwise, with the variable unset or empty naming none. It creates no directory and writes no file. A capture test asks it and skips its writes on `null`; its assertions run either way (`l105_captureDir_names_a_directory_only_for_a_listed_id`, `l105_captureDir_writes_nothing`).
