# Loop rules

Module: `loop/rules.sh`, `loop/builder.py`, `loop/orders.py`, `loop/stall.py` for L94, and the workflows each id names. Each id's cases are its `L<n>` tests in `loop/rules.test.sh`, `loop/builder.test.py`, `loop/workflows.test.py`, `loop/orders.test.py` and `loop/stall.test.py`.

| Exit | Means |
|---|---|
| 0 | holds |
| 1 | a rule is broken; stderr names it |
| 2 | bad input or usage, before any network call |
| 4 | `gh` or `git` failed, or `gh` exceeded `LOOP_GH_TIMEOUT` (20 s, fractions allowed); never read as a pass |

**L2 authorship.** `ci-trailers <pr>` passes when every commit carries `Author-Agent`, except a clean merge of `main` (L54) or a Copilot Autofix commit (L37), and no commit carries `Reviewed-by-Agent`: an approval is a verdict comment.

**L3 vocabulary.** `vocab` fails naming the word when a public Rust item, TS export or `contracts/` name holds a `GLOSSARY.md` _Avoid_ word, except under `crates/agents/claude_code/`.

**L23 Builder runs.** `build.yml` runs when `check` ends on `main` (claude-code-action rejects push events), hourly, on dispatch, and when an Issue adds work: a new or reopened Issue from the user (`saadshahd`) or a loop App, or a removed `flag:needs-user` or `flag:needs-mac`. Build jobs and fix runs share the slots the repository variable `CODEX_RUNS` sets: each queued or running `build #<issue> / build` job and each `fix.yml` run whose `fix-run` model job has not ended holds one, so a fix run frees its slot when its model ends, as a build job does (`l23_a_fix_run_frees_its_codex_slot_when_its_model_job_ends`), and a fix run that finds every other slot held ends without a task. Its `pick` job runs one at a time: `builder.py pick` first starts, while a slot is free and for ready PRs before drafts, a fix run (L82) for each open same-repository `build/` PR that conflicts with `main`, failed `check`, `rules` or `review` on its head (for `check` and `rules`, in its latest result there, L82), or is a draft with no `Stopped:` line whose Issue no build job holds and which no fix run holds; then it takes L34's ready rows that no queued or running `build #<issue> / build` job holds, in Priority order, into the slots left. Each row calls `build-issue.yml`, whose `build` job runs one job per Issue at a time, for at most two hours. Build and fix runs start on Codex on `gpt-6.1-sol` for every Issue and PR. `builder.py engine` runs Claude Code on `claude-sonnet-5-5`, never Fable, with the Max token `CLAUDE_CODE_OAUTH_TOKEN` as review does, with the same prompt only when Codex's model used no tool (a usage limit, a broken ChatGPT login or another setup failure, read as `worked` reads a run below, so its checkout is untouched); a broken login also prints an `::error::` annotation on the run; when Codex worked, Claude Code never starts. The owner chose Codex first for every build and fix on 2026-10-18, so the Claude limit goes to review and the critic; build and fix runs share the `CODEX_RUNS` slots. Codex signs in with the user's ChatGPT login, the `CODEX_AUTH_JSON` secret, which the user seeds from a `codex login` into its own `CODEX_HOME` with `cli_auth_credentials_store = "file"`; `builder.py engine` takes it out of the environment before either engine starts, writes it outside the checkout for Codex and masks each token in the log, and the public step log shows only each event's kind, never a command, its output or a message. Every run starts from that one login, so a refresh one run makes can leave the others signed out: those runs did not work, and the user seeds the secret again. The repository is public and OpenAI advises against a ChatGPT login in public CI; the user accepted that risk to spend the ChatGPT plan when the Max plan's budget is spent, and a run with a shell can read the login as it can read `CLAUDE_CODE_OAUTH_TOKEN` (policy). `orders.py task` checks the Issue again before any model call; a refusal (exit 3) ends the job with no run and no strike. The prompt is `.agents/builder.md` byte for byte, a `## Task` heading, then the task, its delimiter on its own line even when the task has no trailing newline. A run worked when its model used a tool, read from the event lines of Claude Code or Codex (a review or critic run's from claude-code-action's execution file); a usage limit or setup failure is a run that did not work and records nothing. The run answers `{ask}`, empty unless only the user can act (`.agents/builder.md`). After a run that worked, `builder.py built` hands an open `build/<Key>` PR to L81; with none, it reads the Issue. One a person closed, one closed after its `build/<Key>` PR merged, one whose Key starts `stall-` (L94 closes it on any merge), or one `flag:needs-user` or `flag:needs-mac` holds, records nothing; one a bot closed without such a PR reopens and is struck. Otherwise a non-empty `ask` goes where its screen sends it (L79), and one a dependency or PR holds records nothing. One still ready gets a `<!-- strike -->` comment linking the run, and so does the Issue of a Builder PR that used its three fix runs (L82), linking that PR; strikes ask nobody, and L34 holds an Issue struck three times in 24 hours. Each Issue's own `after` job in `build-issue.yml` runs `builder.py built` as soon as that Issue's build job ends, and when its model worked dispatches `build.yml` on `main` with its workflow token, so a freed slot fills without waiting on the run's other jobs, the next merge or the hour; a job whose model did not work dispatches nothing, so a usage limit ends the chain. A fix run's `after` job does the same once `builder.py fixed` runs. Build and fix runs push and publish with a Claude App token that `builder.py engine` trades for the job's OIDC token, holding contents, pull-request and Issue writes and `workflows: write`, plus `actions: read` and `checks: read` for CI evidence; their commits name the account of the engine that ran, `claude[bot]` or the Codex App's. They request no check, status, administration or Actions write authority. Review runs keep their separate read-only workflow token. The App's token lasts an hour and a run may not, so the engine step ends after 105 minutes, and an always-run step then runs `main`'s `builder.py keep`: when the run's branch holds commits the run did not push, or a build run's branch holds commits and its still-ready Issue no open PR, it trades the job's OIDC token for a fresh App token, as the action does, pushes the branch and, for that Issue, opens a draft PR naming `Refs #<issue>`, which `built` hands to L81 like any draft, then revokes the token. Builder checkouts install a prepare-commit-msg hook from `main` (`author.sh`) that supplies a missing `Author-Agent` trailer and keeps existing attribution. A build run reads every comment on its Issue starting `<!-- fix-exhausted` as an approach already tried (`.agents/builder.md`) and takes another (policy). A build run that finds its Issue's acceptance already met by other merged PRs opens its `build/<Key>` PR with one empty commit and `Closes #<issue>`; its review run runs a test that asserts each then-clause, and the merge closes the Issue, so work already done ends in no strike (policy). While the repository variable `CODEX_ONLY` is non-empty, every model call runs on Codex: review and critic run their prompt and schema through `builder.py engine-read-only` (Codex with the job's read token, no App token) in place of claude-code-action, `engine` fails a Codex run that did no work instead of falling back, and the screen asks Codex in place of Haiku; unset, nothing changes. The owner lifted the freeze for it because the Claude weekly quota runs out before its reset (policy). While the repository variable `CLAUDE_API` is non-empty (its value, a positive number, is the count of build and fix slots in place of `CODEX_RUNS`, and a PR gets two fix runs instead of three), every Claude Code call runs on Claude API credit, signed in with the secret `ANTHROPIC_API_KEY` instead of the Max token: only the steps that run `claude` receive the key, none receives `CLAUDE_CODE_OAUTH_TOKEN`, and a step fails when the key is empty; `engine` skips Codex; build and fix runs are capped at $3 (`--max-budget-usd`) at `--effort medium`, the screen at $0.25 at `--effort low`, and review and critic run through `builder.py claude-read-only` (Sonnet at medium, $1.50; Sonnet at high, $3) in place of claude-code-action and Codex; a Claude Code run that used no tool annotates what it said as an error; each call logs its `total_cost_usd` to the log and the job summary; unset, nothing changes. The owner lifted the freeze for it to run the loop on API credit (lift 2 of 3, policy; Workload Identity Federation was tried and dropped because the federation rule rejected GitHub's immutable subjects). Tests: `l23` and `l79` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L24 review.** `check` skips a draft's heads, so a Builder's red pushes hold no macOS runner, and runs on push to `main`. When `check` succeeds on a same-repository PR head, `review.yml` runs from `main`'s definition, so no PR edits its own review; a newer head of the branch cancels an older head's review. `builder.py review-task <pr> <head>` prints the review run's task only when the PR is open at that head and not a draft, else exits 3 and no model starts. The task holds the body's `Scenarios:` and `Moves:` lines, the full text of each scenario the `Scenarios:` line names as `main`'s `scenarios/` holds it (a named id no heading holds gets a line saying so), and earlier verdicts, each finding a claim the run re-derives from the head, git and those scenarios and drops when they no longer support it, never repeats on trust; never the rest of the body. The review run is a Builder run, `.agents/builder.md` byte for byte and then the task, on Sonnet with a read-only token, answering `{verdict, findings}`. Its checkout of the head holds `main`'s `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.agents/` and `loop/` in place of the head's, and no other `CLAUDE.md` or `AGENTS.md`, so no PR instructs its own review; it reads the PR's changes to them through `gh pr diff`. `builder.py review-post` posts the answer as `VERDICT:`, `Head:`, the findings and `Reviewed-by-Agent: reviewer-<run id>`, drops any findings line that would forge one of those fields, and sets the commit status `review` on the head: `success` for approve, `failure` for reject. A reject on a `build/` PR starts a fix run (L82). A head that moved since posts nothing. A run whose model used no tool (L23) leaves `review` pending; each `pick` reruns that review run once it has ended, and after six attempts asks the user (L79) instead. A run that worked with no verdict sets `review` to `error`, asks the user and fails. Tests: `l24` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L33 base.** `base <pr>` passes only when the PR's base is `main`.

**L34 Issue queue.** Work orders are open GitHub Issues, in the format of `.agents/data/work.md`, that the user (`saadshahd`) or a loop App (`claude[bot]` for a Builder's prerequisite, `github-actions[bot]` for a stall Issue) filed. Anyone else's Issue, a collaborator's included, is unspecified and never runs whatever its labels, since the repository is public. `orders.py ready` reads all pages and prints each Issue and its derived state; `--json` exposes structured records. Existing same-repository open `build/<Key>` PRs, or PRs explicitly naming the Issue with Refs/Closes/Fixes/Resolves, are in flight. An open work order is ready only when every native blocked-by dependency is closed as completed and it lacks `flag:needs-user` and `flag:needs-mac` (L79), either of which holds it unless its Key starts `stall-`; a dependency closed as not planned holds nothing, the row and the Builder's task name it, and a Builder never adds one as a blocker: a dependent that needs the cancelled work says so on its Issue and takes `flag:needs-user`. Three `github-actions[bot]` comments starting `<!-- strike -->` (L23) in the last 24 hours hold an Issue whose Key does not start `stall-` until the oldest of the three is 24 hours old; the row names that time, nobody is asked, and L94 still counts the Issue as waiting work. No intake label is needed. Invalid fields, duplicate Keys and dependency cycles block visibly. API errors or timeouts exit 4, never an empty queue. Test names and file tables have no scheduling or completion authority. A specification Issue may introduce its named scenario. An implementation Issue whose Specification file or a named scenario heading is absent from the checkout, or whose Scenarios line names no ID, runs as Mode `specify` first: its task asks for the scenarios and an Issue that names their IDs and keeps Mode `implement`, so the queue implements it once they merge. An Issue with no `Key:` line is a request, such as a bug report: Mode `specify`, Key `issue-<n>`, Priority 50, so a Builder specifies it before the queue builds it. Tests: `loop/orders.test.py`.

**L37 Copilot attribution.** A commit with no `Author-Agent` is authored by `copilot` when it has the Copilot Autofix `Co-authored-by` trailer, GitHub committed it, and its signature verifies against GitHub's web-flow key in `loop/web-flow.asc` and no other key; anything short of all three still needs `Author-Agent`, and `copilot` can never be the approver.

**L41 tokens.** `tokens` scans every `.css` file and every `.ts` and `.tsx` file under `apps/desktop/src/` except `tokens.css`, `terminal/emulator.ts` and test files (`*.test.*`, `testing/`), and fails naming `<file>:<line> <property>` for each look literal. A look literal is a value that sets one of these without `var(--…)`: a colour (`color`, `background`, `background-color`, `border*`, `outline*`, `fill`, `stroke`, `caret-color`, `text-decoration-color`) holding a `#` hex, an `rgb(`, `rgba(`, `hsl(`, `hsla(`, `oklch(`, `color-mix(` or a bare colour name other than `transparent`, `inherit`, `currentColor`, `none`, `initial` or `unset`; a `font-size` or `border-radius` holding a number with a unit; a `box-shadow` other than `none`; or a `transition*` or `animation*` duration holding a number with `ms` or `s` other than `0s`. In a `.ts` or `.tsx` file only the text of `style={{…}}` objects is read, where `fontSize`, `borderRadius`, `boxShadow`, `color`, `background`, `backgroundColor` and `borderColor` hold the same values. A comment is not read. Exit 0 and no output when nothing is found, 1 with one line per literal, 2 with an argument. Tests (`l41_`, in `loop/rules.test.sh`, on a temporary tree whose `apps/desktop/src/` the script reads from `$PWD` the way `vocab` reads its tree): `l41_a_hex_colour_fails_naming_file_line_and_property`; `l41_rgba_hsl_and_a_bare_colour_name_fail`; `l41_a_unit_font_size_and_radius_fail`; `l41_a_box_shadow_and_a_duration_fail`; `l41_var_reads_pass`; `l41_transparent_inherit_currentcolor_none_and_0s_pass`; `l41_tokens_css_is_not_read`; `l41_emulator_ts_and_test_files_are_not_read`; `l41_an_inline_style_literal_fails_and_a_var_passes`; `l41_a_literal_in_a_comment_passes`; `l41_an_argument_exits_2`. `u130_` (`scenarios/ui-visual.md`) adds the `tokens` step to `.github/workflows/loop.yml` in the PR that leaves no literal.

**L42 delta.** `delta <base-dir> <head-dir>` prints `<step> <id> fixed|regressed|still-failing|still-passing` per check and fails on any `regressed`; a check missing on one side is exit 2, never a pass.

**L46 merge gates.** GitHub auto-merge merges a PR once ruleset `main-2` sees `check`, `rules`, `review` and `critic` succeed on its head, each pinned to GitHub Actions, so no other app or person can post them; the ruleset has no bypass (policy). The user removed Percy and its `percy` check on 2026-10-12, as it gave no value (policy). A Builder that leaves a ready PR arms auto-merge. No gate waits on the user's Mac: agents verify on Linux, the user reports a Mac problem when they see one, and only a problem that needs a Mac gets a Mac CI job or a `flag:needs-mac` ask (L79). `rules.sh empty-diff <pr>` fails a head with no net change against its base (`git diff base...head`) unless the body or a commit message holds a closing keyword (`Closes #N`, the work-already-landed path of `.agents/builder.md`), so a PR that only undid its own change never merges (policy: PR #2760 merged at +0 −0 after a fix run restored main's side of every file). Tests: `l46` in `loop/workflows.test.py` and `loop/rules.test.sh`.

**L54 clean merge.** `clean-merge <commit>` passes for a merge of `main` that conflicts nowhere and changes nothing beyond the trial merge; such a merge needs no `Author-Agent`, and an approve of its first parent still covers it, so a human can merge `main` in from GitHub.

**L79 needs the user.** A PR or Issue waits on the user through the label `flag:needs-user` and one `github-actions[bot]` comment marked `<!-- needs-user -->` saying what to decide; `builder.py` and `stall.py` (L94) add both once and ask nothing more while the label is on. Four things ask: (1) a draft's `Stopped:` question (L81) and (2) a build run's `ask` (L23), each when its screen judges it `user`, (3) a review run with no verdict or six that did no model work (L24) and (4) a six-hour stall (L94). The job that ran the model screens what the run asks the user, the `Stopped:` paragraph of the open draft a build or fix run left or, with no PR, a build run's non-empty `ask`, with `claude-haiku-5-5`, no tools, against `.agents/screen.md`, answering `{verdict, reason, preview}`: `user` (a product choice no scenario settles, or a judgment of how something looks or feels) gets `flag:needs-user` with the preview above the question; `mac` (a check whose pass or fail only the user's Mac can produce: a logged-in real `claude`, or the `just app` window's native behaviour no Chromium check covers; a check `check`'s `macos-latest` jobs already run, or a native look-and-feel check whose Issue's observer is a Linux or Chromium check, or the native behaviour of work `main` already merged whose Linux or Chromium tests pass on `main`, is `loop`) gets the label `flag:needs-mac` and one comment marked `<!-- needs-mac -->`, which an agent on that Mac answers and takes off; `loop` strikes the Issue with the reason (L23), which the next build run reads as an answered ask (`.agents/builder.md`), or sends a draft back to work (L81). `.agents/screen.md` names the run's own GitHub token, push or job (an expired token, a failed push, a re-run) a `loop` fault, which `keep` (L23) or a later run repairs and no user can; Haiku still screens the whole question, so a product or Mac ask beside such a fault keeps its `user` or `mac` verdict. A screen with no valid verdict tries once more; with none again, or with a verdict that never arrived, the question goes back to the loop like a `loop` verdict and the run summary says so, and the user is never asked unscreened. The verdict travels between jobs as base64 (`builder.py` `encode`, `decode`), since GitHub drops an output holding a masked value and the Codex login's `{` and `}` lines are masked. Open items labelled `flag:needs-user` are the whole list; the queue builds no Issue either label holds but a stall Issue (L34), and removing either label returns an Issue to the queue and starts a pick (L23). Only `stall.py` (when a merge lands, L94) takes its own label off; the user takes off the other `flag:needs-user` labels. Tests: `l79` in `loop/builder.test.py`, `loop/orders.test.py` and `loop/workflows.test.py`. Every run executes ordinary engineering choices without approach confirmation; only these reasons wait for the user (policy).

**L81 stopped.** A Builder that stops on a product question leaves a draft with `Stopped: <the question>`, its consequence and a recommendation; after the run, `builder.py` sends that paragraph where its screen says (L79). `loop` replaces the paragraph with the run's link, the question and the screen's reason, so the draft no longer counts as stopped, posts the same text as a PR comment and starts an `unfinished` fix run, which reads it as an answered question (`.agents/builder.md`); L82's three fix runs bound the round trips. After a build or fix run that worked (L23), a draft without a `Stopped:` line gets an `unfinished` fix run (L82), and so does one no build job or fix run holds (L23). A ready PR goes on to `check` and review. Tests: `l81` in `loop/builder.test.py`.

**L82 fix runs.** `fix.yml` runs from `main`'s definition when `check` or `loop` fails on a same-repository `build/` PR, and on dispatch with a PR, its head and a cause: `check`, `rules`, `review` (a reject), `critic` (a design critic reject, L103), `conflict` or `unfinished`. One fix run per PR runs at a time. A `check` or `rules` cause counts only from the latest result on the PR's head: once no run of its workflow is still going there, the check run of that name that ended last decides, so a newer run on the same head supersedes an older run's failure; `pick` dispatches no such cause, and `fix-task` exits 3 for it and counts no attempt. `check`'s gate job runs unless its run was cancelled, so in a run that concurrency cancels (a push and `gh pr ready` start two runs on one head) it ends `cancelled`, which blocks merge and starts no fix run. `builder.py fix-task` prints the task only when the PR is open at that head on a `build/` branch, else exits 3 and no model starts; so does a `review` cause when the PR's last `<!-- fix-attempt -->` is newer than its last `VERDICT:` and under three hours old, since a review of that fix is on its way and the new verdict decides; the task names the cause, where the failed run's log is, the last verdict for a reject, and how the run ends. A fix run that worked posts a `<!-- fix-attempt -->` comment on the PR (a plumbing run excepted); with three there, the next cause starts no run and hands the PR to its Issue instead: `builder.py` posts one comment on the PR's work Issue marked `<!-- fix-exhausted #<pr> -->` holding the PR link, a line per cause (`check`, `rules`, `review`, `conflict` or `unfinished`) with its failing check or the review finding, and what each fix run changed (its commit subjects), then closes the PR unmerged, deletes `build/<Key>` and strikes the Issue as L23 does. A `conflict` whose every conflicted path is generated (`GENERATED` in `loop/builder.py`, `contracts/generated/**`) starts no model: before the engine, `builder.py resolve-generated` merges `origin/main`, takes main's side of those paths, runs the regenerate command (`REGENERATE`, `cargo test -p contracts`), requires no conflict marker and no change from a second run, and commits the merge, which `keep` pushes; any other conflicted path, a failed regenerate or a changed second run restores the branch and the engine runs as for any conflict. A `rules` failure whose only failed step is `rules.sh merge-loss` (L120) starts no model either: `fix-task` writes `merge_loss=true`, and before the engine `builder.py restore-merge-loss` restores main's version of each file `merge-loss` lists (removing one main lacks), commits it with an `Author-Agent` trailer and reruns `merge-loss`; `keep` pushes the commit. It posts no comment and, as no model worked, counts no attempt; a rerun that still fails resets the branch and the engine runs as for any rules failure. A plumbing cause counts no attempt and posts no comment: a `conflict`, or a `rules` failure whose every failed step is `rules.sh ci-trailers`, `base` or `scenario-ids` (PR shape); it still starts a fix run, exempt from the three, and `fix-task` marks it `plumbing=true` so `fixed` posts no `<!-- fix-attempt -->`. Fix runs are titled `Fix PR #<pr>: <cause>`, and Actions history, the runs of that title whose `fix-run` job started, bounds them: after six on one PR the next plumbing cause counts as any other. After each build or fix run that worked, the loop (`builder.py` `built` and `fixed`, through `link`) writes the PR body's `Refs #<issue>` line (the Issue is the one the branch's work Key names; a `Closes` or `Fixes` line already naming it stays) and its `Scenarios:` line (the Issue's own `Scenarios:` line, else the ids of the scenarios the diff adds or changes), replacing a wrong or missing line in place with no comment and no fix run; neither review nor `.agents/data/gates.md` rejects for them. Tests: `l82_the_loop_writes_the_refs_and_scenarios_lines`, `l82_scenarios_come_from_the_diff_when_the_issue_names_none`. A review reject stays counted even when it only names body lines, since a verdict is free text and its fix run is deduplicated by the attempt comment. The next build of an Issue with a `<!-- fix-exhausted #<pr> -->` comment whose PR is closed unmerged starts from `refs/pull/<pr>/head` merged with `main`, and its prompt (`builder.py prompt`) names the PR and its last `VERDICT:` and `CRITIC:` comments instead of asking for another approach. It posts, closes and strikes once per PR, so a repeat of the cause adds nothing, and it sets no `flag:needs-user`. The closed PR keeps its diff at its link and in `refs/pull/<pr>/head`, and the comment names the head commit. The closed PR leaves the Issue with no open `build/<Key>` PR, so L34's ready row starts at most one fresh build run from `main` (L23; policy, as `pick` holds one job per Issue); the Issue stays ready unless the strike is its third in 24 hours (L34). The close, the branch deletion and the strike bypass no required check or review status: nothing merges. A build or fix run ends with `just lint-web`, `just lint-rust` and the tests of the files it changed by hand, never `just check`: `check` on its push judges every test, so the gate stays and the run's own time does not (policy: `.agents/builder.md`; observer: the fix-run step timings). The fix run pushes with the Claude App's token, so its push or its `gh pr ready` starts `check` and then review again (L24); a fix run that outlives that token keeps its commits through `keep` (L23), and its draft goes on through L81. A `review` fix run that worked and left the PR ready with neither (it only edited the body or title) starts no `check`, so `builder.py fixed` reruns the review run behind the head's failed `review` status, unless a `check` run is still going on that head; each such rerun counts toward L24's six attempts of that run. No retry bypasses a required check or the review status. A `review` fix task tells the run never to answer a reject by undoing the PR's whole change: when it cannot meet the findings without dropping the work, it leaves a draft with `Stopped:` (L81); a push that did undo it fails `rules` through `empty-diff` (L46) and counts toward the three. Tests: `l82` in `loop/builder.test.py`: a conflict only in generated files is resolved by regenerating them and a conflict that also touches a source file, a failed regenerate or a regenerate that differs on a second run leaves the branch untouched (`l82_a_generated_only_conflict_is_regenerated_with_no_model`), a plumbing cause runs past three attempts and posts none, a rules failure with any non-shape failed step counts, the sixth plumbing run is the last, a rebuild continues from the closed PR's head with its verdicts; a fourth cause makes the comment, closes the PR, deletes the branch and strikes the Issue with no `flag:needs-user`, and a repeat does nothing more; a reject a fix run already answered starts no run until three hours pass; a reject answered with no push reruns its review run, and none is rerun for a draft, a moved head, a running `check` or another cause; a `check` or `rules` failure that a newer run on the same head superseded, or a cancelled one, starts no run and counts no attempt, while one the latest run failed gets its run; and `loop/workflows.test.py`: the engine step of `fix.yml` runs only when `resolve` did not (`l82_the_engine_waits_for_the_generated_conflict_script`) and `restore` did not (`l120_the_engine_waits_for_the_merge_loss_restore`), the fix task may read check runs, and `check`'s gate job does not run in a cancelled run.

**L84 Linux Builders.** Build and fix runs move to `ubuntu-latest` once a push to `main` passes `just check` there. `.github/actions/setup` installs Tauri's Linux packages (`libwebkit2gtk-4.1-dev`, `build-essential`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`) on Linux, in the background while the toolchain and caches install and joined before the first build or browser install, and GNU coreutils on macOS, and keys the Rust cache by the runner's OS. On each push to `main`, `lint` and `rust 1` to `rust 5` run `check-rust` on `ubuntu-latest`, and `lint-web` and the `web` shards run `check-web` there (L89). `rust 1` saves the Linux cache, since it builds every test target, and `mac` saves the macOS cache; the first job to save a key keeps it, so no other job saves (`save-cache`). `check` on a PR runs the Rust suite on `ubuntu-latest` and the macOS paths on `macos-latest`, where the App ships (L89).
