# Work on a machine (step 5 of the Multi-Machine Strategy)

Module: `crates/herdr`, `crates/agents` (`src/worktree.rs`) and `crates/rupd`. Decision: `docs/adr/0012-herdr-core-machine-layer.md`; Principles: P2, P3, P5, P15 and P16 in `PRINCIPLES.md`; terms: Machine (`scenarios/machines.md`), Worktree, Base, Landing (`GLOSSARY.md`). herdr-core is the one machine layer and the one terminal host on every machine, this Mac included, so a Project folder on this Mac is reached the same way as one on another Machine. This file is specification only; each planned test ships with its implementation Issue. The ids are reserved by the Issues that depend on #6709; a different split renumbers them in this file and on each of those Issues.

Not specified, by the owner's decision of 2026-11-07: a dispatch panel, a machine sidebar or Rail level, Rex or tmux adapters, calls to boxd's API, moving `rupd` off this Mac, and moving a running Agent to another Machine (herdr-core offers none, and none is built until a lower layer does).

**MC30 a Project folder lives on one Machine.** Given a Project whose folder is on Machine `m` (this Mac or another Machine herdr-core lists), when roundup reads the folder, its `git` state (`agent.worktreeState`, G3) or its worktrees (`git worktree list`), then each is read where the folder is, through herdr-core's exec of `git` on `m`; no copy of the folder, its repository or its worktree list is made on this Mac, and a Project has exactly one Machine (planned tests: `mc30_git_state_read_on_the_folders_machine`, asserting against a fake herdr-core that the `git` argv arrives as an exec for `m` with the folder as cwd and that this Mac's disk holds no copy; `mc30_folder_has_one_machine`, asserting a Project with two Machines is refused with a coded error). A Project on this Mac behaves exactly as `scenarios/worktrees.md` says (planned test: `mc30_local_folder_unchanged`, asserting G3's replies are equal to the pre-change replies for a local folder).

**MC31 a worktree is made and landed through herdr-core's exec.** Given a Project folder on a remote Machine `m` with `worktrees` on (G1), when an Agent starts in it and later lands, then the Worktree and its branch are made by exec on `m` as G2 says, the Agent's Terminal has the Worktree as its one cwd, and `agent.land` rebases onto the Base, runs the Project's `check` command in the Worktree on `m` and fast-forwards the Base, never writing the Base any other way (P2, P5, G4). A dropped or rejected Agent leaves nothing in `git worktree list` or `git branch` on `m` (G5). A failed exec leaves the Base untouched and returns the coded error (planned tests: `mc31_remote_worktree_one_cwd_per_working_agent`, asserting two working Agents on `m` have two cwds, P2's Observer; `mc31_remote_land_is_rebase_check_fast_forward`, asserting the exec argv sequence is rebase, `check`, fast-forward and that a red `check` ends the sequence before the fast-forward; `mc31_remote_reject_leaves_no_worktree_or_branch`, asserting both lists equal their state before the spawn, P5's Observer). A `check` or `git` the Machine lacks is a coded error, not a skipped step (policy, same planned test as the red `check`).

**MC32 files are read and written through herdr-core's file methods.** Given a Project folder on Machine `m`, when roundup reads or writes a file in it (a Pad, a Todo's file, the Project's `check` setting, a Worktree file), then the read or write is a call to the file method `hello` lists on `m`, and roundup runs no `cat`, `tee` or shell redirect through exec for it and opens no second ssh channel for it (planned tests: `mc32_read_and_write_use_file_methods`, asserting against a fake herdr-core that a write then a read returns the bytes written and that the fake saw only file-method calls and no exec; `mc32_file_error_is_coded`, asserting a missing path or a refused write returns herdr-core's `code`, `kind` and `hint`). When `m`'s herdr-core lists no file method, the read fails with a coded error and no fallback to exec is used (planned test: `mc32_no_file_method_is_coded_error`). The file methods' names are the ones `hello` returns on the pinned version (PR #6705's spike report, row Q1), read by the implementation, never copied here.

**MC33 the Door picks the machine when work starts, by free capacity.** Given a Door that starts an Agent for a Project whose folder is on no Machine yet, when the Agent starts, then the Door picks the reachable Machine with the most free capacity (this Mac included), ties going to this Mac, and the Agent runs there, as MC30 and MC31 say. Free capacity is a Machine's slots minus its Agents that have a live Terminal there. An unreachable Machine (MC4's causes) is skipped, never an error for the start, and no Machine reachable means the Agent starts on this Mac. A Project whose folder is already on a Machine starts there and is not re-picked. The pick is made once, at the start, and a running Agent is never moved (planned tests: `mc33_pick_most_free_capacity_ties_to_this_mac`, asserting the pick against a fake herdr-core listing three Machines with different live Terminals; `mc33_unreachable_machine_skipped`, asserting the pick when the best Machine times out; `mc33_pick_made_once`, asserting a later change in capacity moves no running Agent and calls no herdr-core method that moves one). Where a Machine's slot count comes from is the implementation's call, and the count shows as no new Machine row (MC1; policy).

**MC34 the user overrides the pick.** Given the Door's pick (MC33), when the user names another Machine for the start, then the Agent starts on the named Machine and the Door does not re-pick it; the user's choice wins over the Door's, as P6 says of Homes. The pick shows as a chip on the Agent (MC3): the Machine's name, with the override marked the same way as the pick, and clicking it opens nothing but that Agent's own matter. There is no dispatch panel, no machine sidebar and no Rail level, and the override is a field of the start, never a surface of its own (planned tests: `mc34_override_starts_on_named_machine`, asserting the Agent's cwd Machine equals the named one and that no pick ran; `mc34_pick_shows_as_chip_on_agent`, asserting by role that the Agent's row carries one chip naming the Machine, picked or overridden; `mc34_no_dispatch_panel`, asserting by role that no panel, sidebar or Rail level names a Machine, MC3's check at the start path). A named Machine that is unreachable fails the start with a coded error and picks no other (planned test: `mc34_unreachable_override_is_coded_error`).

**MC35 three machines raise no more interruptions than one.** Given the replay P3's Observer uses (`spikes/hooks-state/*.jsonl`) run once with every Agent on this Mac and once with the same Agents spread over three Machines, when each replay ends, then the count of interruptions, as P3's Observer counts them (one attention entry per `needs-you`, no bell, no OS alert with its choice off, no entry for a routine transition), is equal in the two runs, and each entry opens its Agent's Terminal on that Agent's Machine. A Machine that goes away raises nothing by itself: its Agents' states come back through the Door and the alerts the user turned on, as P16 says (planned tests: `mc35_interruptions_equal_one_machine_and_three`, asserting equal counts against fake herdr-cores; `mc35_machine_loss_raises_no_alert`, asserting a dropped bridge adds no attention entry and no alert, MC4's check for a running Agent).

**MC36 opening a Project on a Machine records that Machine.** Given `project.open {path, machine: m}` where `m` is a listed Machine and `path` a folder on it (the check in `remote_folder`, `crates/rupd/src/actions.rs`), when the App opens that Project, then the App calls `project.setMachine {machine: m}` on the opened Project's own Daemon before it answers the relayed open, so `project.get` on that Daemon names `m` and its `git` state and worktree commands run on `m` as MC30 says, never on this Mac against a path that exists only on `m`. A call without `machine` leaves the Project's Machine unset, and a Project that is already open with a Machine keeps it when the same path is opened without one. A failed `project.setMachine` fails the open with its coded error and leaves no Project open with the wrong Machine (planned tests: `mc36_open_with_machine_sets_the_projects_machine`, in `apps/desktop/src/state/`, asserting against the fake App seam that `project.setMachine` is called once with `m` on the opened path's Daemon before the open resolves; `mc36_open_without_machine_sets_none`; `mc36_set_machine_failure_fails_the_open`; `mc36_real_daemon_open_on_machine_records_it`, asserting against a real Daemon and a fake herdr-core that `project.get` returns `m` after `project.open`).

Policy: the pick and the override are the whole of dispatch; nothing here adds a surface (P16). Observer: `loop/rules.sh vocab` exits 0; the Issues that depend on #6709 show `"respecify": false` for MC30 to MC36 in `python3 loop/orders.py ready --json`.
