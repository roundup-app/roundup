# Machine channel (step 4 of the Multi-Machine Strategy)

Module: `crates/rup`, `crates/rupd` and `crates/herdr`. Decision: `docs/adr/0012-herdr-core-machine-layer.md`; Principles: P15 and P16 in `PRINCIPLES.md`. Specification only; each planned test ships with its implementation Issue. Evidence: the spike of PR #6705 (`spikes/herdr-core-client/REPORT.md`, raw proof in `raw/`), cited as S7 where a clause measures against it.

`rup` on a machine writes to a queue on that machine. The Mac dials in with one ssh bridge per machine, which drains the queue into `rupd`; `rupd` applies each report once. Nothing listens on the machine for the Mac to reach, and no queue lives on the Mac: boxd's ssh refuses `ssh -R`, so the forward is never specified. rupd and the Doors stay on this Mac.

## Vocabulary

- **Spool**: the append-only file of reports on a machine, `~/.rupq/spool`, each line `{id, method, params}` with `id = <agent>:<seq>`. A line is deleted only when the bridge's ack for its `id` returns.
- **Seq**: an Agent's sequence number on its machine, from 1, increasing by 1 per report. The machine keeps each Agent's last `seq` in `~/.rupq/seq/<agent>`, written and fsynced before the spool line, so a reboot or a `rup` restart never reuses one.
- **Mark**: `rupd`'s high-water `seq` for one Agent, stored in the Daemon's database beside the report's effect, in one transaction, so a restart keeps it.
- **Away**: the Status of a machine, shown on its Agents' rows, while no bridge to it is up (MC26). The word of the error a live call returns then: `{"error":"away"}`, `rup` exit 1 (I4).

**MC20 rupd applies each report once.** Given a report `{id: "a1:7", ...}`, when `rupd` receives it, then it always acks `id`; it applies the report only when `7` is above the Mark of `a1`, and then advances the Mark in the same transaction as the effect. A `seq` at or below the Mark is acked and ignored: no effect, no Event, no Touch. Marks are per Agent (`b2:3` applies while `a1`'s Mark is 7). A `seq` above the Mark applies even when it skips (`a1:9` over a Mark of 7 sets 9), since the bridge sends in order (MC23); a later `a1:8` is then ignored. A report without an `id` is applied as today, for a local `rup` (policy). Tests: `mc20_a_repeated_report_is_acked_and_applied_once` (the second `a1:7` returns the ack and leaves the store as after the first); `mc20_marks_are_per_agent` ; `mc20_mark_survives_a_rupd_restart` (apply `a1:7`, restart the Daemon on the same database, send `a1:7` again: acked, not applied); `mc20_a_failed_apply_does_not_advance_the_mark` (a report whose apply errors is not acked and its retry applies). Laws: a Message report touches M1 (typed at most once), M5 (unique ids; the Message id is derived from `id`, so a retry is the same-id retry B12 already treats as one) and M6 and M9 (no silent loss, replay); `proofs/messages` and `docs/messages.md` stay unchanged and agree, as no transition is added.

**MC20b a crash between the effect and the Mark does not double it.** Given `agent.signal` with `report: "a1:7"` and a Mark of 6, when `rupd` dies, or the Mark write fails, after the apply returned Ok and before the Mark commits, then the retry of `a1:7` is acked and leaves the store, the Events and the Touches as after the first apply: the effect and the Mark are one atomic write, or the effect itself is keyed by `id` so its repeat is a no-op (B12). "In the same transaction" in MC20 holds for that write, not for a second connection that follows it. Tests: `mc20b_a_failed_mark_write_does_not_double_the_effect` (the Mark write is made to fail after a successful apply; the retry returns the ack, and the store has one effect, one Event, one Touch); `mc20b_a_kill_after_the_effect_does_not_double_it` (restart the Daemon on the same database after the apply and before the Mark; the retry is acked, not applied again). Laws: M5 and M9 as MC20; `proofs/messages` and `docs/messages.md` stay unchanged.

**MC21 hooks on a machine return at once.** Given `rup signal` run by a hook on a machine, when the Mac is present or away, then it appends one Spool line, fsyncs, prints nothing it did not print before and exits 0 within I8's deadline (1 s); it never waits for the bridge or `rupd` and never exits 1 for an away Mac. The cost is measured: a queued report is acked after fsync in 0.34 ms p50 and 1.06 ms as a whole process in the spike, and the head is no more than 10% or 5 ms slower than that (rule 7). A Spool it cannot write (disk full, read-only) exits 1 with the cause on stderr; the hook then fails visibly, never silently (P4). Tests: `mc21_signal_spools_and_exits_0_with_no_bridge` (no relay socket, exit 0, one durable line, in under 1 s); `mc21_signal_exits_0_the_same_with_the_bridge_up`; `mc21_signal_with_an_unwritable_spool_exits_1_with_the_cause`; `mc21_seq_never_repeats_across_a_rup_restart` (two processes, then a reboot-like fresh process on the same files: strictly increasing `seq`).

**MC22 away, some tools wait and some fail loud.** Given a machine's Agent with the bridge down, when a roundup tool runs, then its side is as in this table, one clause per tool. The names are M1's, M13's and M14's, each dot replaced by `_`.
- **Waits** (the call is spooled and returns `{queued: true, id: "<agent>:<seq>"}` at once; the effect happens once, after the bridge drains it, by MC20): `message_send` (a Message to wait is the owner's decision, as is a report), and the hook reports `rup signal` sends (MC21). A queued Message is typed under B-scenarios' rules once applied, so a Message sent away and the same one sent present end in the same record (M1, M4, M5, M6, M9, M10 hold unchanged: the Message is created when `rupd` applies it, and it keeps the order of its Spool line among that Agent's own).
- **Fail loud** (the call returns `{"error":"away"}` and `rup` exits 1 at once, never a hang; the Agent can retry): `message_get`, `message_list`, `todo_create`, `todo_comments`, `todo_get`, `todo_list`, `todo_update`, `todo_complete`, `todo_reopen`, `todo_setBlockers`, `pad_create`, `pad_read`, `pad_list`, `pad_write`, `pad_append`, `pad_move`, `pad_delete`, `pad_appendSection`, `terminal_screen`, `terminal_read`, `terminal_search`, `terminal_spawn`, `terminal_open`, `terminal_close`, `terminal_write`, `terminal_resize`, `terminal_kill`, `route_set` and `agent_digest`. A read has no value while the Mac is away; a write that returns an id or a conflict (a Todo's id, a Pad's `base`) cannot answer without `rupd`, and a queued write could apply long after the state it assumed (policy).
- **Complete**: the two lists together hold every tool `tools/list` offers a machine's Agent, and a new tool joins one of them in the PR that adds it. Away changes nothing on this Mac: an Agent on this Mac keeps every tool live.
Tests: `mc22_message_send_waits_and_applies_once_on_drain`; `mc22_signal_waits` (the hook report, as MC21); `mc22_each_fail_loud_tool_returns_away_at_once` (every name above, against a dead relay socket, in under 1 s, exit 1, `{"error":"away"}`); `mc22_the_two_lists_cover_tools_list` (the list `rup mcp` serves a machine's Agent equals Waits plus Fail loud, no overlap); `mc22_a_local_agent_is_never_away`; `mc22_a_message_sent_away_is_the_one_sent_present` (same final record, M5 and M6, through the real Daemon, as `crates/rup/tests/` does for M2).

**MC23 the bridge drains the queue in order.** Given a Spool of reports `a1:1`, `a1:2`, `b2:1`, when the bridge connects, then it relays each line to `rupd` in Spool order and returns `{"ack": "<id>"}` to the machine only after `rupd` acked that `id`; the machine deletes the line on that ack and not before. The bridge is one ssh `socat - UNIX-CONNECT:~/rupq-relay.sock` to the machine and `rupd`'s socket (ADR 0003) on this Mac, holding no queue and no state of its own. A report `rupd` does not ack (error, refusal) stays in the Spool and is retried at the next connect, before any later line of the same Agent (an Agent's reports never reorder). The Spool is replayed on every connect (S7's design (1)). Tests: `mc23_ack_follows_rupd_ack` (a fake `rupd` that holds its ack: the Spool line stays; after the ack it is gone); `mc23_order_is_spool_order_per_agent`; `mc23_an_unacked_report_blocks_its_agents_later_ones_not_other_agents`; `mc23_bridge_keeps_no_queue` (kill it mid-drain, restart: nothing is lost and nothing it held was the only copy). Observer: a live call over the bridge takes p50 35 ms in the spike (one ssh round trip); rule 7 does not apply to it, but the head records p50 and p95 and no more than 10% over.

**MC24 no report is lost or doubled across an absence.** Given 100 numbered reports, 50 ms apart, from `rup` on a machine, when the link is killed for 4 s, or paused for 4 s, and again with every 7th ack lost, then `rupd` applied 0 lost and 0 doubled: each of the 100 `agent:seq` applied exactly once, in order. This is the spike's S7 measurement, repeated on the implementation: S7 got 0 lost and 0 doubled with the link killed and every 7th ack lost, 14 suppressed, with the Mark in memory only; the implementation keeps it in the database (MC20), and the same runs include `rupd` restarted once mid-run (0 and 0 still). Without the Mark the same run applies 14 twice, and without the Spool the killed link loses 15 (S7's negative runs), so the test also runs once with the Mark disabled and expects the double, proving the harness can see it. Tests: `mc24_link_killed_loses_none_doubles_none`; `mc24_link_paused_loses_none_doubles_none`; `mc24_a_lost_ack_doubles_none`; `mc24_rupd_restart_mid_run_loses_none_doubles_none`; `mc24_the_harness_sees_a_double_without_the_mark` (a test of the observer, kept because MC24 is otherwise unfalsifiable). Policy: the runs use a fake link (a socket pair the test kills and pauses) and no real ssh, no real `claude`; the real-ssh run is the spike's, and the timings are on CI's clock. Not measured: two Macs, ssh keepalive tuning, Spool growth over a long absence (the Spool is rewritten on each ack, O(n); the implementation deletes by an append-only ack log or equivalent and records the 10 000-report cost), a random-timing sweep of a report in flight during a kill.

**MC25 a machine gets a Linux `rup`.** Given a machine added by `machine.add` (MC2), when roundup sets it up, then a Linux `rup`, built from the same crate and version as the Mac's, is installed at `~/.rupq/bin/rup` by one `ssh <name>` command that needs nothing but `ssh`, `sh` and `socat` there (`socat` was already on the machine in the spike); an absent `socat` is a coded error naming it, not a silent skip. The install route is: this repo's release build produces `rup-linux-x86_64` and `rup-linux-aarch64` as artifacts of the existing build, and `machine.add` streams the file for the machine's `uname -m` over that ssh and checks `rup --version` equals the Mac's. No file under `.github/workflows/` is edited by the implementation; if the route needs a workflow change, the Issue asks the user (L118). A second install on the same version changes nothing. Tests: `mc25_install_streams_the_matching_binary_and_checks_version` (against a fake ssh with both `uname -m` answers); `mc25_a_missing_socat_is_a_coded_error`; `mc25_reinstall_on_the_same_version_changes_nothing`. Policy: the implementation's diff names no path under `.github/workflows/`, which the review run reads from `git diff origin/main`. Out of scope: macOS machines (herdr-core hosts the Mac's own `rup`), and updating a machine's `rup` on a Mac upgrade, which is a later scenario.

**MC26 one ssh bridge per machine.** Given machines listed (MC1), when the App runs, then `rupd` holds exactly one bridge per machine, started with the machine and never a second for it (two Agents on one machine share it). It reconnects by itself after its ssh ends, with a delay of 300 ms first, growing to at most 30 s, resetting on a success (the spike's bridge reconnected after 300 ms). While no bridge is up the machine's Status is Away, shown as a status on its Agents' rows (MC3), with no alert, no toast and no Rail level or machine sidebar (not doing); it clears when the bridge is up and the Spool has drained. A machine that hibernates (`boxd machine hibernate`) is Away, and the next connect wakes it (0.77 s in the spike), so the guest clock stepping forward on wake changes nothing here: no timeout in the bridge or the machine counts elapsed machine time. A machine removed stops its bridge and keeps its Spool. Tests: `mc26_one_bridge_per_machine` (two Agents, one bridge process); `mc26_reconnects_by_itself_with_backoff` (a fake ssh that exits: 300 ms, then growing, capped at 30 s, reset by a success); `mc26_away_shows_as_a_status_on_the_rows_with_no_alert` (a UI test by role: the Agents' rows carry the status and no alert fires, as MC3 and MC4); `mc26_the_status_clears_after_the_drain`; `mc26_a_removed_machine_keeps_its_spool`.
