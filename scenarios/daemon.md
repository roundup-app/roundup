# Daemon

Module: `crates/rupd` (D1, D7, D9–D12); end-to-end tests in `crates/rup/tests` (D2–D7, D9, D12); App RPC tests in `crates/desktop` (D9). Ids: every `D` heading in the file; D8 lives in `scenarios/resources.md`.

D1 and D7 are in `crates/rupd`. D2 to D7 are end-to-end tests of the whole Daemon. They live in `crates/rup/tests`, the only package whose tests can run both the Daemon (a dev-dependency) and the built `rup` binary that hooks and MCP servers call (`CARGO_BIN_EXE_rup`). They run without `claude`: a fake `claude` named by `ROUNDUP_CLAUDE_BIN` plays recorded hook payloads from `spikes/hooks-state/log*.jsonl`. `CLAUDE_CONFIG_DIR` points at a temp dir, so no test ever touches the user's `~/.claude.json`.

**D1 attached.** Given `rupd <project> --attached`, when its stdin closes, then it exits within a bound the test names, and every program it started in a Terminal is gone. Without `--attached`, a closed stdin changes nothing; CI starts `rupd &` with no stdin. The App passes `--attached`, so no Daemon and no Agent outlives the App, even when the App crashes. The Daemon frees a Terminal's pseudo-terminal when its program ends (`crates/terminal/src/lib.rs:144`), so `openpty` exhaustion (`kern.tty.ptmx_max` on macOS, 511 on the `macos-latest` runner) comes only from tests of several packages opening Terminals at once.

**Daemon**: `rupd`, the local process everything else is a client of.

**D2 Status end to end.** Given a Daemon whose fake `claude` feeds these hook payloads, in order, to the hook command in its `--settings` file: `SessionStart`, `UserPromptSubmit` (prompt "fix the refresh race"), `PermissionRequest`, `PostToolUse`, `Stop`. `ROUNDUP_RUP_BIN` is the built `rup`. When a subscribed client calls `agent.spawn`, then it receives that Agent's `agent.status` Kinds `idle, working, needs-you, working, idle` in order, and `rail.tree` names the Agent `fix-refresh-race` (A9).

**D3 Todos over MCP end to end.** Given the same Daemon with a fake `claude` that starts the `roundup` server from its `--mcp-config` file and calls `todo_create {title: "split checkout"}` over it, then `todo.list` holds that Todo and `provenance.history {item: "todo:1"}` names that Agent.

**D4 ten idle Agents.** Given ten Agents whose fake `claude` sends `SessionStart` and then sleeps, then the Daemon's resident memory grows by less than 150 MB. This is rule 7's budget for roundup's own share; the real `claude` programs are measured on the laptop at the MVP gate. The test prints the number it measured, for the gate report. Every Agent reaches Idle within one bound of 30 s for all ten together, measured from the first `agent.spawn`; a miss is not a pass, and its failure output names the Agents that were not Idle and each Agent's last status, so a lost event can be told from a slow Daemon. The bound covers only the ten `SessionStart` hooks reaching the Daemon, not the machine's load; a test that passes by waiting longer is not a fix.

**D5 no program outlives the Daemon, children included.** Given `rupd <project> --attached` with an Agent whose fake `claude` starts a background child that writes its pid to a file, and a Terminal whose shell does the same, when the Daemon's stdin closes, then the Daemon exits within D1's bound and the fake `claude`, the shell and both children are gone, checked by pid. Without `--attached` the same close changes nothing, as in D1. Owns `crates/rup/tests/e2e/**`, with fixes in `crates/rupd/**` or `crates/terminal/**` only if it fails today. Stacks after D1 and A17; it keeps `d1_attached` tests green and narrows none.

**D6 a Daemon killed without warning leaves a Project that reopens whole.** Given a Daemon with a Group, two Agents, a Terminal (an Agent's own), three Todos where Todo 2 is blocked by 1, and two Pads (one created by an Agent, one by the user), when its program is killed with SIGKILL and a new Daemon starts on the same Project folder, then `rail.tree` has the same node ids, names, parents, `order` values and `meta` flags, every Agent is `done` with `terminal_id: null` (A8, A12) and `terminal.list` holds no Terminal (X11), except that an Agent whose Terminal owner survived the kill and verifies (A12a) is the same Agent with exactly one running Terminal and no replacement launch, `todo.list` has the same three Todos with the same blockers and `done` state, `pad.list` the same Pads with the same Homes and text, `provenance.history` still names the Actors of the earlier writes, and the next `todo.create` returns id 4. Owns `crates/rup/tests/e2e/**`. It keeps A8, T5, P7 and A12 green and narrows none; a failure here is fixed in the module that loses data, never by the test.

**D7 a store that cannot be read stops the Daemon, loudly.** Given a Project whose Rail, Todos or Pads file is truncated to a few bytes of garbage, when `rupd <project>` starts, then it exits with a non-zero status within a bound the test names, writes one line to stderr naming that file, accepts no connection, and leaves the file's bytes exactly as they were: it is never replaced with an empty store. A Project with none of the files starts as today. The App shows the Daemon's failure as it does for any exit (S3); D7 asserts only the Daemon's side. Owns `crates/rupd/**` and `crates/rup/tests/e2e/**`; if the failure sits in a module's `open`, that module's crate carries the fix and its test names D7.

**D9 independent requests on one connection.** Module: `crates/rupd`; socket tests in `crates/rupd/src/lib.rs`, end-to-end tests in `crates/rup/tests/**`. The App keeps its shared `rpc::Client` per Project; clients need no second connection to escape a pending call. Policy: each ordinary request dispatches in its own task, with connection-state changes ordered as below; a connection-wide lock must not cover an awaited module call. Existing JSON-RPC envelopes stay unchanged. Long-call contract changes retain the existing concurrency and App call-bound requirements.

Cost observer (TC1): `d9_workstream_removal_keeps_finite_shutdown_waits_within_the_app_bound` needs real child processes whose descendants hold PTYs open and a real clock: it proves sixteen finite shutdown waits overlap within the App bound, which a mocked kill cannot establish.

Checks on main (policy): 1. `scenarios/rpc.md`, **C1 a call that may have run is not reported as one that failed**; 2. `scenarios/daemon.md`, **D9 independent requests on one connection** retains the independent-reply and connection-state observers below; 3. `docs/perf.md`, **What is enforced, and what is not**. Clear-only acknowledgement and App-bound observers are retired by A32 (#4542). D9 narrows none of C1, D1–D8 or R16.

- **Independent replies.** Given a real socket connection and a test Module whose first call signals entry and waits on a release channel, when the client sends `rail.tree` after that signal without releasing the first call, then the tree reply arrives within 1 s measured from writing its request, before the held reply. On release, both replies have exactly their original JSON-RPC ids and results, including string and numeric ids; interleaved event frames remain complete newline-delimited JSON and notifications receive no reply. `d9_a_held_call_does_not_hold_the_next_reply` and `d9_replies_events_and_notifications_keep_their_envelopes` assert this through the socket, not by invoking `dispatch` directly. A fixture-held call proves concurrent dispatch rather than merely a fast handler reply.
- **Connection state.** Given pipelined `daemon.identify`, `events.subscribe` and an ordinary mutation, then the mutation uses the preceding Actor and its event is observed on that subscription. A later identify affects only requests read after it, never an already-dispatched call; a rejected identify leaves the prior Actor unchanged. `d9_connection_state_changes_precede_later_requests` asserts Actor, event and Provenance using entry/release signals. The fixture holds a call under the first Actor, sends a later identify, and releases it only after a call under the second Actor has completed. Policy: these connection-state changes take effect in wire order before later tasks are dispatched; a client needing one ordinary mutation to precede another awaits its reply rather than relying on reply order.
- **Caller lifetime and ordering. (retired)** Retired by A3564a–f (`scenarios/native-questions.md`): the caller-dependent methods it ordered (`agent.permission`, `agent.ask`) are removed, so no method waits on its caller. An ordinary accepted call still survives a write-side half-close and returns its reply on the readable side (`d9_half_close_keeps_ordinary_calls_alive`).
- **App bound (policy).** Finite App-facing calls whose Daemon wait exceeds `CALL_BOUND` must be inventoried in the implementation PR and either bounded within it or acknowledged with progress/completion events in a Contract PR changing every caller.

Observer: `just check` runs every named `d9_` test and the tests asserting `scenarios/rpc.md`, `scenarios/daemon.md` and D8; then run `just perf`. Policy: a missing named test or an unasserted then-clause leaves implementation acceptance unmet even when `just check` exits 0. Policy: attach the inventory and three R16 qualified, non-skipped `just perf` reports from the implementation head to the implementation PR; compare against the selected machine class's baseline and keep rule 7's absolute budgets. This specification requires tests in its dependent implementation Issue; it does not claim they exist yet.

Validation failures are reported on the Work Issue, one row per failed command or assertion, with its exit code and repair; an observer failure is not completion evidence (policy).

**D10 every event but Terminal output is saved, numbered once.** Module: `crates/rupd` (the log table is a migration in `project.db`, as the Messages and Todos tables are, N16), `crates/rpc` (`Bus`), `crates/contracts` (`Event`). Given a Daemon, when any Module emits an Event (Terminal output is no Event, X14), then the Daemon saves it in `project.db` in the same step that publishes it, with an Event number (`seq`): a positive integer that rises by one per saved Event, never repeats, and is on the Event every subscriber sees. Terminal output is no Event (X14), so it is never saved or numbered, and `terminal.read` is unchanged. Given a Daemon killed (D6) and reopened on the same Project, then its next Event number is the old highest plus one. `d10_every_event_but_terminal_output_is_saved_and_numbered` and `d10_numbers_never_repeat_across_a_reopen` assert this. Policy: the number is the log's own row id, so no second counter can drift from the log; the log's size is bounded by D11's window, never by a timer.

**D11 `events.subscribe` resumes from a number and loses nothing.** Module: `crates/rupd`, `crates/rpc` (`Client`), the App's callers. `events.subscribe` takes an optional `after` (an Event number). Policy: the log keeps the last 10 000 Events (`EVENT_WINDOW`); this one number is the window, and nothing prunes by age.
- **Replay then live.** Given saved Events 1 to 20 and a subscribe with `after: 12`, then the subscriber receives Events 13 to 20 in order from the log, then every later Event live, with no gap and no repeat, including an Event saved while the replay ran. `d11_replay_then_live_has_no_gap_and_no_repeat` emits during a replay held at a signal and asserts the numbers received are exactly one run.
- **No `after`.** Given a subscribe with no `after`, then it behaves as today: only Events saved after it, each now carrying its number. `d11_subscribe_without_after_streams_only_new_events`.
- **Slow subscriber.** Given a subscriber that does not read while more Events than the live ring holds (1024) are saved, when it reads again, then it receives every Event in order with no gap by falling back to the log; Daemon stderr never says it "fell behind and missed" events, and that path is removed. `d11_a_slow_subscriber_catches_up_from_the_log`.
- **Too old.** Given the log's oldest kept number is K and a subscribe with `after` below K-1, then it fails with a new code `rpc::code::EVENTS_EXPIRED` whose message names K, and no Event is sent; `after` equal to K-1 succeeds. `after` above the highest saved number fails `INVALID_PARAMS`. `d11_an_after_older_than_the_window_names_the_oldest_kept`.
- **Contract.** `contracts/generated/` is regenerated from `crates/contracts`; the App, the `crates/rpc` client, `crates/perf` and every test that calls `events.subscribe` change in the same PR (Contract recipe, `.agents/builder.md`). `GLOSSARY.md` gains `Event number` and `Event log`. Terminal output keeps its existing path to a subscriber, un-numbered.

**RPC error data** (`RpcErrorData`): The optional JSON-RPC `data` carried with an RpcError. `events-expired` supplies `oldest`, the oldest retained Event number from the log bounds; only EVENTS_EXPIRED authorizes replay from `oldest - 1`. `other-project` marks a NOT_FOUND from `link.read` (or `deliverable.get`) for an object another Project owns; the App's native open skips those answers and shows only the owning Project's cause, or that the link's Project is not open when no open Project owns it. Diagnostics never supply a cursor.

**D12 a subscriber resumes across a Daemon restart.** Module: `crates/rup/tests/e2e/**`. Given a Daemon and a subscribed client that read Events up to number N, when the Daemon is killed with SIGKILL (D6) and a new Daemon opens the same Project, and the client reconnects with `events.subscribe {after: N}`, then it receives Events N+1 on in order, including Events saved before the kill that it had not read, then later Events live, each number once. `d12_a_client_resumes_after_a_killed_daemon` asserts it with a real Daemon. A failure is fixed in the log, never by the test. It keeps D6 and D9 green and narrows none.

**D13 a published Decision is never seen beside an idle Agent. (retired)** Retired by A3564a–f (`scenarios/native-questions.md`): no Decision is published; a native request produces `needs-you` from the ordinary state hook, with no roundup-owned record.

**D14 the B47 replay test waits on the end of delivery, not on a fixed time.** Module: `crates/rup/tests/e2e/notes.rs`, the Daemon's note delivery. Given the scene of B47(a), when the test has sent the child's two flips, then it waits for the events that end delivery (the Door's first prompt typed, the Digest note with `last: found it` and every setup note `delivered`, read from `message.list` or the delivery Events) and not for a 30 s poll that can end first. If delivery can stall past 30 s with the Daemon answering normally, the stall is found and fixed in the Daemon and the cause is named in the PR body. No timeout is lengthened and no assertion of B47(a) is weakened: the counts of notes and typed prompts before and after the five replays stay equal. Test: `b47_a_replay_of_status_flips_starts_no_door_turn`, which passes 50 runs in a row under CPU load.

**D15 no test reads a second fact once after waiting for a first.** Module: `crates/`. Given every Rust test under `crates/*/tests` and `crates/*/src`, when it waits (a poll, a Event, a `await`) for one published fact and then reads a second fact, then the second read is also a wait on its own condition, or the Daemon publishes the two facts together (D13). Each match found by that search is fixed the same way, and the PR body lists them with the file and the test. Policy: the search is a one-time audit, not a lint; the list in the PR body is its proof, and each fixed test passes 50 runs in a row under CPU load (`stress-ng --cpu 8`, or 8 busy loops), the PR body saying how it was run.

R2965 observer requirement for D9: `d9_the_app_worktree_provision_wait_stays_within_the_call_bound`: the App's attached Daemon runs Git stalled at each provisioning command; observe bounded failure and process cleanup. A fake reply cannot reveal blocking Git IO on the shared App connection.
