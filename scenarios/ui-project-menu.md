# UI: Project commands open center pages

Acceptance for #3511. Ids: U3813–U3816. Builds on #3281's App Settings center page (U3799/U3800). Scope: the native macOS menu in `crates/desktop`, its App seam and the existing Rail, Import and settings surfaces in `apps/desktop/src`. No new Daemon method, import format, Token or motion. This specification changes entry points and presentation, not import authority or persistence.

**U3813 the Project menu replaces Overview sublinks.** Given the mounted App with Project A selected, when the native macOS menu bar is opened, then it has a `Project` menu containing `Import Claude Code Work…` and `Project Settings…`, both enabled. With no Project selected, both remain present and disabled; choosing neither opens a page or makes a Project RPC. Selecting B makes both commands act on B. Assert native menu membership, enabled state and dispatch with `s_u3813_project_menu_tracks_the_selected_project` in `crates/desktop` using Tauri's mock runtime; execute the real menu builder and selection handler rather than inspecting source text. U3812's hiding rule is for object context menus and does not apply here (policy).

Given the actual App against its fake App seam, then the Rail's Overview row has no sublinks, and neither command appears elsewhere in the Rail. When each Project menu command is delivered through that seam, then its center page opens for the selected Project, with no dialog; repeat with A and B holding distinct settings and Import results. The one CI guard is `u3813_overview_has_no_sublinks_and_project_commands_open_selected_pages` (planned integration test beside `apps/desktop/src/App.tsx`, table of the two commands). Check roles, control availability and captured RPC Project paths, not layout or exact copy. The native test proves the menu dispatch; this guard consumes that same dispatch contract, not a second test-only path (policy).

Contract policy: the implementing PR documents menu dispatch and selected-Project synchronization in `scenarios/app.md`'s App seam table, records new public names in `GLOSSARY.md`, and changes every host, webview and fake caller together. Reuse the native menu API and #3281's settings-page ownership; no webview imitation menu or replacement Rail control is added. The specification PR adds no command or identifier.

**U3814 Import and Project Settings stay open as pages.** Given either command in U3813, when activated, then its page replaces only the center, using the shared settings shell's title, close control and named groups, as App Settings does. Rail and Shelf stay usable, with no modal backdrop, focus trap or separate window. Repeating the same command leaves the page and its unfinished input unchanged. When the user selects another Rail row, opens a Shelf item, or works in a Terminal Bubble, then the page stays open; those actions retain their ordinary effects outside its center. Switching to Project B never shows A's page contents as B's; returning to A restores its open page and choices. Tests: `u3814_project_pages_survive_work_elsewhere` (table of both pages and these actions) and `u3814_project_switch_keeps_each_page_with_its_project`, planned at the App seam beside `App.tsx`.

Given a page opened over a center with a focused element, when its close control is activated or Escape is pressed within the page with no child choice list open, then the previous center and focus return. A child choice list consumes Escape first. If the original focused element no longer exists, focus returns to Overview in that Project's Rail. Reopening Project Settings re-reads `project.get`. Tests: `u3814_close_restores_the_previous_center_and_focus` (both pages, close/Escape and missing-element cases) and the existing `u3766_close_returns_the_center_to_what_it_showed`, retargeted to the native command. Policy: opening either page captures the center and webview focus that preceded it; changing between these pages does not replace that return destination with another settings page.

**U3815 Import keeps its existing behavior on the page.** Given Import opened from U3813, when the user changes period, selects results, imports, cancels/closes, refreshes, retries or reopens it, then every U2875a–d and U3037a–d clause still holds. The initial period and empty selection, selection clearing on period change, explicit confirmation, one pending commit, per-source partial-failure retry and successful navigation remain unchanged. Close/Cancel before confirmation imports nothing and keeps recoverable choices. A successful import may navigate to its created work as U2875d requires; ordinary work elsewhere does not dismiss the page. Tests: retarget the existing `u2875d_…` App-seam probes in `apps/desktop/src/importer/u2875d_import_panel.test.tsx` to menu-opened pages; replace `u2875d_dialog_focus_and_escape_return_to_the_rail` with U3814's return-focus observer rather than preserving its dialog assumption.

Given discovery pending on that page, then Cancel and period changes remain usable, the 20-second bound exposes timeout and Refresh, and Refresh recovers without losing or retargeting the draft. Timed-out, superseded, closed or previous-Project responses never replace current results or failure. Assert with the existing `u3037d_discovery_deadline_and_retry` and the U3037d late-result probes, retargeted to the page with controlled promises and a fake clock. Given distinct period/selection drafts in A and B, when closing, switching Projects, reopening, reloading or encountering rejected calls, then each original Project retains its exact choices and preview identities, fresh discovery validates restored picks, and restoration submits nothing. Assert by retargeting U2875d's recovery probes and the existing U3049a/U3049b conflict/recovery probes to the page. U3083b–d's exclusion disclosure, row selection/errors and quiet stale-pick removal also hold on the page, proved by their existing importer probes. Policy: preserve each existing proof; add only uncovered behavior, with no duplicate test that merely repeats one.
