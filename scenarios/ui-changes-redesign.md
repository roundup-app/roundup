# UI: the Changes view shows its files beside the diff (U7674a–U7674f) and folds the sidebars (U8005a–U8005c, U8074)

Module: `apps/desktop/src/changes/`. Ids: U7674a, U7674b, U7674c, U7674d, U7674e, U7674f, U8005a, U8005b, U8005c, U8035, U8074, U8075. Work orders: [#7674](https://github.com/roundup-app/roundup/issues/7674), blocked by #7673, [#8005](https://github.com/roundup-app/roundup/issues/8005) for U8005a to U8005c, [#8074](https://github.com/roundup-app/roundup/issues/8074) for U8074, and [#8075](https://github.com/roundup-app/roundup/issues/8075) for U8075. Owner, 2026-11-18: "this view is awful we need to redesign it", "we need quick easy navigation and clean ui", "prime our moat - simplicity, focus, clean, fast". The owner chose this layout over "All files in one scroll" and "Today's flow, fixed": the tree stays on the left and the chosen file's diff fills the rest. No Daemon method, Message or contract change; it redesigns the centre view U7186c to U7186e built and U7672c switched. The implementation PR's `Reuse:` section names `@pierre/diffs` 1.6.1 (`overflow: 'wrap'`, the `github-light` theme), `@pierre/trees` through `ChangedTree`, and `ui/Select` only if the group switcher needs it; no `!important`, synthetic events or DOM clones. Size: about 700 changed lines. Observer: Vitest against the fake App for U7674a to U7674e; the isolated Chromium harness (U26) for U7674f. Never a native Mac capture.

**Precedence.** A design check (the critic, a D-check) that reads a decision here as a defect changes how it is drawn, never the decision. When both cannot hold, `ask` (`flag:needs-user`). For U7674d a light block in a dark App may read as a defect: its edge, margin or seat changes, never its colour.

**U7674a the tree stays beside the diff and its first file opens.** Given the open Changes view of an Agent with changed files, then:
- **First file.** The first file in tree order opens with the view, with no further click, and keyboard focus lands in the tree. Asserted in `u7674a_the_first_file_opens_and_focus_lands_in_the_tree`.
- **Up and Down.** Up and Down move the tree's focus; a file row that takes focus opens, a folder row opens nothing and the open diff stays. Asserted in `u7674a_up_and_down_open_the_next_and_previous_file`.
- **Tree stays.** The tree stays while a file is open: no Back, and opening a file never replaces the tree (amends U2540a's "the tree is replaced within the transient view" and Back clause). Asserted in `u7674a_the_tree_stays_while_a_file_is_open`.
- **Groups.** With several repository groups a group switcher sits above the tree and shows one group's tree; with one group no switcher shows. Asserted in `u7674a_a_group_switcher_shows_only_with_several_groups`.
- **Kept.** Enter or a double click on a file opens the editor (U2539d). Asserted in the U2539d tests of `u2539d_choose.test.tsx`.

**U7674b the header is one line.** Given the open view, then:
- **Content.** The header holds the Agent's name, From, the switch (U7672c), the shown group's file count with `+added -removed` totals summed from each entry's `counts` (U7610a), U7680a's "N of M viewed" when the lens lists a module, and one close button; no title apart from the Agent's name, no `Changes: <Agent> vs <base>` text (amends U7186c's title), no Back, no status line. Asserted in `u7674b_the_header_holds_name_from_switch_totals_and_one_close`.
- **From.** From is a quiet fixed label, not a control (kept from U7672c). Asserted in `u7672c_from_is_a_label_not_a_control`.
- **Totals.** Choosing another group or switch value changes the count and totals to that listing's; an entry whose `counts` is `null` adds nothing to the totals. Asserted in `u7674b_totals_follow_the_shown_group`.
- **Escape.** Escape closes the view, unless a note field (#7676) holds it, which keeps the view open. Asserted in `u7674b_escape_closes_the_view_unless_a_note_field_holds_it`.
- **Notes bar.** Replaced by U7676a and U7676d (`scenarios/ui-changes-notes.md`): a note starts from the line, and the bar shows only for unsent notes or a send. Asserted in `u7676d_the_bar_shows_only_for_unsent_notes_or_a_send`.

**U7674c every file row shows its counts.** Given the tree, then each file row shows its `+added -removed` through `renderRowDecoration`, a `null` `counts` shows none, and a folder row shows none. Long lines wrap: the reader passes `overflow: 'wrap'` and the view never scrolls sideways. Asserted in `u7674c_file_rows_show_counts` and `u7674c_the_reader_wraps_long_lines`; the sideways scroll itself is U7674f's capture.

**U7674d the diff is GitHub light, always.** Amended by U8035: the diff follows the App's theme. Given the App in dark or light mode, then:
- **Theme.** The reader loads Shiki's `github-light` through `@pierre/diffs`'s `theme` option with the current highlighter, in both modes, and the diff surface is light in a dark App. Asserted in `u7674d_the_reader_uses_github_light_in_both_modes`, extending `z3_highlights.test.tsx`, which proves the theme loads and highlights.
- **Dead code.** `registerCustomCSSVariableTheme("roundup")` in `DiffReader.tsx` and the token-driven syntax colours in `diff.styles.css` are deleted after their callers are checked (policy: the compiler and the lints find no caller). Lost: github-dark and roundup's CSS-variable diff theme.
- **Checks moved.** The PR names the Checks this moves (rule 8: a named theme is not a Token, so outside the diff surface Tokens only) and measures rule 7 against `docs/perf.md`. Policy.

**U7674e opening is fast and never blanks the pane.** Given the fake App, then:
- **One comparison.** Opening the view requests only the first file's `agent.compareFile`. Asserted in `u7678c_opening_a_module_reads_only_the_files_its_first_screen_shows`, which replaces the first-file test.
- **No blank.** Up and Down keep the open diff on screen until the next file's diff paints. Asserted in `u7674e_up_and_down_never_blank_the_pane`.
- **Switch.** Choosing a switch value or group opens its first file. Asserted in `u7674e_choosing_a_value_opens_its_first_file`.
- **Lazy.** The reader chunk loads when the view opens, never at startup, and the 10,000-line fallback stands (amends U2540d's and U7186c's Reader clause: it loaded on choosing a file). Asserted in `u7186c_the_reader_stays_lazy` and `u2540d_lazy`, edited to the open.

**U7674f the rendered view at 1512 by 950 and at 388 px.** Given the U26 harness, dark App, dense fixture (500 changed files, a 120-character path, 100 notes, a 10,000-line diff; `u2540.html?dense` extended), then at 1512 by 950 and at the centre's 388 px minimum: no sideways scroll, the diff reaches the view's bottom edge, one header line, the tree told from the diff by space or ground and no new border (D8), chrome in ghost buttons in `--grey` (U510). **U8005a opening Changes folds the sidebars.** Owner, 2026-11-26: "When the changes of a rail open the sidebars should always auto collapse". "Sidebars" are the Rail (left) and the Bench (right, Todos and Pads). Given the fake App with an Agent selected, then:
- **Fold.** Opening Changes by the Rail's Changes icon or by `leader.changes` (U7671a) folds the Rail to its strip, as the Rail toggle does, and closes the Bench. Asserted in `u8005a_opening_changes_folds_the_rail_and_closes_the_bench`.
- **Restore.** Closing by ✕ or Escape (U7674b) returns the Rail and the Bench to how they were before Changes opened. Asserted in `u8005a_closing_changes_restores_the_rail_and_the_bench`.
- **Already folded.** Opening with the Rail folded or the Bench closed records that state, so closing leaves it folded or closed. Asserted in `u8005a_closing_leaves_a_sidebar_that_was_already_folded_folded`.
- **Hand change wins.** A sidebar the user folds or opens by hand while Changes is open keeps the user's state on close; only a sidebar the user did not touch is restored. Asserted in `u8005a_a_sidebar_changed_by_hand_keeps_its_state_on_close`.
- **Not saved.** The folding Changes causes is not the user's saved state: a restart while Changes is open shows the sidebars as they were before it opened, and no fold writes `roundup:viewer`. Asserted in `u8005a_the_folding_changes_causes_is_not_saved`.
- **Project switch.** Switching Project while Changes is open leaves the new Project's Rail as its user left it: a Rail the user folded stays folded and its saved width is not rewritten, one the user left expanded stays expanded. Closing Changes then restores only what Changes folded. Asserted in `u8074a_returning_to_a_project_with_changes_open_slides_nothing` (U8074 amends this clause).
- **Motion.** The Rail folds and restores with the existing Rail slide (`createRailSlide`), under reduced motion as today; U8075 amends it: the centre takes its final width at the click and the slides take `--duration-layout`. Policy; the design critic judges it.

**U8074 a Project switch replays no fold.** Owner, 2026-11-28: "when I move to a project and then move back to the project that has change view open the sidebars keeps sliding in and out and that sucks and is slow and annoying". Amends U8005a's Not saved and Project switch clauses. A Project's fold is the one record of what Changes folded in it (U8005a), kept per Project, so a switch reads it and starts nothing. Given the fake App with two Projects, Changes open in A, `Element.prototype.getAnimations` stubbed so a slide runs and reduced motion off, then:
- **Return.** Switching back to A shows its Rail, Bench and Changes exactly as they were left, at once: no `data-slide` or `data-animated` attribute takes `key`, `click`, `fade` or `true` during the switch, read from each record's `oldValue` as well as its current value, and the Rail's `data-collapsed` and the Bench's `data-open` equal what they were before the switch. Asserted in `u8074a_returning_to_a_project_with_changes_open_slides_nothing`.
- **Leave.** Switching from A to B changes nothing about A's saved sidebar state (no `roundup:viewer` write) and shows B's sidebars at once, with no slide. Asserted in `u8074a_leaving_a_project_with_changes_open_writes_nothing_and_slides_nothing`.
- **Open and close.** The fold and the restore slide only when the user opens or closes Changes in the Project on screen. Asserted by the existing `u8005a_opening_changes_folds_the_rail_and_closes_the_bench` and `u8005a_closing_changes_restores_the_rail_and_the_bench`, which keep their motion.
- **Hand change.** Closing Changes restores only what the fold changed; a sidebar the user changed by hand keeps its state, in either Project. Asserted in `u8005a_a_sidebar_changed_by_hand_keeps_its_state_on_close`.
- **Class.** Every transition that can run on a Project switch, a window refocus or a re-mount (the Changes fold, the Bench open and close, the Rail and edge peeks, the Rail row fade, the Walk step slide, a Dialog entry) is audited against the Return guard; each that replays is fixed by the same mechanism. Policy: the implementation PR's body holds the audit table.
- **Not wanted.** A setting to turn the fold off; a sidebar state store beyond one record per Project of what Changes folded; a Vitest test of looks (rule 10). Build on the #8077 change to `createChangesFold`, never beside it. Module: `apps/desktop/src/rail/`, `resize/`, `shelf/`. The old `u8005a_a_project_switch_keeps_the_new_projects_folded_rail_folded` goes if the Return test fails when its behaviour breaks. Policy.

**U8075 the Changes fold feels light.** Owner, 2026-11-28: "we need to /review-animations on the open changes sliding as it feels heavy". **U8035 the code follows the App's theme.** Owner, 2026-11-27, on a light, all-green block of code in the dark App: "I find this view highly unusable and need proper designing". The owner picked the sketch: dark App, dark code ground and no line colour on a new file; light App, the same in light; a changed file carries green and red only on its changed lines. Amends U7674d (its Theme clause and "the diff is GitHub light, always"; Precedence's light block in a dark App no longer applies) and U7677a's Light surface clause (the note takes the App's theme through the `data-surface="diff"` tokens). Implementation is a dependent Issue blocked by #8031, which paints the placeholder with the code's ground; this PR specifies. Given the open Changes view, then:
- **Theme.** The reader registers `github-dark-default` beside `github-light` through `registerCustomTheme` from `@pierre/highlights/themes/` (the package ships it) and passes the one that matches the App's colour scheme as `theme`: dark in the dark App, light in the light App. Asserted in `u8035_the_reader_uses_the_theme_of_the_app`, replacing `u7674d_the_reader_uses_github_light_in_both_modes` in `z3_highlights.test.tsx`, which keeps proving the theme loads and highlights.
- **Switch.** Switching the App's theme with a file open redraws the diff with the matching theme, with no reload. Asserted in `u8035_switching_the_app_theme_redraws_the_diff`.
- **New or deleted file.** A file whose status is New or Deleted draws plain code: no line ground and no `+` or `-` sign (`diffIndicators: "none"`, no added or removed line ground), and its bar says "New" or "Deleted" as today (U7854d). Asserted in `u8035_a_new_file_draws_no_added_line_ground`.
- **Changed file.** A changed file keeps green and red on its changed lines only, in the App's theme. Asserted in `u8035_a_changed_file_keeps_its_changed_line_ground`.
- **Surface tokens.** The `data-surface="diff"` tokens (`--diff-text`, `--diff-grey`, `--diff-ground`, `--diff-code-ground`, `--diff-accent` in `tokens.css`) take dark values in the dark App, so a note, a mark and the selection on the code stay readable in both themes. Asserted in `u7677a_the_note_sits_in_the_diff_surface_and_the_bar_in_the_app_theme`, edited to read the App's theme. Colour contrast itself is the critic's.
- **Dead code.** The light-only values of those tokens and any comment saying the diff is light in both modes are deleted with their callers checked. Policy: the compiler and the lints find no caller.
- **Looks.** U26 captures of a new file and a changed file, at 1512 by 950 and at 388 px, dark and light, via `just capture U8035`; evidence under `artifacts/ux/U8035/`, uncommitted; D2, D5, D6 and every Check passing on `main` still pass. Policy; the design critic judges that it matches the sketch, never a Vitest test (rule 10).
