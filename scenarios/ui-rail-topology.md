# Share Rail topology and Todo counts

Acceptance for #5645. First-journey stage: Understand (`.agents/data/journey.md`, **What must work**). This changes frontend data access only; U520's tree, U31's keyboard guards, U4547a's sections, U5483a–c's idle branches and U178's creator-based control retain their behavior. These scenarios name planned implementation tests, not passing observations from this specification PR.

## Acceptance

**U5645a one Rail revision supplies every tree consumer.** Given the production Rail owner with 40-node and 400-node nested chains, mixed root Agents, plain Workstreams and Modes, and input records deliberately out of sibling order, when visible section rows and the full Ark keyboard collection are requested for the same revision, then:

- Exactly one topology construction serves all sections, visible rows, full collection and row consumers. Its boundary reads each source node's parent once, resolves parent ids to dense indices once, and records sorted child ranges and each node's root section. Ancestry and sibling traversal thereafter use those indices, with no complete-source-array search/filter per node or parent. Test: `u5645a_one_topology_serves_rows_and_collection_at_40_and_400` in `apps/desktop/src/rail/u520_tree_walk.test.ts`, exercising the production owner/projection, counting actual constructions and source-parent reads, and asserting the resulting row keys and Ark traversal against the fixture's explicit expected order. A test of a standalone constructor without its production consumers is insufficient.
- A changed membership, parent, sibling order or root classification in the connected Rail invalidates the topology: all consumers see one newly built topology and the updated order/section. This holds when Solid reconciles the update into the same array and retains surviving node records. Selection, focus, clock ticks, disclosure and section preferences, question protection, and Todo-only changes do not construct another topology when those structural inputs are unchanged; projections still update when their own inputs change. Test: `u5645a_reconciled_structure_updates_once_and_view_changes_do_not_rebuild` in `apps/desktop/src/rail/u520_semantics.test.tsx`, using the existing connected Rail update seam, construction counts, row membership/order and expanded values.

Policy: retain the authoritative RailNode records without mutation or replacement by topology records. Keep one revision-scoped topology at the existing Rail owner; add no persistent cross-revision topology cache, store, protocol, RPC or App seam command. Remove duplicate topology construction and derived maps only where every consumer can use the canonical index; retain Ark collections, disclosure/section preferences, and rendered ancestry trails. Descendant status aggregation in rows must also use the shared topology, rather than reintroducing sibling scans. Full ancestry/trail output on a chain can contain quadratically many entries; this specification removes repeated searches and topology construction, and makes no linear-time claim for that output. Sorting costs and the necessary Ark collection/output allocations remain.

Measurement (policy): the Issue's production-layout probe reads parent fields 1,640 times at 40 nested nodes and 160,400 times at 400. Record before/after construction and parent-read counts at both sizes from the frontend path, including every section and the full collection. Count actual work, not fixture generation or calls to a test double. The required topology-boundary result is N parent reads for N source nodes and one construction per consumed structural revision; report remaining source-parent reads outside that boundary separately. No wall-clock threshold or daemon root-only `rail_tree_40_p95_ms` result substitutes for these counts or demonstrates a frontend 16 ms pass.

**U5645b each Todo is counted once for all Agent rows.** Given a mounted Rail with 1, 10 and 40 Agent rows and a shared Todo list containing Agent-created open and done Todos, a user-created Todo, a Todo whose creator differs from its owner, and a creator with no visible Agent, when one Todo-list revision is consumed, then:

- The Rail owner visits each Todo exactly once to count by Agent creator and passes each row its count through existing row ownership. A row shows all Todos that Agent created, including done Todos, regardless of owner or Home; user-created Todos contribute to no Agent count, and an Agent with none has no count control. Accessible names and tooltips retain U178, and activating the control still opens the Shelf on that Agent's created Todos. Test: `u5645b_one_todo_pass_counts_creators_for_every_agent` in `apps/desktop/src/rail/pads/u178_this_one_lists_agent_todos.test.tsx`, mounting the production Rail with the existing shared list, measuring Todo visits independently of Agent count, asserting control names/absence and the selected creator after activation. Isolate this counter to the Rail count pass so Shelf/Drawer consumers are not charged to it.
- After a Todo is added, completed, removed or changes creator through the existing Todo event/refresh seam, every affected count updates with exactly one visit per Todo in the resulting list. Mounting additional rows, selection changes and Rail-only revisions reuse the count result without rescanning an unchanged Todo revision. Test: `u5645b_todo_revisions_update_counts_without_row_rescans` in the same file, asserting both work counts and rendered control counts after those updates.

Policy: remove per-Agent filtered Todo arrays used only for their length. Reuse the existing shared `useTodoList` at the Rail owner, with no additional Todo RPC/event subscription or persistent count cache. A creator-count map is allowed; it is not a second topology. Do not remove creator-filtered lists that actually display Todos elsewhere.

**U5645c sharing data preserves the Rail walk.** Given the same 40/400 nested-node fixtures, equal-order siblings in their original relative order, roots in all three sections, a selected/focused surviving row, a collapsed Workstream and an idle branch, when the user navigates, folds/unfolds or refreshes the Rail, then:

- Visible row keys, root/sibling order and section membership match the fixture's expected existing order; descendants inherit their root's section, including a nested Workstream with a saved prompt. The full collection retains hidden descendants for later expansion, while the active keyboard walk excludes collapsed, hidden, inert and disabled rows. Down/Up, Left/Right, Home/End and typeahead retain Ark's behavior. Tests: `u5645a_one_topology_serves_rows_and_collection_at_40_and_400` for keys/full traversal, `u5645c_sections_and_stable_order_survive_reclassification` in `apps/desktop/src/rail/u4547a_sections.test.tsx` for section membership and stable equal-order siblings, and `u5645c_keyboard_skips_unavailable_rows` in `apps/desktop/src/rail/u31_rail_keyboard.test.tsx` for active navigation/exclusions.
- Surviving source nodes and mounted rows retain identity, and selection/focus stay on the surviving row after a data-only refresh and Todo-count update. Existing collapse/unfold focus recovery remains unchanged. Test: `u5645c_refresh_preserves_row_identity_selection_and_focus` in `apps/desktop/src/rail/u520_semantics.test.tsx`, comparing node and DOM identity and active/selected ids, plus the existing U31 and U520 observers in checks 2 and 3.

Policy: preserve current fold eligibility, clock thresholds, question protection and disclosure timing; drag calls/cancellation and accessibility contracts are unchanged. Resolve concurrent fold/visibility work by retaining main's accepted behavior, without importing an open PR's product changes. This is no authorization to change those scenarios or their acceptance. Tests assert interactions, roles, contracts and counts, never geometry, exact App copy or computed styles. Apply rule 10 to any edited test file, naming the surviving observer or retired scenario for each test removed.
