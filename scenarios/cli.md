# rup as a command line

Module: `crates/rup` (the command line and `mcp.rs`'s tool list), with `crates/agents` (`claude_code/launch.rs`: the Agent's shell variable and the Brief's line) and `crates/rupd` only if a Daemon method needs a parameter the CLI lacks. Ids: I1–I9. Tests start the built `rup` (`CARGO_BIN_EXE_rup`) against an in-process Daemon on a temp socket, as `crates/rup/tests/mcp.rs` does; no `claude` is involved.

Found by the owner's request #2214: "Treat rup as the product your work agents see. An agent should learn it from rup help alone"; "Our CLI must have full parity with the MCP"; the owner chose that every MCP tool also becomes a `rup` command, following https://clig.dev (help, `--json`, stable exit codes). Today `rup --help`, `-h` and `help` print `rup: unknown command` and exit 2, bare `rup` prints one usage line to stderr, and the tools `rup mcp` offers (M1, M5, M13) are reachable only over MCP.

Reuse (rule 9, decided here): the command tree is built at run time from the tool list, so a derive-only parser (`argh`, `bpaf`'s derive) does not fit. Use `clap`'s builder API (`Command`, `Arg`), which builds subcommands from data and writes help and the closest-command suggestion. The PR's `Reuse:` section cites its release evidence against `bpaf` (combinator API) and `argh`.

**I1 one list, two faces.** Given the tool list `rup mcp <agent-id>` offers an Agent (M1, M5, M13: 63 tools, `ask_user` among them) and a Door (those and the Door-only ones, 66), then `rup` has one command for each, `rup <noun> <verb>` for method `noun.verb` (`rup pad read notes`, `rup terminal read 3 --after 120`, `rup todo create "Fix login"`), and no other command but `ping`, `signal`, `context`, `permission`, `mcp`, `help`. Both faces are built from one function in `crates/rup` that returns the list (name, method, description, input schema, Door-only flag); neither keeps its own copy. A command's arguments and flags come from the tool's input schema: a required string or integer field is a positional argument in schema order, an optional field is `--<field>` in kebab-case, a boolean is a flag, an array repeats its flag, and an object field takes JSON. Its help text is the tool's description. Tests: `i1_every_mcp_tool_is_a_command_and_no_command_is_extra` (lists both over a Daemon, for an Agent and for a Door, and fails on a name in one list only), `i1_a_commands_flags_are_its_schemas_fields`, `i1_a_door_only_command_is_refused_to_an_agent` (exit 2 naming that only a Door has it). `m1_`, `m5_` and every earlier `rup mcp` test pass unchanged.

**I2 help.** Given `rup`, `rup help`, `rup -h` or `rup --help`, then stdout holds, in this order, what roundup and `rup` are in two sentences, a few examples, the commands grouped by noun (one line each: the command and the first sentence of its description), and the exit codes (I4); stderr is empty and the exit is 0. `rup help <command>` and `rup <noun> <verb> --help` print that command's description, usage line, arguments, flags with their types and one example, to stdout, exit 0. `rup help <noun>` lists the noun's commands. An unknown command prints `rup: unknown command "padd"` and `did you mean "pad"?` (clap's closest match) and `run "rup help"` on stderr, nothing on stdout, exit 2. Tests: `i2_every_spelling_of_help_prints_the_same_text_on_stdout_and_exits_0`, `i2_help_has_the_four_parts_in_order`, `i2_a_commands_help_names_its_arguments_flags_and_an_example`, `i2_a_mistyped_command_suggests_the_closest_and_exits_2`, and `i2_help_alone_teaches_every_command` (reads only `rup help` and `rup help <noun>` output and shows each of the tools' commands appears with its usage).

**I3 output.** Given a command that succeeds, then stdout is the text the MCP tool returns for the same call (the method's result as `rup mcp` renders it), one line per item where the tool returns a list, ending in a newline. With `--json`, stdout is exactly the method's result as one JSON document, nothing else. A Daemon error is one line on stderr, `rup: <message> (<code name>)`, then a line on what to do next (`FORBIDDEN`: "this Agent may not act on that node"; `NOT_FOUND`: "list them with `rup <noun> list`"; no Daemon: the socket path), nothing on stdout, exit 1 (I4). `--json` leaves errors on stderr as text. Tests: `i3_stdout_is_the_text_the_mcp_tool_returns`, `i3_json_prints_the_result_alone`, `i3_a_daemon_error_is_on_stderr_with_what_to_do_next_and_exits_1`, `i3_no_daemon_names_the_socket_and_exits_1`.

**I4 exit codes.** `rup` exits 0 when done, 1 when it failed (the Daemon refused, did not answer, or was not there; a call that exceeds `CALL_TIMEOUT` of 10 s), 2 on bad usage (an unknown command, a missing or invalid argument or flag, a missing Agent id, a Door-only command run by an Agent). The help lists the three. The hook commands `signal`, `context` and `permission` never exit 2, since exit 2 makes Claude Code block the tool call or prompt: their usage errors stay at 1 (and `context` at 0 as E3 says), the parser's own usage exit included. Tests: `i4_exit_codes_are_0_1_and_2_as_the_help_lists`, `i4_a_hook_command_with_bad_usage_exits_1_not_2` (for each of the three, with no argument, an extra argument and an unknown flag); the help's listing of the three is asserted by `i2_help_has_the_four_parts_in_order`; the A4/E3 tests on `signal` and `context` pass unchanged.

**I5 who is asking.** A command that acts as an Agent uses the Agent id from the `ROUNDUP_AGENT` variable, which `Launcher` sets in the environment of the Agent's `claude`, so every shell it runs inherits it, and `--agent <id>` overrides it. With neither, stderr says `rup: no Agent id: run it in an Agent's shell, or pass --agent <id>` and the exit is 2. A call is then the same Touch by that Agent as over MCP (M2) and the same Reach limits apply (M7, M13). A Door's variable gets the Door-only commands (`agent digest`, `checkpoint write`, `workstream handoff`, B20, M10, A32) as the role does over MCP. `rup mcp <agent-id>` keeps its argument. Tests: `i5_launch_sets_roundup_agent_in_the_claude_environment` (in `crates/agents`, on the written environment), `i5_a_call_is_the_touch_of_the_agent_named`, `i5_the_agent_flag_overrides_the_variable`, `i5_no_agent_id_says_so_and_exits_2`, `i5_a_door_gets_the_door_only_commands`.

**I6 text in, not base64.** Amends M13's "typing stays the user's" for the CLI only as far as the MCP offers it today: whatever Reach (M7) lets `terminal_write` and `agent_prompt` do over MCP, the commands do, no more. `rup terminal write <id> "text"` sends the text's UTF-8 bytes followed by Enter (`\r`), as Solo's `send_input` does; `--no-enter` leaves the Enter out; `--base64 <data>` sends the raw bytes `terminal_write` takes, and conflicts with `--no-enter` (exit 2). `rup agent prompt <id> "text"` sends the text and Enter as an Agent prompt the same way (`--no-enter` applies). Any text argument (`pad write`, `pad append`, `message send`, `agent spawn --order`, `agent spawn --prompt`, `terminal write`, `agent prompt`) takes `-` for the whole of stdin, read as UTF-8 (invalid bytes are exit 2), so a long body is never quoted in the shell. Tests: `i6_terminal_write_types_the_text_and_presses_enter`, `i6_no_enter_leaves_enter_out_and_base64_sends_the_raw_bytes`, `i6_base64_and_no_enter_together_are_bad_usage`, `i6_agent_prompt_sends_text_and_enter`, `i6_a_dash_reads_the_text_from_stdin` (for each listed command), `i6_invalid_utf8_on_stdin_exits_2`.

**I7 same limits, plain output.** `rup terminal read <id> --after <n>` prints the text on stdout and `next: <offset>` (and `truncated` when set) on stderr, so a loop of reads needs no parsing; with `--json` the whole result `{from, next, text, truncated}` is on stdout. The 16 384-byte cap of X13 and the 10 s call timeout of M2 and M3 hold as over MCP, and `terminal screen` and `terminal search` print likewise (matches as `<offset>: <line>`). Tests: `i7_read_prints_text_on_stdout_and_next_on_stderr`, `i7_read_json_has_next_in_the_result`, `i7_a_loop_of_reads_from_next_misses_and_repeats_nothing`, `i7_a_reply_over_the_cap_is_cut_as_over_mcp`, `i7_a_daemon_that_never_answers_exits_1_in_ten_seconds`.

Cost observer (TC1): `i7_a_daemon_that_never_answers_exits_1_in_ten_seconds` needs the built `rup` process and real elapsed clock to prove the CLI exits 1 within its promised timeout; a returned timeout error alone does not prove process termination.

**I8 speed, and the Agent learns it.** `rup signal`, `rup context` and `rup permission` stay inside their hook deadlines (1 s and 4 s): building the command tree is done only for a command that is not one of those five, which are matched before it, and `rup ping` and the hook commands start no later than on `main`. The PR records `rup signal` startup (median of 20 runs of `rup signal x` against a Daemon that answers at once, `hyperfine`) on `main` and on the head, and the head is no more than 10% slower or 5 ms, whichever is more (rule 7). Every Agent's Brief says to run `rup help` to learn roundup, in one line, and a Door's Brief says it too; the Brief names no command the list lacks (M9, M11, E1 amended). `rup mcp` keeps working unchanged. Tests: the hook commands skipping the command tree is proved by `i4_a_hook_command_with_bad_usage_exits_1_not_2` (the parser would exit 2 on those arguments), `i8_every_brief_says_to_run_rup_help`, `i8_startup_is_within_ten_percent_of_main` (policy: recorded in the PR body, `just perf` has no probe for it).

**I9 `rup events` follows the Event log, exactly once.** Module: `crates/rup`, with `crates/rpc` and `crates/contracts` for the `head` below (Contract recipe, `.agents/builder.md`; D10, D11 own the log and the resume). Needs D10 to D12 and I1 to I4 on `main`. `events.subscribe` (D11) answers with `{head}`, the highest Event number saved when it was accepted (0 for an empty log), instead of `null`; the App's callers and `contracts/generated/` change in the same PR. `rup events [--after N] [--follow]` is a command of I1's one list with `events.subscribe` as its method, marked as a stream: it is a `rup` command and the help lists it with an example (I2), and `rup mcp` does not offer it, since an MCP call returns once, so I1's two-face comparison skips stream entries and lists them apart. It prints one JSON object per line on stdout, always, whether or not `--json` is given (`--json` is accepted for symmetry): the Event as `events.subscribe` sends it, with its `seq`.
- **Replay and stop.** Given saved Events 1 to 20, `rup events --after 12` prints Events 13 to 20 in order, one per line, then exits 0 once it has printed the Event numbered `head`; `--after 20` prints nothing and exits 0. `i9_events_after_prints_each_saved_event_past_n_and_stops_at_the_end`.
- **Follow.** `rup events --after 12 --follow` prints 13 to 20, then every later Event as it is saved, with no gap and no repeat, including an Event saved while the replay ran, and never exits 0 on its own (it ends on a signal, or exit 1 when the Daemon goes). `i9_follow_streams_live_after_the_replay_with_no_gap_and_no_repeat`.
- **No `--after`.** It subscribes with no `after`: nothing from the log is printed, only Events saved after it; without `--follow` that is no Event, and it exits 0 at once. `i9_no_after_starts_at_the_end`.
- **Too old.** An `after` below the oldest kept number less one makes the Daemon answer `EVENTS_EXPIRED`; `rup` prints I3's error line (the Daemon's message, which names the oldest number kept, then what to do: "start without `--after`, or pass `--after <oldest - 1>`"), nothing on stdout, and exits 1. An `after` above the highest saved number is `INVALID_PARAMS`: exit 1 the same way. A non-integer or negative `--after`, an unknown flag, or `--follow` repeated is bad usage: exit 2 (I4). `i9_an_after_older_than_the_window_exits_1_with_the_daemons_error`, `i9_a_bad_after_exits_2`.
- **A caller resumes.** A caller that keeps the `seq` of the last Event it handled and passes it as `--after` on the next run, once with `--follow` killed mid-stream and once without, receives every Event once across the runs, including Events saved while it was down and across a Daemon restart (D12). `i9_a_restarted_caller_loses_and_repeats_nothing`.
- **Fixed output.** `--follow` flushes each line as it prints it, so a pipe reads it at once; a closed stdout pipe ends it with exit 0; Terminal output never appears (D10). `i9_each_line_is_flushed_and_terminal_output_is_absent`.

Policy: `rup events` adds no timer, poll or retry: it waits on the Daemon's stream, and a lost connection is exit 1 with the last printed `seq` on stderr (`rup: connection lost after event <seq>; resume with --after <seq>`), so the caller, not `rup`, decides to reconnect. The 10 s `CALL_TIMEOUT` (I4) covers the subscribe answer only, not the stream.
