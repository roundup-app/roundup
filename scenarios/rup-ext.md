# The `rup` command line for a user and an outside Claude Code

Module: `crates/rup` (`ping`, `help`, the `--as` and `--json` options), with `crates/rupd` (the `daemon.ping` reply). Ids: CL1–CL4, LK1–LK4 (the link read). `scenarios/cli.md` (I1–I9) owns the command tree, `rup help` and the exit codes; this file adds `ping`'s line and the `--as` option, and where the two meet, I1–I8 hold.

The owner switches to roundup from their own terminal, and drives it from a Claude Code started outside roundup. Neither is an Agent: the Daemon knows an Agent by walking the caller's parent processes to a running Agent, so every other `rup` call acts as the User, and only `rup mcp <agent-id>` can name a caller. `rup` reaches the Daemon at `RUPD_SOCKET`, else `~/.roundup/rupd.sock`. Tests start the built `rup` (`CARGO_BIN_EXE_rup`) against an in-process Daemon on a temp socket, as `crates/rup/tests/ping.rs` does. No `claude` is involved.

**CL1 ping says which Daemon it reached.** Given a Daemon opened on a Project folder and serving a socket, when `rup ping` runs with `RUPD_SOCKET` set to that socket, then it exits 0 and prints one line `rupd <pid> at <socket> for <project folder>` (policy: the words and order), with the Daemon's process id, the socket path `rup` connected to and the Project folder the Daemon was opened on; the Daemon's `daemon.ping` reply gains `pid` and `project` (the absolute folder) beside `pong` and `contract` (`cl1_ping_names_the_daemon_its_socket_and_its_project`). Given `RUPD_SOCKET` unset and no Daemon on `~/.roundup/rupd.sock`, then `rup ping` exits 1 with one stderr line naming that default path, so a shell that does not reach the App's Daemon shows it at once (`cl1_ping_without_a_daemon_names_the_default_socket`). `rup ping --json` prints one JSON object `{actor, socket, result}` (CL2) where `result` is the unchanged `daemon.ping` reply (`cl1_ping_json_holds_the_actor_the_socket_and_the_reply`). The line replaces the old output `{"result": …}`; `loop/ci-ping.sh`, which `check.yml` runs as the hello-world round trip and `loop/launch-sites.test.py` runs, asserts the output contains `pong`, so the same PR changes it to assert the output starts with `rupd ` (L118 exempts that helper from the freeze).

**CL2 `--as ext:<name>` acts as an Ext Actor.** Given a Daemon, when `rup --as ext:claude-code mcp` runs (the option comes before the command) and an MCP client calls `todo_create {title: "x"}`, then the Todo's `wrote` Touch has actor `{kind: ext, id: "ext:claude-code", parent: null}` and not the User's `you` (`cl2_an_ext_actor_mcp_call_is_a_touch_under_its_name`). `rup` sends `daemon.identify` with that Actor before its first call, and for `rup mcp` with no agent id it serves the tools of a non-Door caller. `<name>` is 1 to 64 characters of lowercase letters, digits, `-` and `_`; any other name, an empty one, or `--as` with a value that does not start `ext:` exits 2 with a stderr line naming the rule and sends nothing to the Daemon (`cl2_a_bad_actor_name_exits_2_and_sends_nothing`). `--as` before `signal` or `context` exits 1 with a stderr line saying those are Agent hooks (they never exit 2, E3, H15), and `rup mcp <agent-id>` with `--as` exits 2: an Agent id and an Ext name cannot both be given (`cl2_as_with_an_agent_command_is_refused`). With `--json`, `rup ping` prints `actor` as `{kind: "ext", id: "ext:<name>", parent: null}`, and as `{kind: "user", id: "you", parent: null}` when `--as` is absent (`cl2_json_prints_who_rup_acted_as`). `--json` before any command other than `ping` exits 2, since `mcp` owns stdout for the protocol. A caller that is below a running Agent stays that Agent whatever `--as` says (the Daemon's rule for `terminal.write` and held actions); no new check.

**CL3 an Ext Actor's reach is the Daemon's, not the caller's.** Given the Daemon's present rules, when an Ext Actor calls `agent.context` or `agent.brief` for an Agent, or `agent.actionHistory`, then each is `FORBIDDEN`, unchanged; every `todo.*`, `pad.*` and `message.*` tool that M1 offers the Daemon accepts from the User is accepted from the Ext Actor, and its Touch names the Ext Actor. Tests: `cl3_an_ext_actor_is_forbidden_what_the_daemon_forbids_it`, `cl3_an_ext_actor_todo_and_pad_calls_touch_under_its_name`. The tests record what the Daemon does today; a method the Builder finds that the Daemon refuses the Ext Actor but `rup help` (CL4) would list is a defect in CL4's list, never a change to the Daemon.

**CL4 `rup help` states who may run what.** On top of I2's text, when `rup help`, `rup --help` or `rup` with no command runs, then it prints to stdout and exits 0 (`rup` with no command also exits 0, replacing the old exit 2) a text with one line per command (`ping`, `mcp`, `signal`, `context`, `help`) and under each the words `User` and `Ext` saying whether a shell outside every Agent (the User) and `--as ext:<name>` may run it: `ping` and `mcp` both; `signal` and `context` neither, because Claude Code runs them as an Agent's hooks and they need an Agent id. It also names `--as`, `--json`, `RUPD_SOCKET` and the default `~/.roundup/rupd.sock`, and says that `rup ping` shows which Daemon answered (`cl4_help_lists_each_command_and_who_may_run_it`). An unknown command still exits 2 with its stderr line and the same text after it (`cl4_an_unknown_command_exits_2_with_the_help`). Policy: the owner's request for "full parity with the MCP" is met by `rup mcp` being the parity surface for both; a command per tool is not built here.


**CL2706a outside callers read Rail names too.** Implements A2703a for the outside-caller surfaces owned by `crates/rup`. Given User and Ext MCP connections to a real isolated Daemon, when each performs the authorized M2706a actions and reads its permitted tree/list results, then the same Rail-name requirements hold before and after rename; CL3's forbidden operations remain forbidden, not widened to obtain a name. Test: `cl2706a_outside_callers_read_current_rail_names` in `crates/rup/tests/cl.rs`. Given the top-level help variants of CL4, then they explain human-readable Rail names and machine ids without changing who may run each command. Test: `cl2706a_help_explains_rail_names` in `crates/rup/tests/cl.rs`.

Checks on main: 1. `scenarios/rup-ext.md`, headings CL2 and CL3 preserve Actor identity and authority. 2. `crates/rup/tests/cl.rs`, `cl4_help_lists_each_command_and_who_may_run_it` preserves help availability. Policy: ping's Daemon pid, socket and Project path are not Agent identities and remain unchanged.

**LK1 a link names one object of one Project.** Implements #2692. A **link** (`GLOSSARY.md`) is `roundup://<kind>/<id>?project=<key>`, `<kind>` one of `pad`, `todo`, `agent`, `workstream`, `terminal`. `<id>` is percent-encoded: a Pad's name (`PadName`), a Todo's number (`TodoId.id`), or an Agent's, Workstream's or Terminal's string id (`NodeId`, `TerminalId`). `<key>` is the Project's key as `project_data` in `crates/rupd/src/data.rs` makes it, `<folder name>-<first 16 hex digits of the SHA-256 of the canonical path>` (percent-encoded), so two Projects with a Pad `notes` give two links. The Daemon's `daemon.ping` reply gains `projectKey` beside `project` (CL1), and `rup ping --json` shows it, so a maker learns the key from the Daemon it asked. Given a Daemon, when `link.read {url}` gets a URL that is not that form (another scheme, an unknown kind, a missing or repeated `project`, a Todo id that is not a whole number, an extra path segment or parameter), then it is `INVALID_PARAMS` whose message names the broken part (`lk1_a_malformed_link_is_invalid_params_naming_the_part`). Given a link whose `project` is not this Daemon's key, then it is `NOT_FOUND` whose message says the link belongs to another Project and names the key it carries, and nothing is read or resolved locally, even when this Project has a same-named Pad (`lk1_a_link_for_another_project_is_not_found_and_never_resolved_here`).

**LK2 `link.read {url}` returns the object's content now.** Contract change (rule 4): one method, `link.read`, served by the Daemon from `crates/contracts`; `rup link read <url>` and the `link_read` tool of `rup mcp` exist by I1 with no `rup` code, and `contracts/generated/` is regenerated. The reply is `{kind, id, …}` with the composed read, never a copy taken when the link was made: a Pad gives its text and revision as `pad.read` does; a Todo gives `todo.get`'s Todo; an Agent gives its Card and digest as `agent.digest` and the Rail row as `rail.tree` give them; a Workstream gives its Rail row and the ids of its children; a Terminal gives the screen text of `terminal.screen`, plain as X16 reads it. Given one of each, when `link.read` runs, then each reply equals the existing method's result for that object (`lk2_each_kind_reads_what_its_own_method_reads`). Given a Pad link read, then the Pad edited, then read again, then the second reply holds the new text and revision (`lk2_a_pad_edit_between_two_reads_shows_in_the_second`). An unknown Pad, Todo, Agent, Workstream or Terminal of this Project is `NOT_FOUND` naming the kind and id (`lk2_an_unknown_object_is_not_found`). `link.read` is read-only, writes no Touch and widens no caller's reach: an Ext Actor reading an Agent link gets what CL3 gives it, `FORBIDDEN` where `agent.brief` is, never more (`lk2_link_read_gives_no_caller_more_than_the_method_it_composes`). Existing `pad.read`, `todo.get`, `terminal.read` are unchanged. Policy: `link.read` adds no send path and no link-making method; the Copy Link surface (#2694) builds the URL from the kind, id and `projectKey`.

**LK3 a link outlives a Daemon restart, a Terminal's does not.** Given a Pad, a Todo, an Agent and a Workstream of a Project and a link to each, when the Daemon is stopped and started again on the same Project folder, then `link.read` of each returns the same content as before (`lk3_pad_todo_agent_and_workstream_links_read_the_same_after_a_restart`). Given a Terminal link read before the restart, then after it `link.read` is `NOT_FOUND` whose message says the Terminal ended with the Daemon, never an empty screen (`lk3_a_terminal_link_fails_loud_after_a_restart`). Policy: this narrows the settled "valid across restarts" for Terminals only, since a Terminal is never stored (`GLOSSARY.md` Terminal). Outside check (not a CI test): a real Claude Code Agent (E10) sent only a Message holding a Pad, Todo or Terminal link and the `rup link read` command quotes the object's current text, including text written after the link was made.

**LK4 a Pad link may name a section.** Work order: [#3193](https://github.com/saadshahd/roundup/issues/3193). Amends LK1's "extra parameter" clause for the `pad` kind only. A Pad link may end in `#<heading>`, the heading text percent-encoded, matched as P15 matches a heading (case, whitespace runs and leading `#` marks ignored; the first match when several). `link.read` of such a link returns the LK2 Pad reply plus `section: {heading, text}`, the heading as the Pad writes it and the text under it up to the next heading of the same or a higher level. A fragment on any other kind is `INVALID_PARAMS` naming the fragment, and a heading the Pad lacks is `NOT_FOUND` naming the Pad and the heading. Tests: `lk4_a_pad_section_link_reads_the_heading_and_its_text`, `lk4_a_missing_heading_is_not_found_and_a_fragment_on_another_kind_is_invalid`. No new method.
