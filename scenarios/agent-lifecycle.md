This specification proposes exact laws for owner review; neither that authorization nor this specification approves the laws. `docs/quality-target.md` is absent at the inspected baseline, so no acceptance is inferred from that path.

The proposed declarations use specification notation whose domains and predicates are defined beside them; formal encoding and checking belong to A3795f after exact-law approval. Policy for the proposed laws: quantify over every finite, well-formed event list and every prefix from the initial state, including refused requests, duplicate results, stale Observations and crash/reopen cuts. An event is well-formed by its payload shape, not by whether its request succeeds; admission guards must reject conflicting requests inside the step. Use Project-scoped Agent identity and its per-Agent Attempt ordinal for every target. Count Terminal-start effects cumulatively through the prefix, not only Terminals still linked in the final state. A starting, resuming, actually live or unresolved possibly-live Attempt occupies its Agent until authoritative ending/refusal establishes that no program remains; Status `done` and a missing acknowledgement do not free that occupancy. These are specification predicates, not new public types or RPCs.

Policy for the specification build: put the quantified domains and predicate definitions beside the four open declarations in `LAWS.bend`, including exact retained-field equality for replay, target equality for stale events, and cleanup authority by mode. Definitions describe the acceptance above/below; do not add a transition implementation, proof body, placeholder proof or import of a nonexistent model. Proposed declarations remain open; this stage claims no lifecycle proof-gate pass. Preserve the existing Message proof gate unchanged.

**A3795b launch once for one admitted Attempt.** State: Project, stable Agent/Workstream identity and Home, persisted next/current Attempt, launch admission, Starting/Resuming/Running facts, Terminal identity and actual liveness, saved conversation/cwd, Status/revision, pending initial Steer, and Worktree ownership. Status `done` alone never proves a Terminal ended. Events: authorized spawn, start Door or resume; launch success/refusal/unknown outcome; current Attempt acknowledgement; Signal/title/Tick/exit tagged with Agent and Attempt. Effects: persist admission and Attempt, prepare launch configuration, request Terminal start, attach/publish its acknowledged identity, submit the eligible initial Steer once, or clean up a refused start. I/O results and clock readings enter as events; the pure step performs no I/O and reads no clock or random source.

Then one admitted launch request emits at most one Terminal-start effect for its allocated `(Agent, Attempt)`, and one Agent has at most one starting, resuming or live Attempt. Duplicate acknowledgements cannot launch again; concurrent starts lose with the existing conflict behavior. Unknown launch completion does not authorize retry while its program may live. A later explicit authorized start/resume allocates a later Attempt; this is not a promise of deduplicating arbitrary fresh RPC requests across crashes. Older Attempt Observations cannot mutate the current Attempt. Planned observer: `a3795b_launch_is_admitted_once`, replaying duplicate start results, both concurrent admission orders and old Observations; retain A7/A14/A20/A22 public-seam coverage rather than duplicating it.

Proposed safety law `a3795b_launch_once`: over every event trace from the initial state, the above per-Attempt start count is at most one and per-Agent live/admitted occupancy is at most one. Fairness/fuel: none (safety). Without the admission and actual-liveness guards, concurrent or repeated completion can start two programs.

**A3795c restart replays retained records without starting a program.** State: stored Rail identities, Home/order/membership, last allocated Attempt, saved conversation and cwd, Worktree path/branch/Base and reservation/provisioning facts; transient Terminal links are distinct from these records. Events: Daemon reopen with stored records, authoritative reconciliation results and explicit later start/resume. Effects: restore the replayed state, clear stale Terminal links and reconcile unfinished owned provisioning; no Terminal start or prompt merely from reopen.

Then the restored durable projection equals replay of the supplied stored records, with only the A8/A12 and G6/G2542d recovery normalization: retain identity, membership, last Attempt, conversation and established Worktree assignment; unlink old-run Terminals; distinguish unfinished fresh provisioning from an enrolled directory. Recovery may request G6's authorized cleanup of never-used fresh provisioning, not deletion of established or enrolled work. Replaying reopen is idempotent on the restored projection. Explicit later resume follows A22 rather than replaying the original prompt. Planned observer: `a3795c_restart_replays_without_launch`, comparing exact retained identities and effects before/after repeated reopen with both Worktree modes and unfinished provisioning.

Proposed safety law `a3795c_restart_is_replay`: for every reachable state, reopening its stored records yields exactly that normalized replay and emits no start or prompt effect. Fairness/fuel: none (safety). Without retained identity and stale-link normalization, restart can attach another Terminal, duplicate work or delete the wrong directory. This law adds no recovery scheduler and changes no Message law.

**A3795d ending fences one Attempt.** State: current Attempt, closing/ended facts, actual Terminal/owned-child liveness, pending launch/input effects, and retained Rail membership. Events: authorized stop/removal/discard, natural exit, shutdown completion/refusal, and delayed Observation or effect completion tagged with its original Attempt. Effects: request the existing clean exit, bounded fallback kill, settle pending input honestly, publish final Status and complete authorized cleanup. Preserve A7's clean-exit sequence and bounds and A17's attached-child guarantee; no vendor command parsing moves outside the Adapter.

Then an ended Attempt admits no new program-input or launch effect, and its later Signals/titles/Ticks/exits cannot change current Status or another Attempt. Already issued physical effects are not promised undone; their results remain attached to the original Attempt. Final bookkeeping and authorized Worktree cleanup remain possible. Stop preserves the Workstream and its children; only explicit removal changes membership under A16. A later authorized resume/start creates a new Attempt of the same Agent, so “ended” is not a permanent ban on that Agent. Planned observer: `a3795d_ended_attempt_is_fenced`, replaying each delayed event after exit and after the next Attempt, checking effect targets and unchanged children.

Proposed safety law `a3795d_no_input_after_end`: for every reachable state and next event, no new input/start effect targets an already ended Attempt, and stale Attempt events cannot mutate its successor. Fairness/fuel: none (safety). Without the Attempt fence, a delayed callback can write to or stop the successor. These safety laws do not claim eventual exit; any later liveness law must name fair completion delivery and finite fuel, plus the failure when either is absent.

**A3795e Worktree cleanup follows ownership and ending.** State: Project, Agent and Worktree path/branch/Base, legacy versus enrolled mode, durable exclusive reservation, provisioning/readiness result, all roundup-managed users, and observed clean/landed facts. Events: explicit enrollment/assignment, reservation commit, preparation/readiness completion, launch/exit, authorized remove/discard, second clean/landed check and crash reconciliation. Effects: persist ownership before branch mutation, prepare/validate through existing Git/Project commands, launch only after readiness, and remove a legacy directory or park/release an enrolled one as authorized.

Then destructive cleanup/release requires the matching recorded ownership and all relevant users ended; an unstarted fresh provisioning record may be rolled back as G6 says. Ordinary removal refuses dirty/ahead work before stopping and rechecks after stop; a changed check keeps the stopped Agent and its files. Explicit discard alone authorizes discarding unlanded Agent work. Enrolled directories and ignored dependency roots survive release, discard, unenrollment and recovery; unknown ownership stays unavailable. Unowned worktrees are untouched. Two active assignments cannot own one enrolled directory, and a Home move never changes the assigned path. The Project's default worktrees-off setting remains unchanged. Planned observer: `a3795e_cleanup_requires_ended_owner`, with both modes, second-check changes, explicit discard, unowned paths and crash cuts; reuse G5/G6/G2542c/G2542d real-Git observers for physical preservation.

Proposed safety law `a3795e_cleanup_only_after_end`: over every trace, each destructive cleanup/release effect names its exclusive recorded owner with no remaining live users and obeys its mode's preservation rule. Its authority is either ordinary removal with both required clean/landed checks, explicit discard for that owner, or G6 rollback of recorded unfinished, never-used fresh provisioning. The rollback exception never applies to an established or enrolled directory. Relevant users include the owning Attempt, its attached children, other roundup-managed Terminals using the directory and preparation commands; unknown liveness does not satisfy ended. Bind both checks to the same recorded owner/path/branch/Base; a failed or changed second check emits no cleanup/release effect. Fairness/fuel: none (safety). Without these guards, cleanup loses live, dirty, unlanded or another owner's work.

## Idle session start (A4452)

Source: Issue #4452, the owner on 2026-10-27: the first prompt of a session is the user's, and roundup passes its own coordination text through the Claude inbox. Implementation: the Issue filed from this specification, blocked by #4452. A4452a–A4452d amend H12, H19, O2 and A22, whose first-prompt clauses they replace there; A4452e is the audit.

**A4452a a new session starts idle.** Given `agent.spawn` or `door.start`, when the Terminal's `SessionStart` arrives, then the Terminal is at an empty prompt with no turn running and the Agent's Status is `idle` (test: `a4452a_spawn_and_door_start_write_no_user_input`, asserting the Terminal received no byte after launch and the argv holds no prompt argument). As amended by A5556a, passive startup guidance and Context never become a wake-up Message for an Agent awaiting user input. An explicit input supplied at start (O2/O8/O9) is written as one Message to its Claude inbox (B50), `delivered` on its transcript receipt (test: `a4452a_coordination_text_reaches_the_inbox`). The inbox write waits for `SessionStart` and never types; a refused or unknown-outcome write settles to the Message states of B3563c, not to Status `error` and not to a typed retry.

**A4452b the user's first prompt is theirs.** Given A4452a's idle session, when the user types a first prompt, then it is the first user message of the conversation, and A9 names the Agent from it, not from roundup's text (test: `a4452b_first_user_message_is_the_users_words`). Policy: H19's gate is not a precondition of A4452a's inbox write, which types nothing. The user's Ask part for a new Door remains typed input under A4452d and waits for H19's gate as H4612a (`scenarios/control.md`) specifies.

**A4452c a Mode sends its saved first prompt.** A Mode is a Workstream holding one saved first prompt (GLOSSARY "Mode first prompt"; U4547a–e in `scenarios/ui-rail.md`): the user's words, set by the user in the App and stored on the Workstream, never written by an Agent. Given a Workstream with an opening prompt, when the user restarts its Door's session, then after `SessionStart` roundup types exactly that text once as the first user message, and sends nothing else as user input (test: `a4452c_restart_sends_exactly_the_saved_prompt_once`). Standing Context reaches the Door passively under A5556a, and a retry after a failed session restart never types it again (A35's restart reservation records the text once). Given a Workstream with no opening prompt, then its restarted session starts idle (test: `a4452c_no_saved_prompt_starts_idle`). Clear and its prompt-delivery test are retired by A32 (#4542); session restart is independent of Clear. The App edits the prompt in the Workstream's settings; a Message, an Agent or an Ask cannot set it (test: `a4452c_only_the_user_sets_the_opening_prompt`).

**A4452d only the user's words are typed.** The Daemon types into an Agent's Terminal only (1) an Ask part (A2698a) or a Steer by the user, byte for byte; (2) A4452c's opening prompt. Given `agent.prompt` by an Agent actor, or a changed Order (O2), then the text goes to the target's inbox as a Message (B50), subject to A5556a's first-input boundary, and no byte is written to its Terminal (test: `a4452d_agent_authored_text_never_types`). Rewind (A35) and resume (A22) start no prompt and type nothing. Restart reads A3795c.

**A4452e the audit of input-writing paths.** Every path below moves to the inbox, stays the user's, or writes nothing, subject to A5556a's prohibition on automatic input before the user's first input; the implementation PR body lists them with the test that holds each:

| Path | Today | After |

## User-started Agents wait for input (A5556)

Acceptance for #5556; amends O3, A4452a/e and the matching A25, U191 and A26 clauses in `scenarios/workstream.md`. This specification delivers acceptance only. Implementation owns `crates/agents/**` and `crates/rupd/**`, with existing lifecycle, Context, Message and reaction seams; no new RPC, Message kind or App surface is prescribed (policy).

**A5556a every user-started Agent waits for the user's input.** Given the user starts a new Workstream's Door, a direct Agent (inside a Workstream or at the Project root), or a Mode without a saved opening prompt, with no supplied prompt or order, when startup completes, then it stays idle and roundup delivers no turn-starting input before the user's first input. A turn-starting input includes any inbox Message, note, coordination text, Steer or reaction delivery, even when it writes no Terminal bytes. Starting a program, `SessionStart`, readiness, selection, a timer tick and an idle event are not user input. The user's submitted Terminal prompt, Ask, Message, Steer or explicitly set order is input; an explicit prompt/order the user supplies at creation is already input. Merely retaining a stored order on resume is not new user input (policy).

Observer: the O3 Daemon test owns the unordered Workstream case; `a5556a_user_started_agents_receive_no_automatic_first_input` in `crates/rupd/src/workstream_door.rs` covers direct Agents at both Homes and a Mode without an opening prompt through the production start/delivery paths. For each, drive `SessionStart`, startup readiness and repeated idle events to completion with no user input; assert zero inbox writes and zero Steers. Submit the user's first input, assert it is delivered exactly once, and that ordinary delivery becomes eligible without another start or an unrelated event. Reuse A4452b's first-user-message observer for exact prompt words and naming rather than duplicating it.

Policy: standing intent/clarification guidance and Context use passive launch instructions or hook context, never an unsolicited inbox Message. O3's generated-guidance observer proves the Door's actions; existing E3/A3516b observers preserve Context identity and role guidance. Role-shared Brief bytes and other P9 cached inputs remain unchanged during an Attempt. The Agent does not need a model turn to discover its instructions.

**A5556b automatic messages cannot wake an Agent awaiting input.** Given any A5556a start with no first user input, when roundup produces a Message, note, Steer or reaction at startup or later, then it delivers no input to that Agent. Audit startup order/Spawn prompt coordination and Context, resume/restart, Agent-authored changed-order instructions, rename notes, Todo ownership/comment notes, peer/route/digest Messages and reaction firings (policy). Pending durable Messages remain readable with their existing identity, authority, batching, Attempt and receipt rules; suppression of startup chatter grants no deletion, fake receipt or replay permission. When the user's first input arrives, eligible pending automatic Messages may follow it, never precede it or become a separate clarification startup turn.

Observer: `a5556b_automatic_delivery_waits_for_first_user_input` in `crates/rupd/src/workstream_door.rs` drives each audited producer through real production routing/stores, using controlled lifecycle/readiness and reaction time. Assert no inbox writes or Steers before user input, retained pending Message identities/states, then normal single delivery and genuine receipt after user input. Startup guidance remains passive after that input and is not replayed as a queued clarification. Include one rename note, Todo comment/ownership note, Agent-authored changed order, peer Message/digest and reaction firing; the implementation's audit lists each producer and the observer that proves its admission. Extend existing Message/reaction observers where they already prove post-input delivery instead of duplicating them. No vendor program, PTY, browser, wall-clock sleep or polling is needed for this admission observer.

**A5556c one cheap guard covers starts and keeps intended input.** Policy: add one parameterized Rust CI guard, `a5556c_start_paths_require_explicit_input`, alongside the production start/admission seam in `crates/agents` or `crates/rupd`, reached by the existing Rust test lane. It exercises production decisions/effects, not source-text patterns or a second test-only implementation. Cases cover a fresh Door, direct Agent at either Home, Mode without an opening prompt, and resume/restart without fresh user input. Each case must reject automatic startup delivery and remain able to accept explicit user input. Drive controlled start/readiness/idle observations and drain scheduled work deterministically; no assertion may pass merely because a background task has not run. Run under five seconds on CI with no subprocess, PTY, browser or real `claude`.

Positive cases preserve the two intentional starts: a Subagent a Door spawns with an explicit Work order receives that order/details once (O8/O9), and a sticky Workstream/Mode whose user-chosen saved opening prompt is resent receives exactly those saved words once (A4452c). A user's explicit creation prompt/order or newly placed Ask is also input and remains deliverable. The guard asserts these admissions; existing O9, A4452c and H4612a observers retain byte/receipt and readiness-gate proof. Demonstrate that allowing O3's default clarification through the production admission makes the guard fail; no recurring test reads this scenario or a report as proof.

Gates derived from this start boundary (policy): P9 asks whether launch or automatic delivery spends a turn before input; O3/A5556a–c observe both delivery sinks. P10 asks whether per-Agent guidance changes the shared Brief; preserve Check 3. P1 asks whether a Message becomes Terminal input or direct Agent access disappears; preserve Check 2. P3 asks whether clarification alone raises `needs-you`; preserve O4. P13 asks whether a reaction spends a turn merely because a new Agent becomes idle; A5556b observes a firing before first input. This is the first journey's Enter → Request boundary (`.agents/data/journey.md`): creating the Workstream waits; the user's request starts the work. No visual change or native Mac observation is required by this specification.
