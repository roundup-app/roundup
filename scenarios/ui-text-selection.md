# Text selection

Work Issue: #2680. Journey stage: Intervene — select and copy Terminal output, then return to the App without a lingering highlight. Terms: Terminal, Bubble, Door, Rail, Shelf, Pad, Todo (`GLOSSARY.md`). U2680 changes no contract, RPC method, App seam command, Token or domain term; #3529 below adds one text-selection Token and retires selection sending.

**U2680a Terminal drags never create browser selection.** Given output containing several words in each of a Bubble Terminal, an Agent's centre-pane Terminal and a Door's Terminal, when the user drags with the primary mouse button, then:

- A drag across output selects nonempty text through the Terminal emulator, while `window.getSelection()` stays collapsed. A double-click on a word selects that word through the emulator and leaves browser selection collapsed. Test: `u2680a_output_drag_and_double_click_use_only_terminal_selection`, parameterised by the three placements.
- Drags starting in each Terminal's insets, the strip below its last drawn row, and the unused part of its final cell or space after its last column never create browser selection, including when they end over output, the Bubble header, the pane outside the Bubble or the Rail. Drags from output to each of those areas, and reverse drags into output, also leave browser selection collapsed. The Bubble header applies only to the Bubble placement; the other cases apply to all three placements. Test: `u2680a_terminal_boundaries_never_create_browser_selection`, parameterised by placement, start and end area. It asserts browser selection only; a drag through blank space need not select Terminal text.

**U2680b one click clears old selections throughout the App.** Given a nonempty emulator selection and a stray noncollapsed browser selection, when the user makes a primary-button click anywhere in the App, then both are empty after that click. Cover an output row, the Terminal insets and bottom strip, a Bubble header and every resize edge, the pane, Rail, Shelf, window title bar, bottom bar and shortcut hint line, including targets whose handlers prevent default or stop propagation. Apply the Terminal cases to all three placements in U2680a. Test: `u2680b_a_click_clears_browser_and_terminal_selections`, parameterised by target and placement; install a browser Range as setup when chrome cannot be selected through gestures. Assert the emulator's selection is empty even if an outside click minimises its Bubble; restore it and assert it stays empty. Test: `u2680b_minimising_and_restoring_does_not_restore_selection`.

An old selection clears without cancelling the clicked control's action or a new drag, double-click or editable-field selection. A new gesture may establish its own selection after the old one clears. U2680a's gesture tests and U2680d's editor tests prove new selection remains possible. Existing U101 tests in `apps/desktop/src/terminal/u101_copy_paste.test.tsx` retain the keyboard-copy contract (policy: keep passing).

**U2680c chrome cannot be selected as browser text.** Given the rendered App, when the user drags across or double-clicks chrome text, then browser selection remains collapsed. Cover the window title, Project and Terminal tabs, the Managed chip where present, Rail rows and buttons, Shelf tabs and section heads, the Todo button and nonediting Todo titles, bottom-bar Terminal action and resource readouts, shortcut hints, overview headings and empty-state titles and hints. Include drags from the centre pane across the Shelf and from the blank Bubbles layer past the last Terminal column into the pane. Test: `u2680c_chrome_drag_and_double_click_leave_no_browser_selection`, parameterised by surface and gesture. A double-click that starts renaming is tested before selecting text within the resulting editor; entering rename remains allowed.

**U2680d editable text remains selectable and copyable.** Given a Pad editor, a text input, a Todo title in edit mode or a name in rename mode, when the user drags across text or double-clicks a word, then that editor holds the selected text; copying it yields that text. For an input, observe `selectionStart`/`selectionEnd`; for a document editor observe its selected text. Clicking elsewhere clears the old selection as U2680b says, without changing the edited value. Test: `u2680d_editors_keep_native_selection_and_copy`, parameterised by the four editor kinds and both gestures. Test: `u2680d_leaving_an_editor_clears_selection_without_changing_text`, parameterised by editor kind. These exceptions apply within chrome and floating editors as well as the centre pane.

## Native text and Terminal interactions (#3529)

Journey stage: Intervene — select/copy output and interact directly with the Agent program. These are implementation obligations, not evidence of delivery by this specification PR. U3529a–d replace the retired selection-send and pane-menu clauses in the amended scenario files, including U3515a/b’s excerpt-picker cases; object-link receivers remain governed by U3515a/b. No new RPC method or App seam command is needed (policy).

**U3529a selection and right-click draw no App controls.** Given a selected Agent Terminal, a Door Terminal or a Bubble Terminal with selectable output, when dragging to select output and then right-clicking within that Terminal, then the selection adds no App dialog, textbox or button, and the right-click opens no App popover or menu, calls no native App context-menu command, sends no Message and performs no clipboard action. The Terminal receives the right-button press and release. One parameterized App-seam CI guard, `u3529a_terminal_selection_and_right_click_stay_in_the_terminal`, planned beside the Terminal tests, mounts the actual App with its normal fake-Daemon seam and injected emulator, establishes the selection through that emulator and dispatches the complete pointer/mouse/contextmenu sequence. Observe controls added by the gesture rather than unrelated existing buttons or xterm's input textarea; record delivery at the emulator host and App calls. Do not test only Pane or a menu model, and do not add separate guards repeating these clauses (policy).

Given editable or selectable text outside Terminals (input, textarea, Pad source/rich editor, rename field, diff source and selectable overview text), when selecting text or right-clicking, then no selection-, paste- or right-click-triggered App floating control appears, and the WebView's own text menu remains available with no App entries. `u3529a_text_keeps_its_webview_menu`, planned in the existing isolated App browser harness, covers these surface kinds and asserts the contextmenu event remains uncancelled by App handlers, native text selection remains usable and zero App menu/Message calls. The browser observer proves event routing, not the native menu's appearance (policy).

**U3529b Terminal gestures belong to its program.** Given a live Terminal in each placement of U3529a, first with mouse reporting off and then with the program enabling it, when primary-selecting, double-clicking, right-clicking, Ctrl-clicking and right-dragging beyond U421's threshold inside the emulator, then xterm handles the gestures as in a plain terminal: selection/copy work when the mode allows them, and enabled mouse reporting delivers the same ordered bytes exactly once. The App neither delays/replays mouse presses to detect Pull nor consumes the gestures to open, restore or move a Bubble. No App replacement menu is installed, including a macOS menu (policy). Observer: `u3529b_terminal_gestures_match_plain_xterm`, planned in the existing isolated headless browser harness, drives identical gestures against the real emulator mounted in the App and a plain instance configured with the same modes; compare selection and input-byte journals, plus unchanged Bubble state and no `terminal.open`. Use a real `rupd` and live shell for the reporting leg, enabling the standard terminal modes explicitly, never parsing vendor-specific output. Wait on emulator output parsing and recorded input acknowledgements, not sleeps (policy).
