# Text selection

Work Issue: #2680. Journey stage: Intervene — select and copy Terminal output, then return to the App without a lingering highlight. Terms: Terminal, Bubble, Door, Rail, Shelf, Pad, Todo (`GLOSSARY.md`). U2680 changes no contract, RPC method, App seam command, Token or domain term; #3529 below adds one text-selection Token and retires selection sending.

**U2680a Terminal drags never create browser selection.** Given output containing several words in each of a Bubble Terminal, an Agent's centre-pane Terminal and a Door's Terminal, when the user drags with the primary mouse button, then:

- A drag across output selects nonempty text through the Terminal emulator, while `window.getSelection()` stays collapsed. A double-click on a word selects that word through the emulator and leaves browser selection collapsed. Test: `terminal/u514_browser.test.ts::u3529b_terminal_gestures_match_plain_xterm_bubble` first drives a real primary drag and double-click, asserting nonempty emulator selection and collapsed browser selection after each gesture, then compares the mode/byte journal below in the same mounted Bubble. `bubbles/u2694e_right_click.test.tsx::u3529a_terminal_selection_and_right_click_stay_in_the_terminal` retains the actual App routing guard for Agent, Door and Bubble placements; all use the same emulator.
- Drags starting in each Terminal's insets, the strip below its last drawn row, and the unused part of its final cell or space after its last column never create browser selection, including when they end over output, the Bubble header, the pane outside the Bubble or the Rail. Drags from output to each of those areas, and reverse drags into output, also leave browser selection collapsed. The Bubble header applies only to the Bubble placement; the other cases apply to all three placements. Test: `u2680a_terminal_boundaries_never_create_browser_selection`, parameterised by the Agent and Bubble placements, looping over start and end area. It asserts browser selection only; a drag through blank space need not select Terminal text.

**U2680b one click clears old selections throughout the App.** Given a nonempty emulator selection and a stray noncollapsed browser selection, when the user makes a primary-button click anywhere in the App, then both are empty after that click. Cover an output row and the Terminal insets in an Agent's Pane, an output row, a Bubble header and a resize edge in a Bubble, and the window title bar, including targets whose handlers prevent default or stop propagation (one chrome handler stops propagation, `u2680b_a_click_clears_browser_and_terminal_selections_stopped_%s`). Other chrome targets share one document-level handler and need no case of their own. Test: `u2680b_a_click_clears_browser_and_terminal_selections`, parameterised by placement, visiting each target with a fresh emulator selection and browser Range in the same mounted App; install a browser Range as setup when chrome cannot be selected through gestures. Assert the emulator's selection is empty even if an outside click minimises its Bubble; restore it and assert it stays empty. Test: `u2680b_minimising_and_restoring_does_not_restore_selection`.

An old selection clears without cancelling the clicked control's action or a new drag, double-click or editable-field selection. A new gesture may establish its own selection after the old one clears. U2680a's gesture tests and U2680d's editor tests prove new selection remains possible. Existing U101 tests in `apps/desktop/src/terminal/u101_copy_paste.test.tsx` retain the keyboard-copy contract (policy: keep passing).

**U2680c chrome cannot be selected as browser text.** Given the rendered App, when the user drags across or double-clicks chrome text, then browser selection remains collapsed. Cover the window title, a Rail row and the Shelf tabs; all other chrome shares the one non-selectable rule. Include drags from the centre pane across the Shelf and from the blank Bubbles layer past the last Terminal column into the pane. Test: `u2680c_chrome_drag_and_double_click_leave_no_browser_selection`, parameterised by gesture, visiting the window title, Rail row and Shelf tabs in the same mounted App. A double-click that starts renaming is tested before selecting text within the resulting editor; entering rename remains allowed.

**U2680d editable text remains selectable and copyable.** Given a Pad editor or a name in rename mode, when the user drags across text or double-clicks a word, then that editor holds the selected text; copying it yields that text. For an input, observe `selectionStart`/`selectionEnd`; for a document editor observe its selected text. Clicking elsewhere clears the old selection as U2680b says, without changing the edited value. Test: `u2680d_editors_keep_native_selection_and_copy`, covering a double-click in the Pad editor and a drag in the rename input. The same `u2680d_editors_keep_native_selection_and_copy` cases then click outside the editor after copying and assert empty selection with the exact edited value unchanged. Under T3779c and #4970 this shared setup replaces `u2680d_leaving_an_editor_clears_selection_without_changing_text`; no selection or source-preservation clause is retired. These exceptions apply within chrome and floating editors as well as the centre pane.

## Read-only native text menus (#5515)

Journey stage: Intervene and Review — select Terminal output and read the resulting text. These clauses extend U3529a/b: Terminals keep the WebView's native text menu, with no App menu. For right-click selection behavior, the clauses below replace comparison with plain xterm's editable-input menu; U3529b's ordered, exactly-once program mouse reporting remains unchanged. This specification delivers acceptance only.

**U5515a Terminal right-click keeps the whole selection.** Given each of an Agent's Terminal, a user-opened Terminal and a Terminal Bubble's body, with mouse reporting off and output containing several words, when the user drags to select several words and right-clicks a word strictly inside that selection, then the exact selected text remains unchanged through the press, contextmenu event and release, and the native menu's selected text is the entire Terminal selection. The right-click target is not editable; selecting only the clicked word or leaving the selection solely in xterm's editable hidden input fails. App handlers leave the contextmenu event uncancelled and add no App menu or floating control. No clipboard write, Terminal input, Message or Agent start occurs merely from selecting or opening the menu. Observer: planned parameterized browser test `u5515a_terminal_right_click_preserves_the_whole_selection` in `apps/desktop/src/terminal/u514_browser.test.ts`, with a separately reported case per placement. Read both emulator selection and the browser text selection made available to WebKit; compare exact Unicode text including spaces and a multi-line case. Record the actual contextmenu target through its composed path, including any Shadow DOM, and reject an editable target or editable ancestor. Assert uncancelled routing and the App call/clipboard journals. Use the real installed emulator inside the App and real browser pointer gestures; dispatching only a synthetic contextmenu event or mounting only a fake emulator cannot prove this clause.

**U5515b right-click outside a Terminal selection is read-only.** Given each Terminal placement in U5515a, first with no selection and then with an existing selection elsewhere in the output, when right-clicking an unselected word, then the event's target is non-editable and App handlers leave the native menu available with no App replacement. Selecting the word under the pointer is permitted; preserving an unrelated selection is not required. If a word is selected, the native menu receives that word's entire text. Observer: planned parameterized `u5515b_terminal_unselected_word_uses_a_readonly_target` in `apps/desktop/src/terminal/u514_browser.test.ts` checks the actual pointer event target, selection exposed to the browser and uncancelled contextmenu event in both initial states. Policy: preserve U3529a's no-menu-side-effect contract, already proved for all placements by `apps/desktop/src/bubbles/u2694e_right_click.test.tsx::u3529a_terminal_selection_and_right_click_stay_in_the_terminal`; do not duplicate that proof here.

**U5515c non-editable App text keeps its selection and menu.** Given selected text spanning several words in a diff, a rendered code block, a Message body or a read-only Pad (source and rendered views where offered), when right-clicking inside the selection, then the browser selection remains exactly the same, the actual event target is non-editable and App handlers leave the native text menu available without opening an App or editor-library floating control. When right-clicking an unselected word, the same non-editable-target and native-menu conditions hold; optional word selection follows U5515b. Observer: planned parameterized `u5515c_readonly_text_preserves_selection_and_native_menu` in `apps/desktop/src/terminal/u514_browser.test.ts` exercises every listed surface in the actual App, with real pointer gestures and composed-path inspection, and reads exact selection text and uncancelled contextmenu routing. This includes text inside editor-library Shadow DOM rather than testing only its host. Policy: audit all other non-editable selectable text surfaces on the implementation head in source and rendered use; record each surface, observer and result on #5515, fix either fault in the same implementation PR and extend this parameterization for any additional affected surface. A missing fixture is an observer gap to repair, not grounds to omit Messages or read-only Pads.

**U5515d editable fields and Terminal input keep working.** Given an editable Ask bar, Pad source/rich editor, rename field, input or textarea with selected text, when right-clicking within that selection, then the full selection survives and the target remains editable with uncancelled native-menu routing. Observer: extend `apps/desktop/src/terminal/u514_browser.test.ts::u3529a_text_keeps_its_webview_menu` to use a complete real pointer gesture and assert exact selection preservation, retaining its no-App-control assertions; do not add a second proof of the same editable-field behavior. Given each Terminal placement after opening and dismissing its text menu, when typing ordinary text, composing non-Latin text through IME, copying a multi-word selection with ⌘C and pasting with ⌘V, then typed/composed text reaches the program exactly once, composition's intermediate text is not sent, copy writes the whole selected text once and paste reaches the program once with its existing bracketed-paste behavior. Observer: planned `u5515d_terminal_input_survives_readonly_context_menu` in the same browser test file, parameterized by placement, observes the emulator input and App write/clipboard journals after menu dismissal; include composition start/update/end and the committed input sequence. Policy: browser composition events prove event handling, not a real macOS input method; U5515e supplies the native observation. Keep the existing clipboard, write-order and program-mouse proofs in `terminal/u101_copy_paste.test.tsx`, `terminal/u12_typing.test.tsx` and `terminal/u514_browser.test.ts::u3529b_terminal_gestures_match_plain_xterm_bubble` (paths relative to `apps/desktop/src/`). Extend those existing proofs only for a behavior not already asserted; do not weaken or duplicate them. Standard mouse reporting still delivers the same ordered bytes exactly once, including right-button press/release and Ctrl-click, with no vendor-specific App interpretation.

**U5515e WebKit supplies the read-only Mac menu.** Policy, native observer: on the implementation commit, the loop owner selects several words in each Terminal placement and each U5515c surface, right-clicks inside the selection and confirms that WebKit offers its read-only selected-text menu. Dismiss the Terminal menu, type text, commit text with a real IME, use ⌘C on a multi-word selection and ⌘V to paste, and confirm the program receives exactly the intended text. Record the commit, placements, actions and any failure on #5515. Linux/headless browser results prove selection and event targets, never native menu entries or service actions. The implementation run's required Mac observation names what to build from which commit, these steps and which result passes or fails this clause; this specification run requests no Mac observation.

Policy: obtain the read-only menu from WebKit's own text behavior. Do not construct an App menu, filter menu entries in native Rust, or globally make Terminal input read-only. Preserve editable fields' full native menu, U3529's ban on App text menus, and existing selection-clearing behavior for ordinary primary clicks outside a selection. The implementation chooses its repair after reproducing the behavior; this spec prescribes no hidden-input workaround, DOM clone or synthetic production gesture.
