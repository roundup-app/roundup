# Control channel

Module: `crates/agents` (`agent.prompt`, `agent.interrupt`), `crates/rup`. Ids: every `H` heading in the file.

How the Daemon sends a prompt to an Agent, and ends its turn, without timed keystrokes. Read `docs/control-channel.md` and `spikes/hooks-permission/REPORT.md` (the recorded behaviour of Claude Code 2.1.287; "H1" below cites its findings, the scenario itself being retired) first. Tests run with a fake `claude` that calls the hook commands in its `--settings` file and reacts to the bytes written to its Terminal the way the report records; no test needs the real one. These ids continue the retired series in `scenarios/decisions.md`.

**H11 a Steer waits for a readiness Signal, not for a delay.** Given a running Agent, when `agent.prompt {id, text}` is called, then nothing is written to its Terminal until the Agent's Kind is `idle` from a `SessionStart` or `Stop` Signal, and then `text` is written once, as one bracketed paste (`ESC[200~`, the text, `ESC[201~`) followed by `\r` in the same write. A test with an injected clock that never advances still delivers the text. The call returns `null` when the Agent's `UserPromptSubmit` Signal arrives (H1: it names the text). For a user's Steer whose text starts with `/`, acceptance also includes a `SessionStart` Signal (even `idle` to `idle`), a change of the Adapter's session identity, or a Signal changing the Kind, observed after that Steer's write in the same Attempt; observations preceding the write or from another Attempt do not count. A command need not submit a model prompt. Without any qualifying acceptance within the bound the test names (default 10 s), the call fails with `NOT_ACCEPTED`: the Terminal's input line keeps the text, nothing is sent again, and the error names the Agent. An Agent whose Kind is not `idle` when the call arrives fails at once with `BUSY` naming the Kind; an Agent that has ended fails with `NOT_FOUND`. `agent.prompt` is called by the user or by an Agent for one of its Subagents; a call for any other Agent is `FORBIDDEN`. The text is one Steer, or the batch of every pending Message of B30 joined by blank lines; either way H11 types it once. The write path is one Rust function, `Agents::prompt(id, text) -> Result<(), PromptError>` with the variants `Busy`, `NotAccepted` and `NotFound`, which the RPC method and the mailbox series' in-process delivery both call; no other code writes a prompt. Contract change: `agent.prompt {id, text}` returns `null`, and the errors `BUSY` and `NOT_ACCEPTED`. The slash-command acceptance and its regression observers are specified in A2698a (`scenarios/ask-bar.md`); ordinary instructions still require `UserPromptSubmit`. Naming amendment A2703a: `NotAccepted`, `Busy` and `NotFound` identify the Agent by its current Rail name, or the gone-Agent fallback when no node remains; the NotAccepted wording otherwise stays unchanged. Observer: `a2703a_prompt_errors_use_rail_names` in `crates/agents/tests/scenarios/steer.rs`. Acceptance timing and A2698a are unchanged.

**H12 the first prompt goes through the same path.** Given `agent.spawn {cwd, prompt}` (A4), then the prompt is written by H11 once H19's gate opens (the first `SessionStart` Signal and the first star title have both arrived), and the one-second `SUBMIT_DELAY` and the "typed at the first idle" wording are gone. A4 says "the prompt is sent as a Steer (H11) once H19's gate opens". When the Steer fails, `agent.spawn` has already returned, so the Agent's Status is `error` with the label `prompt not accepted`; nothing is dropped silently. No Message is typed before the first Steer is written: until then `Agents::prompt` answers `BUSY` and the Message waits (`h12_a_message_waits_until_the_first_steer_is_accepted`). The test uses an injected clock that never advances and the fake `claude`.

**H13 an Interrupt is a call with an observable result.** Given an Agent whose Kind is `working`, when `agent.interrupt {id}` is called, then the Daemon writes `ESC` to its Terminal and returns `null` when the Agent's title Observation changes from the spinner glyph to the star (A2) within the bound the test names (default 5 s, H1: about 12 bytes after the Esc); its Kind is then `idle`. Without that change it fails with `NOT_ACKED`, the Kind is left as it was, and nothing else is written. An Agent that is `idle`, `done` or `error` fails with `NOT_RUNNING` and no byte is written. H1 records that no hook event reports an Esc, so the acknowledgement is the title and not a hook; this is the one place the Adapter reads the screen for a result, and it is the title string A2 already reads. `agent.interrupt` is called by the user or by an Agent for one of its Subagents, as in H11. Contract change: `agent.interrupt {id}` returns `null`, and the errors `NOT_RUNNING` and `NOT_ACKED`.

**H14 an Agent asks the user through the MCP server. (retired)** Retired by A3564a–f (`scenarios/native-questions.md`): an Agent asks the user with Claude Code's native `AskUserQuestion`, answered in its Terminal; roundup offers no question tool.

**H14b the Brief tells Agents how to ask. (retired)** Retired by A3564a–f (`scenarios/native-questions.md`): the Brief names `AskUserQuestion` for the user and `message_send` for another Agent (A3564c); it carries no question-form rules.

**H15 a tool-use loop spawns a bounded number of hook processes.** Given a fake `claude` that runs a loop of 100 tool uses, calling the hook command for `PreToolUse` and `PostToolUse` around each, when it runs against a Daemon with the built `rup`, then every `rup signal` answers (exit 0, so 200 calls) and, with the loop opened by a `UserPromptSubmit` and closed by a `Stop`, a subscribed client sees the Agent's Kind go `working` and then `idle` and rail.tree reports `idle` (a Daemon that answers but drops the Signals sends neither event and fails), every `rup signal` runs at most one OS thread (the runtime of `crates/rup/src/main.rs` is single-threaded; observed with `/proc/<pid>/task` on Linux and `ps -M -p <pid>` on macOS, sampled every 5 ms from the spawn while the process waits on a Daemon that never answers, so a 4 ms run cannot slip past; the most threads seen counts, and a test that never read one sample fails), and `just perf` reports `hook_loop_ms`, the wall time of the 200 calls (two per tool use), as a limit-only metric (AGENTS.md rule 7, R13 for load) with its limit in `docs/perf.md`. Which events leave `STATE_EVENTS` is not chosen by hand: the test replays each `spikes/hooks-state/log*.jsonl` and `D2` with one event type removed at a time, comparing the whole Status, and an event whose removal leaves every Status unchanged is removed from `STATE_EVENTS` and from the settings (the list is `STATE_EVENTS` in `crates/agents/src/claude_code/launch.rs`); the measured outcome is that none is, so `STATE_EVENTS` keeps all nine. There is no CPU-time clause: a cut in CPU time needed an event to leave `STATE_EVENTS`, and none can. The same test asserts that a lost Signal (the Daemon not answering) makes `rup signal` print one line on stderr and exit 1 (never 2, as A4 says), and that a Signal which changes the Kind reaches a subscribed client as a Status event within 30 s (`BOUND` in `crates/rup/tests/e2e/daemon.rs`, the wait every e2e test uses) (the keystroke-to-render budget is rule 7's `just perf-keystroke`; a wall-clock assertion of it in a test would measure the CI runner).

**H16 no keystroke is ever a silent fallback.** Given the control channel above, when a Signal the Daemon waits for is lost (H11's `UserPromptSubmit`, H13's title), then the Daemon returns the typed error and writes nothing else to the Terminal; it never retries a prompt by another path, never types an answer into a dialog, and never calls `terminal.write` on behalf of an Agent. The test greps `crates/agents/` and `crates/rupd/` for a second caller of `terminals.write` (the one in H11, the one in H13, the user's direct Terminal input, and A7's exit keys) and fails on any other. An Agent's own message, MCP call or Signal text never reaches the Terminal as input, except as the text of a Message the mailbox series delivers through H11's write path after its Route rules (`Agents::prompt`); that is the only way a Message becomes input.

**H17 a lost Interrupt acknowledgement is loud.** The title is the one screen read left in the control channel (H1 records that no hook event reports an Esc), so it is the one known limitation, and it fails loudly. Given an Agent whose title never changes after the Esc (the fake `claude` ignores it), when `agent.interrupt {id}` is called, then after the bound the call fails with `NOT_ACKED` naming the Agent, the Daemon logs one line on stderr, the Kind is unchanged, no second Esc and no other byte is written, and a later title change to the star is still folded as A2 says. The test never advances a clock to pass; it names the bound.

**H19 the first Steer waits until the input takes a submit.** On Claude Code 2.1.296 a `\r` that arrives right after the first `SessionStart` is dropped: the pasted text stays unsent in the input and H12's Steer ends `error` with `prompt not accepted`, while the same bytes sent later are accepted at once. Given `agent.spawn {cwd, prompt}` (A4), then the first Steer (H12) is written only after both the first `SessionStart` Signal and the Agent's first title Observation with the star glyph (A2) have arrived, whichever comes last; no byte is written before, and H11 and H12 hold except for that timing (one write, one bracketed paste and `\r`, accepted on `UserPromptSubmit`). A Steer to an Agent that has already been idle (H11) is not delayed. When the star never arrives, the first prompt is not accepted, the bound running from the first `SessionStart` (H16: nothing else is written, no retry). Tests: `h19_*` in `crates/agents/tests/scenarios/steer.rs`, using a fake `claude` that drops every `\r` written before it has set its star title, as 2.1.296 does, and keeps the text in its input; the earlier fake accepted any `\r`, so the test fails on today's `main`. `agent.spawn` with a one-line prompt and with a multi-line prompt (the input shows `[Pasted text #1 +4 lines]`) both end `idle` with no later Enter. The real-`claude` observation is the O6 check in `just app` (#389), not a test; whether versions before 2.1.296 accepted the Steer at `SessionStart` stays unrecorded.

**H20 a Steer is the user's typed instruction, never bare pasted text.** On Claude Code 2.1.296 a bracketed paste of several lines (a Work order with limits has at least four) reaches the model as `<pasted_content id="…">…</pasted_content id="…">` with no typed text around it, and the model, told to follow instructions inside a pasted block only where the user's own typed text asks, declines the order; a three-line Clarification Steer arrived as plain text and was followed (which rule wraps a paste, line count, list or length, is unchecked and the fix does not depend on it). Given `Agents::prompt(id, text)` for any `text`, one line or many, that carries a Work order or a user's Message (a prompt that holds only pushed Digests is typed with B33's status lead instead), then H11's single write is `LEAD_IN`, typed outside the paste markers, then `ESC[200~`, the text, `ESC[201~` and `\r`; `LEAD_IN` is the constant `Follow this instruction: ` in `crates/agents/src/claude_code/mod.rs`, so the model's first user message holds typed text that asks it to act on the pasted block. H11 and H16 hold: one write, one submit, accepted on `UserPromptSubmit`, no second path and no retry. Tests: `h20_*` in `crates/agents/tests/scenarios/steer.rs`, using a fake `claude` that records the bytes of each write: `h20_four_line_steer_has_typed_lead_in` (the write starts with `LEAD_IN` before `ESC[200~` and holds exactly one paste and one `\r`), `h20_one_line_steer_has_typed_lead_in` (the same for one line), and `h20_spawn_order_with_limits_is_one_write` (an Order with `limits` spawns through the same path, one write). The real-`claude` observation is in #692, not a test: the same spawn `{kind: "work", ask: "Reply with the single word ready. Use no tools.", limits: ["edit no file"]}` ends with the Agent replying `ready`, read from the session transcript under `~/.claude/projects/`; when it still declines, the lead-in is reworded under this id, and the Steer is never split across writes (H11).

R2965 observer requirement for H11: `h11_an_agent_that_ends_while_a_steer_waits_is_not_found`: observe prompt bytes reaching a real PTY before stopping its Agent and observing the pending caller's refusal. An event-only fixture cannot reveal bytes failing to reach the waiting vendor before exit.
