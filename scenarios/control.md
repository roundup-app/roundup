# Control channel

Module: `crates/agents` (`agent.prompt`, `agent.interrupt`, `ask_user`), `crates/rup`. Ids: every `H` heading in the file.

How the Daemon sends a prompt to an Agent, ends its turn, and lets an Agent ask the user, without timed keystrokes. Read `docs/control-channel.md`, `docs/permission-decisions.md` and `spikes/hooks-permission/REPORT.md` (the recorded behaviour of Claude Code 2.1.287) first. Tests run with a fake `claude` that calls the hook commands in its `--settings` file and reacts to the bytes written to its Terminal the way the report records; no test needs the real one. These ids continue the Decisions series in `scenarios/decisions.md`.

**H11 a Steer waits for a readiness Signal, not for a delay.** Given a running Agent, when `agent.prompt {id, text}` is called, then nothing is written to its Terminal until the Agent's Kind is `idle` from a `SessionStart` or `Stop` Signal, and then `text` is written once, as one bracketed paste (`ESC[200~`, the text, `ESC[201~`) followed by `\r` in the same write. A test with an injected clock that never advances still delivers the text. The call returns `null` when the Agent's `UserPromptSubmit` Signal arrives (H1: it names the text). For a user's Steer whose text starts with `/`, acceptance also includes a `SessionStart` Signal (even `idle` to `idle`), a change of the Adapter's session identity, or a Signal changing the Kind, observed after that Steer's write in the same Attempt; observations preceding the write or from another Attempt do not count. A command need not submit a model prompt. Without any qualifying acceptance within the bound the test names (default 10 s), the call fails with `NOT_ACCEPTED`: the Terminal's input line keeps the text, nothing is sent again, and the error names the Agent. An Agent whose Kind is not `idle` when the call arrives fails at once with `BUSY` naming the Kind; an Agent that has ended fails with `NOT_FOUND`. `agent.prompt` is called by the user or by an Agent for one of its Subagents; a call for any other Agent is `FORBIDDEN`. The text is one Steer, or the batch of every pending Message of B30 joined by blank lines; either way H11 types it once. The write path is one Rust function, `Agents::prompt(id, text) -> Result<(), PromptError>` with the variants `Busy`, `NotAccepted` and `NotFound`, which the RPC method and the mailbox series' in-process delivery both call; no other code writes a prompt. Contract change: `agent.prompt {id, text}` returns `null`, and the errors `BUSY` and `NOT_ACCEPTED`. The slash-command acceptance and its regression observers are specified in A2698a (`scenarios/ask-bar.md`); ordinary instructions still require `UserPromptSubmit`.

**H12 the first prompt goes through the same path.** Given `agent.spawn {cwd, prompt}` (A4), then the prompt is written by H11 once H19's gate opens (the first `SessionStart` Signal and the first star title have both arrived), and the one-second `SUBMIT_DELAY` and the "typed at the first idle" wording are gone. A4 says "the prompt is sent as a Steer (H11) once H19's gate opens". When the Steer fails, `agent.spawn` has already returned, so the Agent's Status is `error` with the label `prompt not accepted`; nothing is dropped silently. No Message is typed before the first Steer is written: until then `Agents::prompt` answers `BUSY` and the Message waits (`h12_a_message_waits_until_the_first_steer_is_accepted`). The test uses an injected clock that never advances and the fake `claude`.

**H13 an Interrupt is a call with an observable result.** Given an Agent whose Kind is `working`, when `agent.interrupt {id}` is called, then the Daemon writes `ESC` to its Terminal and returns `null` when the Agent's title Observation changes from the spinner glyph to the star (A2) within the bound the test names (default 5 s, H1: about 12 bytes after the Esc); its Kind is then `idle`. Without that change it fails with `NOT_ACKED`, the Kind is left as it was, and nothing else is written. An Agent that is `idle`, `done` or `error` fails with `NOT_RUNNING` and no byte is written. An Agent with an open Decision is Interrupted by the same call and H7(b) clears the Decision. H1 records that no hook event reports an Esc, so the acknowledgement is the title and not a hook; this is the one place the Adapter reads the screen for a result, and it is the title string A2 already reads. `agent.interrupt` is called by the user or by an Agent for one of its Subagents, as in H11. Contract change: `agent.interrupt {id}` returns `null`, and the errors `NOT_RUNNING` and `NOT_ACKED`.

**H14 an Agent asks the user through the MCP server.** Given an Agent and its `roundup` MCP server (A11), when the Agent calls the tool `ask_user {question, answers}`, then the tool does not return, a Decision opens whose `tool` is `ask_user` and whose `args` are the JSON of `{question, answers}`, the Kind is `needs-you` (H2's rules for one Decision per Agent and for `replaced` hold), and when the user answers through `decision.answer {id, answer, note, proof}` the tool returns `{answer, note}` and the Decision clears with outcome `answered`. User decision (2026-10-12, the Pad `workstream-view-drafts`): an answer shows its tradeoff and a sketch of what it builds, and the user may add a note or write their own answer. The names are those of Claude Code's `AskUserQuestion` options, which Agents already write.
- **The question.** `question` is a non-empty text of up to 600 characters; policy (the Brief, H14b): its first line is the decision and at most 3 lines of context follow.
- **The answers.** `answers` holds zero to four objects `{label, description, preview?}`. `label` is 1 to 200 characters and no two labels are equal; `description` is 1 to 400 characters; `preview` is up to 4000 characters of Markdown and may be absent. A label that ends in ` (recommended)` marks the recommended answer; at most one does, else `INVALID_PARAMS`. Zero answers is an open question: the Decision shows the question and a note field (U406) and only an own answer settles it. Any other shape, a bare text instead of an object included, is `INVALID_PARAMS` and opens nothing. The tool's schema is the derived schema of the params type (M4).
- **The reply.** `decision.answer` takes `answer` (a text or null) and `note` (a text of up to 2000 characters, default empty). For an `ask_user` Decision `answer` is one of the labels, and `note` is the user's text, maybe empty, and the tool returns `{answer: <label>, note}`. `answer: null` is the user's own answer and needs a non-empty `note`, and the tool returns `{answer: null, note}`. A label not in the list, a null `answer` with an empty `note`, or a `note` past its bound is `INVALID_PARAMS` and leaves the Decision open. For a permission Decision `answer` is `allow` or `deny` as H3 says and `note` must be empty, else `INVALID_PARAMS`. H4 and H21 hold unchanged: the user's `proof`, or an Agent whose Reach holds the asker (H21), answers it with one of the labels or with its own note.
- **Unchanged.** Where the Decision first appears (the user's Inbox at once, or after the escalation chain of the mailbox series) is that series' rule and not this one; a permission Decision never climbs (H10). When the Agent ends the tool call fails and the Decision clears as in H6. `ask_user` is allowed by the settings that already allow `mcp__roundup__*` (A11), so its call raises no permission dialog. H21's Message to the Door carries `args` cut at 200 characters as before. `decision_answer` in `rup mcp` takes the same `answer` and `note`. Contract change (rule 4): the tool's params and return, `decision.answer`'s `answer` and `note`, with `crates/contracts`, `contracts/generated/`, `crates/agents/src/decision.rs`, `crates/rup/src/mcp.rs` and `apps/desktop/src/decisions/` changed together.

Tests (existing `h14_*` in `crates/agents/tests/scenarios/decisions.rs`, `crates/rup/tests/mcp.rs` and `crates/contracts/src/decision.rs` change to the new shape): `h14_ask_user_returns_the_label_and_the_note`, `h14_an_own_answer_returns_null_and_the_note`, `h14_an_own_answer_with_no_note_is_invalid_params`, `h14_zero_answers_opens_an_open_question`, `h14_a_text_answer_a_duplicate_label_two_recommended_or_an_overlong_field_is_invalid_params`, `h14_a_permission_decision_takes_no_note`, `h14_ask_user_schema_is_the_contract_schema` (M4), and `h21_a_door_answers_a_childs_ask_user_with_a_label_and_a_note`.

**H14b the Brief tells Agents how to ask.** Given any Agent's E1 Brief, then `crates/agents/src/claude_code/brief.rs` holds these rules for `ask_user`, each a line of the Brief: the question is one line, the decision; the context is at most 3 lines, only what the pick turns on, and `reduce` runs on it (Q6); the answers are 2 to 4, the recommended one first and its label ending ` (recommended)`; a label is at most 5 words; a description is the tradeoff, what the pick gains and what it costs; a preview is the smallest `show-me` sketch of what the pick builds, and is required when the user has not met its terms; an open question the user answers in their own words takes no answers; the Agent never asks what it can answer by looking, and never asks `you` in a Message what `ask_user` asks. Test: `h14b_the_brief_carries_the_ask_user_rules` in `crates/agents/tests/launch.rs` asserts each line by its text. Q1, Q6 and B24 hold.

**H15 a tool-use loop spawns a bounded number of hook processes.** Given a fake `claude` that runs a loop of 100 tool uses, calling the hook command for `PreToolUse` and `PostToolUse` around each, when it runs against a Daemon with the built `rup`, then every `rup signal` answers (exit 0, so 200 calls) and, with the loop opened by a `UserPromptSubmit` and closed by a `Stop`, a subscribed client sees the Agent's Kind go `working` and then `idle` and rail.tree reports `idle` (a Daemon that answers but drops the Signals sends neither event and fails), every `rup signal` runs at most one OS thread (the runtime of `crates/rup/src/main.rs` is single-threaded; observed with `/proc/<pid>/task` on Linux and `ps -M -p <pid>` on macOS, sampled every 5 ms from the spawn while the process waits on a Daemon that never answers, so a 4 ms run cannot slip past; the most threads seen counts, and a test that never read one sample fails), and `just perf` reports `hook_loop_ms`, the wall time of the 200 calls (two per tool use), as a limit-only metric (AGENTS.md rule 7, R13 for load) with its limit in `docs/perf.md`. Which events leave `STATE_EVENTS` is not chosen by hand: the test replays each `spikes/hooks-state/log*.jsonl` and `D2` with one event type removed at a time, comparing the whole Status, and an event whose removal leaves every Status unchanged is removed from `STATE_EVENTS` and from the settings (the list is `STATE_EVENTS` in `crates/agents/src/claude_code/launch.rs`); the measured outcome is that none is, so `STATE_EVENTS` keeps all nine. There is no CPU-time clause: a cut in CPU time needed an event to leave `STATE_EVENTS`, and none can. The same test asserts that a lost Signal (the Daemon not answering) makes `rup signal` print one line on stderr and exit 1 (never 2, as A4 says), and that a Signal which changes the Kind reaches a subscribed client as a Status event within 30 s (`BOUND` in `crates/rup/tests/e2e/daemon.rs`, the wait every e2e test uses) (the keystroke-to-render budget is rule 7's `just perf-keystroke`; a wall-clock assertion of it in a test would measure the CI runner).

**H16 no keystroke is ever a silent fallback.** Given the control channel above, when a Signal the Daemon waits for is lost (H11's `UserPromptSubmit`, H13's title), then the Daemon returns the typed error and writes nothing else to the Terminal; it never retries a prompt by another path, never types a `y` or `n` into a dialog, and never calls `terminal.write` on behalf of an Agent. The test greps `crates/agents/` and `crates/rupd/` for a second caller of `terminals.write` (the one in H11, the one in H13, the user's Takeover path, and A7's exit keys) and fails on any other. An Agent's own message, MCP call or Signal text never reaches the Terminal as input, except as the text of a Message the mailbox series delivers through H11's write path after its Route rules (`Agents::prompt`); that is the only way a Message becomes input.

**H17 a lost Interrupt acknowledgement is loud.** The title is the one screen read left in the control channel (H1 records that no hook event reports an Esc), so it is the one known limitation, and it fails loudly. Given an Agent whose title never changes after the Esc (the fake `claude` ignores it), when `agent.interrupt {id}` is called, then after the bound the call fails with `NOT_ACKED` naming the Agent, the Daemon logs one line on stderr, the Kind is unchanged, no second Esc and no other byte is written, and a later title change to the star is still folded as A2 says. The test never advances a clock to pass; it names the bound.

**H19 the first Steer waits until the input takes a submit.** On Claude Code 2.1.296 a `\r` that arrives right after the first `SessionStart` is dropped: the pasted text stays unsent in the input and H12's Steer ends `error` with `prompt not accepted`, while the same bytes sent later are accepted at once. Given `agent.spawn {cwd, prompt}` (A4), then the first Steer (H12) is written only after both the first `SessionStart` Signal and the Agent's first title Observation with the star glyph (A2) have arrived, whichever comes last; no byte is written before, and H11 and H12 hold except for that timing (one write, one bracketed paste and `\r`, accepted on `UserPromptSubmit`). A Steer to an Agent that has already been idle (H11) is not delayed. When the star never arrives, the first prompt is not accepted, the bound running from the first `SessionStart` (H16: nothing else is written, no retry). Tests: `h19_*` in `crates/agents/tests/scenarios/steer.rs`, using a fake `claude` that drops every `\r` written before it has set its star title, as 2.1.296 does, and keeps the text in its input; the earlier fake accepted any `\r`, so the test fails on today's `main`. `agent.spawn` with a one-line prompt and with a multi-line prompt (the input shows `[Pasted text #1 +4 lines]`) both end `idle` with no later Enter. The real-`claude` observation is the O6 check in `just app` (#389), not a test; whether versions before 2.1.296 accepted the Steer at `SessionStart` stays unrecorded.

**H20 a Steer is the user's typed instruction, never bare pasted text.** On Claude Code 2.1.296 a bracketed paste of several lines (a Work order with limits has at least four) reaches the model as `<pasted_content id="…">…</pasted_content id="…">` with no typed text around it, and the model, told to follow instructions inside a pasted block only where the user's own typed text asks, declines the order; a three-line Clarification Steer arrived as plain text and was followed (which rule wraps a paste, line count, list or length, is unchecked and the fix does not depend on it). Given `Agents::prompt(id, text)` for any `text`, one line or many, that carries a Work order or a user's Message (a prompt that holds only pushed Digests is typed with B33's status lead instead), then H11's single write is `LEAD_IN`, typed outside the paste markers, then `ESC[200~`, the text, `ESC[201~` and `\r`; `LEAD_IN` is the constant `Follow this instruction: ` in `crates/agents/src/claude_code/mod.rs`, so the model's first user message holds typed text that asks it to act on the pasted block. H11 and H16 hold: one write, one submit, accepted on `UserPromptSubmit`, no second path and no retry. Tests: `h20_*` in `crates/agents/tests/scenarios/steer.rs`, using a fake `claude` that records the bytes of each write: `h20_four_line_steer_has_typed_lead_in` (the write starts with `LEAD_IN` before `ESC[200~` and holds exactly one paste and one `\r`), `h20_one_line_steer_has_typed_lead_in` (the same for one line), and `h20_spawn_order_with_limits_is_one_write` (an Order with `limits` spawns through the same path, one write). The real-`claude` observation is in #692, not a test: the same spawn `{kind: "work", ask: "Reply with the single word ready. Use no tools.", limits: ["edit no file"]}` ends with the Agent replying `ready`, read from the session transcript under `~/.claude/projects/`; when it still declines, the lead-in is reworded under this id, and the Steer is never split across writes (H11).
