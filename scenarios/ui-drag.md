# UI: one drag and drop look

Module: `apps/desktop` (shared Sortable and its callers). Work order: [#3540](https://github.com/saadshahd/roundup/issues/3540). This specification claims no implementation, native compatibility or performance result.

**U3800a one drop look.** Given the App with reorderable Todos (including children), Rail items, Agent-owned Todo leaves and Shelf Pads, when a row is dragged to an allowed gap, then release commits exactly that gap's order or `{id, parent, index}` once; preview commits nothing. Escape before release preserves the original order and parents, calls no mutation and restores focus to the initiating row/handle; another drag still works. A press on non-control row content remains U3789a selection, never Open. A grip press released with less than 4 CSS px travel focuses the grip without opening, renaming, completing or reordering; it calls no mutation. Interactive children retain their own actions and do not start a drag. Extend `u3800a_one_drag_fixture` for grip-only activation and retained child actions; extend the existing connected consumer cases for selection/Open separation. Assert these behaviors in `u3800a_one_drag_fixture` in `apps/desktop/src/ui/u484_browser.test.ts`, using the installed shared Sortable, real pointer input and caller-recorded commits/actions. Consumer regression observers remain in force (policy).

Policy, rendered observer: throughout the drag the source row remains in its original list position with its content visible and a solid `--accent` outline. Exactly one empty dashed `--accent` slot, the height of that row, marks the release destination. It is an outline with no filled row wash. Its left edge equals the border-box left edge a row at the projected depth will have after release, within 1 CSS px: include the list's base inset and one shared Token indent per depth, not the list's outer left edge. Its right edge equals that destination row's right edge within 1 CSS px; its top marks the selected sibling gap. A nested slot aligns to the destination parent's child depth, including the first child of an empty parent. Root, child, grandchild, outdent and clamped-depth previews use the same validated destination as the commit. An invalid destination shows no allowed landing slot. Compare the preview and accepted row after release on the same fixture; slot boxes/paint are critic observations, never UI test assertions. There is no live swapping of rows, flickering between destinations, duplicate landing marker or jump back to an old destination. Only space for the slot opens/closes; unrelated rows and controls remain stable. The critic compares source, slot, depth and release against the owner's Solo sidebar reference described in #3540. Looks are never unit-test assertions.

Policy — handles (#4535), visibility amended by U5147e: every draggable content row has a rightmost grip, shown during hover, focus and selection, with existing Token spacing/colour and a minimum D6 hit area. A disabled/non-draggable row exposes no inert drag control. Each grip is a separately focusable, accessibly named control identifying its item; it is distinct from Open, checkbox, disclosure and quick actions. Only the grip starts a pointer drag. Bind it through the installed drag library's own handle API (`useSortable`'s `handleRef` for the current dnd-kit); do not add a second sensor, synthetic events, DOM clones or hand-written pointer lifecycle. Register/unregister each handle with its own row and preserve keyboard focus after accepted refetch or cancellation. U361's required-control exception permits the added grip without hiding an existing completion/disclosure/Open path; unrelated menu and Rail quick actions remain intact. U155's historical “no handle” and row-button pointer activation clauses are replaced only by these grip clauses; its keyboard neighbour moves, accepted-refetch, failure and cancellation contracts remain.

Policy, motion: the slot's entrance and exit provide spatial feedback, using one interruptible ease with existing `--duration-crossfade` (120 ms) and `--easing-out`. Retarget from the displayed state on rapid gap changes or cancellation; no queued animation, spring or bounce. Use CSS transform/opacity for the visual effect, with slot geometry available for hit testing immediately; do not animate layout properties on every pointer move. Reduced motion and keyboard preview are immediate. The implementation updates the affected rows of `docs/motion.md`; this supersedes only drag-preview/displacement and release motion in U152/U155/U3010c and the Rail drag policy, not unrelated Todo insertion, completion or keyboard neighbour-swap motion.

**U3800b files dropped on the centre.** Given two eligible centre targets and the fake App's existing `onFileDrop`, when `over` enters the first and then the second, then only the target currently under the reported CSS coordinates is active; `leave`, release or selection of a different pane clears that state. A `drop` with absolute paths including `/Users/me/My Pics/it's.png` delivers the identical ordered paths to that target's handler once, never the other handler, and starts no row reorder. Empty paths and an ineligible target deliver nothing. Assert active target identity, cleared state, exact paths and handler/commit counts in `u3800a_one_drag_fixture`, using the real file-drop routing with the fake App event seam rather than directly calling the target handler.

Other targets have no drop decoration. **U3800c keyboard reorder.** Given the separately named right-edge Sortable grip of U3800a focused (focus shows it, U5147e) and fresh A,B,C order, when Space lifts A, ArrowDown moves its destination one sibling down and Space drops, then the rendered and committed order are B,A,C, exactly one commit occurs and focus remains on A. The same pointer destination gives the same order. Escape after moving the keyboard destination leaves A,B,C unchanged with no commit and focus on A. Assert in `u3800a_one_drag_fixture`. Existing Todo neighbour-swap shortcuts remain available (policy). Space on a completion checkbox still toggles completion, and Return on a Todo row or its Open arrow still opens; neither lifts a drag. Policy — keyboard preview uses the same depth/inset slot as pointer preview, updates immediately and disappears after drop/Escape; the critic compares the preview destination with the committed row. The handle remains reachable by Tab even when the row is unselected, and after drop/cancel focus returns to that item's grip, never body.

Given U535's P with children P1/P2, Q and R fixture, when Space lifts P2, ArrowDown moves below Q, ArrowRight selects Q as parent and Space drops, then one move `{id: "P2", parent: "Q", index: 0}` occurs; ArrowLeft before dropping instead gives `{id: "P2", parent: null, index: 2}` and focus stays on P2. ## Scope and retained acceptance

Native file events remain the source of real paths, not a competing internal reorder engine. No unrelated UI redesign, new RPC, App seam command, contract or Token is commissioned. If a necessary public interface changes, apply the Contract recipe and update every caller in the same PR.

Policy: U3800a/c replace U484's flat pointer/keyboard/cancel proofs and preview-displacement appearance; U3800b replaces their covered native-file coexistence proof with path delivery. U535 is narrowed to its remaining tree-specific proofs: exact parent/index, first-child/clamp, descendant rejection, in-place no-op, depth keys, post-drag click suppression, preview cleanup and flat/tree callback exclusivity. Keep U484's external target and scroll/stop cases. All other acceptance remains, including U522's outside-Rail cancellation, conflict handling, daemon-gone behavior, edge scroll and button exclusion.

Policy: the selected library owns drag lifecycle, hit tests and scrolling. U484/U535/U485's prior dnd-kit selection and library-keyboard-sensor requirement are superseded only where necessary for the measured replacement. A library-documented keyboard alternative may adapt focused-row commands to the same validated move callback, with equivalent semantics and focus retention; no second pointer/collision/scroll engine. U535's historical no-consumer-migration limit does not restrict this work order.
