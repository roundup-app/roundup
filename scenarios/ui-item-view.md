**U4698a Todo and Pad open filling the centre pane in the Drawer.** Given a Project and either item kind with no saved size choice, when an item is explicitly opened, then the existing Drawer opens maximised. “Maximised” for these two kinds means the centre pane's box **before opening**: between the Rail and any visible right-side Shelf, below any shared window header. The Rail and right side keep their size, visibility and operability. With no right side it reaches the window's right edge. The underlying centre stays mounted, hidden and outside Tab navigation while covered; the right side stays reachable. A previously maximised Shelf retains its own state on close; the item does not silently restore, close or resize that Shelf to make space. Policy: the rendered observer judges these boundaries in both right-side states, and restoration of the pre-open layout. Test `u4698a_filled_drawer_preserves_other_surfaces` in `apps/desktop/src/drawer/` asserts mounted identity, reachability and independent Shelf state, without geometry assertions.

Given either item kind open, when the user clicks its existing expand icon or presses plain `M` with focus in the Drawer outside an editor/menu/dialog, then it toggles between this centre-filling state and U430's side Drawer at the existing width (`--drawer-span`, currently the larger of `--drawer-min-width` and the Shelf span plus `--space-5`, constrained by the window), keeping the same item, editor and draft. In the side state U430 still narrows the centre so input beside the Drawer remains usable; clicking there does not close it. `M` in a field remains text. There is exactly one expand control, named `Restore` when maximised and `Maximise` when minimised; no Bubble is created. Policy — keep it in the existing Drawer head for the opening-state slice; U4698b/d moves that same control to the toolbar's trailing end, removing its head placement in that change. `Close` remains separate. Test `u4698a_one_control_and_m_keep_the_item_and_draft` in `apps/desktop/src/drawer/`, parameterised over Todo/Pad and pointer/key, asserts control count, state, item/editor identity, exact draft, typing guard, zero Bubble opens and no item read/write/comment calls caused by a size toggle.

Given a minimised Todo or Pad, when it closes and another of the same kind opens, or the Project reloads, then the saved choice returns without a size animation; other kinds and Projects retain their own choice. Existing saved true/false U4458 choices remain valid; missing records default to maximised for Todo/Pad only. Work orders and unknown kinds retain U4458's default and span. Test `u4698a_choice_survives_reopen_and_is_scoped` in `apps/desktop/src/drawer/` covers both stored booleans, missing records, reload, kind and Project boundaries. Retain Esc, Close, prevent-scroll focus return, Help/switcher layering, and U5's existing motion/reduced-motion policy; no new animation is specified (policy; Regression holders below). Design-critic observer: Shared rendered observer, capturing both kinds filled/minimised, right side open/closed and close/restore.

**U4698c a Todo has an optional priority.** Work order: [#4695](https://github.com/roundup-app/roundup/issues/4695). This is the contract prerequisite for #4696's meta row and #4697's Activity. It refines the existing priority acceptance without changing U4698d/e's presentation. Tests below are planned acceptance, not implementation evidence.

**Priority** (`Priority`, `priority`): a Todo's optional urgency: Low, Medium, High or Urgent. Unset is distinct from Low. Policy: use a closed enum whose wire values are exactly `low`, `medium`, `high`, `urgent`; unset serializes as null. Add this term to `GLOSSARY.md` with user label Priority in the implementation PR, alongside the contract and all callers.

Given a caller of `todo.create` or `todo.update`, including an Agent through the Todo MCP tools, when it sends the following JSON, then the resulting priority follows this table. Test `u4698c_priority_round_trips_and_old_data_loads` in `crates/todos/src/tests/priority.rs`, table-driven over all four values and unset, asserts create/update replies, `todo.get`, `todo.list`, `todo.created` and `todo.updated`, plus close/reopen persistence. Deserialize a pre-field Todo JSON as unset as well as exercising old request JSON. No default priority is invented.

| Input | `todo.create` | `todo.update` |
|---|---|---|
| `priority` omitted | Unset | Keep the stored value, including when another field changes |
| `priority: null` | Unset | Clear the stored value |
| `priority: "low"`, `"medium"`, `"high"`, `"urgent"` | Set that value | Set that value |

Given a Todo with priority, when title, body, completion/reopening, owner, blockers, Home or order changes without a priority patch, then priority is retained; another Todo is never changed by the priority patch. Test `u4698c_other_mutations_keep_priority` in `crates/todos/src/tests/priority.rs` exercises these existing public methods, including an Agent-owned Todo updated by the user. Policy: priority changes no ordering, blocking, ownership, Home, hand-off eligibility or automatic Agent scheduling. Extend T30's existing last-change test to include an actual priority change: `updated_at` equals that Change's recorded time; a priority no-op leaves it unchanged.

Given create or update with a priority outside the closed set, when parsed, then the call returns INVALID_PARAMS and leaves every Todo, History, Event and Touch unchanged.
