# UI: Todo and Pad item views

Module: `apps/desktop`, with the Todo priority contract in `crates/contracts` and `crates/todos`. Ids: U4698a–U4698e. These are acceptance specifications, not claims that the implementation or tests exist. Tests named below are planned unless listed under Regression holders. No runtime code or script is introduced by this specification.

## Shared rendered observer (policy)

Every scenario below uses this observer, including the priority's eventual presentation. Implementation starts with the views as rendered on its main baseline, then repeats the same actions/data on its head in an isolated headless agent-browser session and fresh profile. Use dark mode at **1280×820 and 1512×950**, overriding the journey's single-viewport default for this work. Use `tree-40`, extended through the existing harness with 200-character titles, long Unicode names, missing owner/estimate/priority, a done Todo, 30 blockers, a 10,000-word Pad, headings nested through the supported levels, a wide table with a 500-character unbroken cell, and empty/3/200-comment threads. Include Agent status details folded and open. No personal browser, desktop or OS input.

The design critic judges reading measure, type hierarchy, common edges, toolbar stickiness, wrapping, contrast and targets; behavior tests assert actions, roles, identities and calls, never CSS, boxes or exact copy. Read `window.__checks()` at rest, while editing, with menus open and with complete rejected-save/send failure text visible on the densest seed. Run `just capture U4698a U4698b U4698c U4698d U4698e` as each implementation supplies its observers; leave paired base/head PNGs, videos and Check readings under `artifacts/ux/<id>/`, with immutable SHAs and matching fixture metadata, as `.agents/data/harness.md`, heading “Captures”, requires. Commit no image/video. A missing capture setup is an observer failure, not evidence of acceptance. The independent critic must pass; the user reports their own read on the Mac, with no extra native gate for Chromium-observable behavior.

Journey stage: **Review** (`.agents/data/journey.md`). The final integration observer, planned `u4698e_reopen_result_from_workstream` in `apps/desktop/src/todos/`, uses the real Daemon and existing fake-vendor tool seam: create resulting Todo and Pad work in a Workstream, open it from that Workstream, edit/save as the user where permitted, comment on the Todo, close/reopen the Project and read back the same identities and saved work. Assert persisted values through the Daemon; a seeded success is not proof of the journey. Preserve the accepted journey's other stages. Missing behavior follows the journey's next-gap rule, with a bounded Issue rather than expanding this specification's scope.

**U4698a Todo and Pad open filling the centre pane in the Drawer.** Given a Project and either item kind with no saved size choice, when an item is explicitly opened, then the existing Drawer opens maximised. “Maximised” for these two kinds means the centre pane's box **before opening**: between the Rail and any visible right-side Shelf, below any shared window header. The Rail and right side keep their size, visibility and operability. With no right side it reaches the window's right edge. The underlying centre stays mounted, hidden and outside Tab navigation while covered; the right side stays reachable. A previously maximised Shelf retains its own state on close; the item does not silently restore, close or resize that Shelf to make space. Policy: the rendered observer judges these boundaries in both right-side states, and restoration of the pre-open layout. Test `u4698a_filled_drawer_preserves_other_surfaces` in `apps/desktop/src/drawer/` asserts mounted identity, reachability and independent Shelf state, without geometry assertions.

Given either item kind open, when the user clicks its existing expand icon or presses plain `M` with focus in the Drawer outside an editor/menu/dialog, then it toggles between this centre-filling state and U430's side Drawer at the existing width (`--drawer-min-width`, constrained by the window), keeping the same item, editor and draft. In the side state U430 still narrows the centre so input beside the Drawer remains usable; clicking there does not close it. `M` in a field remains text. There is exactly one expand control, named `Restore` when maximised and `Maximise` when minimised; no Bubble is created. Its final location is the toolbar's trailing end (U4698b/d), never a duplicate in the Drawer head. `Close` remains separate. Test `u4698a_one_control_and_m_keep_the_item_and_draft` in `apps/desktop/src/drawer/`, parameterised over Todo/Pad and pointer/key, asserts control count, state, editor identity, exact draft, typing guard and zero Bubble opens.

Given a minimised Todo or Pad, when it closes and another of the same kind opens, or the Project reloads, then the saved choice returns without a size animation; other kinds and Projects retain their own choice. Existing saved true/false U4458 choices remain valid; missing records default to maximised for Todo/Pad only. Work orders and unknown kinds retain U4458's default and span. Test `u4698a_choice_survives_reopen_and_is_scoped` in `apps/desktop/src/drawer/` covers both stored booleans, missing records, reload, kind and Project boundaries. Retain Esc, Close, prevent-scroll focus return, Help/switcher layering, and U5's existing motion/reduced-motion policy; no new animation is specified (policy; regression holders 1–2). Design-critic observer: Shared rendered observer, capturing both kinds filled/minimised, right side open/closed and close/restore.

**U4698b Pad and Todo share document reading rules and the exact toolbar.** Given a Pad open, then its vertical order is large title, formatting toolbar, body. Pad ownership, export, delete, saved/conflict/failure feedback remain reachable through existing actions without becoming another document heading (policy). Given either item view, the title, toolbar content, body and subsequent Activity/composer share one document left edge inside a centred reading column. At sufficient width the body measure is **60–75 characters**, selected as a shared reading-width Token (target 68ch); a narrower minimised Drawer uses its available width with Token gutters instead of forcing horizontal page scrolling. Tables and code may scroll inside their own blocks, never the whole view. This allows a reading-width Token to be declared in the implementation; no raw measure may be scattered in component styles (policy).

Policy — type and spacing: use existing `--font-ui`, `--text-pad-heading` for the large bold title and first body heading, `--text-pad-subheading` for the next heading, `--text-title` for lower headings/body, `--text-small` for metadata and toolbar labels, `--font-mono` for code, and `--line` for body line height. Use `--space-6` for document gutters where available and major section separation, `--space-5` between title/meta/toolbar/body sections, `--space-4` between paragraphs and `--space-2` within chips and toolbar groups. At the side width gutters may reduce to `--space-4`. Shared Tokens own weight and any needed reading-measure role; apply the user's interface scale. Links are underlined; headings, lists, quotes, code, rules and tables have distinct reading structure. Tables have visible Token borders; cells wrap prose and break unbroken words, with local horizontal scrolling when columns cannot fit. Never clip cell contents or let text paint over another cell. The critic, not Vitest, judges these clauses with the shared worst-case fixtures and both widths.

Given an editable Pad or Todo body, when the user invokes a formatting action, then its selection receives that operation and saved/reopened Markdown retains it. Test `u4698b_toolbar_edits_and_reopens_each_format` in `apps/desktop/src/pads/`, parameterised over both bodies and all eleven operations, asserts resulting document semantics and saved source through the existing editor/App seams. The buttons' accessible names are exactly **Bold**, **Italic**, **Inline code**, **Link**, **Bullet list**, **Numbered list**, **Checklist**, **Heading**, **Quote**, **Code block**, **Table**. Heading may offer heading levels; Link and Table may offer their parameters. Policy: these are the entire formatting set in the toolbar and insertion menus; add no underline, strike, image, highlight, alignment, colour or other format. Existing source containing unsupported constructs remains source-preserved under P2544. Read-only Agent-owned Pads retain ownership rules rather than becoming writable from a toolbar action. Test `u4698b_read_only_toolbar_cannot_write` in `apps/desktop/src/pads/` asserts no write before ownership transfer.

Policy — the toolbar is thin, uses named icon buttons, stays visible while the body scrolls and carries U4698a's single expand control at its right end. At narrow width its formatting portion may scroll horizontally while expand remains reachable; no action disappears or wraps over another. Body text and long titles wrap, including 200-character titles; Pad title wrapping supersedes U29's Drawer-only ellipsis, retaining Shelf ellipsis. Keep U20/U36/U147/P2544/P3557 source preservation, ownership, autosave, revision/conflict and failure recovery. Shared reading styles have one owner reused by Todo and Pad, rather than copied rules (policy). Design-critic observer: Shared rendered observer, title/body/table/toolbar at rest, scroll and source-edit/conflict states.

**U4698c a Todo has an optional priority.** Given an old Todo or old caller omitting priority, when it is loaded, created or updated, then missing priority remains valid and unset. Given a caller of `todo.create` or `todo.update`, including the Todo MCP tools, when it sets priority to Low, Medium, High or Urgent, then that value persists and reads back after restart; omission on update leaves it unchanged and explicit null clears it. The wire values are `low`, `medium`, `high`, `urgent`, or null; any other value is invalid and changes nothing. Every accepted actual priority change uses existing Todo update/Event/Touch and history rules; a no-op creates no duplicate history. Old history with no priority still loads. Tests `u4698c_priority_round_trips_and_old_data_loads`, `u4698c_invalid_priority_changes_nothing`, `u4698c_priority_history_records_actual_changes` in `crates/todos/`, and `u4698c_mcp_sets_priority_as_the_authenticated_actor` in `crates/rup/`, assert persistence, omission/null, migration, bounds, attribution and existing Event sequencing through the public seams. Contract policy: regenerate contracts, update every caller and add the priority term to GLOSSARY.md in that implementation, with no unrelated Message/Route/Held/Takeover change. Design-critic observer: Shared rendered observer when U4698d exposes the field, all four values and unset; this contract-only slice makes no new webview claim.

**U4698d Todo header, title and meta form one document.** Given an open Todo, then top-to-bottom presentation is header bar, large editable title, one meta row, sticky formatting toolbar, body, Activity, comment composer (policy, Shared rendered observer). The header breadcrumb reads Project then Todo title. Previous Todo, Next Todo, copy-id chip and More actions trail it. Prev/next follows the originating list's visible Todo order in its current scope, does not wrap, disables the missing endpoint and, with no originating list, uses the current Home's Todo order. Switching opens the selected Todo through the existing open path with one read Touch, retains the previous item's drafts and creates no writes from navigation. Copy-id copies `#<id>` only and performs no Todo mutation. More actions contains existing delete, hand-to-Agent and owner actions, preserving their refusal/confirmation/Undo rules. Tests `u4698d_header_navigates_and_copies_without_mutating` and `u4698d_actions_keep_existing_authority` in `apps/desktop/src/todos/` assert destinations, calls, clipboard content and authority using the existing App seam.

Given the meta row, when the user changes state or priority, then state uses existing completion/reopen authority and priority uses U4698c's update/clear behavior on this Todo. `Blocked by n` counts its open blockers; `Blocking n` counts open Todos it directly blocks. Each opens the existing blocker menu with the appropriate relationship direction, including zero; changing a relation updates that relation once and never reverses it. Owner and estimate retain existing editing, assignment and empty states; unset priority offers setting a value or leaving it unset. Test `u4698d_meta_edits_the_selected_todo_and_relations` in `apps/desktop/src/todos/`, covering done, blocked, missing owner/estimate, all priority values, zero and 30 blockers, asserts resulting fields, offered relationships and calls.

Policy — meta order is state, priority, Blocked by n, Blocking n, owner, estimate, as icon+label chips in one horizontal row. At side width the row scrolls locally instead of stacking into a grid; each action stays keyboard reachable. The title wraps and remains editable with existing save/draft/conflict rules. No second title line, dependency grid, scattered delete action or second expand control. Creator, Home/Move and provenance remain discoverable in More actions or Activity; these are relocated, never discarded. Reuse U4698b's reading style and exact eleven-button toolbar, sticky below the header. Tests for formatting are owned by U4698b, not duplicated here. Design-critic observer: Shared rendered observer, long breadcrumb/title, done state, 30 blockers and all menus; it judges alignment, hierarchy, stickiness and overflow.

**U4698e Activity and comments read as one thread.** Given an open Todo with comments and history, when Activity loads, then comments and changes appear together oldest first by recorded time, with stable ties (history before comments, then each source's sequence/id); old changes without timestamps retain sequence order before timed entries and do not invent a time. Each comment names its Actor and relative time; each change names its event and Actor where existing attribution requires it. Existing read/comment/history APIs, unread boundaries, Inbox destinations and acknowledgement guards remain authoritative. Test `u4698e_activity_merges_sources_and_keeps_read_boundaries` in `apps/desktop/src/todos/` asserts order by source identity, attribution and read call bounds, including old untimed history and equal times.

Given more than 20 Activity entries, when the view opens, then the newest 20 are exposed and one older-entries disclosure reveals the remainder in that same order without losing status-fold state or sending a comment. Entries hidden behind that line are not acknowledged as viewed history until exposed; comments retain their existing open-thread read rules. With zero entries the composer remains available. Test `u4698e_older_activity_unfolds_without_mutation` in `apps/desktop/src/todos/`, using zero, 3 and 200 comments mixed with changes, asserts revealed identities, preserved expansion and calls. Given an Agent's status comment, when its summary is activated, then only its details fold; plain user text remains plain and Agent Reply focuses this Todo's composer. Reuse the existing U3775 observer rather than duplicating its parser proof; test `u4698e_reply_keeps_the_todo_destination` asserts recipient and focus after unfolding older Activity.

Given the last composer with text, when Enter (not composing) or the Comment button submits, then it sends exactly once to this Todo; Shift+Enter adds a line and Cmd/Ctrl+Enter keeps its existing submit meaning. Blank/pending submits do nothing. Failure keeps exact text and an actionable visible cause; successful acknowledgement consumes only its submitted revision. Navigation/reopen restores drafts under P11 without sending them; a new comment announces once without stealing focus or replaying opening comments. These are retained U3741/U3776/U2773/P3579 behaviors, not new duplicate tests. Test `u4698e_composer_keeps_existing_send_and_draft_contract` in `apps/desktop/src/todos/` covers the integrated composer after rearrangement, reusing those fixtures and removing overlapping old assertions when the same break is proved there.

Policy — Activity is a heading below the body, with quiet event dots, event text, middle-dot separator and relative time; comments occupy the same aligned reading column with author/time and wrapped text. Agent work remains a summary line folding open to detail. The composer comes last, an Actor mark beside one wide rounded field and its submit action. Long words break; no nested scroll box for each comment and no grid of history cards. New arrivals preserve existing no-animation and focus behavior. The Shared rendered observer judges empty/3/200 entries, folded/open older entries and Agent details, a long unsent draft and rejected send, plus D2/D5/D6. The real-Daemon Review journey observer above is the final persisted-work check.
