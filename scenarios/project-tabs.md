# Project tabs: the header is a strip of open Projects (#653)

Module: `crates/desktop` (S8–S10) and `apps/desktop` (the webview; U179–U186). Ids: S8, S9, S10, U179, U180, U181, U182, U183, U184, U185, U186, U382. Decided by the user (2026-10-10, #653): "roundup" leaves the header; the header becomes horizontal tabs, one per open Project, each with only the Project's name and one circle; no boxes, borders or underline; counts stay off the tab. Chromium shows the webview against the fake App (as U131 does), so the observer is a rendered page, never a native Mac capture (#389).

The App holds several Daemons, one per open Project, so the App seam and the Daemon's lifetime change, not only the header. This is a contract change (rule 4, the Contract recipe of `.agents/builder.md`): S8 changes every caller in one PR, and `GLOSSARY.md` holds **Project tab** and **Tab mark** (added with this file). Ids stay per Project (G7); nothing in `contracts/` changes and no Daemon method changes. Native macOS window tabs are not used: Tauri 2.12.1 does not expose AppKit's `NSWindowTab.accessoryView`, so a native tab cannot carry the circle and the strip lives in the webview.

Engineering calls, each made here so the implementation run asks nothing:

- **Several Daemons.** The App keeps a map from Project path to its running Daemon and socket (S1's rules per entry). A Daemon is the Project's; closing its tab ends it (S8).
- **Keys.** `⌘1`/`⌘2` stay the focus keys (U41) and `⌥1..9` reach the Terminal (U12); the tab strip takes neither. Tabs take `⇧⌘[` and `⇧⌘]` (previous and next, the Safari, Ghostty and Warp convention) and `⇧⌘J`. `⌘J` stays inside the open Project, because its count is the one the user sees. `⌃Tab` is not taken (the HIG lists it as a focus move).
- **Overflow.** Names shorten with `…`, then the strip scrolls; a hidden tab with a circle is still shown at the strip's edge (U184).
- **Order.** Tabs keep the order they were opened in, and a new tab goes last; no key or drag reorders them, and attention never does (wireframes decision 3).
- **The name.** Stored per Project path in the App's data folder beside `recent_projects` (S10); no better owner exists, because the Daemon would need a Project it has not opened and the webview's saved state (U100) is per window.
- **A restart** reopens the Projects that were open, in their order, with the one that was open last selected (S10, U186).

## App seam, several Projects (S8, S9, S10)

The App seam table of `scenarios/app.md` is replaced by this one. Commands S6 added (`recent_projects`, `claude_binary`) and the permissions in S1 are unchanged.

| Webview calls | Arguments | Result |
|---|---|---|
| `projects` | none | `[{name, path, running}]`, the open Projects in tab order; `running` is false once that Daemon exited (S3) |
| `open_project` | `{path}` (absolute) | `{name, path}`; the Project joins the end of `projects` |
| `close_project` | `{path}` | `null`; the Project's Daemon ends and it leaves `projects` |
| `rename_project` | `{path, name}` | `{name, path}` (S10) |
| `rpc` | `{path, method, params}` | the method's JSON result, unchanged |
| `subscribe` | `{path, channel}` | `null`; then every Event of that Project's Daemon is sent on the channel |
| `recent_projects`, `claude_binary` | none | as S6 |

`project` no longer exists. A call that names a path that is not open fails with `CONFLICT` saying so, and `rpc` and `subscribe` never wait (S2). `daemon-exited` carries `{path, code: number | null}`.

The `rpc` and `subscribe` invocations in `crates/desktop/tests/app.rs` (521, 546, 600, 621, 637, 704, 836, 1039) gain `{path}`. Given an open Project, when the webview calls `open_project {path: <another directory>}`, then the App starts a second `rupd <path> --attached` exactly as S1 does, on a socket path unique to it, with `RUPD_SOCKET` set in its environment only, so Terminals, hooks and MCP servers of one Project never reach the other's Daemon. Then `projects` lists both, in the order they were opened. `open_project` for a path whose Daemon runs returns its `{name, path}` and starts nothing (`CONFLICT` is gone), and for a path whose Daemon exited it reopens as S5 says. `rpc {path, …}` and `subscribe {path, …}` reach only that Project's Daemon: a `todo.create` on one is never seen by the other's `todo.list` or channel. `close_project {path}` closes that Daemon's stdin, so the Daemon and its Agents and Terminals stop (S3), and the other Project's Daemon, Agents and channel go on; a path that is not open is `CONFLICT`. When one Daemon exits on its own, `daemon-exited {path, code}` names it and the other keeps answering. When the App exits, every Daemon's stdin closes (S3). Tests (`s8_`) use a fake `rupd` and run two real in-process Daemons on temp sockets: two open paths, isolation of `rpc`, of events and of sockets, `close_project` of one, one exit among two, and a path that is not open.

**S9 the webview's permissions do not grow.** Given S8's commands, then the webview is granted exactly the list S1 names, and nothing in the App seam lets the webview choose a socket or a Daemon binary. U449 permits only the current-window title, drag and zoom operations (`window-bar:allow-set-window-title`, `window-bar:allow-drag-window`, `window-bar:allow-zoom-window`); none accepts a window label. The exact permission list remains policy; its copied-config test is retired under AGENTS.md rule 10.

**S10 names and the open list survive a restart.** Given the App's data folder (S6), then:
- `rename_project {path, name}` for an open Project stores `name` for that path, trimmed, and returns `{name, path}`; afterwards `projects`, `open_project` and `recent_projects`' consumers show it. A name of 1 to 40 characters is stored; an empty or all-space name removes the stored name, so the Project is named after its folder again (S1); a longer name or one with a line break is `INVALID_PARAMS` naming the limit. A path that is not open is `CONFLICT`. The stored name is per path, so the same folder always comes back with its name.
- The open Projects, in order, are stored in the data folder when `open_project` or `close_project` succeeds. At launch the App starts a Daemon for each stored path that is still a directory, in order, one at a time, then for `roundup <project>` when given (selected last: it ends the list, or keeps its place when already there). A path that no longer is a directory is dropped. A Daemon that fails to start leaves its Project in `projects` with `running: false`, so the tab shows U25's state and `Reopen`; it never stops the others from opening or the App from launching.
- A failed write of the names or the list never fails the call (S6). Tests (`s10_`) use a temporary data folder and a fake `rupd`: rename and restore, the limit, the empty name, the stored order after open and close, a vanished folder, one failing Daemon among three.

## The strip (U179–U186)

> Narrowed by U440 to U443: a tab is a bordered box on a ruled header and the Tab mark is a dot; "no box, border, background or underline" no longer holds.

**U179 the header is the strip.** Given the App, then the header holds no `roundup` text and no Project text outside the strip. It reads, left to right, one Project tab per entry of `projects` in that order, then a quiet `+` (`--grey`; its `aria-label` is `Open a folder`) at the end of the strip, which ends at the Shelf's leading edge (U369) and, with the Shelf closed, at a `Show work items` icon button (U370) at the header's trailing edge, which opens the folder chooser as U2's `Choose folder…` does and then `open_project`. A Project tab is its name and one Tab mark, and nothing else shows until hover (U182): no count, no path, no icon, no box, border, background or underline; only space separates tabs. The tab of the open Project is in full ink and the others are `--grey` (`docs/design-system.md` Tokens); every tab keeps `--grey`'s 4.5:1 contrast (U4). Each tab is `role="tab"` in a `role="tablist"`, the open one has `aria-selected="true"`, and the Mark has a text `aria-label` (`Needs you` or `Error`) so colour is never the only cue. With no Project open (U2), the header is the `+` alone, and U2's first-run text reads `then the header reads` as this sentence says. Tests (`u179_`) in `apps/desktop/src/header/u179_strip.test.tsx`: the order, no `roundup` in the header, the two inks, no border or background on a tab, the roles, the `+`, and the first run. Narrows U2 (its header sentences), U25 and U37 (`roundup   <Project name>` becomes the strip; see U185), and the header-text assertions change with them: the six in `apps/desktop/src/app/u2_first_run.test.tsx` (lines 52-154); the design critic judges the header's contrast, so `apps/desktop/src/app/u4_contrast.test.tsx` is cut (AGENTS.md rule 10).

**U180 the Tab mark.** Given the Kinds of the Agents in a Project (`rail.tree`, as U10 counts), then its tab shows one mark: `◉` in red Ink when any Agent has Kind `error`; else `●` in amber Ink when any has Kind `needs-you`; else nothing. `●` is the Rail's own needs-you Glyph. `◉` is not the Rail's error Glyph `✕`: the ring is the tab's own shape for error, so the mark stays distinct from `●` without colour. A plain ring `○` is never a Tab mark, because `○` means working in the Rail (U4). A Door counts as an Agent as U10 does; Terminals never count (U164). The mark is one character, the same size on every tab, and never carries a number. Every open Project is counted, not only the one on screen, from its own Daemon's `rail.tree` and `rail.changed` (U179's webview subscribes to each Project: `subscribe {path}`). The mark clears at once when the Agent's need is answered (`PRINCIPLES.md` P3) or its Kind changes; there is no snooze and no dismiss. The ambient mark never animates; the one ~400 ms pulse of a Kind becoming `needs-you` (`docs/motion.md`, "Needs-you arrival") is unchanged and runs on the Rail row only. Tests (`u180_`): error over needs-you, needs-you alone, working and blocked and idle and done give nothing, a Terminal gives nothing, a background Project's mark, the mark clearing when the Agent's Kind changes, the characters and Inks, no number.

**U181 clicking a tab.** Given two or more open Projects, then a click on a tab's name makes that Project the open one: the Rail, the Shelf and the pane show that Project (each Project keeps its own selection, collapsed Groups and drawer state, as U100 keeps them), and no call is made to a Daemon that is not shown. The other Project's Daemon, Agents and subscription keep running, so its Tab mark stays current. A tab is `aria-busy="true"` until its Project's Rail is current (its Daemon answered the first `rail.tree` and the tab shows the Tab mark of that answer) or connecting to its Daemon failed, then `aria-busy="false"`; nothing else about the tab shows it. A click on the already open tab changes nothing. A click on a Tab mark, wherever it is, makes that Project the open one and selects its most urgent Agent exactly as `⌘J` does in the open Project (U30: `error` before `needs-you`, the oldest Status `since` first, the row scrolled into view and any collapsed Group above it expanded); it is one click, not two. Neither click animates (`docs/motion.md`). Tests (`u181_`): switching shows the other Project's Rail, state kept per Project, a click on the open tab, a mark click selecting the right Agent in a background Project, no call to the Project that is hidden, `⌘J` after the switch using the new Project's order, a tab busy until its Project's Rail is current, a tab not busy once connecting to its Daemon failed.

**U182 hover tells the count.** Given a tab that shows a Tab mark, when the pointer rests on the tab, or focus is on it from the keyboard (U3528, `ui-pointer-focus.md`; focus draws no ring), then a tooltip (`role="tooltip"`, linked with `aria-describedby`) reads `<n> need you; <m> have errors.` with `n` the Agents of Kind `needs-you` and `m` those of Kind `error` in that Project, both always shown, as the wireframe does, so `0 need you; 1 have errors.` and `2 need you; 0 have errors.` are both real. It is `--grey` text, never Ink, appears with no animation and goes when the pointer or focus leaves. A tab with no mark shows no tooltip. The Dock badge (U10) counts the Agents of Kind `needs-you` or `error` in every open Project, so it is the sum of the strip's `n` and `m`, and no badge at zero; this narrows U10, and `u10_dock_badge.test.tsx` keeps passing for one Project. The header chip `<n> need you` of U30 is gone from the header: the open tab's mark and tooltip say the same, and the click of U181 and `⌘J` do what the chip did. Narrows U30: its header sentence is replaced and its selection order is unchanged. Tests (`u182_`): the text for each mix, both counts shown, absent without a mark, keyboard focus, the badge as the sum over two Projects, no chip in the header.

**U183 rename in place.** Given a tab, when the user double-clicks its name, or presses `F2` with the tab focused (as U41 does for a row), then the name becomes a text field in the tab's place, selected, with the current name (the folder name until renamed). `Enter` calls `rename_project {path, name}` and closes the field; `Escape` closes it and calls nothing. A name that is empty or all space returns the folder name (S10). While the field is open the tab keeps its width and place, and no key in it reaches a Terminal, a Rail chord or `⌘J`. Focus returns to the tab on `Enter` and `Escape` before the call answers, and stays where the user put it when the field closes by a click elsewhere, which saves like `Enter` as U9's rename does. A failed call restores the old name and shows U80's `✕ <message>` line in the header after the strip. Two Projects with the same name are allowed; the `title` of each tab holds its absolute path. Tests (`u183_`): the field, `Enter`, `Escape`, the empty name, a failed call, the width kept, focus returned, `F2`, the `title`.

**U184 close with a question, and overflow.**
- **Close.** The tab shows `✕` only while the pointer is on it or focus is within it (never in the layout as a visible mark otherwise; it keeps its place so the tab does not move). Clicking it, with no Agent running in that Project (no Kind `working`, `needs-you` or `blocked` in its `rail.tree`), or when its Daemon has exited (U25), calls `close_project {path}` at once, with no question. With any running, an inline dialog (`role="alertdialog"`, over the centre as U51's switcher is, `esc` cancels) asks once: `Close <name>?`, then `<k> Agents run: <name>, <name>, <name>.` (at most three names in Rail order, then `and <j> more`; `1 Agent runs:` for one), then `Closing stops them.`, with two words, `Cancel` and `Stop and close`; focus starts on `Cancel`. `Stop and close` calls `close_project {path}` and the dialog closes; `Cancel`, `esc` and a click outside change nothing. Closing the open tab opens the tab to its left (the first when it was first), and closing the last leaves U2's first run. A failed `close_project` shows U80's line and keeps the tab. The dialog never opens for a Project the user did not click, and a tab that needs you is closed by the same question, never by a shortcut that skips it.
- **Overflow.** Given more tabs than the strip's width, then names shorten with `…` to at least 8 characters, then the strip scrolls sideways; its `+` stays in view at the strip's right end (the Shelf's leading edge, or the `Show work items` button, U369), and the open tab is scrolled into view when it opens. A tab with a Tab mark that is scrolled out of view is never hidden: one pinned edge line on that side, `◂ ●` at the left or `● ▸` at the right, shows the most urgent mark of the hidden tabs on that side (`◉` before `●`) and how many of them have one (`◂ ● 2`), in that mark's Ink, as the Rail's `● 1 below` does. Clicking it scrolls the nearest hidden tab with a mark into view and does not switch Project. With none hidden marked, no line shows, and no `+N` count hides anything. Tabs never reorder to bring one into view. The observer is Chromium at the window's 640 px minimum (S7) with eight Projects, seeded with marks on the second and on the eighth. Tests (`u184_`): `u184_no_agents_closes_at_once`, `u184_the_dialog_names_up_to_three_running_agents`, `u184_cancel_and_esc_close_nothing`, `u184_stop_and_close_ends_the_project`, `u184_closing_the_open_tab_opens_the_left_one`, `u184_closing_the_last_shows_first_run`, `u184_a_failed_close_keeps_the_tab`, `u184_the_close_mark_is_hover_only`, `u184_a_hidden_tab_with_a_mark_shows_an_edge_line`, `u184_the_edge_line_scrolls_and_does_not_switch`, `u184_the_order_never_changes`.

**U185 a Daemon gone, in a tab.** Narrows U25 and U37. Given `daemon-exited {path, code}`, then the tab of that Project shows the mark `◉` in red Ink (U180's error mark, whatever its Agents' Kinds were) with the tooltip text `daemon exited <code>` (`daemon exited by signal` when the code is `null`) instead of U182's counts. When that Project is the open one, the header after the strip reads `✕ daemon exited <code>` or `✕ daemon exited by signal`, in Ink, then `Reopen` as a `--grey` word (`.word`); the Rail, Shelf and pane are U25's greyed and disabled state for that Project only. The other Projects are unaffected: their tabs, Rails and calls go on. Clicking `Reopen` calls `open_project {path}` for that Project and does what U37 says on success (refetch every region, subscribe again), and on failure `✕ <message>` replaces the exit text, with `Reopen` still offered. The tab's `✕` closes it with no question (U184). Tests (`u185_`): the mark and tooltip for an exit by code and by signal, the header text on the open Project only, another Project unaffected, `Reopen`, a failed `Reopen`, closing an exited tab.

**Daemon recovery** (`DaemonExited.recovery`, `DaemonExit.recovery`): The Project's native process owner waits (`waiting`) after a failure, then asks the App to replace its whole connection (`connecting`) after readiness. An absent recovery state means the bounded attempts are exhausted; `cause` carries the final startup/connection failure when available. Only a successful replacement subscription resets the Project's failure count. Closing cancels that Project's recovery.
