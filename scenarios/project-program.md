# A Project's own program runs on the Rail and comes back after a crash (PG1–PG6)

Module: `crates/rupd` (start, restart, attach), `crates/contracts`, `contracts/generated/` and `apps/desktop`. Ids: PG1–PG6. Work order: [#7730](https://github.com/roundup-app/roundup/issues/7730). Principles served: P3, P9 (`PRINCIPLES.md`). Builds on PS1–PS11 (`scenarios/terminal-program-status.md`) and A12a (`scenarios/agents.md`).

Decided by the owner (2026-11-20): a Project names at most one program of its own; roundup starts it in a Terminal when it opens the Project and shows it on the Rail with its program status (PS10); roundup restarts it after any exit the user did not ask for, waiting longer after each crash, and holds a stop the user asked for until the user starts it again; only the user sets or clears it. A design check that reads one of these as a defect changes how it is drawn, never the decision.

`GLOSSARY.md` gains **Project program** (`ProjectProgram`, `project.setProgram`, `project.startProgram`, `project.stopProgram`: the one outside program a Project names, its `argv` and its `dir`, started in a Terminal by the Daemon), in the implementing PR (Contract recipe of `.agents/builder.md`). The App label is `Program`.

## Checks on main

1. `scenarios/terminal-program-status.md`, heading `PS10 the Rail and the Terminal tab show it`: the row of a Terminal with a program status.
2. `scenarios/agents.md`, heading `A12a a surviving owner keeps its Agent's one Terminal across reopen`: reattach launches nothing and sends no input.
3. `scenarios/agents.md`, heading `A43 an Agent's shell runs `rup` as that Agent`: the `PATH` whose first entry is the `rup` directory.
4. `scenarios/workstream-queue.md`, heading `A3197 a restart and a changed cap start nothing`: nothing but the program starts at open.
5. `scenarios/fork-open.md`, heading `FOP5978b no Terminal owner is re-attached and every Auto is off`: a Fork attaches no owner.
6. `scenarios/user-actions.md`, heading `Policy: where Extensions run` (the Extension host): a Project folder adds nothing that runs.
7. `crates/rupd/src/route/policy.rs`, `Gate::UserOnly`: a call by any Actor but the user is `FORBIDDEN`.
8. `scenarios/failure-handling.md`, heading `Reuse decision`: backon for native restart delays.

**PG1 the program is set by the user, stored with the Project, and runs nothing from the folder.** Contract change (the Contract recipe). New methods `project.setProgram {argv, dir}` and `project.clearProgram {}`; `project.get` returns `program` (`{argv, dir}` or `null`). Given a Project, then `argv` is a non-empty list of non-empty strings, and `dir` is a path relative to the Project folder that stays inside it after resolution (no `..` out, no absolute path, no link out); anything else is `INVALID_PARAMS`, changes nothing and keeps the old entry. A second `project.setProgram` replaces the first: a Project holds at most one. The entry is stored in the Project's data (G1's store), never in a file of the Project folder, so opening a repository that holds a file naming a program starts nothing, and it survives a Daemon restart. Both methods carry `Gate::UserOnly`: a call by an Ext or an Agent is `FORBIDDEN` and changes nothing, and no MCP tool or `rup` command offers either (M1). Setting or clearing starts and stops nothing by itself; it takes effect at the next open or the user's Start (PG3). Tests (`pg1_`, `crates/rupd`): `pg1_set_stores_one_entry_and_replaces_it`, `pg1_a_bad_argv_or_dir_changes_nothing`, `pg1_an_ext_or_agent_call_is_forbidden_and_changes_nothing`, `pg1_a_file_in_the_project_folder_names_no_program`.

**PG2 opening the Project starts the program once, in a Terminal on the Rail.** Given a Project whose entry is set (PG1), when the Daemon opens it, then one Terminal starts running `argv` in `dir` (relative to the Project folder), with `RUPD_SOCKET` set to the Daemon's socket and a `PATH` whose first entry is the `rup` directory, then the Daemon's own `PATH`, as A43 gives an Agent's shell; no `ROUNDUP_AGENT_ID` is set, because the program is no Agent. `rail.tree` carries one row for it, and the row shows the program's reported status as PS10 shows any Terminal's (`status: null` until it reports). The user's earlier choice to name it is the start (P9): the open sends no input and starts no Agent, Door or Queue entry (A3197). A Project with no entry, and a Fork (FOP5978b: no Terminal owner is attached, and no program starts), start nothing. Tests (`pg2_`, `crates/rupd`, with a fake program that writes an OSC 7501 report and waits): `pg2_open_starts_the_program_once_with_its_dir_and_environment`, `pg2_the_row_shows_the_reported_status`, `pg2_a_project_without_a_program_and_a_fork_start_nothing`.

**PG3 the user stops and starts it, and a stop holds.** Contract change. New methods `project.stopProgram {}` and `project.startProgram {}`, both `Gate::UserOnly` (PG1). `project.stopProgram` ends the program's Terminal, records that the user asked, and nothing restarts it afterwards (PG4), across a Daemon restart too: opening the Project starts none while the stop stands. `project.startProgram` clears the stop and starts it as PG2 does; it is `CONFLICT` when the program is running, or when the Project names none. `project.setProgram` and `project.clearProgram` while it runs leave the running Terminal alone; `project.clearProgram` also clears any stop. The program's row on the Rail shows `Stop` while it runs and `Start` while it is stopped or waiting to restart; each is one call, and the row shows why it is down (`Stopped` or `Restarting in <n> s`) so a down program never reads as idle. Tests: `pg3_stop_holds_until_the_user_starts_it_and_survives_a_restart`, `pg3_start_while_running_or_without_a_program_is_a_conflict`, `pg3_clear_leaves_a_running_program_and_clears_a_stop`, and, in `apps/desktop/src/`, `pg3_the_row_offers_stop_when_running_and_start_when_down`.

**PG4 an exit the user did not ask for restarts it after a wait that grows.** Given a running program that exits for any reason but PG3's stop (a signal, a non-zero code, or code 0), when it exits, then the Daemon starts it again after a wait: 1 s after the first such exit, then twice the previous wait for each further one in a row, at most 30 s (policy: the owner asks only for longer waits; these numbers are the specifier's). A program that has run for 60 s without exiting counts as healthy, and its next exit is a first one again. The waits come from backon (Reuse decision, check 8), with no jitter, and no polling loop runs: one timer waits at a time. A wait ends at once when the user starts it (PG3) and is dropped when the user stops it, clears the entry or the Project closes; a Daemon shut down by the App (D1) stops the program and restarts nothing. A restart starts the same entry as PG2 does, with the same `dir`, `RUPD_SOCKET` and `PATH`, and sends no input; if the entry was cleared or replaced in the meantime, the restart uses the entry now stored, or none. Tests (`pg4_`, `crates/rupd`, with a controlled clock): `pg4_a_kill_restarts_after_the_first_wait`, `pg4_a_second_kill_in_a_row_waits_longer_and_the_wait_is_capped`, `pg4_a_healthy_run_resets_the_wait`, `pg4_a_stop_or_clear_during_a_wait_cancels_the_restart`.

**PG5 a Daemon restart attaches the program that outlived it and starts no second copy.** Given a Project whose program's Terminal runs under a surviving owner (A12a) when its Daemon was lost without an explicit shutdown (D6), when a new Daemon opens the Project, then the program's Terminal is attached again with its row and status, exactly one Terminal runs it, and no launch and no input follow. The owner's incarnation and original program are verified first as A12a does; an owner that is gone, exited, replaced or in another Project is dropped and the Daemon starts one program as PG2 does, unless a stop stands (PG3). Explicit attached shutdown (D1) stops the program, so a normal reopen starts one. Tests (`pg5_`, `crates/rupd`, fake owners as A12a's observers): `pg5_a_surviving_program_is_attached_and_nothing_is_launched`, `pg5_a_gone_or_replaced_owner_starts_one_program`.

**PG6 the user names the program in the Project's Settings.** Given the Project settings where U3745 puts the cap, then a `Program` section holds a `Command` field, a `Folder` field (blank means the Project folder) and a `Clear` button, and shows `project.get`'s `program`. Enter or blur with a changed value calls `project.setProgram {argv, dir}` once; `Command` is split into `argv` by shell-style quoting, and an empty command, an unclosed quote or a `Folder` outside the Project is refused in the field with `✕ <message>`, calls nothing and keeps the old entry. `Clear` calls `project.clearProgram` once. The section states that roundup runs this program whenever the Project is open and starts it again after a crash. A `FORBIDDEN` or other failure shows as the change failure of `scenarios/failure-handling.md` shows one and keeps the form's text (P11). Tests (`pg6_`, `apps/desktop/src/`): `pg6_a_commit_sets_the_program_once_and_clear_clears_it`, `pg6_a_bad_command_or_folder_calls_nothing_and_keeps_the_entry`, `pg6_the_section_reads_what_the_daemon_stores`. Layout and looks are the design critic's; the rows of PG3 and this section move D2, D5 and D6 and use Tokens only.

## Gates

P9: opening starts only the program the user named, which is the user's earlier choice; nothing else starts at open (A3197), a Fork starts none, and a restart sends no input and spends no Model turn. P3: a program that is down or restarting shows on its row, never silently. The owner's decisions above hold; a design check never overrides them.

Mac: name a program in Settings, quit and reopen the App, then kill the program: it comes back after the wait, and its row shows its status. Policy: the program's own credential is a later Issue's, and this specification adds no way to identify a caller.
