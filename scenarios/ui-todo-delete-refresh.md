# UI: acknowledged Todo deletion survives a failed list refresh

Acceptance for [#5127](https://github.com/roundup-app/roundup/issues/5127), Journey Review. Extends U3787a (`scenarios/ui-mac-expectations.md`) for the Todo Drawer only. These are implementation obligations, not claims about main.

Policy: retain the existing Project-owned deletion/Undo history, `todo.delete` contract and Todo list failure surface. No new RPC, App seam command, Token, domain term, confirmation, success feedback or motion. A failed list read cannot turn an acknowledged deletion into an unknown or refused deletion. Bulk deletion, Pad deletion and lost deletion acknowledgements keep their existing acceptance.

**U5127a an acknowledged Drawer deletion closes even when the list refresh fails.** Given one Project with Todos 5 and 7, its Todos list visible and Todo 5's Drawer open, when the user activates Delete Todo, `todo.delete` acknowledges deletion of only Todo 5, and the subsequent `todo.list` rejects with an Error whose message is `Todo list unavailable`, then after both outcomes settle:

- The Drawer is closed and deletion is no longer pending. Exactly one `todo.delete` was sent, with the original Project, operation and ids `[5]`; Todo 7 was not deleted. The read failure causes no unhandled promise rejection. Test: planned `u5127a_acknowledged_delete_closes_after_failed_list_refresh` in `apps/desktop/src/todos/u3787a_undo.test.tsx`.
- The existing Todos failure surface exposes the returned list-read cause. No deletion-failed or unconfirmed-deletion state replaces the acknowledged result, and no deletion success bar or toast appears. The same test asserts the cause and absence of contradictory deletion feedback through the rendered App.
- With focus in the returned Todo list region, the existing Undo action remains available for that exact deletion; invoking it sends one `todo.restore` with the acknowledged operation in its original Project, not another `todo.delete`. The same test asserts the restore contract. Native editor and Terminal Undo ownership remains U3787a policy.

**U5127b a later successful list refresh recovers without repeating deletion.** Given U5127a's failed refresh and no Undo invoked, when a later refresh succeeds with Todo 7 present and Todo 5 absent, then the list shows only the surviving Todo, the list-read failure clears, the Drawer stays closed and the deletion remains available to Undo. Only the original `todo.delete` has been sent. Test: planned `u5127b_successful_refresh_clears_failure_without_redeleting` in `apps/desktop/src/todos/u3787a_undo.test.tsx`.

Policy/test seam: mount the production App using the existing fake App and Project connection fixture in that file. Let `todo.delete` acknowledge normally; fail the next post-acknowledgement `todo.list` at the RPC boundary, with ordinary deletion events/refetch enabled. Do not replace `TodosState.reload` with a rejecting test double: the production state adapter owns the foreign failure. Observe unhandled rejections with the test runner's normal rejection detection enabled, and wait on RPC settlement and rendered state, never fixed sleeps. Retain the existing U3787a success/identity tests; these tests prove the added failed-read case, not another copy of normal deletion. No real Daemon or vendor process is needed for this unchanged contract's webview failure handling.
