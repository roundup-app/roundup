# Remove a Workstream: its finished work goes, its work in progress stays (A34, U367)

Module: `crates/agents`, `crates/rupd`, `crates/contracts`, `crates/rup`, `contracts/generated/` and `apps/desktop`. Ids: A34, U367. Found by the user's report #954: after a Workstream's work is finished, removing it left its Agents, Todos and Pads at the Project root. Decided by the user: removal deletes what is finished and keeps what is in progress; work whose branch the Base lacks is kept, not discarded (G5), and the user picked this over a box per Agent in the confirm; Pads follow their Home under P4; the earlier kept-maker exception is retired by #4909. Not removing a single Agent (A16, G5 unchanged) and not clearing a Workstream (A32).

**A34 removing a Workstream removes its finished work and keeps the rest.** Narrows A16 ("lifts its children", "Pads are never touched"), T13 and P12's removal clauses and G5 for a Workstream. Contract change (the Contract recipe of `.agents/builder.md`): `rail.remove` of a Workstream returns `{removed, kept}` where `removed` is a list of `{id, kind, name}` and `kept` a list of `{id, kind, name, reason}`; `reason` is `running`, `dirty`, `ahead` or `open`; `rail.remove` of an Agent or Terminal still returns `null`. The App seam passes it through. Given a Workstream with Subagents, Todos and Pads, then:
- **Agents.** Each Agent in the Workstream, at any depth, is judged by its Status. An Agent with a running program (its Kind is not `done` or `error`) is kept, moved to the Project root in its order, and its reason is `running`. An exited Agent with no Worktree, or whose Worktree is clean and not ahead of the Base, is removed as G5's clean path says: its Worktree directory and branch are deleted. An exited Agent whose Worktree is dirty or whose branch is ahead of the Base is kept at the Project root with reason `dirty` or `ahead` and nothing of its directory, branch or files changes. The Daemon checks a Worktree again after its Agent's stop, as G5 says, and keeps the Agent on a change.
- **Todos.** A done Todo whose Home is the Workstream is deleted, with its Touch and `todo.deleted`. An open Todo gets `home: null` as T13 says, with reason `open`. A Todo another Todo is blocked by is judged by its own `done`. A kept Todo whose blocker is deleted loses that blocker, as `todo.setBlockers` would.
- **Pads.** Every Pad whose Home is the removed Workstream is deleted with its Touch and `pad.deleted`, independent of who created it or which Agents are kept. Pads at another Home remain unchanged. Amend the existing `a34_` cascade observers to assert this Home-only target set (planned; policy: retain failed-removal atomicity and exact undo restoration).
- **Terminals.** The Workstream's Terminals close as X12 says.
- **Order.** The Door stops first, as A16 says. Then the Daemon judges every Agent, Todo and Pad before it changes anything; if a judgement fails, the call returns the error and everything stays as it was. Then it removes and moves, and last deletes the Workstream. `rail.changed`, `todo.updated`, `todo.deleted`, `pad.changed` and `pad.deleted` follow once the Workstream is gone.
- **Failure.** A failed removal changes nothing, as A16 says, and a second call retries: nothing is removed twice and nothing kept is lost.
- **Unchanged.** Todos and Pads of other Workstreams and of the Project root, and every Worktree outside the Workstream, are untouched.

**U4461 removing a Workstream asks Remove this, Remove all or Cancel.** Extends A34 and U367 (the owner, 2026-10-27: "When I remove a workstream I should get asked if I want to remove this, remove all, cancel"; asked which "all", the owner chose "everything inside it"). Journey: Intervene/Review. Contract change (the Contract recipe of `.agents/builder.md`): `rail.remove` takes an optional `scope` of `this` or `all`; omitted means `this`, so A34 stands for every caller that sends none. Only a Workstream accepts `all`; for an Agent or Terminal, `all` returns `INVALID_PARAMS` and changes nothing. Given a Rail row of a Workstream, then:
- **Remove this.** `rail.remove {id}` (scope `this`) is A34 and U367 unchanged: running Agents, Agents with unlanded work, open Todos and their Pads stay at the Project root.
- **Remove all.** `rail.remove {id, scope: "all"}` removes everything under the Workstream: each Agent at any depth, stopped first as `agent.stop` does when running, with its Worktree directory and branch deleted as G5's clean path says; every Todo whose Home is the Workstream, open or done; every Pad whose Home is the Workstream; the Terminals as X12 says. Nothing of it is moved to the Project root, so `kept` is empty. The result lists everything in `removed`. The order, the judge-before-change rule, the failure and the unchanged clauses of A34 hold; a stop that fails returns its error and changes nothing, and a second call retries. Todos and Pads of other Workstreams and of the Project root, and every Worktree outside the Workstream, are untouched. A Todo that stays elsewhere and was blocked by a deleted Todo loses that blocker, as A34 says.
- **The question.** Choosing `remove` or pressing `⌘⌫` opens one native alert through `app.ask` (U3512a), not an inline question, with three answers: `Remove this` (the default, Enter), `Remove all` (the destructive button) and `Cancel` (Escape). It always asks, even when everything is finished. The message is U367's Goes and Stays lines, then, when anything would stay, a line `Remove all also removes: <n> Agents, <n> open Todos, <n> Pads` and the reason line of each such Agent (`Running`, `Unlanded: <n> ahead`, `Unlanded: Uncommitted changes`), so the loss Remove all adds is visible before the click. When nothing would stay, the alert still offers all three and the extra line is left out; Remove all then does what Remove this does.
- **Answer.** Remove this calls `rail.remove {id}` once; Remove all calls `rail.remove {id, scope: "all"}` once; Cancel and Escape call nothing that writes. After the call the alert is gone and the Rail, Shelf and Home lines follow the events (U158); a failed call shows `✕ <message>` as U9 says and the row stays. Focus returns as U3512a says.
- **Native alert.** `app.ask` returns a boolean and cannot carry three answers; the App seam gains one command that opens a native alert with three named buttons and resolves to the chosen one (`this`, `all` or `cancel`), a rejected plugin call being an `RpcError` as `ask` does. It follows `scenarios/app.md`'s seam rules and `NativeAlert` stays the one opener (U3512a's single pending question).
Acceptance (#4461): Remove this on a Workstream with a running Agent leaves that Agent at the Project root; Remove all on the same Workstream stops and removes the Agent, its open Todos and its Pads, nothing of it staying at the root; Cancel and Escape leave the Workstream unchanged.

**U4601 removal consent shows two lists of consequences.** Journey: Intervene/Review. This is specification acceptance for #4601, not an implementation claim. It supersedes U367's count/reason/name-line presentation, U4368's requirement to spell out container live-process loss, and U4461's question text and offer of Remove all when nothing stays. A34's classification and U4461's deletion scopes, failure behavior and authority remain unchanged. The method is [Apple HIG, Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts): essential consequences and useful actions, with concise informative text.

- **Plan before prose.** Given the selected Workstream, when Remove reads its consequences, then the two lists derive from the same removal judgment used for A34/U4461: Goes contains the chosen Workstream and everything both scopes remove; Stays (Remove this) contains everything preserved/moved to the Project root by Remove this but deleted by Remove all. Each affected Agent's Rail name appears once in its list, in Rail order, without an additional Agent count or a second reason/name list. The Workstream's Rail name leads Goes; other names precede counts of done Todos, open Todos and Pads as applicable. Zero counts and empty lines are omitted. Only Agent nodes enter Agent names; Groups and Door-bearing Workstreams are not counted as Agents. Test: planned `u4601_the_lists_follow_the_removal_plan`, using `judgeRemoval` and the summary formatter with finished, running, dirty and ahead Agents, a nested container, done/open Todos and Pads owned by removed/kept Agents; compare identities/classification and formatted membership. Keep the affected-node set for consent; do not change what the Daemon deletes, stops or moves.
- **Question and information.** Given that plan, when the native alert opens, then its message text is `Remove “<Rail name>”?` (the selected name, unchanged, in curly quotes). Its informative text contains at most two nonempty logical lines, in order: `Goes: <list>` and, only when nonempty, `Stays: <list>`. The App seam's `title` carries the question and `message` carries the informative text. No separate state/reason, Worktree-loss, running-program or Terminal-input sentence is added; this confirmation grants the consent for the chosen removal scope, including container-owned live Terminals. Names are not repeated in additional informative lines. Tests: planned pure unit `u4601_three_plans_have_two_list_copy` pins the table below, and planned `u4601_the_native_request_uses_the_plan` checks the actual native request against the formatter and zero mutation calls before an answer. This explicitly requires exact prose in the pure formatter test; UI tests assert request contracts and actions, not duplicate exact-copy or layout assertions.
- **Answers.** Given a nonempty Stays list, when the alert opens, then the buttons are Cancel, Remove all and Remove this; Remove this is the default (Enter), Cancel is Escape, and Remove all retains native `hasDestructiveAction`. Given an empty Stays list, then Remove all is absent, Cancel remains, and the default is Remove. Remove and Remove this each call `rail.remove {id}` once for the captured Workstream; Remove all calls `rail.remove {id, scope: "all"}` once. Cancel/Escape authorize no mutation. There is one pending native question, with the existing final-focus, failed-alert retry and failed-removal feedback behavior. Tests: planned `u4601_buttons_follow_what_stays`, parameterized over empty/nonempty Stays through `mountRail` and the existing native-question probes, and `u4601_each_answer_keeps_its_removal_authority`, covering each offered answer and keyboard mapping. Preserve U4461's captured-target, rejected-alert/retry and failed-removal proofs; retire/replace only its contradictory text and always-three-button assertions, recording the remaining proof per rule 10 on the implementation Issue.
- **Plural and copy ownership.** Given any positive Todo or Pad count in either list, then singular/plural selection uses `Intl.PluralRules` or an existing App plural helper: `1 done Todo`, `2 done Todos`, `1 open Todo`, `3 open Todos`, `1 Pad`, `2 Pads`.
