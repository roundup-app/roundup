# UI: Every scrollbar stays on its area's edge and moves with it (U7543a–U7543c)

Module: `apps/desktop` (the webview). Ids: U7543a, U7543b, U7543c. Work order: [#7543](https://github.com/roundup-app/roundup/issues/7543).

The owner reports that in the Todo Drawer, Pads and almost everywhere, scrolling moves the bar the opposite way and hides it, and that the bar cannot be dragged. Look is unchanged: thin overlay bars that show only while scrolling (U3530b). This file adds acceptance for where the bar sits and how it moves; U3530b keeps its visibility, overlay and containment clauses.

**U7543a the bar stays on its area's edge while it scrolls.** Given each scroll area of the App (the Todo Drawer's list and body, a Pad's list and document, the Rail, the Shelf's lists, Settings, the Changes view's tree and diff, a dialog's list and a menu), when the user scrolls it by wheel, trackpad or keyboard, then its thumb stays inside that area's edge, moves in the same direction as the content (down when the content moves up), and its offset along the track is the area's scroll position divided by its scroll range. The Terminal's thumb (Z3742a) is on the list and meets the same clause. When the user drags the thumb, then the area scrolls in the same direction by the same ratio, and the thumb stays under the pointer. Dragging and wheeling through the bar works for every area.

**U7543b one slot placement serves every host, measured from the slot's own containing block.** Policy: the bar of a host inside a scrolling ancestor travels with that ancestor's content when its slot is the host's next sibling, placed from the host's rect against the slot's own `offsetParent` (a fixed host has none and uses the window scroll), so no scroll-time re-placement exists. Every scroll host is Solid-owned: the library's in-host mode wraps a host's children in its own viewport element, and a node Solid inserts afterwards lands beside that wrapper and never scrolls, so no host takes the in-host mode and each keeps the host itself as the viewport. There is one placement path, in `apps/desktop/src/scrollHover.ts`, `trackScrollbars`, and no per-view fix. The Terminal's thumb is xterm 6's own and stays as `showScrollbars` has it. The PR body names these hosts (every Solid-owned scroll host, and the native `textarea`, whose thumb the library gives zero height, Z3742a) and this reason. Shared shape: one change in the shared files (policy).

**U7543c no stylesheet overrides a scroll host's position for the bars.** Given the stylesheets that touch a scroll host, when the in-host mechanism serves them, then no declaration exists only to make a bar fit: `changes/styles.css` (the `.changes-body` note on OverlayScrollbars' `position: relative`) and `settings/styles.css` lose theirs, and no `position` override on a scroll host remains in `todos/drawer.styles.css` or `ui/reading.styles.css` for that reason. Test `u7543c_no_scroll_host_stylesheet_overrides_position_for_the_bars` (Vitest, reads the real `src` stylesheets) asserts it for the named files; a host's `position` that its content needs for another reason (a sticky header, an absolutely placed child) is not an override and stays.

**Guard (policy).** One planned WebKit test, `u7543a_every_scroll_area_keeps_its_bar_on_the_edge_and_drags_with_it`, in `apps/desktop/src/scrollbar_webkit.test.ts` (the `webkit-guards` project, shard 1; `.github/workflows/check.yml`), covers every area of U7543a and carries U7543a to U7543c's proof. Use the U26 fake-Daemon harness and isolated headless WebKit at 1512×950, dark, a fresh profile, never the user's browser; seed `tree-40`, `agents-10` and an open Todo Drawer, Pad, Settings and Changes, with content that overflows. For each area: wheel it with real pointer wheel input, wait on the observable scroll position and read the thumb's box from the library's `.os-scrollbar-handle`, asserting that the thumb lies inside the area's box, moved the same way as the content and by the ratio above; then drag the thumb with real pointer events and assert the area's scroll position moved the same way. The thumb is revealed by scrolling (U3530b), so the test reads it while it shows and never forces it visible. It fails on today's `main`, where the thumb of a host inside a scrolling ancestor leaves its edge, and so cannot pass with scrollbars hidden or with the bar placed once. No duplicate Chromium, jsdom or per-surface test is commissioned (rule 10).

Observer: the WebKit test in CI. After merge, the loop owner scrolls the Todo Drawer, a Pad and Settings on the Mac and reports what they meet; Linux WebKit makes no native claim. Checks moved (policy): D2, D5 and D6 (`docs/design-system.md`, heading "The checks"); none passing on `main` regresses. Scope: `apps/desktop/src/scrollHover.ts`, `scrollbar.css`, the stylesheets that touch a scroll host and their tests; a file outside it is added to the Issue with its reason.
