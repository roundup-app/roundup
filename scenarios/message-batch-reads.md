# Read Message delivery history and names once per batch

Acceptance for #5640. Ownership: `crates/messages/src/{store,receiver_view,delivery,inbox,pushes}.rs` and existing tests in `crates/messages`. This specification preserves B2, B7, B22 and B30 (`scenarios/messages.md`), B5168f (`scenarios/workstream-github.md`) and B2705a's durable sender labels (`scenarios/messages.md`). It adds no RPC, contract type or domain term.

5. Flush cadence, missed ticks and slot lifecycle: `crates/messages/src/delivery.rs`, `spawn_push_clock`; `crates/messages/src/pushes.rs`, `Slot::expire`, `flush` and `roll_up`.
6. Caps, reachability and retry: `crates/messages/src/tests/b_push_tests.rs`, `b22_the_ninth_push_in_a_window_waits_and_leaves_at_its_end_as_one_rollup`, `b22_after_a_burst_of_100_changes_every_change_is_counted_once`, `b21_removed_door_discards_unsent_entries_even_inside_the_cap_window` and `b21_live_door_refusal_keeps_entries_eligible_for_retry`; inbox receipt replay: `crates/messages/src/tests/b_hop_tests/inbox.rs`, `b52_question_restart_replays_receipts_once`.

These checks locate existing behavior, not evidence that the following savings already hold. Test names below marked planned belong to the implementing PR.

**B5640a select only this receiver's delivered digest history.** Given receiver `m`, delivered history containing plain pushes, Rollups and merges, and 100,000 unrelated Messages, when one eligible batch needs historical digest comparison, then only Messages addressed to `m`, with status `delivered`, whose Actor equals `Actor::daemon()` and whose body starts with `[digest]`, are materialized for that history read. Selection preserves Check 3's exact Actor/prefix predicate, with no new Message-kind restriction. Results retain Message-id order, independent of timestamps and pending delivery rank. Planned `b5640a_history_materializes_only_matching_rows` in `crates/messages/src/store/tests.rs` asserts selected ids and counts actual row-to-Message conversions, excluding fixture insertion and later inspection.

Include unrelated receivers, pending and dropped digests, delivered ordinary text, an Agent/Extension/user authoring a digest-looking body, and a Daemon-kind Actor with a different id. Include a delivered Daemon question with the prefix: the historical predicate still selects it. Run the same selection before and after adding the unrelated rows; none of those rows reaches Message conversion. Count conversions at the database mapping boundary, not the length after filtering a whole-Project vector. Policy: push filtering into the database; remove the whole-Project history copy. Add a SQL index only with `EXPLAIN QUERY PLAN` evidence that the query needs it; no blanket index requirement or wall-clock performance assertion.

**B5640b resolve historical entries once for the batch.** Given several pending Digests with overlapping child names and selected delivered history, when the batch's quiet decision is computed, then each selected historical body is parsed at most once across that batch, in a newest-Message-id-first pass resolving only requested names. For a name present in multiple historical Messages, its entry from the greatest Message id wins; within that body the first occurrence wins. A missing name stays missing. Reversing timestamps does not change those choices. Planned `b5640b_history_is_parsed_once_per_batch` in `crates/messages/src/receiver_view.rs` asserts per-Message parse counts at the real history parser and the resulting quiet/news decisions, including two conflicting occurrences in one body and a name absent from every body.

Use plain, Rollup and merged history and multiple pending entries for the same name. An empty history body or one with no parsed entries supplies no prior entry. Preserve Check 2's comparison: a new `error` or `needs-you` Kind, a changed `last`, or fewer open Todos is news; unchanged entries and non-news changes remain quiet. A digest with no parsed entries is not quiet. Planned `b5640b_history_is_parsed_once_per_batch` asserts these branch cases as well as the count bound. Policy: this lookup exists only for the current batch; no latest-digest cache, persistent parsed-history copy or pending Message treated as delivered history.

**B5640c refresh sender names once before constructing inbox entries.** Given 32 pending Messages with repeated Agent senders mixed with user, Extension and Daemon senders, when one eligible inbox batch is prepared, then Agent sender ids are deduplicated and there is at most one sender-name Rail refresh for the batch, before its entries are constructed. Each Agent label is its current Rail name, or its last durably observed name after removal; non-Agent labels remain their Actor ids. A batch containing no Agent sender performs no sender-name refresh. Planned `b5640c_one_sender_refresh_labels_the_whole_batch` in `crates/messages/src/inbox.rs` counts actual `rail.tree` calls during inbox batch preparation and asserts all entry ids, kinds, texts and sender labels, not just a deduplication helper's output.

Include a rename between enqueue and delivery, a sender removed after its name was observed, an observed rename followed by removal, and a removed sender after store reopen. A removed sender with no stored name uses the existing gone-Agent label without its machine id. Planned `b5640c_sender_names_survive_removal_and_reopen` in `crates/messages/src/inbox.rs` asserts those labels and durable names. Fixture setup, startup reconciliation and receiver eligibility reads happen before the sender-refresh counting interval; they are not sender-name refreshes. Policy: keep stored names and the current rename/removal semantics; do not trade repeated reads for stale labels or a long-lived Rail cache.

**B5640d a flush shares one Rail read only when work waits.** Given slots retaining sent timestamps but no waiting changes, when the existing flush runs, then it performs zero Rail reads, still expires timestamps and removes slots only when both queues are empty. Given many slots with waiting changes, when that flush runs, then one Rail read supplies the lifecycle view for all of them. Planned `b5640d_flush_reads_once_for_waiting_slots_and_never_for_sent_only` in `crates/messages/src/pushes.rs` counts actual Rail calls with all waiting slots still inside full rate windows, so no downstream Message-send validation contributes calls; it also asserts retained waiting entries/weights and timestamps before and after expiry. Separate successful sends keep their existing receiver validation; the shared read replaces per-slot rollup eligibility reads.

Given waiting slots for live, stopped and removed receivers, when a flush observes their Rail state, then a removed receiver's waiting work is discarded even inside a full rate window; a stopped receiver retains its work; an eligible live receiver sends only when its window permits. A failed shared Rail read retains every waiting entry and weight for a later existing flush. A failed digest send retains that slot's work for the existing retry. Neither failure spends a successful-send timestamp, discards other receivers' waiting work or adds a retry timer. Planned `b5640d_flush_preserves_lifecycle_and_retries` in `crates/messages/src/pushes.rs` asserts those effects and the successful next-flush retry, including failure followed by removal and multiple receivers with different outcomes. Policy: retain Check 5's 500 ms cadence, immediate interval behavior and `MissedTickBehavior::Skip`; no new scheduler.

**B5640e savings preserve eligible delivery and flight identity.** Given delivered history and only Quiet Digests pending, when the receiver becomes eligible, then no inbox write occurs and those ids remain pending. When an ordinary Message or non-quiet Digest subsequently becomes deliverable, the held work joins the existing single idle batch in delivery order, with no duplicate entry on a later idle. Entries remain pending/in-flight until their matching transcript receipts. Planned `b5640e_quiet_work_rides_one_idle_batch` in `crates/messages/src/delivery.rs` asserts the held ids, one captured batch, its ordered entries, receipt transitions and no repeat write, with zero Terminal writes or prompt calls throughout.

Given sender refresh fails, an inbox write fails, or a prepared batch has a stale receiver generation/binding, when delivery is attempted, then no stale batch is written, no Message is falsely delivered and pending work/receipt identity follows the existing retry rules. A failed sender refresh writes no partial batch; a failed inbox write clears retryable flight records as before; a later eligible event with successful reads writes the same pending ids once. A stale batch does not acquire valid flight records for the replacement generation. Planned `b5640e_failed_or_stale_preparation_keeps_pending_identity` in `crates/messages/src/inbox.rs` asserts these cases through existing in-memory Rail/inbox seams, advancing generation before the final flight check rather than sleeping.
