# Checkpoint file contents use Git objects

Module: `crates/checkpoints/`. Terms: Checkpoint, Mark, Project data, Worktree and Rewind (`GLOSSARY.md`). Acceptance for #1714, the implementation follow-up to specification #1616. Prerequisite: #1662 delivers the versioned store schema from #1617. #1714 is natively blocked by #1616 and #1662; #1642 and #1648 also wait on #1714 so specification completion does not release implementation dependents early.

Keep the public `File`, `FileContent`, `Mark`, `Marks`, `RecordMarks` and `Checkpoints` interface unchanged. Encode object references at save and hydrate original bytes at read inside Checkpoints; the existing recorder and Rewind callers need no edits. Own content-format compatibility and any new numbered migration in this crate, using the existing migration library; do not change other crates, the schema migration engine, RPCs, App seams, conversation handling or Message laws M1–M10. The implementation records its fetched main SHA; this specification's baseline is `ae11e413f61fb23a68564ac3d68227b0da65f38e`.

**N12 file contents are reusable Git objects.** Given Marks containing equal file bytes at different paths, for different Agents and in successive Checkpoints of one Project, when Checkpoints saves them, then regular contents and symlink targets are Git blobs with equal contents referring to the same object id, written through Git plumbing or `gix`; SQLite stores object references and metadata rather than copies of those byte arrays (`n12_equal_contents_share_git_objects`, inspects persisted rows and objects through Git, not only deserialized Marks). Path bytes, file kind and executable state remain distinct metadata even when content is shared (`n12_metadata_does_not_change_blob_identity`). Git owns object hashing, compression and deduplication; do not implement these algorithms (policy).

Object storage may use the Project's Git object database or a private Git object store in its N1 Project data folder, outside working files; a private store beside `checkpoints.db` also supports existing opens that supply only the data folder. No new folder is created beside or inside the Project's working files, preserving N1 and N2 (`scenarios/project-data.md:5`, `:7`). When saving and loading Marks, then the Project's HEAD, branches, user refs, index bytes, working files and remotes stay unchanged, with no checkout, reset, staging or push; only the chosen object store and private Checkpoint refs may change (`n12_save_and_load_leave_project_git_state_unchanged`, includes a linked Worktree, staged changes and an unborn repository). Objects remain reachable from private refs while their Marks are stored, including unusable Marks; a Git garbage collection with immediate pruning followed by reopen still reads them (`n12_stored_marks_survive_git_gc`). Ref identities include Workstream as well as Checkpoint identity, because Checkpoint numbers are local to a Workstream (`n12_workstreams_do_not_collide`). No new retention or expiration policy is introduced (policy).

**N13 object reads preserve Rewind files.** Given a Mark containing binary bytes, empty files, executable files, symlinks including a broken link, non-UTF8 and newline path bytes, and identical contents at multiple paths, when saved and read after Checkpoints reopens, then its files and conversation bytes equal the input Mark exactly (`n13_object_marks_round_trip_after_reopen`). Git attributes, clean/smudge filters and end-of-line conversion do not transform captured bytes (`n13_objects_preserve_bytes_despite_attributes`). File selection remains main's `git ls-files -z --cached --others --exclude-standard` in `crates/agents/src/marks.rs:112`: tracked files stay included even if an ignore pattern matches them; ignored untracked files stay excluded (policy).

When the existing Rewind restores the loaded Mark after changing, adding and deleting working files, then its restored paths, bytes, executable state and symlink targets match the captured selection, ignored untracked files keep their current bytes, and HEAD, branches and index stay unchanged (`n13_loaded_marks_restore_existing_file_semantics`, invokes the existing restore operation with files read through Checkpoints). Repeating restoration gives the same result (`n13_restoration_is_idempotent`). When Rewind keeps files, then all working files retain their current bytes (`n13_keep_leaves_files_unchanged`). Preserve the safe-path, symlink and hardlink protections and ignored-directory obstruction errors of the existing restore operation (policy).

**N14 old Marks and failed object operations remain recoverable.** Given a non-empty `checkpoints.db` written by the recorded baseline's Checkpoints with JSON file-byte arrays, when the new Checkpoints opens it and writes an object-backed Checkpoint, then old and new Marks both load byte-for-byte after reopen, and titles, blocks, conversation bytes, Iteration and usable flags keep their original values (`n14_legacy_and_object_marks_coexist`). Old Marks may migrate or remain readable; do not invent an age-out that discards them. If migration is chosen, then a failed conversion leaves the original payload readable on retry and a successful conversion repeated on reopen changes nothing (`n14_conversion_failure_preserves_legacy_marks`, `n14_conversion_is_idempotent`; required only for a converting implementation). Fixtures are produced by the baseline checkout's real store, recording SHA and command, rather than hand-written approximations (policy).

When object writing or private-ref publication fails, or the run ends after objects are written but before metadata is committed, then no new usable Mark references missing or unretained objects, previously saved Marks remain readable, and retry can complete (`n14_failed_publication_preserves_existing_marks`, injects each failure at the production persistence seam and reopens). Unreferenced objects left by an interrupted write are permitted (policy). Given a missing or corrupt referenced blob, when Marks are read, then the call fails with an error identifying the Checkpoint and object, never silently substitutes empty files, and restores no working files from that failed read (`n14_missing_or_corrupt_object_fails_before_restore`). Preserve the current card-on-recording-failure behaviour in `crates/checkpoints/src/lib.rs:75`; failure must not advertise usable Marks (policy).

**N15 the repository size and timing comparison is reproducible.** Observer (policy): the implementation PR reports measurements through the actual baseline and new Checkpoints save/read paths, using separate fresh Project data folders and the same captured file selection from this repository at one recorded source SHA. Create two Checkpoints of the identical selection and a third after changing one regular file; use five fresh-store repetitions per implementation and report medians. Use identical fixed Mark metadata and conversation bytes, record file count and total selected content bytes, OS, Git version, commands and build profile. Exclude ignored files and Git internals exactly as the recorder does; no `target/` or `node_modules/` is added to the selection.

Report total physical bytes attributable to Checkpoints (database, WAL, SHM, object files, packs, refs and other private-store files) after each of the three writes, plus elapsed milliseconds for each save and each subsequent full Marks read, including object publication and hydration. For an existing Project object database, report its byte delta from before the first Checkpoint as well as the Checkpoints database delta; disclose pre-existing shared objects. Do not compare only JSON length with blob size or omit subprocess costs. Record whether new total bytes are lower than baseline and each measured timing ratio; no unmeasured speedup or numeric latency target is claimed. Equal contents adding no new blob is asserted by N12; no timing threshold is added beyond existing repository budgets (policy).

The observer emits one row per failed measurement or validation with command, condition and exit code; exit 0 means all three Checkpoints were written and read correctly and all measurement fields exist, exit 1 means a measurement or equality check failed. Report these rows in the implementation PR, including failures (policy). This specification PR does not claim implementation measurements.
