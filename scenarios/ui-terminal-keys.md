# UI: Mac editing keys in a Terminal (U2242)

Module: `apps/desktop` (the webview). Ids: U2242.

**U2242 Mac editing keys reach a Terminal's program as they do in Ghostty.** Found by the user's report #2334: `⌘⌫` in a Terminal running Claude Code deleted nothing. `createXtermEmulators` (`apps/desktop/src/terminal/emulator.ts`) attaches one `attachCustomKeyEventHandler`, which maps only `⇧⏎` (U399), and xterm 6.0.0 (`@xterm/xterm/src/common/input/Keyboard.ts`) encodes no `⌘` editing key: `⌘←` and `⌘→` produce nothing, `⌘⌫` produces `\x7f` (the plain `⌫` byte), and `⌥←` and `⌥→` produce `\x1b[1;3D` and `\x1b[1;3C`, which Claude Code and the shell do not read as word moves. The bytes below are the defaults of `ghostty +list-keybinds --default` on macOS (`cmd+backspace=text:\x15`, `cmd+left=text:\x01`, `cmd+right=text:\x05`, `alt+left=esc:b`, `alt+right=esc:f`) plus xterm's own `⌥⌫` encoding, which already equals Ghostty's. Changes no contract, App seam command or Token; roundup's own shortcuts are another Issue's (`ui-shortcuts.md`). Given any Terminal of the webview (an Agent's pane under Takeover, the Door's Terminal, a Terminal bubble) with focus in it, when the user presses the key, then `terminal.write` receives exactly these bytes, once, and the event reaches no other encoding, so nothing else is sent:
1. `⌘⌫` writes `\x15` (delete to line start); `⌘←` writes `\x01` (line start); `⌘→` writes `\x05` (line end).
2. `⌥⌫` writes `\x1b\x7f` (delete a word); `⌥←` writes `\x1bb`; `⌥→` writes `\x1bf` (move by word).
3. Every `⌃` key writes what xterm encodes for it, unchanged: `⌃A` to `⌃Z` write `\x01` to `\x1a` (so Claude Code's `⌃Y` is `\x19` and `⌃S` is `\x13`), `⌃Space` writes `\x00`, and `⌃[`, `⌃\`, `⌃]`, `⌃3` to `⌃8` write what xterm's table holds. The custom handler never returns a `⌃` event as handled, and no `⌃` key is claimed by a roundup listener while a Terminal has focus.
4. (a) A key repeat of 1 or 2 writes its bytes each repeat. (b) The same keys with `⇧` or another modifier added than the ones named, and the unmodified `⌫`, `←` and `→`, write what they write today. (c) During IME composition none is mapped; the composition owns the key. (d) A press whose `keydown` the handler maps writes nothing on the following `keypress` or `keyup`.

Tests (`u2242_`), in `apps/desktop/src/terminal/u2242_mac_editing_keys.test.tsx` against the fake App with the real xterm: `u2242_cmd_backspace_left_right_write_line_start_and_end_bytes` (1), `u2242_option_backspace_left_right_write_word_bytes` (2), `u2242_every_ctrl_letter_and_symbol_writes_xterms_byte` (3), `u2242_a_held_key_writes_each_repeat_and_extra_modifiers_write_what_they_did` (4a, 4b), `u2242_composition_and_the_follow_up_events_write_nothing` (4c, 4d), `u2242_the_door_and_a_bubble_terminal_do_the_same`. Observer: the same table as a real-WebKit run in the Tauri webview engine, each press compared with the bytes `od -c` prints in Ghostty; policy, asserted by no jsdom test, because jsdom cannot report WebKit's `keyCode` for `⌘` chords. A run on the user's Mac with a logged-in `claude` confirms `⌘⌫` clears to line start in its input.
