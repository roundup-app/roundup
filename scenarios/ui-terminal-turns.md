# UI: turns in a shell Terminal, and sending them to an Agent (X15, U514–U516)

Module: `crates/terminal` (X15) and `apps/desktop` (the webview; U514–U516). Ids: X15, U514, U515, U516. Asked by #2178: the user wants to select a command and its output in a Terminal and hand it to a running Agent, so the Agent stays in the loop.

Scope (policy): the shell a user opens (`terminal.open`, X12) and the Quick Terminal (`scenarios/quick-terminal.md`). An Agent's or a Door's Claude Code Terminal gets no integration and no turns, because it is not a shell. Plain text selection stays as U101 and U110 say; nothing here changes them. `GLOSSARY.md` gains **Shell mark** (OSC 133 and OSC 7 sequences from the shell), **Turn** (code term; user label "command") and **Excerpt** in the implementing PR (Contract recipe, rule 4). The existing **Block** (a Checkpoint part) is a different thing, so no code name uses it for a Turn. The only Daemon change is X15's environment; the send is B1's `message.send` unchanged, so there is no new RPC method, nothing under `contracts/` and no new App seam command.

**X15 a shell the user opens emits shell marks.** Given `terminal.open` (X12) starting `$SHELL -l` whose basename is `zsh`, `bash` or `fish`, then the Daemon adds the integration before the shell reads its first line and the user's own startup files still run:

- **Injection.** zsh starts with `ZDOTDIR` pointing at a Daemon-written folder whose startup files source the user's own (`$ROUNDUP_USER_ZDOTDIR`, else `$HOME`) and then the integration; bash starts with `--rcfile` naming a Daemon-written file that sources `/etc/profile`, the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`, then the integration; fish gets the integration as a `vendor_conf.d` file through `XDG_DATA_DIRS`. The files live in the Project's data folder under `shell-integration`, mode `0700`, rewritten at each `terminal.open`. Policy chosen by this spec: environment injection only, so no file of the user's is edited. The integration scripts are adapted from the open-source ones the research below finds (VS Code, kitty, WezTerm, Ghostty), with their licences kept; the implementing PR's `Reuse:` section (rule 9) names the candidates, links and release evidence before any script is written. Asserted in `x15_zsh_bash_and_fish_get_the_integration_and_keep_the_users_startup_files` in `crates/terminal/tests/`; a shell absent from the runner makes its case print `skipped: <shell> not installed` and the PR names the shells that ran.
- **The marks.** After injection a prompt prints `OSC 133;A` before the prompt, `OSC 133;B` after it (where typing starts), `OSC 133;C` when the command starts running and `OSC 133;D;<exit code>` when it ends, and `OSC 7;file://<host><path>` after each prompt, all terminated by `BEL` or `ST`. Policy: those are the sequences iTerm2, VS Code and WezTerm read, so a Turn's edges are the same bytes those programs mark. Asserted in `x15_a_command_prints_the_four_marks_with_its_exit_code_and_the_directory`, running `true` and `false` and `cd` in a real shell and reading `terminal.read` (X13) output with the marks present in the raw log (the log keeps raw bytes, X13 clause 1).
- **Nothing else changes.** The shell's visible output, `terminal.title` (X4) and the screen are the same as without the marks, and a shell that is not `zsh`, `bash` or `fish`, a command given to `terminal.spawn` and an Agent's Terminal get no environment change and print no mark. A nested shell or `ssh` that does not print the marks gives no Turn (U514). Asserted in `x15_other_shells_and_spawned_programs_get_no_injection`.
- **Observer.** Rust tests in `crates/terminal/tests/` against real shells, `just check`, and the real-Daemon run (the U144 harness) opening a Terminal and reading `echo hi`'s marks back.

**U514 each command in a shell Terminal is a Turn the user selects from its gutter.** Given a shell Terminal of X15 whose output has the marks, with the real xterm emulator (`apps/desktop/src/terminal/emulator.ts`), then:

1. **Turns come from the marks.** The emulator registers xterm's OSC handlers (`parser.registerOscHandler` for 133 and 7, with markers and decorations from xterm.js itself; the implementing PR's `Reuse:` section considers xterm's shell-integration code in VS Code and the `@xterm` addons before writing a parser) and keeps one Turn per `A`…`D` span: prompt line, command, output, the exit code of `D`, the directory of the last `OSC 7` before `C`, as rows by marker so scrollback, resize and reflow keep them. A Turn still running (no `D`) is a Turn with no exit code. The Turns of the scrollback that xterm drops are dropped with it. Asserted in `u514_a_turn_spans_its_prompt_command_and_output` and `u514_a_turn_keeps_its_rows_through_resize_and_scrollback`.
2. **The gutter.** Each Turn shows a gutter at its left edge, one narrow strip (`Token` colour only, rule 8) covering the Turn's rows, and a hover tint on the whole Turn. The gutter is a `button`-role strip with the `aria-label` `Select command`. Asserted in `u514_browser_the_gutters_select_turns`.
3. **Click selects, Shift-click extends.** A click on a Turn's gutter selects that Turn's rows (prompt, command and output) with xterm's selection, so `⌘C` copies exactly that text (U101). Shift-click on another Turn's gutter selects from the first selected Turn through the clicked one, in order. A click inside the text, or on a Turn's gutter while text is dragged, does what U101 and U110 say. Asserted in `u514_a_gutter_click_selects_the_whole_turn`, `u514_shift_click_extends_over_the_turns_between` and `u514_the_copied_text_is_the_turns_text`.
4. **No marks, no gutter.** A Terminal whose output holds no mark (a shell of another kind, `ssh`, an Agent's Terminal) shows no gutter and offers no Turn selection, and drag selection, `⌘C` and U110 work as before. A Terminal whose marks stop (a nested `ssh` begun after Turns) keeps its earlier Turns and makes no Turn of the unmarked output. Asserted in `u514_a_terminal_without_marks_has_no_gutter_and_plain_selection_works` and `u514_unmarked_output_after_marks_is_no_turn`.
5. **Look.** The gutter follows #2173's native look (no box, no border on hover, only the tint of U170) and uses only Tokens; dark, D2, D5 and D6 at the scenario's viewport. Policy: no motion (`docs/motion.md` has no row). Observer: the Chromium run of `apps/desktop/src/terminal/u514_browser.test.ts` against the harness, with the densest seed (40 Turns, a 5 000-line output and a 200-column line); the shell leg is Vitest against the real emulator.

Moves D2, D5, D6.

**U515 "Send to agent" offers a selection to a running Agent.** Given a Terminal pane with a selection of any kind (a Turn from U514 or ordinary text, a non-empty selection of xterm), then:

1. **Where it appears.** A control labelled `Send to agent` (user label) appears by the selection (an Ark `Popover`-anchored button at the end of the selection, `ui/` wrapper, rule 9), as an item of the pane's context menu (an Ark `Menu` context trigger, also the home of `Copy` and `Paste`), and on the shortcut `⇧⌘A` (chosen by this spec; it conflicts with no shortcut of U32, U186 or `apps/desktop/src/keys/`). With no selection none of the three is offered. Asserted in `u515_send_to_agent_is_offered_for_any_selection_in_three_places`, `u515_no_selection_offers_nothing` and `u515_the_shortcut_conflicts_with_no_other_binding`.
2. **Who can receive.** The list is the Agents and Doors of this Project that B1 accepts as receivers: those whose Kind is not `done` and whose Attempt has not ended, in Rail order, each by its Rail name and Kind Glyph. A Terminal and a Run are never listed. With no such Agent the control is shown disabled with the title `No running agent` and sends nothing. With exactly one, activating the control sends at once (no menu); with more, an Ark `Menu` lists them and a pick sends. `Escape` closes the menu and sends nothing. Asserted in `u515_the_list_holds_only_running_agents_in_rail_order`, `u515_one_agent_receives_without_a_menu`, `u515_several_agents_open_a_menu_and_a_pick_sends` and `u515_no_agent_disables_the_control`.
3. **The note.** The control by the selection holds an optional one-line input, `Add a note (optional)`, empty by default and capped at 280 characters (policy: one line of context, not a second message). `Enter` in it, or activating the control, sends as clause 2 says (straight with one Agent, through the menu with several), carrying the note typed so far; the context-menu item and `⇧⌘A` open this same control focused. `Shift-Enter` adds nothing. Asserted in `u515_a_note_goes_with_the_excerpt`, `u515_an_empty_note_adds_nothing`, `u515_the_note_is_capped_at_280_characters` and `u515_the_menu_item_and_shortcut_open_the_control_focused`.
4. **The excerpt.** The Excerpt is the selection's text as xterm gives it, trailing blanks trimmed per row. Policy: at most 6 000 bytes (below B1's 8 192-byte bound once the note and header are added); a longer one keeps its last bytes, cut on a character boundary, with a first line `[… N lines cut]`. The send is blocked, with the line `Nothing selected`, only when the text is blank. Asserted in `u515_a_long_excerpt_keeps_its_end_and_says_what_it_cut` and `u515_a_blank_selection_is_not_sent`.
5. **Look and keyboard.** The control, menu and input are keyboard-reachable (Tab, arrows, `Enter`, `Escape`) through the Ark parts, named by `aria-label`, use only Tokens and #2173's native look, and do not take focus from the Terminal until activated. Observer: `apps/desktop/src/terminal/u515_browser.test.ts` in headless Chromium and Vitest for the logic.

Moves D2, D5, D6.

**U516 the Agent receives the excerpt as a message from the user, never interrupted, and the user sees where it went.** Given U515 sends to Agent `a`, then:

1. **One Message.** The webview calls `message.send {to: "a", kind: "note", body}` once (B1), so `from` is the user and no other call is made (no `terminal.write`, no `agent.prompt`). `body` is, in order: the note and a blank line when a note exists; the Excerpt in a fenced block whose fence is three backticks, or one more than the longest run of backticks inside the Excerpt; then a blank line and the facts known for a Turn, one per line and only when known: `command: <command line>`, `cwd: <directory>`, `exit: <code>` (a Turn still running reads `exit: running`). Ordinary text selected outside a Turn sends no facts. The body is at most 8 192 bytes (B1); U515's caps make that hold. Asserted in `u516_the_body_is_note_then_the_fenced_excerpt_then_the_known_facts`, `u516_the_fence_outgrows_backticks_in_the_excerpt` and `u516_plain_text_sends_no_facts`.
2. **A busy Agent is not interrupted.** Delivery is B2's and B30's: an `idle` `a` is typed the Message as one prompt (`[from you, note] <body>`), a `working` `a` gets it at its next `idle`, in B7's order, and under B32's rule nothing is typed over the user's unsent input or a Takeover. The webview does not retry, does not call `agent.interrupt` and does not wait for delivery. Asserted in `u516_a_working_agent_is_sent_nothing_until_idle` (the real Daemon on real Claude, `crates/rup/tests/real_claude.rs`) and `u516_the_webview_never_interrupts_or_retries`.
3. **The user sees where it went.** On `message.send` success a Toast (U503) reads `Sent to <Rail name>` for the Agent that received it, with no sound, and follows U410–U414's lifecycle (it is not a U410 event, so no chime and no selected-Agent suppression); when `a` is not the selected Agent the Toast's action selects it (U412). A rejection (B1's `CONFLICT` for a receiver that ended or has 32 Messages waiting, or `NOT_FOUND`) shows `✕ Could not send to <Rail name>: <message>` in the same Toast style and keeps the selection and note, so the user can send again or pick another. Asserted in `u516_a_sent_excerpt_toasts_the_agent_it_went_to`, `u516_the_toast_selects_a_background_agent` and `u516_a_rejected_send_says_why_and_keeps_the_selection`.
4. **It shows in the history.** The Message is stored and listed by `message.list` (B1, B11) and the Thread shows it under U160 and U189 as a message from you to `a`, with the fenced Excerpt rendered as code (**Markdown**, not a second parser). For an Agent with no Thread (a child of a Workstream), `message.list {to: "a"}` holds it and the Agent's own Terminal shows it when typed. Asserted in `u516_the_sent_message_shows_in_the_thread_as_from_the_user` and, on the real Daemon, `u516_message_list_holds_the_sent_excerpt`.
5. **Observer.** Vitest against the fake App (U11) for the webview legs, a Rust test on the real Daemon for the Message legs, and the Chromium run of `apps/desktop/src/terminal/u516_browser.test.ts`. A real `claude` reading the typed prompt is not shown by the harness; the PR that implements this asks the user for a `macOS:` line: in a Terminal run `ls`, select its Turn, press `⇧⌘A` with an Agent running and report whether the Agent received it.

Moves D2, D5.
