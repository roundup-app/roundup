# Workstream: the Room's new name and its one entry point (A25, A26, U191, U163, U392)

Module: `crates/agents`, `crates/contracts`, `crates/rupd`, `crates/rup`, `contracts/generated/` and `apps/desktop`. Ids: A25, A26, U191, U163, U392. Found by the user's report #369: the word `Room` confuses, the Rail offers `+ agent  + terminal  + room` as three equal adds, and a Terminal is among the first things a new user meets. Decided by the user: **Workstream** replaces **Room** everywhere at once; the unit of work is opened first and staffed after; one add action opens it; an Agent or a Terminal is added inside a Workstream; Agents come before Terminals wherever both appear. `Door` keeps its meaning, now "of one Workstream". `Project` stays the repository.

The Room's behaviour is unchanged: A6, A7, A8, A16, A18, A23, A24, O3, O6, U6, U8, U9, U62, U143, U145, U160 and the rest keep every clause, read with `Workstream` for `Room`. This file changes the name, the entry point and the order only. The implementing PR is the atomic one that A25 describes (rule 4: every caller changes in the same PR); it then rewrites the word in every scenario file, doc and test name (`u160_room_scope` becomes `u160_workstream_scope`), so no scenario keeps the old word except where it is quoted as the old name.

**A25 Room becomes Workstream on the wire and on disk.** Contract change (the Contract recipe of `.agents/builder.md`). Given the Daemon, then:
- `NodeKind::Room` is `NodeKind::Workstream` and serializes as `"workstream"`; `CreateRoomParams` is `CreateWorkstreamParams`; `rail.createRoom` is `rail.createWorkstream {name, parent, order?}` with A6's and O3's behaviour. The method `rail.createRoom` and the value `"room"` no longer exist: a call to `rail.createRoom` fails with `METHOD_NOT_FOUND`, and a node of Kind `"room"` is never produced. `contracts/generated/` is regenerated from `crates/contracts`, never hand-edited.
- A Rail stored by an earlier Daemon (A8) holds `kind: "room"`. `Agents::open` reads it as a Workstream with the same id, name, parent, order, Door and children; the next write stores `"workstream"`. Nothing else in the stored Rail changes, and a Rail that never held a Room opens as before.
- O3's default Door question for a Workstream created without an `order` is `What is this Workstream for?`. A stored order keeps the text it was stored with. B24's Door Brief and the Door's system prompt say `Workstream` for `Room` (policy, read in the real-Daemon run). Every `rup` tool description, error message and `--help` line that named a Room names a Workstream.
- Every Rust module, file, public item, test and doc names it `Workstream` (`room_door.rs` becomes `workstream_door.rs`); `GLOSSARY.md` replaces **Room** by **Workstream** (`_Avoid_: room, folder`) and rewrites **Project**, **Home**, **Door**, **Rail**, **Shelf**, **Thread** and **Route**'s sentences with it, so `loop/rules.sh vocab` (rule 6) fails any public name that still uses `room`. A `GLOSSARY.md` entry for **Workstream** says "The persistent place for one body of work, named for the work", never "place" as a location, and keeps the sentences on Door, nesting and cross-Workstream dependencies. The same PR changes `docs/wireframes.md`, `docs/messages.md`, `docs/design-system.md`, `PRINCIPLES.md` and `proofs/` wherever they name a Room, and keeps `proofs/messages` and `docs/messages.md` agreeing (M1 to M10 are untouched in meaning: the laws weaken nowhere).
- Not rewritten: the historical artifact-relative captures under `artifacts/ux/*/observer.txt` and `loop/plans/`, which record what was observed.

**A26 a Workstream is one Door with Agents nested under it; Workstreams never nest.** Contract change (the Contract recipe of `.agents/builder.md`) with `GLOSSARY.md`'s **Subagent**, **Workstream**, **Hop** and B13 to B17. Decided by the user (2026-10-10, #620). Given the Daemon, then:
- **Flat.** `rail.createWorkstream {parent}` with any `parent` but `null`, and `rail.move {id, parent}` of a Workstream to any `parent` but `null`, fail with `CONFLICT` naming the Workstream, and change nothing (no `order` shifts and no `rail.changed`). A `parent` that is a Workstream is the case the user raised; an Agent parent fails the same way.
- **One Door to start.** A Workstream created by `rail.createWorkstream` holds its Door alone: `rail.tree` shows no other row under it until an Agent is started. The Door starts Agents, each holding a Work order or a Clarification order (O2).
- **Any depth.** `agent.spawn` called by any Agent (F3), not only a Door, places the new Agent under the caller, so Agent `b` started by `a` started by the Door `d` sits `d`, `a`, `b` in `rail.tree`, with no limit on depth. A `parent` in the params from an Agent is ignored (P6). `rail.move` of an Agent under an Agent stays `CONFLICT` (A6, test `a26_move_an_agent_under_an_agent_is_conflict`): only a start nests it.
- **Escalation stays inside.** A question climbs the Agents above the asker to the Door and then to the user, and never reaches another Workstream (B13).
- **Stored nested.** A Rail stored by an earlier Daemon in which Workstream `w2` sits under Workstream `w1` loads flat: `w2` keeps its id, name, Door, Agents and their `order`, and moves to the Project root, after the last root node, in the order the nested Workstreams had by depth then `order`; every other node keeps its `parent` and `order`, and sibling `order` values stay contiguous from 0. Nothing is deleted, no program starts, and the next write stores the flat tree. A Rail that holds no nested Workstream opens as before.
- **Words.** An Agent another Agent started is a Subagent; no public name, UI string or doc says `meta-agent`, `parent agent` or `lead` for the Door (`GLOSSARY.md` _Avoid_). `docs/wireframes.md` no longer lists Workstream nesting as open. E2's `agent.context` names a Door's child's parent `"agent"`, never `"meta-agent"` (test `a26_parent_node_names_no_meta_agent`, which replaces the `"node": "meta-agent"` assertion in `crates/rupd/src/context.rs`). The rest of the clause is policy, held by `loop/rules.sh vocab`.
