## Supported boundary

`one_run` at the pinned candidate creates ten login shells, finishes both Rail
loops and ping, then creates the eleventh Terminal for raw `cat`. The common
probe's compatibility patch preserves this order. Both references name its PTY
reader `terminal-11` and its input writer `terminal-11-input` (Linux truncates the
latter to `terminal-11-inp`). `*-boundaries.txt.gz` identifies their Daemon PID and
TIDs, distinct from the probe's identically named Tokio workers.

Use the first `terminal-11` COMM record as an approximate lower boundary and the
first Daemon thread EXIT as the teardown boundary. This includes echo setup,
100 warmups per loop, both 50000-call diagnostic write loops, percentile sorting
and initial cleanup. It excludes the earlier Rail and ping loops. COMM is a
thread-name event, not an exact phase marker: the new thread may execute briefly
before that event. These are conservative workload bounds, not exact timed spans.
Neither recording contains a boundary between the two write loops.

## Request/reply and echo are different branches

Source inspection of the **pinned** references establishes the following
boundaries; it is not a stage timing measurement:

```text
Client request → Daemon dispatch → input queue acceptance → RPC reply → Client completion
                                  ↓
                         input-thread write/flush → cat read/write
                                  → PTY reader → output delivery
                                  → Client decode/adapt → output receiver wake
```

- Both references' `Terminals::write` acknowledge queue acceptance. Candidate
  `write_completed` is for Agent writes; the probe uses an unidentified user
  connection. RPC completion therefore does not assert physical PTY completion.
  The worker thread runs `type_queued`; the PTY reader runs `pump`.
- Candidate `connection::serve` dispatches ordinary requests through a JoinSet,
  queues replies, and writes queued replies/selected output from its writer
  task. Historical `handle` dispatches inline with a separate frame writer.
  This is a scheduling seam to observe, not evidence it caused a measured rise.
- Common-probe `paced_writes` stops its timer after `ask` resolves, then waits
  for the echo before starting the next call. Output adaptation is outside that
  timer's explicit echo wait but can contend with request work on the runtime.
- Common-probe `write_to_output` joins reply and echo reception, retaining the
  receiver's `Instant`, so output can be timestamped before the reply completes.
  Neither the reply p95 nor its subtraction from echo p95 isolates PTY latency.
  Even per-call reply and echo spans are overlapping branches, not additive
  stages; the two metric p95s also come from different loops.

Verify these boundaries with `git show <reference>:<path>` using the exact
references retained in the original README. Paths/functions: historical
`crates/rupd/src/lib.rs` (`handle`, `dispatch`); candidate
`crates/rupd/src/connection.rs` (`serve`), `crates/rupd/src/route.rs`
(`dispatch_parsed`), `crates/rupd/src/output.rs` (`forward`); both
`crates/terminal/src/lib.rs` (`write`, `type_queued`, `pump`); common probe's
candidate `crates/perf/src/measure.rs` (`one_run`, `paced_writes`,
`write_to_output`, `wait_for_output`) plus the retained `compatibility.patch`.

## Precisely unresolved result

| Boundary | What survives | What cannot be derived |
|---|---|---|
| Request/reply vs echo loops | Correct ordering and coarse shared write window | Separate loop start/end, per-request stage spans and tail samples |
| Daemon vs probe CPU | Original PID/TID records and sample counts above | Phase/PID-resolved function stacks for the remaining CPU difference |
| Input enqueue vs physical PTY write/read | Dedicated input/reader TIDs and their CPU samples | Queue delay, blocking write/read duration and cat wake latency |
| Output delivery scheduling | CPU samples on Daemon/probe Tokio workers | Output enqueue, socket send/read and receiver wake delays |
| Historical translation | Exact common-probe bytes and adaptation operations | Translation CPU/wait cost isolated from Daemon and native-client work |

The header records only `cpu-clock` samples (199 Hz, inherited, DWARF 16384-byte
stacks) plus task/mapping metadata. There are no scheduler switch/wakeup,
syscall-enter/exit or per-write/loop marker events. `--show-switch-events`
cannot create those missing records. CPU stacks containing scheduling functions
are on-CPU work; the intervals between samples are not attributable off-CPU
waits. The separate `strace -f -c -w` summaries discarded event order/TIDs and
combine all phases; overlapping read/futex/epoll wall seconds cannot repair this.

The original build IDs are extractable, but original probe/Daemon executables
are absent at their recorded paths. Offline leaf samples for these DSOs remain
addresses; the original resolved aggregate reports preserve names without
per-sample timestamps/PIDs. A report exiting 0 does not establish successful
symbolization. Do not use a same-name rebuilt DSO without matching its recorded
identity. Neither rebuilding symbols nor adding symbol names could recover
scheduler events and phase markers that were never recorded.

The common probe's historical-only `read_loop` branch takes the Event's nested
`data` Value, inserts `offset: 0`, deserializes it and broadcasts an OutputFrame.
Native output instead takes `params`, deserializes and broadcasts. Both first
parse the JSON frame and use the same mutex/output sender, but the historical
branch does additional envelope tests and Value manipulation. The flat table's
Parsed/Value/allocation samples do not identify that branch separately. No
adapter-only timing, same-binary probe variant comparison or causal Daemon
attribution is supported by these recordings.
