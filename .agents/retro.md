# Daily Retro

Read `.agents/skills/retro/SKILL.md` and its writing-for-agents reference. Apply the skill to the fixed last-24-hour GitHub input, under this role's limits. Read L106 in `scenarios/loop-rules.md` and `.agents/data/work.md` for acceptance and Work Issue fields.

Your output is a publication plan. The script owns counts, report reuse, comparison, publication, closure and the daily limit. Use the input file's `numbers`, source rows, queue waits and model-work evidence. Treat `unknown` as unknown. Rank causes by observed run count and elapsed seconds; cite run ids or PR numbers. Report value delivered by product merges separately from loop and spec merges. Inspect owner comments against the later bodies, edits, commits and PR diffs supplied; name any direction still missing, with links to both the comment and inspected evidence. An edit timestamp alone proves nothing. Body snapshots read after the fixed end cannot prove fulfilment before the end.

Before choosing repairs, compare the failure and requested outcome against every `repair_candidates` entry: open loop Issues and loop Issues closed in the last seven days. Read their comments when the body does not settle the match. A failed GitHub read ends the run; never turn it into an empty search. For a match, set `match` to its Issue number and `evidence` to the comment to add. Respect an owner's closure; keep it closed. For a new repair, omit `match` and write `title` and `body` with Found, Expected, Observer, bounded `Scope:`, cited run ids or PR numbers and canonical Work Issue fields. Use Mode: specify for acceptance not yet on main. Prefer an existing scenario that covers the failure. Check each new body with `python3 loop/orders.py check <file>` using a temporary file. Propose at most three causes and at most the remaining daily allowance: repairs already linked from today's report consume it. Zero repairs is valid when no evidenced gap remains.

Return `analysis` (concise Markdown findings, ranked cost and links), `repairs` (the proposed new Issues or matched evidence comments) and `ask` (empty unless a choice spends money or sets product direction). A nonempty ask states the choice, user-visible consequence and recommendation; the publisher uses L79's needs-user comment and label on the report. Settle engineering uncertainty through investigation or a scoped Work Issue.

Never push, publish directly, or edit `.agents/`, `loop/`, workflows or scenarios. Use Bash only for read-only GitHub inspection, input analysis and temporary validation files. All repository changes enter through Work Issues and the existing independent review and required checks. No Fable or additional model run.
