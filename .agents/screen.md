# Screen

A build or fix run ended with a question for the user, who owns roundup: a build run's `ask`, or the `Stopped:` paragraph of the draft PR a run left. Decide who must answer it before the user sees it (L79, L81). Answer `verdict`, `reason` and `preview`.

- `user`: only the user can answer it. Either a product choice that changes what roundup does or shows, which no scenario, `GLOSSARY.md` entry or recorded direction settles; or a judgment of how something looks or feels, which has no pass or fail a script can read.
- `mac`: a check whose pass or fail only the user's Mac can produce, which an agent there reads from a state, a log, a session transcript, a screenshot or a timing: a logged-in real `claude`; the logged-in state cannot be replaced by a fake check. A check that `check`'s `macos-latest` jobs already run (a test, its failure rate) is `loop`: a Builder reads it from CI history (`actions: read`). A native look-and-feel check whose Issue names a Linux or Chromium observer is `loop`: the Builder closes the Issue on that observer, and the user reports what they meet on the Mac (L46). The native behaviour (a drag, a modifier click) of work `main` already merged, whose Linux or Chromium tests pass on `main`, is `loop` too: the Builder closes the Issue as completed. Only a logged-in real `claude` stays `mac` there.
- `loop`: an open PR's native `just app` window check, including traffic-light placement, Window menu or Mission Control titles, drag, zoom and modifier clicks, even when phrased as a look-and-feel judgment. An open PR never waits on this check, regardless of Chromium coverage or whether the work has merged: the Builder makes it ready on passing Linux and Chromium tests and arms auto-merge; the user reports what they meet on the Mac. Also anything else, which a Builder settles itself: a failing test or check, a missing tool, work the Issue or its scenarios specify that is not built yet, a choice between two ways to build the same outcome, a task that looks wrong or already done, a prerequisite to file, a question the Issue or the scenarios already answer, or the run's own GitHub token, push or job (an expired token, a failed push, a re-run).

For a mixed ask, exclude native window checks from the delivered question and preview; preserve each separate unresolved product or logged-in real `claude` question and its `user` or `mac` route. An open-PR native-only window ask is always `loop`, including when screening fails; routing resumes the draft through L81 without either waiting label. With no valid verdict on a mixed ask, only the separate question reaches the user unscreened.

When unsure whether it is `user`, answer `user`: a wrong `loop` hides a real decision, while a wrong `user` costs the user one read.

`reason`: one sentence naming what decides the verdict.

`preview`: what its reader does next, in plain words. For `user`, at most three short lines the user reads first: what to do or decide, and what each answer changes. For `mac` and `loop`, one line.
