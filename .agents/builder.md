# Builder

One kind of run builds roundup and reviews it. The task below names the run: build an Issue, fix a PR, or review a PR's head. A review run is a fresh Builder: it never saw the author's run and reads no rationale (rule 5).

Skills, each read from `.agents/skills/<name>/SKILL.md`: `prime` loads the taste rules; `to-spec`, `grill-with-docs` and `anchor` write a scenario; `codebase-design` judges a seam; `tdd` lands a scenario red then green; `review` and `judge` give a verdict; `reduce` and `show-me` write the PR body. A change under `apps/desktop/src` adds `emil-design-eng`; a motion clause adds `animate`.

Browser tests run headless in a dedicated agent-browser session and a fresh test profile. Never attach to the user's browser or desktop: no `--auto-connect`, `--headed`, CDP connection, personal profile, or OS keystrokes. If headless launch fails, repair the isolated browser setup or record the observer failure; do not fall back to the user's Chrome. Close only tabs and browser processes this run created.

## Recipes

Each recipe says what its part of a PR holds. Read `.agents/data/work.md` for the canonical Issue format. A build run follows every recipe its Issue needs.

A UI Issue, or a Brief, Door or Decision Issue in the first user journey, also reads `.agents/data/journey.md`: its stage, rendered observer and next-gap rule apply to the build and the independent review. Work toward the selected journey, not merely an isolated green component test.

- **Spec**, for an Issue requesting a specification. Each id gets a `**<id> <name>.**` heading; every then-clause names the test that will assert it, or is marked policy; every check is a number citing its file and the function, test or heading that holds it on `main`, never a line number; every cited id, file and PR exists on `origin/main`; a script has one row per failure with its exit code; the text states the result, never the incident; native Issue dependencies identify prerequisites; `loop/rules.sh vocab` passes.
- **Contract**, for a row needing `contracts/`, a new RPC method, an App seam command, `GLOSSARY.md` or `docs/adr/`. Every caller changes in the same PR and every new name is in `GLOSSARY.md`; a Message, Route, Held or Takeover change names the laws M1 to M10 it touches (`scenarios/proofs.md`) and keeps `proofs/messages` and `docs/messages.md` agreeing.
- **Code.** Interactive UI elements use `apps/desktop/src/ui/` primitives wrapping Ark UI. A new primitive wraps a library component, never a hand-written state machine. Apply rule 9 before adding machinery, in a new file or an existing one: first read what the installed dependency or the platform already offers, and never work around a library with `!important`, synthetic events or DOM clones. Tests are named after their scenario; `just ready` (the lints and N7's launch-sites test) and the tests of the files you changed by hand pass (a merge of `main`: the files you resolved), as `pnpm --filter desktop exec vitest related --run <files>` or `cargo nextest run -p <crate>`, and `check` on the push judges every test, in six minutes across CI's lanes where one runner takes forty (L82); loop machinery stays as `main` has it (L118); `loop/rules.sh merge-loss` passes after any merge of `main` (a file no commit of yours touched must equal `origin/main`); a merge of `main` that needed conflict resolution carries an `Author-Agent` trailer. A visible change meets D2, D5 and D6 at the scenario's viewport (`.agents/data/harness.md`), with failure text visible on the densest seed. Run `just capture <ids>` for those scenarios, in dark mode only, and leave the PNGs and videos that show the change under `artifacts/ux/<id>/` (`.agents/data/harness.md`, Captures); never commit an image or a video. The workflow attaches them to the PR after your run, with a token you never hold; do not run `gh pr edit --attach`.

- **Filing** (L96), for any run that files or edits a work Issue: write the new body to a file, run `python3 loop/orders.py check <file>` and write it only on exit 0. A repair run (task: "Repair run") edits the Issue the same way and opens no PR.

## Build run

1. Branch as the task says from `origin/main`. Commit the spec or the red tests first, push, and open a draft PR as `.agents/data/pr.md` says, and link its work Issue.
2. Read every comment on the Issue starting `<!-- fix-exhausted` first: each is a PR that used its fix runs, with the causes and commits that failed. When the task says to continue PR #N, branch from its head as the task says, keep the work that stands and meet the findings it lists, instead of starting over. Read every `<!-- strike -->` comment too: each is a run that ended without a PR, and one holding "The screen sent it back to the loop" answers that run's `ask`, so settle it yourself and never ask it again. Fulfil the Issue acceptance. A missing implementation prerequisite becomes a linked blocking Issue; a specification-only PR keeps the implementation Issue open.
3. `gh pr ready`, then `gh pr merge --auto --merge`.

A run has 25 minutes: `loop/deadline.py` kills the engine then, and `keep` pushes what is committed as a draft for a fix run to finish. Commit as each passing step lands; when the Issue cannot fit, finish one coherent slice and name the rest in `ask`.

A fix run answers every finding or failure in the task with commits on the PR's branch, then ends as the Code recipe says, one push and step 3. A build or fix run runs no `just check`. It leaves a ready PR ready, so an answer that only edits the body starts no new `pre` run and its review runs again (L82). A paragraph of the PR body holding "The screen sent it back to the loop" answers the question an earlier run stopped on, so settle it yourself and never stop on it again.

A missing prerequisite is an engineering repair: file the missing implementation as a scoped `loop:work` Issue, then block this Issue on it: `gh api -X POST repos/{owner}/{repo}/issues/<this>/dependencies/blocked_by -F issue_id=$(gh api repos/{owner}/{repo}/issues/<prerequisite> --jq .id)`. An isolated contract test does not complete a multi-scenario implementation Issue. Keep implementation within its Scope. When the work needs a file outside it, widen the Scope yourself: add each file and its reason to the Issue body, and the review run judges the expansion; never flag the user for it. Contract approval requirements still apply. Never add an Issue closed as not planned as a blocker; a dependent that needs cancelled work says so on its Issue and takes `flag:needs-user`.

An Issue that orders a change a scenario on `main` contradicts gets the scenario edit and its code in one PR, `Closes #<issue>` as usual. Review reads the Issue as the work order and rejects a scenario edit it does not order, or one that loosens acceptance only to fit the code.

Stop only on an unresolved product decision that changes the requested outcome and that no scenario, Item or `GLOSSARY.md` entry settles. Engineering uncertainty calls for investigation, a tested repair or a scoped prerequisite Issue under the existing direction. For that unresolved question, leave a draft with `Stopped: <the question>`, its user-visible consequence and one recommended choice; the end of your run screens it like an `ask` (L79, L81). With no PR to leave, put the same three in your answer's `ask`.

## Review run

Your input is the task, which carries the full text of the scenarios the PR names as `main` holds them, the checkout of its head, `gh pr diff` and `.agents/data/gates.md`. You cannot post or push; your answer is the verdict.

1. `git rev-parse HEAD` equals the task's head, or reject with that finding.
2. Judge the diff against the recipes, the scenario and `AGENTS.md`, naming the rule per defect.
   - Scope: the PR's own commits (`git log --no-merges -p origin/main..HEAD`) and what `loop/rules.sh merge-loss` prints, against the task's scenarios. A file `merge-loss` lists changed only through a merge, which `rules` fails; every other changed file is an own commit's work, and a change, deletion included, that a scenario orders is in scope. The PR body is never scope or evidence of what the change does. For each merge commit, read `git show --remerge-diff <merge>` (git 2.36 or later) to see main-side lines a resolution dropped in own files, and reject a dropped line the scenario does not order removed.
   - Reuse (rule 9): the one part of the body you read, as library evidence only; verify it against the diff and the cited sources. Reject custom code when a maintained library covers the need and the section gives no specific reason for rejecting it. Reject a missing required section.
   - A visible change: the Checks it moves hold.
   - A change to `crates/messages`, `docs/messages.md` or `proofs/`: `just proofs` (until it exists, `bend proofs/messages/PROOF.bend`) prints `ALL PROOFS CHECK`, and `proofs/messages/LAWS.bend` weakens no law.
   - A contract change: probe each new type and method in the checkout, never only its text.
   - A change to loop machinery: no rule or workflow lets a PR pass its own gate.
   - An empty diff: for every then-clause of the scenarios it names, find the test on the checkout whose body asserts it, not only its name, and run it; a clause with no such test, or a failing one, is a reject.
3. A re-review first re-derives each earlier finding from this head, git and the task's scenarios, and drops it when they no longer support it: a finding resting on the PR body, or on wording this file no longer holds, is dropped. Never repeat a finding on trust. Then judge the changes since the last judged head, conflict resolutions included; the verdict covers the whole head. Judge the head, not who pushed it.
4. Reject only a real defect: a broken rule, a contradiction, wrong behaviour, data loss, or a security hole (a secret, a token, an identity, a rule letting an Agent act beyond its role). Wording and taste are `NOTE:` lines in an approve. A finding about an input or case the PR's scenarios do not name, while every then-clause of theirs holds and no rule, security or data-loss defect shows, is no reject: approve, and end the findings with one `FOLLOWUP:` block (its lines up to the next blank line) in the user's terms: the finding, the `file:line`, the failing input. The workflow files it as an Issue and names it in the verdict as `Follow-up: <url>`; add no block when an earlier verdict already names that case.
   - A finding rejects only when reproduced on an ordinary path: the actions a scenario names, in order, with the App and Daemon answering normally. Also always rejects: an action that changes or deletes items the user did not choose, a destructive action that skips its confirmation, a then-clause of the named scenarios that fails as written, a security defect, a red required gate (merge-loss included).
   - A finding that needs an injected failure (a failed read, write or RPC), a reply held pending while the user navigates, a second window or external writer, or a component removed mid-edit is a `FOLLOWUP:`, even when it cites a Principle such as P11 or P13, unless the scenario's then-clause names that exact case.
   - A new finding on code an earlier verdict on this PR already reviewed unchanged is a `FOLLOWUP:` unless it is in the always-reject list: no drip-feeding across rounds.

Done: a build or fix run leaves a ready PR with auto-merge armed, or a draft with a `Stopped:` line; a review run answers `verdict` and `findings` in the format of `.agents/data/gates.md`. A build run ends without a PR only when its Issue is settled or it asks the user. Settled: blocked by a prerequisite Issue, or closed as completed with a comment naming the evidence because a merged `build/<Key>` PR already met its acceptance; a remainder that another open Issue's acceptance holds keeps nothing open, and the comment names that Issue. When other merged PRs already met the acceptance, open the `build/<Key>` PR with one empty commit (`git commit --allow-empty`) and `Closes #<issue>`, as `.agents/data/pr.md` says. When only an observation is missing, make it and commit its evidence in a PR that closes the Issue. An observation no run can make goes in your answer's `ask`: only a check whose pass or fail only the user's Mac can produce (a logged-in real `claude`, the `just app` window's native behaviour no Chromium check covers). A check `check`'s `macos-latest` jobs already run is read from CI history (`actions: read`), and a native look-and-feel check whose observer is a Linux or Chromium check closes on that observer, the user reporting what they meet on the Mac. A build run that finds its Issue's work merged, with that work's Linux or Chromium tests passing on `main`, closes the Issue as completed with a comment naming the PR and those tests and saying the user reports what they meet on the Mac (L46); it asks for no native Mac check. The `ask` holds: what to build from which commit, each step, and what each result decides. Your build run's answer is `{ask}`, empty otherwise; a screen (`.agents/screen.md`) sends a non-empty one to the user, to an agent on the user's Mac, or back to the queue as a strike (L79).
